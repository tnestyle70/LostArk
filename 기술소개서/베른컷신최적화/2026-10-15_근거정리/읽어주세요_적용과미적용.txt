베른 최적화 적용 상태와 기술소개서 이미지 사용 안내 — 2026-10-15

현재 결론
저폴리 교체 전체가 미적용됐던 것은 아니다. PILLAR06/PILLAR07 2종·53 asset ID·62 placement에
실제 저폴리 VB/IB와 70m/1200px 선택 규칙이 설치돼 있었다. 사용자 F7 캡처에서도 실제 저폴리
draw가 0~19, 느린 구간에서는 8~19회 제출됐고 fallback/preflight/late failure는 0이었다.
다만 전체 배경을 교체한 것은 아니며 준비 범위와 카메라 조건 때문에 적용 대상이 제한됐다.

적용됐고 측정한 부분
- 기존 mesh LOD: 원본 VB를 유지하고 단순화 IB를 선택한다. 두 캡처의 source 내 saved-index 평균
  175,322.8 / 525,871.0. native HLOD도 평균 4,895.8 / 23,530.8을 기록했다. 전체 장면 절감률이 아니다.
- 새 저폴리: 별도 저폴리 VB/IB를 기존 CModel 경로에 넣는다. 원본을 무조건 숨기지 않고 준비 및
  shader 바인딩 성공 후 선택된 placement만 원본 color draw에서 제외한다. 실패 시 원본으로 복귀한다.
- 거리 기준: P06의 이전 121.6m/202px, P07의 82.6m/553px 대신 두 모델 모두 70m/1200px를 사용한다.
  거리만이 아니라 화면상 지름, frustum/depth, 준비 성공, 재질, 컷신 활성 조건도 모두 통과해야 한다.
- 통제된 성탑62개 부분 장면 0초: VS 445,695 → 242,225 (45.65% 감소), Idx 1,081,890 → 620,544
  (42.64% 감소), map draw 260 → 145. 동일 카메라/설정과 GPU query 완료를 원문 JSON으로 확인했다.

적용되지 않았거나 적용 범위가 제한된 부분
- 이전 준비 결과는 60 batch 중 37 준비/23 거절이었다. 최초 거절 이유는 mirrored 13,
  transform 6, material identity 4였다. 그러므로 지원 이름이 있다고 모든 배치를 저폴리로 그리지 않았다.
- G44는 미러 13개 중 안전한 균일 미러 9개를 허용했다. CPU 필요조건 기준 준비 placement 39→48,
  batch 37→46이다. 코드·Release/Debug 빌드 반영과 별개로 이 9개 추가분의 GPU 감소량은 미측정이다.
- 남은 14개는 비균일 변환 9개·재질 불일치 5개다. 기존 TBN/재질을 깨뜨리며 강제 허용하지 않았다.
- 기본 카메라는 컷신 lease가 없어서 이 저폴리 교체를 사용하지 않는다. 사용자 복구 확인은 있으나
  통제된 기본 카메라 FPS 전후 실험은 없다.
- 기존 xatlas 경로는 indexCount를 보존한다. 텍스처 mip도 삼각형을 줄이지 않는다. 이를
  저폴리 VB/IB 교체와 같은 기하량 최적화 성과로 계산하면 안 된다.
- atlas512 새 품질 후보는 미설치다. 현재 설치는 atlas256이다.
- 전체 베른 1/8 목표는 미달성이다. 전체 장면 GPU 비교는 로드 중 메모리 하한에 도달해 첫 draw 전에 중단됐고,
  성탑62개 실험을 전체 게임 또는 G44 추가 개선 수치로 확대할 수 없다.

저장된 캡처의 경계
두 사용자 JSON은 정상 파일이며 SHA를 재확인했다. 그러나 bernCutsceneGeometry와 meshDraws 상세는
그 파일에 없다. 당시 저장 누락의 정확한 단일 분기는 재현하지 못했다. G44에서 일반 JSON 저장도
보관한 거리 기록을 포함하도록 수정했고 상태검사55건/serializer13범주를 통과했다. 실제 F7 저장 및
재열기의 최종 UI 확인은 별도다. 통계 그림은 실제게임 수치이지만 두 구간은 전후 A/B가 아니다.

기술소개서에 사용할 문장
“동일 카메라의 성탑 62개 부분 장면에서 저폴리 대체를 적용해 GPU VS 호출을 445,695에서
242,225로 45.65%, 제출 index를 1,081,890에서 620,544로 42.64% 줄였다.”
‘전체 베른 FPS 몇 % 향상’, ‘전체 1/8 달성’, ‘미러9개 추가분 실측 완료’라고 쓰지 않는다.
VS는 GPU vertex shader 호출 수이며 고유 정점 수와 다르다. 실제게임 Idx 통계는 CPU-known
제출량이다. 서로 다른 카메라/해상도/시간 구간의 수치를 동일 프레임 화면에 합성하지 않았다.

후속 요청: HUD 80만 → 50만의 초반 실측
그 두 수치가 정확히 같은 카메라·설정·지표라면 산술 감소율은37.5%다. 현재 저장 파일만으로
그 조건을 증명하지 못하므로 이번 기술소개서의 검증된 개선율로 사용하지 않는다.
HUD Vtx와 일반 JSON pipeline VS는 모두 Update→Render 전체 GPU 프레임을 센다. HUD를 맵만,
JSON을 전체 장면이라고 구분하지 않는다. HUD는 완료된 과거 geometry frame을 표시하고 FPS는
별도 평활값이므로 화면의현재카메라·통계중앙값·GPU결과를 같은 순간으로 임의 연결하지 않는다.
거리 JSON의 cutsceneSamples[].geometry.vsInvocations/totalIndices는 HUD와 같은 geometry query다.
captureFrameNumber와 geometry frame, cue, view/projection, viewport를 대조해야 한다.
새 측정 도구 실행 전 free commit5.1899GiB(기준8GiB), 물리여유1.7052GiB로 native를 시작하지 않았다.
과거 전체맵 로드 중 중단과 이번 실행 전 거절은 별도 사건이다. 현재 추가 GPU 측정 성공은 없다.
