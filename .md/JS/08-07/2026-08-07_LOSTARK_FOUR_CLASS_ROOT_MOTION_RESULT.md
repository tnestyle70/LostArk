# 네 클래스 루트 모션 — 구현 결과

작성자: JS · 2026-08-07 · 브랜치 `feature/player-hold-skill`

창술사·워로드·도화가·차원술사의 루트 모션을 굽고 새 문서 셋을 프로젝트에 등록했다.
같은 작업 지시에 있던 원본 애니메이션 배속은 근거를 찾지 못해 되돌렸다. 그 조사 결과가
이 문서의 절반이다.

## 1. 결과

| 클래스 | 곡선 보유 | 주요 이동 |
|---|---|---|
| 창술사 | 18 / 23 | 탄영 3.50m · 돌파 2.50m · 유성강천 2.50m · 공의연무 6.53m |
| 워로드 | 14 / 16 | 돌격 3.21m · 리프 어택 2.85m(수직 3.15m) · 전장의 방패 6.32m |
| 도화가 | 12 / 15 | 흘리기 9.04m · 저무는 달 1.37m |
| 차원술사 | 10 / 13 | 공간 도약 8.73m · 경계 돌파 4.69m · 분광 2.31m · 분절 1.53m(수직 3.10m) |

COMBO와 HOLD는 스테이지별 시계를 써서 `extract_rootmotion.py`가 건너뛴다(평타 4종, 콩콩이,
적룡포, 풀배럴 캐넌). 곡선이 없는 나머지는 원본에 이동이 없다.

**차원술사 건너 찌르기(2050160)와 너머 베기(2050180)는 `b_root` 델타가 전부 0이다.** 둘 다
제자리 공격이고 "공간을 넘어" 가는 것은 이펙트 표현이지 캐릭터 이동이 아니다. 도화가
한획긋기·범가르기도 0.05m 수준이라 사실상 제자리다.

## 2. 워로드 전장의 방패의 up 누적

`17820`의 `up`이 -12.417로 끝난다. 체인 구성 때문이다.

```text
_01      dUp +12.417   상승
_03_re   dUp -12.417   하강
_03      dUp -12.417   또 하강
```

`_01`이 한 번 올리는데 하강 클립이 둘 들어가 있어 누적된다. 창술사 공의연무와 같은 유형이고,
publisher가 `SKILLROOTMOTION` 행에 `timeMs:forward:lateral`만 담고 `up`은 넣지 않으므로
서버 판정에는 영향이 없다. `forward 6.322`만 전달된다.

## 3. 배속은 원본에서 뽑을 수 없다 — 되돌렸다

지시에 "원본 애니메이션 배속"이 있어 먼저 데이터를 찾았고, **두 가지 방법 모두 실패했다.**

### 3.1 클립 길이에 배속이 박혀 있지 않다

`.wmodel`의 클립 duration과 `.animnotify`의 `len=`을 바인딩된 클립 전부에 대해 비교했다.

```text
창술사 53/54   워로드 31/33   도화가 23/24   차원술사 23/24  일치
```

어긋난 소수도 4% 이내라 반올림 수준이다. 유일한 예외 `flm_sk_penetrationlunge_02`
(model 1500 / notify 250)는 `playMs=200`으로 잘라 쓰는 클립이라 별개다.
**게임은 클립을 저작된 길이 그대로 재생한다.**

### 3.2 DB 시각으로 역산해도 흩어진다

`.skilltiming`의 히트 시각은 시전 전체 기준, `.animnotify`의 HIT는 클립 로컬이다. 기준 체인에서
그 히트가 원본 속도로 몇 ms에 오는지 구해 공식 시각과 나누면 배속이 나와야 한다.

```text
skillId  공식히트  체인상 원본  역산배속  실제 튜닝값
34090      1730      350      0.202     1.4
34110      1857      200      0.108     1.2
34120      1295      400      0.309     1.2
34150      1345     1400      1.041     1.2
34560      1245     1250      1.004     1.2
34570      1657     1400      0.845     1.0
→ 9개 중 튜닝값과 0.12 이내 0개
```

0.108부터 1.041까지 흩어진다. 철량추는 애니 HIT이 350ms인데 DB는 1730ms로 5배 차이다.
배속이 아니라 아예 다른 시계다. 07-31 추출 문서의 "159개 중 35개만 120ms 안에 든다"와 같은
결과이며, 이번에는 기준 체인을 정확히 짝지어 비교했는데도 그렇다.

### 3.3 그래서 배속은 감각으로 정하는 값이다

창술사의 1.1 / 1.15 / 1.2 / 1.3 / 1.4 / 1.45가 제각각인 것도, 연환섬 하나 안에서 클립별로
1.2 / 1.0 / 1.1로 다른 것도 그 때문이다.

균일 1.2를 세 클래스에 걸어보고 44행을 재계산했으나 근거가 없어 되돌렸다. 사용자 판단으로
데이터를 더 확보한 뒤에 걸기로 했다.

**되돌린 뒤 루트 모션을 구웠으므로, 나중에 배속을 걸면 루트 모션을 다시 구워야 한다.**
베이커가 바인딩의 `playRate`를 읽어 곡선의 시간축을 만들기 때문이다.

## 4. playRate와 playMs의 결합

배속 계산을 위해 런타임 계약을 확인했다. `Character.cpp`의 `Start_Clip`과 `Is_ClipFinished`다.

```text
playRate → Set_AnimationSpeed, 트랙이 그만큼 빨리 감긴다
playMs   → 원본 클립 기준 컷 지점, ticks로 환산해 트랙 위치와 비교
벽시계 시간 = min(클립길이, playMs) / playRate
```

창술사 연환섬으로 검산된다.

```text
900/1.2 + 582/1.0 + 1866.7/1.1 = 3028.97  →  저장된 actionDurationMs 3029
```

**`playMs`는 원본 클립 시간이고 벽시계로 환산할 때 `playRate`로 다시 나눈다.** 배속을 걸 때
duration을 재계산하려면 이 식을 써야 한다.

## 6. 남은 것

- 배속. 데이터를 더 확보한 뒤 걸고, 그때 루트 모션을 다시 굽는다.
- 다단 히트 미구현. 차원술사 너머 베기 3타, 워로드 버스트 캐넌 계열이 1타만 적용된다.
- 도화가는 HIT 노티파이가 전체 2개뿐이라 타격 시각 7개가 여전히 추정값이다.
- 전장의 방패의 `up` 누적은 서버에 영향이 없지만 저작 문서에는 남아 있다.
