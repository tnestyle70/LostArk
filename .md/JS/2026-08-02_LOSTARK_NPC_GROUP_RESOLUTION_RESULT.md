# NPC 파이프라인 — 패키지 그룹 해석 오류 수정

작성자: JS · 2026-08-02

`2026-08-01_LOSTARK_NPC_ASSET_PIPELINE_RESULT.md`의 후속이다. 그 문서 5장이 "rest pose가
조각마다 다르다"고 진단하고 6장에서 리타깃 재작성을 제안했는데, **실측해보니 그 문제는
존재하지 않았다.** 원인은 리그가 아니라 추출 단계에서 잘못된 조각을 골랐던 것이고,
같은 원인이 아일라라 목 텍스처(9장 4번)까지 함께 만들었다.

앞 문서의 5·6·9장은 이 문서로 대체된다.

## 1. 원인 — LookInfo의 가운데 토큰은 패키지 그룹이다

```text
SkeletalMesh'NP_LHER_00.mesh_new.NP_LHER_00_SK'
                        ^^^^^^^^ 그룹
```

NPC 패키지는 대부분 같은 오브젝트 이름으로 에셋을 **두 벌** 싣는다.

| 그룹 | 내용 |
|---|---|
| `mesh` / `mat` / `tex` | 구본. 머리까지 포함한 자기완결형 바디, 고유 체형 리그 |
| `mesh_new` / `mat_new` / `tex_new` | 신본. 머리 없는 바디, 아키타입 리그. LookInfo가 가리키는 쪽 |

그런데 `umodel -uncook`만 주면 디렉터리를 **클래스 이름**(`SkeletalMesh3/`,
`MaterialInstanceConstant/`, `Texture2D/`)으로 만든다. 그룹이 사라지면서 두 벌이 한
폴더에 섞이고, 이름이 겹치는 쪽에는 umodel이 임의로 `_2`를 붙인다.

`npc_lookinfo.py`와 `cook_npc.py`는 파일명 stem으로만 골랐으므로 어느 쪽이 걸릴지가
운이었다.

```text
np_lren_00_sk.psk      실제로는 mesh     ← 우리가 쓴 것
np_lren_00_sk_2.psk    실제로는 mesh_new
np_lhgw_00_sk.psk      실제로는 mesh     ← 우리가 쓴 것
np_lhgw_00_sk_2.psk    실제로는 mesh_new
np_lher_00_mi.mat      실제로는 mat      ← 우리가 쓴 것
np_lher_00_mi_2.mat    실제로는 mat_new
```

판별은 각 `.props.txt`가 해준다. 메시 props의 `Materials[i] =
MaterialInstanceConstant'<그룹>.<이름>'`가 소속 그룹을 그대로 적어둔다.

## 2. 5장의 rest 불일치는 구본 메시의 값이었다

`bip001-head` 절대 rest 위치를 REFSKELT에서 직접 계산했다.

```text
                          bip001-neck                bip001-head          본
hm_ma01_sk   아키타입      (-0.756, 0.002, 119.276)  ( 1.080, 0.002, 124.546)  124
np_lren_00_sk    mesh_new  (-0.756, 0.002, 119.276)  ( 1.080, 0.002, 124.546)  124
np_lhgw_00_sk    mesh_new  (-0.756, 0.002, 119.276)  ( 1.080, 0.002, 124.546)  124
mn_head_ma01_010 머리      (-0.756, 0.002, 119.276)  ( 1.080, 0.002, 124.546)  124

np_lren_00_sk    mesh      (-2.545, 0.000, 108.366)  (-0.655, 0.000, 113.723)   37
np_lhgw_00_sk    mesh      (-5.689, 0.000, 114.205)  (-4.629, 0.000, 118.336)   57
```

FE04 계열도 같다 — 아키타입·바디·머리가 모두 `(-0.812, 0.001, 109.110)`.

**신본 바디는 아키타입·머리와 비트 단위로 같은 rest에 124본이다.** 앞 문서가 잰
10.8 / 6.2 오차는 전부 구본 메시의 수치였다. 아일라라만 정상이었던 이유도 여기서
설명된다 — LHER는 구본 이름이 `np_lher_skin`이라 충돌이 없어서 우연히 신본 메시를
집었다.

따라서 다음이 전부 불필요해졌다.

- 리타깃 재작성 (앞 문서 6장·9장 1번) — 맞출 rest 차이가 없다
- psa 이동 키 처리 결정 (9장 2번) — 트랙이 그대로 안착한다
- 포먼 자체 머리 705정점 처리 (9장 3번) — 구본 바디가 머리를 갖고 있었을 뿐이다
- 본 graft — 124 = 124라 대상이 없다 (아일라라의 옷깃 본 1개만 예외)

## 3. 아일라라 목 텍스처

바디 메시는 우연히 맞게 골랐는데 **재질을 구본으로 골랐다.**

```text
mat.np_lher_00_mi      Diffuse = np_lher_00_d            ← 우리가 쓴 것
mat_new.np_lher_00_mi  Diffuse = np_lher_00_d_loc_int
```

두 아틀라스는 섬 배치가 같지만 그림이 다르다. 목·어깨 UV가 놓인 자리에 구본은
얼굴을, 신본은 숄을 그려놨다. 그래서 목 그루터기에 눈썹이, 어깨에 뺨이 찍히고 빈
배경을 문 삼각형은 검게 나왔다.

`_loc_int`는 지역화본이 아니라 이 NPC의 현행 텍스처다. 같은 패키지의 `_u_mi`,
`_mi_dead` 변형이 전부 이걸 쓰는 것과도 일치한다.

**서브메시↔재질 매핑에는 문제가 없었다.** 세 방향으로 확인했다 — psk 면 수와 wmodel
서브메시 인덱스 수 일치(머리 2,284 / 바디 4,814), UV를 아틀라스에 겹쳐 그렸을 때 섬
경계와 정확히 정렬, `EXTRAUV0`로 렌더하면 노이즈(=디퓨즈 UV가 아님).

## 4. 고친 것

### 4.1 추출 — `-groups`를 반드시 준다

```powershell
umodel_lostark_v7.exe `
  -path="C:\ProgramData\Smilegate\Games\LOSTARK\EFGame" `
  -game=lostark -kr -nameresolve `
  -export -psk -uncook -groups -out="<staging>" <PACKAGE>
```

`<PACKAGE>/<그룹>/<오브젝트>` 구조가 되어 LookInfo 참조를 그대로 해석할 수 있고 `_2`
추측이 사라진다. 파일럿 11개 패키지를 `_export_npc_pilot_g`로 재추출했다(전부 exit 0).

### 4.2 `npc_lookinfo.py`

- `split_ref`가 `(package, group, object)`를 돌려준다.
- `find()`가 그룹 디렉터리를 타고 내려간다. `group=None`은 아키타입 리그 탐색 전용.
- `refs()`가 클래스별 버킷 대신 **파일 순서**를 유지한다. 재질 오버라이드가 자기 앞의
  메시에 붙기 때문이다.
- `MaterialInstanceConstant` 참조를 수집해 각 메시의 `materialOverrides`에 담는다.
  LookInfo가 공용 머리를 다시 칠하는 경우가 있다(`MN_Head_MA01_024-1_MI`).
- 출력 JSON의 각 메시에 `group`이 추가됐다.

### 4.3 `cook_npc.py`

- `.mat`/`.tga`를 stem으로 인덱싱하던 것을 제거하고 **props 2단 추적**으로 바꿨다.
  메시 props → 재질 그룹, 재질 props의 `texture_diffuse` / `texture_normal` /
  `texture_specular` → 텍스처 그룹.
- 애매하면 추측하지 않고 오류를 낸다.
- 교차 패키지 참조를 지원한다. 슈미트의 도구는 `WP_NP_LHGW_00-3`에 있으면서
  `NP_LHGW_00`의 재질을 쓴다. 후보가 유일할 때만 받아들인다.
- **파일명 충돌 처리를 넣었다.** 한 NPC의 모든 패키지가 `textures/` 한 폴더를 공유하고
  컨버터는 원본 파일명 그대로 복사한다. 슈미트 바디는 `tex_new/np_lhgw_00_d`,
  도구는 `tex/np_lhgw_00_d`를 쓰는데 도구가 나중에 구워지면서 바디 텍스처를 덮었다.
  먼저 잡은 쪽이 이름을 유지하고 나중 것은 `np_lhgw_00_d__tex.tga`로 나간다.
- LookInfo 재질 오버라이드가 있으면 로그로 알린다. **적용은 아직 안 한다** — 파일럿
  4명 중 쓰는 NPC가 없어 슬롯 대응 규칙을 검증할 방법이 없다.

### 4.4 `build_npc.py` — 들고 있는 도구 복구

엔진 확인에서 슈미트가 들고 있던 도구가 사라진 것이 드러났다. 신본으로 바꾸면서
생긴 회귀다.

```text
구본 np_lhgw_00_sk (57본)   bip001-prop1  40정점 / bip001-prop2 123정점  ← 메시에 박혀 있었다
신본 np_lhgw_00_sk (124본)  b_wp_1 0 / b_wp_2 0 / b_wp_3 0             ← 도구 없음
WP_NP_SDWA_00_SK             40정점                                      ← 망치
WP_NP_LHGW_00-3_SK          123정점                                      ← 정(끌)
```

40 / 123이 정확히 일치한다. 신본은 도구를 별도 패키지로 분리했고 바디 props가 붙일
자리를 선언한다.

```text
wp_1_06  <- b_wp_1 (bip001-r-hand 자식)  loc(0.255, 2.053, 0.435)   rot(Y -3705, P -1525, R -3886)
wp_2_45  <- b_wp_2 (bip001-l-hand 자식)  loc(3.811, 0.458, -1.537)  rot(Y 950, P 261, R 13374)
```

`CNpc`는 무기를 붙이지 않으므로 **빌드 시점에 소켓 위치로 구워 넣었다.** 프롭은
변형되지 않으니 전 정점을 소켓 본에 가중치 1로 물리면 원본과 같아지고, 오히려 구본보다
낫다 — 구본 prop 본은 `bip001` 직속이라 손을 따라가지도 않았다.

주의점 둘:

- 소켓 오프셋은 게임 축 기준인데 psk 임포터는 본을 Blender의 +Y 관례로 재정렬한다.
  그래서 본 rest를 Blender에서 읽지 않고 임포터와 같은 방식으로 psk에서 다시 계산한다.
- **도구가 바디와 재질 이름이 같을 수 있다.** 슈미트의 정은 `mat.np_lhgw_00_mi`,
  바디는 `mat_new.np_lhgw_00_mi`다. 임포터가 이름으로 재사용해버려 손잡이가 검게
  나왔다. 무기 재질은 `<이름>__<패키지>`로 분리하고 `cook_npc.py`가 같은 규칙으로
  리맵을 만든다.

도구가 NPC 메시의 일부가 됐으므로 무기를 옆에 따로 굽던 경로는 제거했다. 런타임에서
소켓 부착으로 가려면 `CNpc`에 무기 파츠 지원을 넣어야 하고, 그때 되돌리면 된다.

## 7. 같은 실수 반복 방지

- **참조의 가운데 토큰을 버리지 말 것.** 패키지·오브젝트만 보고 파일을 찾으면 구본과
  신본 중 하나가 임의로 걸린다. 두 벌은 리그도 정점 수도 텍스처 그림도 다르다.
- **umodel의 `_2` 접미사는 정보가 아니라 충돌의 흔적이다.** 어느 그룹인지 알려주지
  않는다. `-groups`로 뽑거나 `.props.txt`를 읽어야 한다.
- **한 폴더에 여러 패키지를 구울 때 텍스처 파일명 충돌을 확인할 것.** 조용히 덮어쓰고
  wmodel은 같은 상대 경로를 가리키므로 로그에 아무것도 남지 않는다.
- **재질 이름이 같다고 같은 재질이 아니다.** 그룹이 다르면 다른 텍스처를 가리킨다.
  Blender 임포터의 `should_reuse_materials`가 이름으로 합쳐버리므로 한 FBX에 두 그룹을
  섞을 때는 꺼야 한다.
- **구본에서 신본으로 바꿀 때 무엇이 빠졌는지 정점 수로 확인할 것.** 슈미트의 도구
  163정점은 렌더를 봐도 몸에 가려 눈에 띄지 않았고, 엔진에서야 없어진 게 보였다.
- 원본은 Smilegate 저작물이다. 스테이징과 결과물 모두 Git에 올리지 않는다.
