# 2026-09-27 아이템 수리창과 내구도 HUD RESULT

대응 PLAN: `.md/TJ/09-27/2026-09-27_수리창_PLAN.md`
브랜치: `feature/durability-repair-window`

## 구현한 것

PLAN의 G01~G06을 구현하고, 사용자 확인 뒤 텍스트·HUD 위치를 고쳤다. 작업 중 추가로
요청받은 수리 NPC 상호작용과 미니맵 NPC 아이콘도 같은 단위에 넣었다.

### 1. 아이템 수리창

`interactionrepair.gfx`의 저작 배치를 2/3로 환산해 `Data/UI/Repair/RepairUI.json` 53 슬롯으로
만들고 `CRepairWindowView`가 소비한다. 창 틀, 착용 8×2와 소지 8×3 슬롯, 두 비용 줄과 길드
할인 아이콘, 두 수리 버튼, 소지금 줄을 그린다. 제목 바 드래그와 화면 클램프, 닫기 버튼,
Esc 닫기, 창 위 클릭 가로채기가 동작한다.

내구도 수치와 수리비는 넣지 않았다. `ItemCatalog.json`에도 Server snapshot에도 내구도
필드가 없어서, 슬롯은 빈 프레임만 그리고 비용은 표시하지 않는다.

### 2. 내구도 HUD

`durability.gfx`의 `DurabilityFrame`을 `Data/UI/Durability/DurabilityUI.json` 9 슬롯으로
만들고 `CDurabilityHudView`가 소비한다. 갑옷 실루엣과 부위 8개 오버레이를 소유하며,
`set setDurabilityPart`의 원작 계약(`-1` 정상 / `0` 손상 / `>=1` 파괴)을 `PART_STATE`로 옮겼다.
부위마다 손상·파괴 두 그림의 크기가 달라 `Set_SlotTexture`와 `Set_SlotRect`를 함께 바꾼다.

상태 데이터가 없어 전부 `NORMAL`이고 실루엣만 나온다. `Set_PartState`가 단 하나의 입구다.

### 3. 수리 NPC 상호작용

베른 광장의 수리 NPC를 우클릭하면 걸어가서 수리창이 열린다.

수리 NPC는 `Data/UI/WorldMap/WorldMapNpcSymbols.json`에서 모루 심볼
(`Minimap_Symbol_158`)을 단 배치 둘이다. 슈미트(`npc.bern.schmidt`)는 망치 심볼이고 이미
강화 창에 연결돼 있어 건드리지 않았다.

| 배치 ID | archetype |
|---|---|
| `npc.bern.src.31` | `NPC_25182` |
| `npc.bern.src.48` | `NPC_25012` |

기존 `Ready_ItemUpgradeNpc` / `Update_ItemUpgradeNpcInteraction` / `Advance_ItemUpgradeNpcWalk`
삼단 구조를 그대로 따랐다. 우클릭 레이 피킹 반경 1.5m, 정지 거리 3m, 도착 시
`CMainApp::Get_Active()->Open_RepairWindow()`. NPC가 둘이라 찍힌 쪽을 placement ID로 기억하는
부분만 발탄 가이드 NPC 방식을 썼다.

### 4. 미니맵 NPC 아이콘

M 맵에만 보이던 NPC 심볼이 우상단 미니맵에도 나온다. 버그가 아니라 미니맵 쪽 미구현이었다 --
`Minimap_Layout.json`에 NPC 슬롯 자체가 없었고, 보스·파티·플레이어 마커만 있었다.

M 맵과 같은 문서(`WorldMapNpcSymbols.json` + Area `Gameplay.world.json`)를 읽어 미니맵의 기존
`PlaceMarker` 투영에 넣는다. `MinimapAreas.json`의 Area 행에 optional `worldAreaId`가 있을
때만 그리므로, 심볼이 없는 Area는 종전과 같다. 현재는 베른만 해당한다.

심볼 파일 이름이 전부 `Minimap_Symbol_*`인 것이 근거가 된다 -- 원작에서 미니맵용 심볼
아틀라스에서 뽑은 자산이다.

## 도중에 해결한 것

### umodel이 못 읽는 패키지

텍스처를 뽑으려다 umodel이 `EFUI_DURABILITY`를 아예 못 여는 것을 확인했다. LostArk는
`FCompressedChunk`를 20바이트로 쓰는데 umodel은 표준 16바이트로 읽어서, 첫 청크 이후 오프셋이
전부 파일 끝을 넘어간다(`Unable to read 24570 bytes at pos=0x89B4B`, 파일은 350,731바이트).

`Tools/LpkPipeline/export_upk_texture.py`를 만들어 해결했다. 20바이트 청크 + AES-256-ECB +
LZ4로 패키지를 풀고, 태그 프로퍼티를 읽고(export 데이터는 `SerialOffset+4`에서 시작하고
`IntProperty`는 int32 셋으로 직렬화된다), 불크 헤더에서 밉을 찾는다. 저장 형식 세 가지를
모두 처리한다.

- crunch 밉 -> `unpack_unity_crunch`
- 블록 스트림 밉(`0x9E2A83C1`) -> 패키지와 같은 복호화 재사용
- `pf_dxt1/3/5`와 `pf_a8r8g8b8`

압축 해제 결과가 기존 `durability.gfx`와 **바이트 단위로 일치**하는 것으로 검증했다.

**crunch 함정**: `unpack_crunch`와 `unpack_unity_crunch` 둘 다 성공을 반환하고 둘 다 정확히
131,072바이트를 돌려주는데, stock crnlib 쪽은 노이즈가 나온다. Unity 변형만 유효한 블록을
만든다. 길이가 맞으므로 실패한 추출이 성공한 것처럼 보인다.

### 사용자 확인 후 고친 것

**텍스트가 깨져 보임** -- `Draw_Text`에 배율을 직접 넘겨 32~42px로 구운 스프라이트 폰트를
11px로 축소 샘플링했다. `UILabelFont.h`가 정확히 이 증상을 위해 있는 파일이고 다른 창은 전부
그것을 쓴다. `UILabelFont::Resolve`로 교체하고 위치를 정수 픽셀로 반올림했다. 크기도 박스
높이 비율 대신 원작 저작값(제목 `YoonGasiIIM` 18, 라벨·버튼 `YG760` 16, 소지금 14)을 쓰고,
형제 창 `CHonorTitleWindowView`와 같은 `TEXT_BOOST = 1.15`를 곱했다.

**HUD 위치** -- 처음 `(1218, 206)`은 근거 없는 추측이었다. 사용자가 "미니맵 왼쪽 아니었나?"
하고 **질문**했는데 그것을 확인된 사실처럼 옮겨 적은 것이 잘못이었다. 실제로 확인한 것은
다음과 같다.

| 확인한 곳 | 결과 |
|---|---|
| `durability.gfx` | 화면 좌표 없음. `alignType()`이 내부 정렬만 함 |
| 다른 660개 `.gfx` | `DurabilityFrame`을 품는 문서 없음 |
| `UserOption.xml` | HUD 좌표 항목 0건 |

화면 위치는 호스트 C++가 정하고 그 값은 읽을 수 있는 데이터에 없다. 최종 값
`(1007, 12)`는 사용자가 제공한 원작 레이드 캡처에서 측정한 것이다 -- 화면 최상단, 오른쪽
끝에서 약 21% 지점. 압축된 스트림 프레임이라 ±10px 오차를 가정한다.
