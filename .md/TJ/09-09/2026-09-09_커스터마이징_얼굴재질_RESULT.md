# 2026-09-09 커스터마이징 얼굴 재질 RESULT

`feature/customizing-finish`. 09-08 RESULT의 "남은 것" 중 눈알 웨이트 회귀와 피부·꾸미기
탭을 처리했다.

## 1. 눈알 웨이트 회귀 — 원인이 문서보다 넓었다

09-08 22절이 "이식이 눈알 정점까지 덮어썼다"고 기록했고 수정 방향을 "기존 지배 본이
`b_fc_*_eye_ani`인 정점을 건너뛴다"로 잡아 두었다. 실측해 보니 그 규칙으로는 절반만
고쳐진다. 이식은 눈알뿐 아니라 **eye-AO 껍질까지** 덮었고, 두 클래스가 서로 반대 방향으로
틀어져 있었다.

| 클래스 | 서브메시 | 이식 전 | 이식 후(회귀) |
|---|---|---|---|
| 워로드 | 5 `pc_wr_eye_mi` | `b_fc_l_eye_ani` 93 / `b_fc_r_eye_ani` 92 | `b_fc_l_eye_up_cm` 89 / `b_fc_l_eye_dn_cm` 88 / … |
| 도화가 | 2 `pc_sp_eye_mi` | `bip001-head` 226 | `b_fc_mouse_ut_cm` 113 / `b_fc_mouse_dt_cm` 113 |
| 도화가 | 1 `pc_sp_eyeao_mi` | `bip001-head` 322 | 눈꺼풀·볼 본 |

도화가는 눈알이 **입 본**을 따라가고 있었다. 지배 본으로 거르는 규칙은 도화가의
`bip001-head` 정점을 보호하지 못한다.

### 정답이 있는 곳

원본 얼굴 메시에는 없다. `pc_ft_00_face_sk`, `pc_wr_00_face_sk`, `pc_sp_00_face_sk` 셋 다
bone map에 `b_fc_*_eye_ani`가 **아예 없다**. 눈알은 바디에만 있으므로 바디 추출본이 정본이다.

```
pc_wr_00_sk    prim6 162정점  b_fc_l_eye_ani 81 / b_fc_r_eye_ani 81, 전부 1.0
pc_sp_00_sk    prim2 226정점  bip001-head 226, 전부 1.0
               prim1 322정점  bip001-head 322, 전부 1.0
pc_sp_m_00_sk  prim7 242정점  b_fc_l_eye_ani 121 / b_fc_r_eye_ani 121, 전부 1.0
```

즉 **도화가 눈알은 원작에서도 리그가 없다.** 원작은 이 프로젝트가 로드하지 않는 별도 face
메시를 그린다. 복원은 바디 추출본이 말하는 값을 쓰는 것이지 도화가에 눈 리그를 만들어
주는 것이 아니다.

### 축 규약을 거리로 고르면 안 된다

`restore_body_eye_weights.py`는 48개 축·부호 후보를 **본 이름 일치율**로 고른다. 24개
정회전으로 좁히지 않는다. 오른손 좌표계끼리 옮기는 이식과 달리 여기서는 오른손 y-up glTF
추출본을 읽으므로 진짜 대응이 반사일 수 있고, 실제로 그렇다(`(0,2,1)` 부호 `(1,-1,-1)`).

거리만으로 고르면 조용히 좌우가 바뀐다. 차원술사에서 실측하니 거울 후보가 **모든 웨이트
값을 자릿수까지 그대로 재현하면서 각각을 반대 눈에 얹었다**. 바인드 포즈 몸이 좌우 대칭이라
위치 잔차로는 구분되지 않는다. 본 이름 일치율은 워로드 84.7% 대 28.4%로 갈린다(84.7%는
이식이 건드린 1508정점을 제외한 나머지 전부).

### 좌표가 겹친 정점

창술사에서 4개 정점이 세 개의 원본 정점 위에 정확히 겹쳐 앉는다(눈알 1, 눈꺼풀 2). 최근접은
부동소수 잡음이 고르므로, 현재 바인딩이 후보 중 하나와 맞으면 쿡의 선택을 그대로 둔다.

### 검증

- 손대지 않은 창술사·차원술사에 돌리면 **파일이 바이트 동일**하다(재기록 0)
- 워로드는 93/92로 복원되어 09-08 문서에 기록된 이식 전 실측치와 같다
- 이식 도구는 이제 얼굴 피부 재질의 서브메시에만 기록한다. 원본 얼굴 메시는 피부뿐이므로
  그 밖으로 나간 짝은 애초에 대응이 없다. 워로드 dry-run에서 185개가 걸러진다.

## 2. 꾸미기 탭 — 합성 경로는 이미 있었다

09-08 RESULT는 "합성 경로가 없어서 못 붙인다"고 적었다. 실제로는 원작 계산이
`Shader_SourceCharacterPrograms.hlsli`의 program 4에 이미 컴파일돼 있다. 빠져 있던 것은
클래스별 재질 행이었다. 지금까지 `source.character.classic-head.v1`에 올라간 얼굴은
차원술사 하나뿐이었다.

### 네 얼굴이 같은 마스터 체인이다

```
창술사    pc_ft_face_mi       -> ft_head_opa_high -> pbr_base_opa
워로드    pc_wr_face_mi_high  -> wr_head_opa_high -> pbr_base_opa
도화가    pc_sp_face_mi_high  -> sp_head_opa_high -> pbr_base_opa
차원술사  pc_sp_m_face_05_mi  -> sp_head_opa_high -> pbr_base_opa
```

**워로드만 예외**다. 바디 메시가 부르는 `pc_wr_face_mi`의 체인은 구 `pc_head_opa`이고, 이
마스터는 텍스처 파라미터가 셋뿐이다(`meshtype_diffuse`, `meshtype_specular`,
`decaltexture`). 립·눈화장·볼이 닿을 자리가 없다. `pc_wr_face_mi_high`는 같은
`pc_wr_00_face_d/n/s`를 쓰는 같은 얼굴이며 나머지 셋이 이미 쓰는 high 마스터 위에 있다.
그래서 워로드 행만 `sourceMaterial`이 다르다.

### 텍스처 레지스터

| 레지스터 | 채널 | 근거 |
|---|---|---|
| 4 | 립 | `var_makeup_lipcolor_ui`와 함께 소비, 1채널 샘플 |
| 5 | 눈 화장 | 아이라인·아이섀도 두 색과 함께 소비, 2채널 샘플 |
| 6 | 볼 | `var_makeup_cheekcolor_ui`. 같은 슬롯을 `var_base_skinfrecklecolor_ui`도 쓴다 |
| 7 | 데칼 | `var_headdeco_decalcolor_ui`, mirror 때문에 2회 샘플 |

program 4에서 각 샘플이 어떤 색 상수와 함께 쓰이는지 역추적한 결과이고,
`CustomizingMeshTypes.json`의 네 makeup 텍스처 변수 순서와도 일치한다. 두 방향에서 같은
답이 나온다.

### 값이 오는 곳

MIC는 자기 override만 말하고 나머지는 부모에서, 기본값은 체인 끝 `Material3`의
`Collected*Parameters`에 있다. `build_face_material_overrides.py`가 자식 우선으로 병합한다.
체인이 말하지 않는 이름은 0으로 채우지 않고 실패시킨다.

레지스터가 비면 CharacterCustomizingRule 문서 → 엔진 상수 순서로 채운다. 창술사의 주름
오버레이(`pc_ft_wrinkle_00_n`)가 그 경우다.

### 도구 검증

차원술사에 돌리면 기존 행의 62개 파라미터 중 **55개가 값까지 정확히 일치**하고 텍스처 12칸
배치가 그대로 재현된다. 나머지 7개는:

- 4개: `buffcolor`, `transcolor`, `fx_color_intensity_*`의 알파가 체인 0, 기존 행 1.
  RGB는 같다. 전부 런타임 FX 입력이다. 기존 차원술사 행은 건드리지 않았다.
- 3개: `selectioncolor`(엔진이 매 프레임 넣는 값, 명시 테이블로 처리),
  `skin_normal_intensity`와 `transcolor_rimlight`(파서 수정 후 해결)

## 3. 런타임 배선

원작 변수를 그대로 움직인다. 색을 따로 곱하는 장치를 만들지 않았다.

- Engine `CMaterial`에 상수 교체와 텍스처 레지스터 override. 패킹은 이름과 그 사이 연산이
  LostArk 것이라 Client가 소유하고 Engine은 결과만 받는다. program과 texture mask는 재질
  것으로 고정해 조작이 표면 자체를 바꿀 수 없다. override는 clone에 얹히므로 같은
  프로토타입을 공유하는 두 캐릭터가 서로의 얼굴을 덮지 않는다.
- `SourceCharacterMaterial`의 읽기와 패킹을 분리했다. 화면이 값 하나를 바꾸고 전체 행을
  다시 패킹해야 하는데 지금까지는 문서에서만 부를 수 있었다.
- 꾸미기 네 페이지: 입술 4 / 볼 터치 6 / 눈 화장 5, 눈썹은 색만. **강도 슬라이더는 그 색의
  알파다** — 원작 값이 볼은 알파 0, 입술은 1로 저작돼 있어 알파가 곧 세기다.
- 피부 세 슬라이더 전부 연결했다. 어느 변수인지는 4절이 근거다.
- 모든 조작이 클래스의 저작값에서 시작한다.

## 4. 문서가 모호했던 넷 — 셰이더에서 근거를 찾았다

09-08 목록이 "근거가 없다"고 남긴 항목들은 근거가 없는 게 아니라 규칙 문서가 말하지 않는
것이었다. 프로그램과 저작 문서를 읽어 넷 다 닫았다.

### 4.1 주름 슬라이더 = `var_headbase_overlaynormalintensity_ui`

규칙 문서는 후보 둘을 두고 "어느 쪽인지 두 source 모두 말하지 않는다"고 적는다. 프로그램에서
둘은 `baseConstants[27]`의 두 채널이고 각각 다른 맵을 스케일한다.

```
285  Texture0 샘플 (얼굴 노멀) -> 289 디코드
291  r2.xy = r1.xy * source[27].z             // .z = skin_normal_intensity * var_base_skinnormalintensity_ui
301  Texture1 샘플 (오버레이 = 주름 맵) -> 307 디코드
315  r1.xyz = source[27].w * r1.xyz + r2.xyz  // .w = var_headbase_overlaynormalintensity_ui
```

레지스터 1은 창술사에서 `pc_ft_wrinkle_00_n`이다. 주름 맵을 스케일하는 쪽이 주름 슬라이더다.
문서도 이쪽을 "likelier"로 봤지만 inference라고 적어 두었는데, 프로그램은 추론이 아니다.

### 4.2 주근깨 슬라이더 = `var_base_skinfrecklecolor_ui`의 알파

규칙 문서: "피부 탭이 FreckleIntensity 슬라이더를 노출하고 주근깨 색은 없다. 주근깨 세기로
명명된 스칼라가 이 문서들에 없다." 남은 건 색 하나뿐이고 프로그램이 이렇게 읽는다.

```
209  r2.xyz = source[12].xyz - skin           // frecklecolor.rgb
213  r0.w = Texture6.Sample(mirrored uv).w    // 볼 스탬프의 알파
215  r2.w = Texture6.Sample(uv).w
217  r0.w = r0.w + r2.w                       // 양쪽 볼 마스크
219  r0.w = r0.w * source[12].w               // x frecklecolor.a
221  skin  = r0.w * r2.xyz + skin             // lerp(skin, 색, 마스크 x 알파)
```

알파가 세기이고 세기 모양인 채널은 그것뿐이다. 덤으로 **텍스처 6은 RGB가 볼 터치,
알파가 주근깨 마스크인 한 장**임이 드러난다. 주근깨 슬라이더가 피부 탭에 있으면서 텍스처는
볼 터치 목록에서 오는 이유다.

두 슬라이더 모두 연결했다. 주근깨는 알파만 움직이고 저작된 색조는 그대로 둔다.

### 4.3 눈알이 눈 슬라이더를 따라오지 않는 것은 회귀가 아니다

`Data/Customizing/FaceSliders/*.json` 네 문서를 전부 읽었다. **18개 슬라이더가 쓰는 33개 본
어디에도 `b_fc_*_eye_ani`가 없다.** 창술사·차원술사처럼 눈알 리그가 멀쩡한 클래스도 마찬가지다.

즉 눈 슬라이더는 눈꺼풀 본만 움직이고 눈알은 원래 따라오지 않는다. `eye_ani`는 슬라이더가
아니라 시선·깜빡임 애니메이션이 쓰는 본이다. 09-08 문서가 이 본을 "눈동자 위치 조작"이라고
적은 것은 틀렸다.

실제 회귀는 따로였고 이번에 고쳤다. 이식이 눈알의 `eye_ani` 바인딩을 없애서 시선 애니메이션이
눈알을 못 움직이게 됐고, 대신 눈꺼풀·입 본이 붙어 **엉뚱한 슬라이더가 눈알을 끌고 다녔다**.
도화가는 눈알이 입 본을 따라갔다.

### 4.4 팔·몸 피부색은 원작에서 닿는다

`var_base_skincolor_ui`가 얼굴 재질에만 걸린다고 적었는데, 원본 MIC를 열어 보니 몸 재질도
같은 변수를 선언한다.

```
pc_wr_00_arm_mi        -> wr_parts_msk_high                  var_base_skincolor_ui [1,1,1,1]
pc_wr_base_upper_mi    -> wr_parts_msk_high                  var_base_skincolor_ui [1,1,1,1]
pc_sp_av_base_body_mi  -> sp_parts_msk_high -> pbr_base_msk  같은 변수 + half_lambert_skin
```

parts 마스터가 피부색을 받고 마스크가 어디에 피부가 드러나는지 정한다. 그래서 "어느 재질이
피부인가"를 판단할 필요가 없다 — parts 마스터 위의 재질 전부에 걸면 그게 원작 동작이다.
차원술사의 `pc_sp_av_base_upper_mi`가 이미 `source.character.classic-skin.v1`로 올라가 있고
같은 마스터 계열이므로, 얼굴에 한 것과 같은 방식으로 행을 만들면 된다. 아직 안 했다.

## 5. 의상 추가 본 — 무력한 게 아니라 깨져 있었다

09-08 3절이 "추가된 본은 렌더 시점에 무력하다"고 남긴 경계다. 실제로는 무력하지 않다.
`CPart_Equipment`가 바디의 팔레트를 바인딩하는데 `CMesh::Bind_Resource`는 그 메시의 본 수만
셰이더에 올린다. 추가 본에 웨이트가 걸린 정점은 배열 끝을 넘어 0 행렬을 읽는다.

범위도 9파츠가 아니다. 설치된 281파츠를 전수로 재니 **76파츠**가 마스터에 없는 본을 갖는다.

| 클래스 | 해당 파츠 | 예 |
|---|---|---|
| 창술사 | 28 | `pc_ft_52_hair` 34개, `pc_ft_50/54_hair` 30~32개 |
| 차원술사 | 11 | `pc_swp_m_av_137/upper` 40개, `lower` 30개 |
| 도화가 | 13 | `pc_sp_51_hair` 10개 |
| 워로드 | 8 | `pc_wr_43_hair` 18개 |

나머지 183파츠의 "추가 본"은 추출기가 본 목록에 넣는 메시 루트 노드 `<mesh>_sk` 하나뿐이라
변형에 관여하지 않는다. 이 구분을 하지 않으면 281개 중 259개가 해당하는 것처럼 보인다.

`CModel::Pose_BonesFrom`을 추가했다. 다른 스켈레톤을 이름으로 매칭해 이 모델의 본을 포즈한다.
양쪽에 있는 본은 소스의 combined를 그대로 받고, 이 모델에만 있는 의상 전용 본은 방금 포즈된
부모 위에 자기 rest local로 다시 세운다. PreTransform은 루트에서만 곱해지므로 의상 본은 항상
바디 공간의 부모를 상속한다. 추가 본을 가진 파츠만 이 경로를 타고 나머지는 종전과 동일하다.

## 6. 소프트 리밋 — 10개가 아니라 거의 전부다

09-08 4절은 "창술사 10개 관절의 `SwingLimitStiffness/Damping = 10`"을 넣지 않았다고 적었다.
원본 `RB_ConstraintSetup` 덤프를 다시 읽으니 그림이 다르다.

| 클래스 | `bswinglimitsoft = true` | 명시 stiffness |
|---|---|---|
| 창술사 | 71 | 10 (`b_upper_cloth_f_03/04`, `b_helmet_b*` 8개) |
| 워로드 | 65 | 0 |
| 도화가 | 73 | 0 |
| 차원술사 | 62 | 0 |

즉 **네 클래스의 천 관절이 사실상 전부 소프트 리밋**이고, 10이라는 숫자는 창술사 10개 관절에만
얹힌 국소 override다. 나머지는 UE3 클래스 기본값을 쓴다.

우리 솔버는 09-08에 넣은 하드 원뿔 클램프다. 그러니 어긋나 있는 것은 "10을 안 넣은 것"이 아니라
**리밋이 딱딱하다는 것 자체**다. 다만 소프트 리밋을 제대로 넣으려면 스프링 상수가 필요하고,
`SwingLimitStiffness`는 PhysX 단위이며 우리 Verlet 블렌드 계수와 대응 관계가 확립돼 있지 않다.
클래스 기본값도 이 덤프에는 없다(직렬화 diff라 기본값은 생략된다). 그래서 이번에도 넣지 않았고,
남은 것의 성격을 "값 하나가 빠졌다"에서 "리밋 모델이 다르다"로 고쳐 적는다.

## 7. 눈 탭 — 프로그램 5가 읽는 변수에 그대로 붙였다

눈 탭의 색상판 둘과 슬라이더 둘이 지금까지 화면만 그리고 아무것도 움직이지 않았다.

### 재질 행

네 클래스의 눈 재질(`pc_ft_eye_mi`, `pc_wr_eye_mi`, `pc_sp_eye_mi`, 차원술사 기존 행)은 전부
마스터 `mastermaterial_ch.pc.eye.pc_eye_opa`, 속눈썹·눈 AO(`pc_ft_eyelashes_mi`,
`pc_sp_eyeao_mi`)는 전부 `mastermaterial_ch.pc.eyelashes.pc_eylashes_trn`이다.

### 세 클래스는 되돌렸다 — 프로그램 5는 UV1·UV2를 요구한다

행을 넣고 실행하니 창술사 입장이 `CLIENT_LOAD_FAILED`로 끊겼다. 진단 JSONL의 마지막 단계는
`[Loader] Character 1/1 | Lance Master models 0/11 | LanceMaster.wmodel`이다. 파일이 없는 게
아니라 `CModel::Create`가 실패한 것이고, 실패 지점은 `Model.cpp`의

```cpp
if ((source.program == 5u || source.program == 7u) && any_of(... !mesh.hasTexcoord1 ||
    (source.program == 5u && !mesh.hasTexcoord2)))
    return failOverride("source character requires native extra UV channels");
```

이다. 스킨 메시의 UV1·UV2는 WModel **1.3**(`WINT_SKINNED_UV_VERSION_MINOR`)에서만 실린다.
네 body의 WINT 헤더를 읽으면 차원술사만 1.3이고 창술사·워로드·도화가는 1.0이다. 그래서
차원술사의 기존 눈 행은 통과하고 새로 넣은 세 행은 body 전체 로드를 막았다.

세 행을 catalog에서 제거하고 생성기 `ROWS`에서도 이유와 함께 주석 처리했다. 눈 재질을 세
클래스에 붙이려면 body를 1.3으로 다시 cook해야 한다. 속눈썹·눈 AO 행은 프로그램 6이라 이
검사에 걸리지 않으므로 그대로 둔다. 눈 탭은 눈 변수를 읽지 못하는 클래스에서 색상판까지
비활성으로 그린다.

오드아이를 켜면 같은 두 색상판이 `var_eye_basecolorleft_ui` / `var_eye_iriscolorleft_ui`를
쓴다. 탭을 오갈 때마다 색상판과 선명도가 그 눈의 현재 값을 다시 읽는다. 네 값 모두 처음에는
클래스가 저작한 값에서 시작한다.

### 선명도의 근거

`customizing_label_alpha`가 "선명도"라는 것만으로는 어느 색의 알파인지 정해지지 않는다.
movie에서 이 텍스트 필드는 `defaultPage` 안 (47,66)에 있고, 위쪽 (37,35)의 홍채 색상보다 한
단 들여 쓰여 있다 — 홍채 색상 그룹의 하위 항목이다. 프로그램 5의 base pass가 그 해석과 맞다.

```
r0.z = r1.w * source[5].w                       // mask * iriscolorleft.a
r2.xyz = -source[4].xyz + source[5].xyz         // iris - base
r2.xyz = r0.z * r2.xyz + source[4].xyz          // lerp(base, iris, mask * iris.a)
```

홍채 색의 알파가 곧 홍채를 베이스 위에 얹는 양이다. 그래서 색상판은 RGB만 쓰고 알파는
슬라이더가 쥐고 있는 값을 유지한다.

### 두 번째 슬라이더가 아니었던 것

이전 메모는 이 슬라이더를 "라벨이 일반 alpha 자리표시자라 근거 없음"으로 남겨 뒀다. 실제로는
`customizing_label_alpha` 자체가 원작 문자열 테이블의 정식 항목("선명도")이고 자리표시자가
아니다. `charactercustomizing.xml`의 `DefineEditTextTag` 여섯 개를 characterID로 되짚어
확인했다.

## 8. 탭 캡션 — 원작 movie와 대조해 맞췄다

`trace_CharCustom_Right_Tab*_d7.txt`의 텍스트 필드 위치와 `strings_pccreate.txt`를 대조해
빠지거나 틀린 캡션을 고쳤다.

- **탭 이름이 얼굴 탭에서만 밝게 떴다.** 탭 그림은 이미 "음성만 흐리게"로 그리고 있었는데
  이름은 옛 기준(`FACE_TAB_INDEX == i`)을 그대로 쓰고 있었다. 같은 기준으로 통일했다.
- **빠져 있던 캡션 넷**: 머리 형태(`hair_form`), 머리 윤기(`hair_gloss`), 동공
  형태(`eye_lenz`), 피부 윤기(`skin_gloss`). 원작에서 윤기는 구역 제목이고 그 아래 들여쓴
  강도 슬라이더가 붙는 구조라 그 형태로 넣었다.
- **꾸미기 네 페이지가 캡션 한 벌을 공유했다.** 원작은 페이지마다 입술 형태/입술 색상,
  볼 터치 형태/볼 터치 색상, 눈 화장 형태/아이라인 색상, 눈썹 색상을 따로 쓰고 슬라이더도
  볼 터치만 강도, 나머지는 선명도다. 페이지별 캡션 표를 만들어 그대로 그린다.
- **아이섀도 캡션 둘이 모든 꾸미기 페이지에 그려졌다.** 그 슬롯은 눈 화장 페이지에만
  보이므로 캡션도 그 페이지에서만 그린다.

### 기본 탭

원작 기본 탭의 목록은 테이블 category 0 — 외형 전체를 한 번에 고르는 큐레이션 세트다.
추출된 것은 `CustomizingFacePresets.json`의 category 1(체계적인 얼굴형 25/35개)뿐이고 얼굴
탭이 이미 그것을 쓴다. 두 목록은 클래스별 행 수가 같아서 서로 바꿔 쓸 수 있어 보이지만 다른
목록이므로, 그대로 채우면 아이콘과 얼굴이 어긋난다. category 0 내용을 추출하기 전에는 빈
패널을 여는 대신 음성 탭처럼 흐리게 두고 클릭을 받지 않는다.
