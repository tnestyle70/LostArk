# 2026-09-26 초상 디퍼드 렌더 PLAN

## 목표

MVP창과 캐릭터 정보창의 캐릭터 초상을 필드와 같은 모습으로 만든다. 지금은 같은 캐릭터를
같은 파츠 구성으로 그리는데도 재질이 기본값으로 나온다.

종료 증거는 사용자가 실제 화면에서 다음을 확인하는 것이다.

```text
커스터마이즈한 얼굴의 피부 톤과 메이크업이 초상에 나온다
염색·틴트가 적용된 의상이 필드와 같은 색으로 나온다
어두운 아레나에서는 초상도 어둡다 (월드 광원을 그대로 받으므로)
```

## 현재 상태 실측

### 초상이 기본 재질로 나오는 이유

`CCharacterPortraitRenderer::Render`가 전용 forward pass를 지정한다.

```cpp
constexpr uint32_t SKINNED_FORWARD_PASS = 5u;    // Shader_VtxAnimMeshBinary ScreenCutin
constexpr uint32_t SOCKETED_FORWARD_PASS = 19u;  // Shader_VtxMeshBinary ScreenCutin
```

그 pass의 픽셀 셰이더 `PS_MAIN_SCREEN_CUTIN`은 `g_DiffuseTexture` 샘플에 선택적 노멀맵과
단순 조명만 쓴다. 재질별 `SourceCharacter` program을 타지 않는다.

`CPart_Body::Render_Pass`와 `CPart_Equipment::Render_Pass`를 보면 메시를 건너뛰는 `continue`가
모두 `iPassIndex == 0u` 조건에 걸려 있다. 즉 초상(pass 5/19)은 모든 메시를 그리고, 월드
deferred 경로(pass 0)만 forward 재질을 별도 그룹에 넘긴다. **파츠가 빠지는 문제는 아니다.**

### 재질 program 개수

`Data/Actors/CharacterCatalog.json`의 family를 `SourceCharacterMaterialParameters.h`의
`family -> program` 표로 환산한 결과다.

| 직업 | family | program |
|---|---|---|
| 창술사 | 9 | 1, 2, 4, 5, 6, 90, 91, 99, 165 |
| 건슬링어 | 9 | 2, 4, 5, 6, 14, 90, 91, 99, 112 |
| 슬레이어 | 6 | 1, 2, 4, 5, 6, 7 |
| 도화가 | 10 | 1, 4, 5, 6, 15~20 |
| 차원술사 | 8 | 1, 3, 4, 5, 6, 7, 8, 9 |
| 워로드 | 9 | 1, 2, 5, 7, 10~14 |
| 가디언나이트 | 12 | 1, 4, 5, 6, 94, 96~99, 162, 198, 199 |

클래스 본체·장비만 32개, catalog의 공용 `modelMaterialOverrides` 52개를 더한 합집합은 68개다.
program별 forward 변형을 만들면 의상이 추가될 때마다 짝을 유지해야 하므로 채택하지 않는다.

### 디퍼드 경로와 재사용 가능성

`CRenderer::Draw`의 순서다.

```text
Begin_MRT(MRT_GameObject)  → Target_Diffuse/Normal/Depth/Specular/CharacterSurface/CharacterGeometry/Emissive
End_MRT
Render_Lights()            → Begin_MRT(MRT_LightAcc) → CGameInstance::Render_Lights(m_pShader, m_pVIBuffer, …) → End_MRT
Begin_MRT(MRT_SceneHDR)    → Render_Scene → 후처리
```

두 전제를 확인했다.

- `CTarget_Manager::Begin_MRT`은 MRT의 모든 타깃에 `Clear()`를 호출한다. 초상이 G-buffer를
  먼저 쓰더라도 월드가 `Begin_MRT(MRT_GameObject)`를 부를 때 지워진다. **복구 코드가 필요 없다.**
- `Light_Manager`와 `Renderer` 어디에도 광원 목록을 비우는 코드가 없다(`m_Lights.clear()` 없음).
  `Render_Lights`는 읽기 전용 패스이므로 한 프레임에 두 번 호출할 수 있다.

그래서 초상 전용 타깃 세트와 조명 태그 인자화는 필요하지 않다. 기존 G-buffer를 프레임
앞부분에서 한 번 더 쓰고 결과만 복사한다.

### 초상 패스가 CRenderer 안에 있어야 하는 이유

`Begin_MRT`은 `CGameInstance`를 통해 부를 수 있지만 `Render_Lights`는 `CRenderer`가 소유한
`m_pShader`와 `m_pVIBuffer`를 넘겨야 한다. Client에서는 그 두 자원에 접근할 수 없다.
따라서 초상 패스는 `CRenderer`가 실행하고, Client는 요청만 제출한다.

Engine이 `CCharacter`를 알면 안 되므로 요청은 그리기 콜백을 들고 간다.

### 초상 패스에서 꺼야 하는 두 입력

- 그림자: `m_pShadowSRV`는 월드 광원 행렬 기준이다. 초상 카메라 깊이에 적용하면 틀린 음영이
  나온다. 기존 `bEnableSceneDirectionalShadow` 인자에 `false`를 넘긴다.
- SSAO: `Target_SSAOBlur`는 월드 G-buffer에서 계산된 값이다. 초상에는 맞지 않으므로 바인딩을
  건너뛴다. 기존 `m_RenderQualitySettings.bSSAOEnabled` 분기와 같은 자리에서 판단한다.

월드 광원은 그대로 쓴다. 캐릭터는 월드 위치에 있고 카메라만 바뀌므로 초상은 필드를 확대한
그림이 된다. 이것이 이번 작업의 목표다.

## G01. 초상 요청 계약과 큐

### 파일 역할

`Engine/Public/Renderer.h`는 렌더 그룹 큐와 프레임 순서를 소유한다. 초상 요청도 같은 성격의
프레임 단위 큐이므로 여기에 둔다.

### 계약

```cpp
	/* One off-screen portrait to draw through the deferred path before the world fills the
	G-buffer this frame. The Client owns the destination target and the draw itself: Engine
	never learns what a character is, it only runs the callback with the portrait camera
	bound and resolves the lighting the world pass would have resolved. */
	struct PORTRAIT_REQUEST
	{
		/* Where the resolved portrait is copied to. Both must outlive this frame. */
		ComPtr<ID3D11Texture2D>				pDestination;
		uint32_t							iWidth = 0;
		uint32_t							iHeight = 0;
		/* The portrait camera for this request, already built by the caller. */
		float4x4_t							ViewMatrix{};
		float4x4_t							ProjMatrix{};
		/* Draws the subject with the G-buffer bound. Returning a failure skips only this
		request. Runs on the rendering thread inside Draw. */
		std::function<HRESULT()>			DrawSubject;
	};

public:
	/* Queued for the next Draw and cleared by it, so a window that stops asking stops being
	drawn without any teardown. Fails only on a request that cannot be drawn at all. */
	HRESULT Request_Portrait(PORTRAIT_REQUEST Request);
```

멤버 변수는 `private:` 구역에 둔다.

```cpp
	vector<PORTRAIT_REQUEST>			m_PortraitRequests;
```

`m_PortraitRequests`의 owner는 `CRenderer`다. 검색 인덱스가 아니라 프레임 큐이고, 수명은
제출부터 그 프레임 `Draw`까지다. 렌더링 스레드에서만 읽고 쓴다.

### 함수 한 줄 책임

- `Request_Portrait` — 요청 하나를 프레임 큐에 넣는다. 목적지와 크기, 콜백이 비면 거절한다.

## G02. 초상 디퍼드 패스

### 목표

큐에 쌓인 요청을 월드 G-buffer 패스보다 먼저 처리한다. 각 요청은 G-buffer에 그려지고 조명이
resolve된 뒤 목적지 텍스처로 복사된다.

### 함수 한 줄 책임

- `Render_Portraits` — 프레임 큐를 비우면서 요청마다 G-buffer 채우기, 조명 resolve, 복사를
  수행하고 VIEW/PROJ를 원래대로 되돌린다.

### 호출 흐름

이번 G가 새로 연결하는 부분만 적는다.

```text
CRenderer::Draw
  Render_Portraits()          ← 새로 추가. 월드 G-buffer 패스 앞
    요청마다
      Set_Transform(VIEW/PROJ, 요청 카메라)
      Begin_MRT(MRT_GameObject)     ← 모든 G-buffer 타깃이 Clear된다
      RSSetViewports(요청 크기)
      Request.DrawSubject()         ← Client가 Render_PreviewParts(0u, 0u, 마스크)를 부른다
      End_MRT()
      Render_PortraitLights(요청)   ← 그림자·SSAO 없이 MRT_LightAcc에 resolve
      CopySubresourceRegion(목적지 <- Target_LightAcc)
    VIEW/PROJ 복원
    m_PortraitRequests.clear()
  Render_Priority() … 기존 순서 그대로
```

### 전체 코드

`Render_Portraits`와 그 조명 보조 함수다. `Render_Lights`가 묶는 입력 중 초상에 유효한 것만
묶는다. 기존 `Render_Lights`는 건드리지 않는다.

```text

작업: 추가
기준점: HRESULT CRenderer::Render_Lights()
위치: 그 함수 정의 바로 위
```

```cpp
/* The portrait reuses the world G-buffer a second time before the world fills it, so it needs
the same lighting resolve the world gets minus the two inputs that are world-only: the shadow
map carries the world light matrix and would shade the portrait against the wrong depth, and
Target_SSAOBlur was computed from the world G-buffer that the portrait just overwrote. */
HRESULT CRenderer::Render_PortraitLights()
{
	if (FAILED(CGameInstance::Get().Begin_MRT(TEXT("MRT_LightAcc"))))
		return E_FAIL;

	const uint32_t noSourceCharacter = 0u;
	const uint32_t noSSAO = 0u;
	const auto& pbrComparison = m_MaterialRenderSettings.MapPBR;
	const float4_t pbrContributions =
		pbrComparison.Is_Active(CGameInstance::Get().Get_CurrentLevelID()) ?
		pbrComparison.vContributionScale : float4_t(1.f, 1.f, 1.f, 1.f);

	HRESULT hResult = S_OK;
	if (FAILED(m_pShader->Bind_RawValue("g_MapPBRContributionScale", &pbrContributions,
			sizeof(pbrContributions))) ||
		FAILED(m_pShader->Bind_RawValue("g_SourceCharacterProgram", &noSourceCharacter,
			sizeof(noSourceCharacter))) ||
		FAILED(m_pShader->Bind_RawValue("g_SourceCharacterRow", &noSourceCharacter,
			sizeof(noSourceCharacter))) ||
		FAILED(m_pShader->Bind_Matrix("g_SourceCharacterViewMatrix",
			CGameInstance::Get().Get_Transform(D3DTS::VIEW))) ||
		FAILED(m_pShader->Bind_Matrix("g_SourceCharacterProjMatrix",
			CGameInstance::Get().Get_Transform(D3DTS::PROJ))) ||
		FAILED(CGameInstance::Get().Bind_RT_SRV(TEXT("Target_Emissive"),
			m_pShader, "g_EmissiveTexture")) ||
		FAILED(CGameInstance::Get().Bind_RT_SRV(TEXT("Target_CharacterSurface"),
			m_pShader, "g_CharacterSurfaceTexture")) ||
		FAILED(CGameInstance::Get().Bind_RT_SRV(TEXT("Target_CharacterGeometry"),
			m_pShader, "g_CharacterGeometryTexture")) ||
		FAILED(m_pShader->Bind_RawValue("g_iSSAOEnabled", &noSSAO, sizeof(noSSAO))))
	{
		hResult = E_FAIL;
	}

	if (SUCCEEDED(hResult))
	{
		hResult = CGameInstance::Get().Render_Lights(m_pShader, m_pVIBuffer, false);
	}

	const HRESULT hEnd = CGameInstance::Get().End_MRT();
	return FAILED(hResult) ? hResult : hEnd;
}

HRESULT CRenderer::Render_Portraits()
{
	if (m_PortraitRequests.empty())
		return S_OK;

	const float4x4_t PreviousView = *CGameInstance::Get().Get_Transform(D3DTS::VIEW);
	const float4x4_t PreviousProjection = *CGameInstance::Get().Get_Transform(D3DTS::PROJ);

	uint32_t iPreviousViewportCount = 1u;
	D3D11_VIEWPORT PreviousViewport{};
	m_pContext->RSGetViewports(&iPreviousViewportCount, &PreviousViewport);

	HRESULT hLastFailure = S_OK;
	for (const PORTRAIT_REQUEST& Request : m_PortraitRequests)
	{
		CGameInstance::Get().Set_Transform(D3DTS::VIEW, XMLoadFloat4x4(&Request.ViewMatrix));
		CGameInstance::Get().Set_Transform(D3DTS::PROJ, XMLoadFloat4x4(&Request.ProjMatrix));

		if (FAILED(CGameInstance::Get().Begin_MRT(TEXT("MRT_GameObject"))))
		{
			hLastFailure = E_FAIL;
			continue;
		}

		D3D11_VIEWPORT PortraitViewport{};
		PortraitViewport.TopLeftX = 0.f;
		PortraitViewport.TopLeftY = 0.f;
		PortraitViewport.Width = static_cast<f32_t>(Request.iWidth);
		PortraitViewport.Height = static_cast<f32_t>(Request.iHeight);
		PortraitViewport.MinDepth = 0.f;
		PortraitViewport.MaxDepth = 1.f;
		m_pContext->RSSetViewports(1u, &PortraitViewport);

		const HRESULT hSubject = Request.DrawSubject();
		const HRESULT hEndGeometry = CGameInstance::Get().End_MRT();
		if (FAILED(hSubject) || FAILED(hEndGeometry))
		{
			hLastFailure = FAILED(hSubject) ? hSubject : hEndGeometry;
			continue;
		}

		m_pContext->RSSetViewports(1u, &PortraitViewport);
		const HRESULT hLights = Render_PortraitLights();
		if (FAILED(hLights))
		{
			hLastFailure = hLights;
			continue;
		}

		/* Target_Shade and Target_Specular are only the lighting terms; Render_Combined
		mixes them with the G-buffer into MRT_SceneHDR, which is the colour the world shows. */
		if (FAILED(CGameInstance::Get().Begin_MRT(TEXT("MRT_SceneHDR"))))
		{
			hLastFailure = E_FAIL;
			continue;
		}
		m_pContext->RSSetViewports(1u, &PortraitViewport);
		const HRESULT hCombined = Render_Combined();
		const HRESULT hEndScene = CGameInstance::Get().End_MRT();
		if (FAILED(hCombined) || FAILED(hEndScene))
		{
			hLastFailure = FAILED(hCombined) ? hCombined : hEndScene;
			continue;
		}

		const HRESULT hCopy = CGameInstance::Get().Copy_RenderTargetRegion(
			TEXT("Target_SceneHDR"), Request.pDestination, Request.iWidth, Request.iHeight);
		if (FAILED(hCopy))
			hLastFailure = hCopy;
	}

	m_PortraitRequests.clear();
	CGameInstance::Get().Set_Transform(D3DTS::VIEW, XMLoadFloat4x4(&PreviousView));
	CGameInstance::Get().Set_Transform(D3DTS::PROJ, XMLoadFloat4x4(&PreviousProjection));
	if (0u != iPreviousViewportCount)
		m_pContext->RSSetViewports(1u, &PreviousViewport);
	return hLastFailure;
}
```

### 실측 결과로 확정한 세 가지

세 항목을 실제 코드에서 확인했고 위 코드는 그 결과를 반영해야 한다.

- `MRT_LightAcc`는 `Target_Shade`와 `Target_Specular` **두 장**이다. 그리고 그 둘은 조명 항일
  뿐이고 최종 색은 `Render_Combined`이 `MRT_SceneHDR`에 합성한다(`Draw` 908~922줄).
  따라서 초상도 combine까지 돌고 **`Target_SceneHDR`에서 복사**해야 한다.
- 텍스처 획득 API는 없다. `CTarget_Manager::Copy_Resource`는 있지만 `CopyResource`를 쓰므로
  크기가 같아야 한다. 초상 목적지는 작으므로 영역 복사가 필요하다. 텍스처를 외부에 노출하지
  않도록 `CTarget_Manager`에 영역 복사를 추가한다.
- SSAO 토글 상수는 `g_iSSAOEnabled`다(`Shader_Deferred.hlsl` 46줄). `g_SSAOEnabled`가 아니다.

### 확정된 초상 패스 순서

```text
Set_Transform(VIEW/PROJ, 요청 카메라)
Begin_MRT(MRT_GameObject)   → G-buffer 클리어
RSSetViewports(요청 크기)
Request.DrawSubject()       → Client가 Render_PreviewParts(0u, 0u, 마스크, 마스크)
End_MRT()
Render_PortraitLights()     → MRT_LightAcc, 그림자·SSAO 없음
Begin_MRT(MRT_SceneHDR)
Render_Combined()           → 최종 색
End_MRT()
Copy_Region(Target_SceneHDR, 목적지, 요청 크기 박스)
VIEW/PROJ 복원
```

`Render_Combined`은 큐브 diffuse와 정적 그림자 캐시를 함께 묶는다. 초상에서 그 입력이 월드
기준이어도 색 합성에는 문제가 없으므로 그대로 쓴다. 화면에서 이상하면 그때 분리한다.

## G04. 초상 렌더러를 요청 제출로 교체

### 파일 역할

`CCharacterPortraitRenderer`는 목적지 텍스처와 SRV를 계속 소유한다. 바뀌는 것은 그리기
방식이다. 직접 그리지 않고 요청을 제출한다.

### 계약 변경

`Render`의 시그니처는 유지한다. 호출부 세 곳을 바꾸지 않아도 되고, 반환 의미도 같다.
내부 구현만 요청 제출로 바뀐다.

`SKINNED_FORWARD_PASS`, `SOCKETED_FORWARD_PASS` 상수와 RTV/DSV 저장·복원 코드는 이 파일에서
사라진다. 자기 RTV에 직접 그리지 않기 때문이다. `m_pRTV`와 `m_pDSV` 멤버도 필요 없어진다.

### 함수 한 줄 책임

- `Render` — 카메라 행렬을 만들고 목적지 텍스처를 확보한 뒤 그리기 콜백과 함께 요청을 제출한다.
- `Ensure_Target` — 목적지 텍스처와 SRV를 요청 크기로 확보한다. RTV/DSV는 만들지 않는다.

### 호출 흐름

```text
창의 Render_Portrait
  m_pPortrait->Render(pCharacter, w, h, Camera, 마스크, 마스크)
    Ensure_Target(w, h)
    카메라 View/Proj 계산                ← 기존 코드 그대로
    CGameInstance::Request_Portrait({ 목적지, w, h, View, Proj,
        [pCharacter, 마스크] { return pCharacter->Render_PreviewParts(0u, 0u, 마스크, 마스크); } })
  Set_SlotTextureSRV("CI_Preview", Get_SRV())
```

`Render_PreviewParts`에 pass 0을 넘기는 것이 이번 작업의 핵심이다. 그러면
`CPart_Body::Render_Pass`와 `CPart_Equipment::Render_Pass`의 월드 재질 분기가 그대로 돌고,
forward 재질은 그 분기가 건너뛴다. 초상에서 반투명·유령 재질이 빠지는지는 화면에서 확인하고,
빠지면 G02에 forward 그룹 단계를 더한다.

콜백이 `pCharacter`를 `shared_ptr`로 캡처하면 프레임이 끝날 때까지 캐릭터가 살아 있다.
요청은 그 프레임 `Draw`에서 소비되므로 수명이 맞는다.

### 전체 코드

이 두 파일은 전문을 싣는다. 실제 코드는 G02의 실측 항목이 확정된 뒤에 확정한다. 지금 단계에서
확정된 것은 위 계약과 흐름이다.
