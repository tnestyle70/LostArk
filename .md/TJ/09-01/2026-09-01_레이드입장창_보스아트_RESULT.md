# 2026-09-01 레이드 입장창 — 원본 gfx 기반 배치와 보스 아트 추적 RESULT

대응 선행 문서: `.md/TJ/08-30/2026-08-30_레이드입장창_PLAN.md`

## 0. 이 문서의 목적

레이드 입장창(쿠크세이튼)의 남은 자리표시자를 실제 에셋으로 채우는 작업과,
"인게임에서는 보스 아트가 컬러이고 움직이는데 추출본은 무채색 정지 이미지"라는
문제를 추적한 기록이다. 결론부터: **배치는 완료했고, 움직이는 아트는 정적 에셋으로
존재하지 않는다는 것을 확인했다.** 같은 길을 다시 파지 않도록 근거와 도구 사용법을
남긴다.

## 1. 확정한 사실 (전부 데이터 근거)

### 1.1 원본 UI는 `epicgatecommanderentrance.gfx`다

08-30 PLAN은 `epicraidentrance.gfx`를 기준으로 좌표를 잡았지만, 사용자가 참조로 준
실제 화면(군단장 레이드 입장)은 **다른 창**이다. 정본은
`X41P9JX2PJB5UXJVHH5OQXGXOUG5OJX.upk`의 `efswfmovie epicgatecommanderentrance`이고,
`displayRect`가 `38400x21600` twips = **1920x1080**이라 우리 레이아웃 문서의 참조
해상도와 그대로 맞는다. 좌표 변환이 필요 없다.

### 1.2 좌표·크기·파일명을 잇는 세 태그

ffdec으로 디컴파일한 XML에서 다음 셋을 조인하면 눈대중 없이 모든 조각이 나온다.

| 태그 | 주는 정보 |
|---|---|
| `DefineSubImage` | 조각의 아틀라스 rect (`imageId`, x1/y1/x2/y2) |
| `DefineExternalImage2` | 그 `imageID`의 실제 텍스처 파일명과 크기 |
| `PlaceObject2/3Tag` (matrix) | 인스턴스의 화면 좌표 (twips/20 = px) |

`SymbolClassTag`는 이름을 스프라이트에 붙여줄 뿐이라, 이름에서 rect까지 가려면
스프라이트 → 자식 PlaceObject → 셰이프 → `fillStyle bitmapId` → `DefineSubImage`로
재귀 추적해야 한다. 이 스크립트를 `trace_symbols.py` / `layout_table.py`로 남겼다.

### 1.3 보스 아트는 두 장이 배타적으로 전환된다

`EpicGateCommanderEntranceContent.as`:

```as
this.monsterInfo.imageTexture.visible = satisfied;   // 입장 조건 충족
this.monsterInfo.bossImage.visible   = !satisfied;   // 미충족
this.monsterInfo.bossImage.gotoAndStop(param1.index + 1);  // 레이드 6종 선택
```

- `bossImage` = SWF에 박힌 **무채색** 그림. 4프레임(I2D2/I2D6/I2D4/I2D8 = 보스 4종).
  우리가 추출해 배치한 것이 이것이다. **무채색인 것은 추출 실패가 아니라 원본이 그렇다.**
- `imageTexture` = 컬러이고 움직이는 쪽. SWF에 그림이 없다.

### 1.4 `imageTexture`는 엔진이 공급한다

`ARKImageLoader.as`:

```as
new URLRequest("img://" + param1.iconPath)   // {iconPath, iconU, iconV, iconWidth, iconHeight}
```

`img://`는 Flash 표준이 아니라 **로스트아크 엔진이 등록한 커스텀 프로토콜**이다.
SWF 안에 있는 값은 `TestUtil` 더미(`../Test/putin.jpg`, "정보처 정보병")뿐이다.

`iconPath`의 실제 값은 게임 데이터테이블에 있다:

```
SourceData/LPK/data2/EFGame_Extra/ClientData/TableData/EFTable_ZoneEpicGate.db
  ZoneEpicGate.EnterUIImg
    PK=37081  EpicGate.LV_LUT_Commander_KoukuSaton  (+_Chaos)
    PK=37051  EpicGate.LV_LUT_Commander_Valtan      (+_Chaos, _Extreme)
```

### 2.3 부분 성공 — `_special` 컬러 아트

패키지 스캔으로 `OVSG0A3WAU27MSFHG82DY2.upk` = **`EFUI_BACKGROUNDIMG`**를 찾았다.

```
lv_lut_commander_koukusaton_special   604x704   컬러
lv_rhd_commander_abrelshud_special    604x704   컬러
lv_ber_commander_illiakan_special     604x704   컬러
lv_lut_commander_valtan_lock         1200x848   무채색
```

이름의 `_special`/`_lock`이 AS3의 `imageTexture`/`bossImage` 분기와 대응한다.

**다만 `_special`은 우리가 찾던 그림이 아니다.** SWF의 무채색본과 나란히 놓고 보면
서로 다른 아트다.

| | `_special` (604x704) | SWF `bossImage` (1201x843) |
|---|---|---|
| 인물 | 광대 가면, 빨간 코, 실크햇 | 뿔 달린 어두운 가면, 모자 없음 |
| 배경 | 미러볼, 무대 조명, 마름모 커튼 | 눈밭의 서커스 천막, 밤하늘 |

사용자가 준 인게임 스크린샷의 중앙 아트는 **오른쪽(SWF 무채색본)과 같은 구도**다.
즉 인게임 화면은 `_special`이 아니라 그 무채색 그림의 컬러·애니메이션 버전이며,
`_special`은 다른 용도(좌측 패널 등)로 보인다. 이 부분은 미확인으로 남겼다.

## 3. 결론

움직이는 컬러 아트는 **정적 텍스처 에셋으로 존재하지 않는다.** SWF에도, EFUI
패키지에도, 게임 패키지 전체에도, 데이터테이블에도 없다. AS3가 `img://`로 엔진에
요청하는 구조이므로 **엔진이 그 영역에 실시간으로 그리는 것**이고, 팀원들이 추측한
"메쉬+텍스처 또는 실제 보스 모델"이 방향상 맞다.

사용자 판단으로 **무채색 정지 이미지 상태로 마무리**했다.

## 4. 앞으로 어떻게 되어야 하는가

우리 엔진에는 원작의 `img://`와 같은 통로가 이미 있다.

```cpp
ComPtr<ID3D11ShaderResourceView> CTarget_Manager::Get_SRV(strTargetTag);
void CUI_Sprite::Set_Texture(ComPtr<ID3D11ShaderResourceView> pOverrideSRV);
```

`Set_Texture`가 임의의 SRV를 받으므로, 렌더타깃 SRV를 넣으면 그 슬롯이 실시간 렌더
결과를 표시한다. 구현하려면:

1. `CTarget_Manager::Add_RenderTarget("Target_RaidEntryPortrait", ...)` + `Add_MRT`
2. 입장창이 열린 동안 매 프레임 `Begin_MRT` → 보스 `CModel` 렌더(애니메이션 재생) → `End_MRT`
3. `RaidEntry_BossPortrait` 슬롯의 텍스처를 그 렌더타깃 SRV로 교체

슬롯의 좌표·크기·레이어 순서는 지금 잡아둔 것을 그대로 쓰면 되고, **텍스처 공급원만
PNG에서 렌더타깃으로 바뀐다.**

준비된 자산:
- 발탄 모델 `Client/Bin/Resources/Character/Valtan` — 클립 27개
  (`idle_normal_1`, `idle_battle_1`, `sc_groupdance_3`, `dead_1` 등)
- 쿠크세이튼 모델 `Character/KoukuSaton`, `Character/KakulSaydon` — `.wmodel` 존재하나 작업 중

**어떤 클립을 재생해야 하는지는 데이터에 없다(2.2 참조).** 원작 재현은 불가능하므로
`idle_normal_1` 같은 대기 모션을 UI 카메라로 잡는 선택을 우리가 하면 된다. 모델이 완성된
발탄으로 먼저 배선을 검증하고 쿠크세이튼은 나중에 교체하는 순서가 안전하다.

남은 미확인 항목: `_special`(604x704)의 실제 용도.

## 5. 도구 사용법 메모 (다음 세션 시간 절약용)

### 5.1 gfx 추출과 디컴파일

```powershell
# .gfx 추출 — ScaleForm은 -3rdparty 필요
umodel_lostark_custom.exe -export -3rdparty -out=<DIR> -path=<PKGDIR> <PKG> <swf이름>
# XML 전체 구조
D:\ClaudeWork\ffdec\ffdec-cli.exe -swf2xml <gfx> <xml>
# AS3 전체
D:\ClaudeWork\ffdec\ffdec-cli.exe -export script <DIR> <gfx>
```

### 5.2 umodel 빌드가 두 개이고 능력이 서로 다르다

| 빌드 | 게임 태그 | 이 패키지 로드 | crunch 해제 |
|---|---|---|---|
| `umodel_lostark_v7.exe` | `lostark` | 실패(LZO) | **가능** |
| `umodel_lostark_custom.exe` | `loakr` | 성공 | 불가 |

큰 UI 텍스처는 **CRN(crunch) 압축**이다(매직 `Hx` = 0x4878). custom으로 뽑으면
DDS 헤더만 씌운 CRN 원본이 나와 디코드하면 노이즈가 된다. 파일 크기가 DXT 기대치보다
훨씬 작으면 이 경우다.

**해결책: 새로 뽑지 말고 사용자의 기존 추출본을 쓴다.**
`D:\로아 리소스\텍스쳐,메쉬\<패키지명>\` 에 v7으로 crunch까지 풀린 DDS가 이미 있다.

### 5.3 이번에 낭비한 시간 — 다음엔 이렇게

패키지 33,902개를 스캔하는 데 오래 걸렸는데, **`D:\로아 리소스`를 파일명으로 먼저
검색했으면 즉시 나왔다**(`EFUI_BACKGROUNDIMG` 폴더에 이미 있었다). 에셋을 찾을 때는
항상 기존 추출본 검색이 먼저다.

부득이 패키지를 스캔해야 한다면:
- 파일명 난독화 + name table 압축이라 **바이너리 grep은 통하지 않는다**(검증함)
- umodel은 실행할 때마다 33,902개 디렉터리를 다시 스캔한다(0.8초). 이게 패키지를 읽는
  시간(0.05초)보다 크다. **`-pkg=`로 여러 패키지를 한 번에 넘기면** 디렉터리 스캔이
  배치당 1회로 줄어 **200개 13초(개당 0.067초), 12배 빨라진다**
- 단, 추가 인자는 `<object> <class>` 필터로 해석되므로 두 번째 패키지부터는 반드시
  `-pkg=` 형식이어야 한다
- 병렬도를 8로 올리면 git-bash가 fork에 실패한다(`0xC0000142`). 3 이하로 두고
  진행 지점을 파일에 기록해 재개 가능하게 만들 것
