# 2026-09-29 워터팡 위험 요소 번갈아 실행·간격 단축·물벼락 범위·건너가기 무적 RESULT

## 요청

1. 워터팡 아레나 맵 애니메이션(워터캐논, 물벼락) 반복 간격이 너무 길다. 간격을 줄여 빠르게 반복한다.
2. 워터캐논 한 번, 물벼락 한 번, 이런 식으로 번갈아 실행한다.
3. 물벼락 범위가 아레나 전체로 되어 있는데, 아레나 안의 노란 원 안쪽만 대상으로 한다.
4. 건너가기(jump)로 도착한 직후 1초 동안 무적으로 한다.

적용까지 했다. 빌드, 게시, Client·Server 실행은 하지 않았다.

## 1. 이전 스케줄 실측 (사실)

정본은 `Shared/Public/Gameplay/MaharakaWaterpangContract.h`의 표와 `Sample_MaharakaWaterpangEvent`이고 Server(`GameRoom_PartyWorld.cpp`)와 Client(`MaharakaWaterpangPresentation.cpp`)가 같은 샘플러를 쓴다.

- 이벤트 길이(변경 없음): 캐논 = 텔레그래프 45틱 + 발사 초×30 + 종료 30틱. 발사 15초는 525틱(17.5초), 20초는 675틱(22.5초), 10초는 375틱(12.5초). 물벼락은 180틱(6초).
- 이전 표 12행의 시작 시각(초): 캐논 20, 65 / 물벼락 120 / 캐논 127 / 물벼락 150 / 캐논 157, 202, 247, 300 / 물벼락 340 / 캐논 347, 377. 그 뒤 417초부터 40초 주기로 빠른 캐논 10초 회전만 반복.
- 이벤트 사이 대기: 캐논→캐논 22.5~37.5초(대개 27.5초), 캐논→물벼락 5.5~37.5초, 물벼락→캐논 1초. 번갈아 나오지 않았고 물벼락은 417초 동안 3번뿐, 꼬리 구간에는 아예 없었다.
- 원작 근거와 프로젝트 조정 구분: 계약 주석에 따르면 원작 트리거 체인 6000-6009에서 가져온 것은 캐논 순서, 속도(보통 15초 4회, 20초 2회, 빠른 15/10/10초), 회전 방향 50/50이다. 체인의 타이머가 서버 조건 기반이라 절대 시각은 원래 프로젝트가 정한 값(PROJECT_TUNED)이었다. 물벼락 120초·150초만 체인 시각을 따랐다.

## 2. 바꾼 스케줄

캐논 1회 다음 물벼락 1회로 정확히 번갈아 나온다. 캐논 순서와 속도·길이는 이전과 같다(보통 15초 ×4, 20초 ×2, 빠른 15초, 10초, 10초). 물벼락은 매 캐논 뒤에 붙는다.

이벤트 끝과 다음 시작 사이 대기는 상수 하나다.

```text
MAHARAKA_WATERPANG_EVENT_GAP_SECONDS = 8u
```

시작은 정수 초에 맞추므로 실제 대기는 8.0~8.5초다. 이전 대기(대개 27.5초)의 약 30% 수준이다. 이벤트 자체 안에 캐논 1.5초 텔레그래프와 물벼락 2.3초 예고 장판이 들어 있어서 반응 시간은 그대로다. 사용자가 값을 정하지 않아서 8초로 정했고, 더 빠르게 하려면 이 상수만 줄이면 된다. 첫 이벤트 시작은 이전과 같은 20초다(`MAHARAKA_WATERPANG_FIRST_EVENT_SECONDS`).

표는 컴파일 타임에 상수에서 만든다(`Make_MaharakaWaterpangSchedule`). 시작 시각(초):

```text
캐논 20, 물벼락 46, 캐논 60, 물벼락 86, 캐논 100, 물벼락 126, 캐논 140, 물벼락 166,
캐논 180(20초), 물벼락 211, 캐논 225(20초), 물벼락 256,
빠른 캐논 270(15초), 물벼락 296, 빠른 캐논 310(10초), 물벼락 331, 빠른 캐논 345(10초), 물벼락 366
```

꼬리 구간은 380초부터 35초 주기로 빠른 캐논 10초 회전 한 번, 21초 뒤 물벼락 한 번을 반복한다. 이전에는 40초마다 캐논만 반복했다.

## 3. 물벼락 범위 (사실 / 추론 / 미확인)

- 현재 판정 실측(사실): Server `Update_MaharakaWaterpangHazards`의 물벼락 분기가 캐논 중심 반지름 `MAHARAKA_WATERPANG_DECK_RADIUS_M = 7.5` 안, 높이 21.5 이상이면 전부 대상이었다. 이것이 "아레나 전체" 판정이다.
- 노란 원의 근거(사실): 아레나 중앙 노란 원판은 `BG_OCN_ETC_FLOOR01_SM_LNH_OVR_8EB1D0D03456` 한 개다. 중심이 (75.05, 22.40, -984.32)로 캐논과 같고 배치 스케일이 0.95×1.1875×0.95다. 설치된 glTF 정점에서 계산한 위쪽 면 반지름은 4.90m, 가장 바깥 정점은 5.01m다. 보라색 블록 고리는 `BG_OCN_ETC_FLOOR01A/B_SM_LNH` 16개이고 블록 중심이 캐논에서 6.15m 떨어져 있다.
- 적용: `MAHARAKA_WATERPANG_WATERFALL_HIT_RADIUS_M = 5.f` 한 값을 계약에 만들고 Server 판정을 이 반지름으로 좁혔다. 보라색 고리, 풀, 해안, 부두는 대상이 아니다. F1 물벼락 강제 실행 버튼도 같은 판정 함수를 쓴다.
- 예고 장판: 도넛 장판 이펙트를 같은 상수로 다시 만들었다. `effect.maharaka.waterpang.mokomoko.telegraph.effect.json`의 지름 값 15.0/1500cm를 10.0/1000cm로 바꿨다. 빌더 함수가 만든 문서와 대조해 차이가 지름 값과 표시 이름뿐임을 확인했다. 이 장판을 캐논 중심에 놓는 월드 시퀀스 트랙은 스케일 1이라 수정하지 않았다.
- 캐논 판정은 그대로다. 물벼락 파동 두 번(69틱, 74틱)의 시각과 발사 거리 규칙도 그대로다.
- 원작 반경과의 차이(추론, 확인 필요): 원작 SkillEffect 4225612는 큰 모코코 앞 3.2m를 원점으로 전방 180도 반원이고 바깥 파동 반경이 5.9m다. 원점은 캐논 중심에서 6.70m라서 원작 반원은 캐논 방향으로 약 0.8m 지점까지만 닿는다. 즉 원작 데이터의 반원은 노란 원 전체와 같지 않고, 모코코 쪽 일부와 그 옆 보라색 고리 일부를 포함한다. 이번에는 사용자가 지정한 '노란 원 안쪽 전체'를 따랐다. 원작 그대로 하려면 별도 결정이 필요하다.
- 반지름 조정: 5.f를 바꾸면 판정이 바뀐다. 이전 동작(덱 전체)으로 돌리려면 7.5f를 쓰고, 예고 장판은 빌더(`build_maharaka_waterpang_source_effects.py --project --install` 계열)를 다시 실행해야 같은 크기로 맞는다.

## 4. 건너가기 무적

- 건너가기 트리거(사실): `Data/Worlds/LV_OCN_EVENTIS_MHP/Gameplay.world.json`의 `jump1`, `jump2`, `jump3`가 1.2초 호 이동(movePlayer, arcHeight 2.5)으로 아레나 안에 착지시킨다. 셋 다 같은 방식이라 모두 포함했다. 사용자가 말한 jump1/jump2 외에 jump3도 넣은 것은 같은 건너가기이기 때문이다.
- 원작 근거(미확인): 저장소 문서와 Data에서 건너가기 후 무적 지속 시간이나 버프 ID 근거를 찾지 못했다. 사용자가 지정한 1초(30틱)를 그대로 썼다.
- 구현(서버 권위): `GameRoom_PlayerSimulation.cpp`의 이동 완료 지점에서, 마하라카 월드이고 `TriggerMove`가 끝났으며 출발 트리거가 위 세 개 중 하나이면 기존 필드 `iInvulnerableEndTick`를 현재 틱+30으로 올린다(이미 더 긴 무적이 있으면 유지). 이 필드는 `Apply_WorldToPlayer`가 이미 검사해 `ABSORBED`로 돌려주므로 캐논 밀치기, 물벼락 발사, 낙사, 다른 fork가 넣는 물총 명중이 모두 적용되지 않는다. 새 필드와 새 프로토콜은 없다.
- 상수: `MAHARAKA_WATERPANG_JUMP_INVULNERABLE_TICKS = 30`(1초), 트리거 목록 `MAHARAKA_WATERPANG_JUMP_TRIGGER_IDS`. 마하라카 월드에서만 적용되고 다른 월드·레벨·다른 이동에는 영향이 없다. 무적이 끝나면 정상 판정으로 돌아간다.
- 경기 밖: 경기 시작 전 워터팡 영역 밖에서 건너가기를 써도 무적 tick만 잠깐 생기며 해가 없다.
- Client 표현: `iInvulnerableEndTick`는 스냅샷으로 복제되지 않아서 무적 표시(버프 아이콘 등)는 자동으로 나오지 않는다. 새 표현은 추가하지 않았다. 필요하면 별도 요청이 필요하다.

## 실행한 검증

- 계약 헤더를 임시 폴더에서 단독 컴파일(`cl /std:c++20 /W4`, 제품 빌드 아님): `static_assert` 통과와 경고 없음. 검증 내용은 표 18행, 짝수 행 캐논·홀수 행 물벼락, 이웃 이벤트 사이 대기 8.0초 이상 9.0초 미만, 첫 시작 20초, 건너가기 ID 판별, 반지름 범위.
- 같은 프로그램으로 2,400초(72,000틱)를 틱마다 샘플: 이벤트 134개, 번갈아 순서 위반 0, 시작 시 경과 틱 위반 0, 캐논 26,475틱·물벼락 12,000틱·대기 33,525틱, 물벼락 히트 틱 69가 경과 69에 정확히 일치.
- 이펙트 도넛 문서: 빌더 함수 출력과 현재 문서의 차이 확인(예상한 값만 다름), JSON 파싱 통과.
- `git diff --check` 통과, `GameRoom_PlayerSimulation.cpp`·`GameRoom_PartyWorld.cpp`의 줄 끝은 순수 CRLF.

## 실행하지 않은 것

- 제품 빌드(Engine, Shared, Server, Client): 하지 않았다. Server와 Client의 수정 파일이 실제로 컴파일되는지는 아직 확인 전이다.
- 게시: 필요 없다. 물벼락 도넛은 Data/Effects의 직접 저작 문서이고, 스케줄·판정·무적은 코드 상수다. 월드 부트스트랩이나 Map 게시는 바꾸지 않았다.
- Client·Server 실행, 화면 확인: 사용자가 한다.

## 사용자 확인 필요

- 계약 상수를 Server와 Client가 모두 컴파일하므로 반드시 둘 다 같은 빌드로 다시 시작해야 한다. 한쪽만 옛 빌드이면 표시와 판정 시각이 어긋난다. 프로토콜 번호는 올리지 않았다(121 유지).
- 간격 8초와 노란 원 반지름 5.0이 원하는 느낌인지, 실제 아레나에서 확인이 필요하다.
- 보라색 블록 고리 위에서 물벼락을 맞지 않는지, 노란 원 안에서는 맞고 낙사하는지 확인이 필요하다.
- jump1, jump2, jump3로 착지한 뒤 약 1초 동안 캐논·물벼락에 밀리거나 떨어지지 않는지 확인이 필요하다.
