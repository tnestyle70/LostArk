현재 가장 중요한 결론은 다음과 같다.

0. **이 작업의 최종 authoring 단위는 family 카운트가 아니라 stable 개별 Element다.** All/Family는
   재생 필터다. BA admitted Element는 기존 전체 Effect Details와 Resource Library를 열고 새 Authored
   Effect로 Save As한다. 도화가 adapter는 exact packet inspection/transform tuning과, native packet을
   보존한다고 주장하지 않는 선택 Decal/Trail generic Authored starting copy를 명시적으로 분리한다.

1. **parse/prewarm만 통과한 상태는 넘었지만 모든 family GPU 검증이 닫힌 것은 아니다.** 기존 Artist/Lance
   first-draw 회귀와 별도로 최신 Lance Ribbon WARP probe는 draw 전 Engine 초기화에서 중단됐다. 화면
   생존과 모양은 사용자가 다시 판정한다.
2. **보인다고 원본 복원이 끝난 것은 아니다.** 현재 Material은 상당 부분 근사 profile이고, Sprite/Decal/Ribbon/Light의 정확한 의미가 남아 있다.
3. **Mesh 100배 축소 버그는 수정됐다.** Mesh StartSize는 dimensionless이고 WModel geometryPreScale과 별개인데, 기존 코드가 다시 `0.01`을 곱하던 오류를 제거했다.
4. **Sprite가 billboard인 것 자체는 정상일 수 있다.** 그러나 연보라색 사각형처럼 보이거나 크기·마스크·UV가 틀리면 Material/texture/size/RNG 문제다.
5. **바닥 출력이 전부 Anchor 문제라고 단정하면 안 된다.** 실제 F에는 weapon follow 5개와 root snapshot 30개가 있고, Decal 3개는 본래 바닥 투영 계열이다. 다른 family가 약하거나 안 보이면 Decal만 남아 전체가 바닥 이펙트처럼 보일 수 있다.
6. **빠른 전개처럼 보이는 이유도 데이터와 버그를 분리해야 한다.** 원본 schedule 자체가 `1.380397 s`에 15개, `1.450642 s`에 12개를 약 70 ms 간격으로 몰아 생성한다. 다만 RateScale·RNG·lifetime 실행 차이도 남아 있으므로 실제 속도를 occurrence별로 재검증해야 한다.
7. **창술사 BA는 실제 Mesh + Ribbon + Animation Trails 복합이다.** `Par_M_FLM_Ribbon_02`에는 실제 `ParticleModuleTypeDataRibbon`이 있으며 기존 V6 artifact가 Sprite로 오분류했다. `Par_M_FLM_PyungMTrail_01`의 main carrier는 별도 TypeDataMesh이고 `Par_M_FLM_Trail_03/_2`는 animation `Trails` notify다.
8. **도화가 F Mesh #4의 +90도는 수동 추측이 아니다.** cooked `ParticleModuleTypeDataMesh`, stable module `FX_PC_SDM_07:export:1289@ref:9`에 `yaw=90.0` literal이 있다. 전역 Mesh yaw가 아니라 해당 carrier에만 적용하고 사용자 forward-axis canary로 승인한다.
9. **Track A는 초기 레시피를 만드는 단계로 동결한다.** ShaderCache와 source 분석은 texture role,
   material 계산, family carrier와 source 수치를 제공했다. 원작 exact 증명 때문에 Element 제작을
   막지 않는다. 완성은 Effect Tool에서 DDS/WModel을 교체·조합하고 저장하는 Track B가 담당한다.
10. **한 universal effect shader는 사용하지 않는다.** stable document/resource/save 계약은 공통이지만
    MeshParticle, SpriteParticle, LocalDecal, CascadeRibbon, AnimationTrail은 각자의 geometry와 adapter를
    사용한다.

## 1. 우리가 복원하는 것은 무엇인가

도화가 F는 단일 Mesh 한 개가 아니다.

```text
도화가 F / skill 31470
  7 action schedule
  35 active emitter occurrence
    MeshParticle   13
    SpriteParticle 16
    DecalParticle   3
    CascadeRibbon   1
    PointLight      1
    ScreenPost      1
  399 ordered module
  629 distribution
  27 unique Material recipe
  34 rendered Material occurrence
  7 unique WModel carrier / 13 geometry use
  48 unique DDS / 72 Material texture binding / 57 renderer texture row
```

따라서 최종 복원은 다음 전체를 연결해야 한다.

```text
cooked 원본 데이터
  -> raw resource 추출
  -> Source Contract
  -> immutable runtime program
  -> C++ parser / Catalog
  -> CPU particle·module·distribution evaluator
  -> Material recipe evaluator
  -> GPU resource prewarm
  -> Mesh / Sprite / Decal / Ribbon / Light / Post typed sink
  -> 실제 animation time + root / bone / socket anchor
  -> 사용자 눈 검증
  -> occurrence별 tuning
```

### 1.1 `원본 데이터를 읽었다`는 말의 정확한 의미

초기 레거시 복원도 원본을 전혀 안 읽은 것은 아니다. 당시에는 주로 다음을 읽었다.

- WModel 또는 변환 가능한 Mesh resource
- DDS 또는 texture 경로
- 일부 Transform, 색, 크기
- 눈으로 확인한 대략적인 위치와 크기

하지만 다음 전체를 실행하지 않았다.

- 35 emitter의 정확한 occurrence 순서
- 399 module의 source class와 handler 의미
- 629 distribution의 random/curve/parameter 의미
- 27 Material recipe의 named scalar/vector/texture/static graph
- Decal/Ribbon/Light/Post 전용 sink
- 7 schedule과 실제 animation action time
- root snapshot 30개와 weapon-bone follow 5개

그래서 예전 결과는 **원본 resource를 사용한 수동·부분 복원**이었고, 지금은 **원본 구조와 계산 의미를 가능한 범위까지 실행하는 전체 복원**이다.

## 2. cooked 한계와 정직한 완료 표현

cooked package에는 source-era 실행체, 일부 shader graph, CDO/default, native handler identity가 완전하게 남아 있지 않다.
따라서 다음 표현을 구분한다.

| 표현 | 의미 |
|---|---|
| `SOURCE_EXACT` | source-era 실행체와 값까지 동일함. 현재 주장하지 않는다 |
| `RECONSTRUCTED` | 남은 cooked 데이터와 검증된 default/handler를 결정론적으로 재구성 |
| `FIRST_VISIBLE` | 실제 GPU 화면에 픽셀이 나옴. fidelity 완료가 아님 |
| `OCCURRENCE APPROVED` | 사용자가 해당 occurrence를 눈으로 확인하고 승인 |
| `FULL F APPROVED` | 35/35 occurrence와 전체 합성이 승인됨 |

최종 목표는 `SOURCE_EXACT`라는 거짓 표기가 아니라, **검증 가능한 최대복원본을 만든 뒤 사람이 원작 기억·참고 PNG와 비교해 occurrence별로 닫는 것**이다.

## 3. 전체 파이프라인과 소유 파일

### 3.1 원본 추출과 Source Contract

| 단계 | 입력 | 출력 | 핵심 파일 |
|---|---|---|---|
| cooked 조사 | UPK/cooked object | emitter/module/material/resource evidence | `Data/Effects/Imported/Artist` |
| raw resource 추출 | cooked package | WModel/DDS | `Client/Bin/Resources/Effect/Artist` |
| source carrier | 추출 구조 | native-v14 document | `Data/Effects/Imported/Artist/Candidates/effect.artist.skill.31470.native-v14.source-contract-candidate.effect.json` |
| source receipt | carrier identity | byte/hash/semantic receipt | `Data/Effects/Imported/Artist/Candidates/skill.31470.native-v14.source-contract-candidate.receipt.json` |

native-v14는 실행 권한 그 자체가 아니다. element order, source node, resource slot, attachment 등 원본 구조를 운반한다.
정확한 timing/RNG/module/material 값은 immutable runtime program과 결합한다.

### 3.2 immutable runtime program

정본 후보:

`Data/Effects/Imported/Artist/Candidates/skill.31470.reconstructed-runtime-program.candidate.json`

고정 분모:

```text
schedule        7
emitter        35
module         399
distribution   629
seed policy     14
burst row       31
```

이 파일은 약 15 MB의 결정론적 JSON 프로그램이다. Python builder가 source/material/geometry/resource authority를 결합하고,
C++ parser가 exact schema와 identity를 fail-closed로 읽는다.

### 3.2.1 현재 실제 파일 identity

2026-08-12 현재 physical file을 직접 다시 계산한 값이다.

| 파일 | byte count | SHA-256 |
|---|---:|---|
| native-v14 source contract | `2,964,365` | `27cfb2b81ce688b9dd55cdc53afe6e5e709cefee390dab0e9f9c5d3e9e7f244e` |
| reconstructed runtime program | `15,072,141` | `72e417747dee14dd0a3be5ffd64f69f904bd696ef1acc049037fc81f38779849` |
| runtime Effect Catalog exact13 | `27,065,827` | `ea3afd4e6f2fb2b2a627a8ba565daf9db931e3306c10da7ee5523611bf481ab3` |

이 세 identity가 달라지면 이전 parser/cache/화면 결과를 같은 기준선으로 부르면 안 된다.
특히 Git blob은 LF인데 오래된 worktree가 CRLF로 materialize돼 byte hash가 바뀌는 문제가 실제로 있었으므로,
현재 세 경로는 LF canonical checkout을 유지한다.

### 3.3 C++ parser와 Catalog

```text
runtime Catalog exact13 entry
  -> strict C++ parse
  -> immutable shared_ptr<const typed program>
  -> same CatalogEntry identity
  -> Presentation / EffectObject / Playback / Renderer
```

Catalog는 프로그램을 한 번 읽어 immutable pointer로 소유한다. Tool, 실제 F, Renderer가 별도 JSON을 각자 다시 해석하면 안 된다.

주요 코드:

- `Client/Private/Effect_Catalog.cpp`
- `Client/Private/Effect_RuntimeAuthority.cpp`
- `Client/Private/Effect_PresentationService.cpp`
- `Client/Private/Effect_ReconstructedExecution.cpp`

### 3.4 runtime document factory

`Client/Private/Effect_ReconstructedExecution.cpp`

현재 factory는 다음을 수행한다.

1. native-v14를 canonical LF domain으로 검증한다.
2. Program의 35 emitter와 native element를 exact ID로 join한다.
3. Program의 7 schedule timing을 runtime document에 덮는다.
4. emitter cap, seed, burst, attachment, renderer kind를 덮는다.
5. cue-local Transform을 runtime Transform에 정확히 한 번 합성한다.
6. parameter/curve distribution을 typed Program 값과 결합한다.
7. Material/geometry/resource row를 renderer 준비 문서로 투영한다.
8. 표준 실행 가능한 nonProduct document로 stage한다.

### 3.5 CPU Playback

`Client/Private/Effect_Playback.cpp`

책임:

- fixed-step simulation
- schedule start
- spawn/burst/rate/SpawnPerUnit
- lifetime
- location/velocity/size/rotation/color/SubUV/dynamic parameter
- particle update
- evaluated Mesh/Sprite/Decal/Ribbon/Light/Post packet 생성

현재 정확한 분모 join은 존재하지만, 실제 Step은 아직 상당 부분 `SourceRecipe` class 문자열 분기로 실행한다.
즉 typed plan을 저장했다고 모든 계산이 typed plan 단일 정본이 된 것은 아니다.

### 3.6 GPU Renderer와 Shader

`Client/Private/Effect_DocumentRenderer.cpp`

```text
evaluated frame
  -> resource lookup / prewarm
  -> Material constants / textures / sampler / state
  -> family sink
     Mesh   -> CModel / MeshPreview shader
     Sprite -> particle rectangle instance buffer
     Decal  -> decal shader
     Ribbon -> dynamic trail buffer
     Light  -> Presentation light batch
     Post   -> Presentation post batch
```

주요 shader:

- `Client/Bin/ShaderFiles/Shader_VtxEffectMeshPreview.hlsl`
- `Client/Bin/ShaderFiles/Shader_VtxEffectParticle.hlsl`
- `Client/Bin/ShaderFiles/Shader_VtxEffectDecal.hlsl`
- `Client/Bin/ShaderFiles/Shader_VtxEffectTrail.hlsl`
- `Client/Bin/ShaderFiles/Shader_EffectCommon.hlsli`

메인 Mesh composite 13개는 현재 occurrence별 Program/sidecar join을 거쳐 `#17` finite missile evaluator 1개와 bounded reconstructed evaluator 12개로 분리됐고 grouped fallback은 0개다. 그러나 Sprite/Decal/Ribbon까지 포함한 34 material occurrence 전체가 source parent arithmetic과 일치하는 것은 아니다. 따라서 first pixel과 메인 Mesh typed bind는 확인했지만 **Full35 전체 Material fidelity**는 아직 닫히지 않았다.

2. Mesh Solo는 갈색 작은 조각, Sprite Solo는 붉은 splatter로 처음 보였다.
3. 이 결과는 GPU draw plumbing 증거였지만 원본 Material fidelity 증거는 아니었다.
4. exact13 source factory, shared prepared cache, actual Artist animation, root/bone anchor를 연결했다.
5. Full35 첫 실행은 distribution index 순서가 달라 문서 생성에 실패했다.
6. module 내부 distribution을 `propertyPath` unique/exhaustive join으로 교정했다.
7. Light Size의 action-cue scalar와 VECTOR_PARAMETER kind 불일치를 frozen constant fallback으로 교정했다.
8. Ribbon cap 500인데 Engine trail buffer ceiling이 256이라 stage가 실패했다. ceiling을 512로 교정했다.
9. Mesh/Particle 전용 shader uniform을 Decal/Ribbon에도 bind하던 오류를 분리했다.
10. Mesh StartSize에 두 번째 `0.01`이 적용돼 13/13 Mesh가 100배 작아지는 오류를 교정했다.
11. Ground module의 `skiplocation=1`을 무시하고 Y=0으로 덮던 2개 occurrence를 교정했다.
12. Light/Post lifetime이 typed 값이 아니라 legacy Detail 값을 쓰던 오류를 교정했다.
13. `blend_masked`를 Alpha로 처리하던 두 recipe를 Opaque로 교정했다.
14. 현재 Full35가 실제 화면에 나타났다.

## 5. 단위와 Scale 장부

Scale 버그는 한 곳에서 전역 보정하지 않는다. 값의 의미별로 변환 위치를 고정한다.

### 5.1 좌표 축과 거리

UE3 source 위치 `(X, Y, Z)`는 Client world에서 대체로 다음으로 변환된다.

```text
Client position = ( X, Z, -Y ) * 0.01
```

예:

| UE source | Client runtime | 의미 |
|---|---|---|
| `[30, 0, 0]` cm | `[0.3, 0, 0]` m | weapon 방향 30 cm |
| `[100, -100, 0]` cm | `[1, 0, 1]` m | 전방/측면 1 m |
| `[0, 0, 60]` cm | `[0, 0.6, 0]` m | 위로 60 cm |
| `[200, 0, 100]` cm | `[2, 1, 0]` m | 전방 2 m, 위 1 m |

Position, velocity, camera offset 등 거리 단위는 cm→m `0.01`을 적용한다.

### 5.2 Mesh geometry scale

```text
WModel vertex carrier
  -> geometryPreScale = 0.01
  -> CModel 생성 시 정확히 한 번 적용
```

Mesh particle의 StartSize는 **거리 cm가 아니라 dimensionless instance scale**이다.

올바른 식:

```text
Mesh final geometry scale
  = WModel geometryPreScale(0.01, exactly once)
  * cue local scale
  * particle StartSize(dimensionless, no extra 0.01)
```

과거 버그:

```text
geometryPreScale 0.01
* Mesh StartSize 0.01  <- 잘못된 두 번째 단위 변환
= 화면에서 약 100배 작음
```

현재 교정 위치:

- `Client/Private/Effect_Playback.cpp`
- `UE3_StartSizeToClient`
- Mesh는 axis reorder만 수행하고 `0.01`을 곱하지 않는다.
- Sprite/Decal billboard StartSize만 cm→m `0.01`을 적용한다.

### 5.3 Sprite size

Sprite StartSize는 renderer plane의 billboard extent이며 cm 단위다.

```text
Sprite world size = StartSize * 0.01 * cue scale * life size multiplier
```

Sprite가 카메라를 향하는 billboard인 것은 정상이다. 다음은 버그 후보다.

- 화면 대부분을 덮는 과대 크기
- 아주 작은 점으로 보이는 과소 크기
- texture alpha/mask가 사라져 사각 quad 전체가 보임
- 원본 색 대신 연보라/흰색 neutral color가 보임
- SubUV frame이 고정돼 한 장의 사각형처럼 보임
- negative/random StartSize를 잘못 보간해 flip 또는 축 왜곡

### 5.4 Decal size

현재 확인된 위험:

1. CPU particle World에 size가 이미 반영된다.
2. Decal shader에 `g_DecalSize`가 다시 전달된다.

따라서 Decal 3개는 size가 이중 적용될 가능성이 있다. 바닥에 지나치게 크거나 작은 흔적으로 보이면 우선 이 경로를 확인한다.

### 5.5 Ribbon width

Ribbon cap은 500 point다. Engine dynamic trail ceiling은 512로 교정했다.
그러나 cap만 맞고 다음 typed 값은 아직 완전히 소비되지 않는다.

- lifetime 2.0 s
- StartSize 15 cm -> width 0.15 m
- color/dynamic parameter
- tilingDistance 600
- tessellation 5

원본 Program의 7 schedule은 다음과 같다.

| 2 | `1.380397` | notify-018 | Sprite 4 + Mesh 11 = 15 |

### 6.1 왜 빠르게 보일 수 있는가

원본 자체가 1.380397초부터 1.452774초까지 약 72 ms 안에 29개에 가까운 후반 occurrence를 집중한다.
따라서 후반 폭발이 빠른 것은 일부 정상이다.

하지만 다음은 별도 버그 후보다.

- `RateScale` default가 Program에는 0으로 남고 실제 UE CDO identity는 1일 가능성
- Rate만 평가하고 RateScale draw/order를 생략한 production Playback
- typed evaluator와 production Playback의 RNG stream 차이
- lifetime random draw 순서 차이
- Tool animation time과 EffectObject sample time의 표시/seek 불일치
- Post/Light/Ribbon lifetime 의미 차이

현재 `빠르다`는 관찰만으로 전역 playback speed를 낮추지 않는다. `0.0`, `1.3377`, `1.3804`, `1.4506` 시점별로 occurrence를 분리해 확인한다.

### 6.2 수정 전 Tool preview clock의 확정 버그

아래는 2026-08-12 P0 교정 전 Full35 Tool 경로에 있던 timing 문제다. 교정 결과와 현재 수동 검증 항목은 G16-01을 정본으로 삼는다.

1. `Play Full F`의 cache acquire/prewarm이 Render/UI thread를 오래 막을 수 있다.
2. frame timer는 Update/Render 전에 delta를 샘플하므로, 3초 stall은 다음 frame의 약 3초 delta로 전달될 수 있다.
3. `CEffectObject`는 이 delta를 Playback accumulator에 더한다.
4. Playback는 한 frame에 최대 60 fixed step(약 1초)만 처리하고 나머지를 보존해 다음 frame들에서 catch-up한다.
5. Artist animation model도 큰 delta를 받아 끝부분으로 점프할 수 있다.
6. Full35 Tool branch는 일반 preview-clock 갱신 전에 return하므로 `m_fPreviewTimeSeconds` UI가 실제 animation time을 따라가지 않는다.
7. 결과적으로 EffectObject는 wall-clock delta로, Artist animation은 model time으로 따로 전진해 stall 뒤 압축·불일치가 생길 수 있다.

교정 방향:

```text
Tool Full35에서는 animation time을 단일 시간 정본으로 사용
  -> post-prewarm 큰 delta를 그대로 적분하지 않음
  -> EffectObject auto-play와 Tool 수동 advance를 중복하지 않음
  -> animation absolute time - previous time만 fixed-step advance
  -> loop/seek에는 explicit rollback-safe seek
  -> UI timeline도 같은 absolute time 표시
```

현재는 deferred zero barrier와 animation single clock이 구현됐다. 다만 사용자 first-frame/loop/tail 확인 전에는 체감 속도만 보고 occurrence timing 값을 튜닝하지 않는다.

### 7.1 root snapshot의 추출 의미 차이와 V5 교정 상태

과거 tracked Program의 30개 `SNAPSHOT_ROOT` row는 `runtimeAnchorSlotId=root`, `follow=false`지만
`enabled=false`로 남아 있었다. factory가 이 값을 그대로 복사하면 Playback는 `ActionRootWorld`를
occurrence 시작 시 캡처하지 않고 live `RootWorld`를 계속 사용했다.

- 정지된 Tool character에서는 겉으로 큰 차이가 없을 수 있다.
- 실제 gameplay에서 캐릭터가 움직이거나 회전하면 이미 생성된 hit/swing occurrence까지 따라갈 수 있다.
- source 의미는 spawn/cue 시점 root snapshot이므로 explicit snapshot mode로 해석해야 한다.

V5 builder와 published Program은 `SNAPSHOT_ROOT = enabled + non-follow`로 교정됐고 follow `5`, snapshot
`30`, disabled `0`을 검증했다. Playback는 schedule edge에서 root를 정확히 한 번 캡처한다. final
candidate는 `15,120,471` bytes, raw SHA-256 `f1e266c1478843bb599cac9d406d48f8de855e80da4b9dff688b7551cdecce70`,
Program SHA-256 `51296469dde1100ffe280b07261ff4fddf396e4e25159c37735d5215edb47c73`이며 approval,
render-resource authority와 runtime catalog까지 재발행됐다.

### 7.2 root occurrence의 방향 basis — V5 typed reconstruction CLOSED, 사용자 재촬영 대기

Artist model prototype에는 presentation pre-transform `scale 0.0001 * Yaw(-90°)`가 있다.

- `b_wp_1` follow 5개는 bone matrix를 통해 이 presentation basis를 상속한다.
- root snapshot 30개는 cue를 actor root에 직접 합성한다.
- Program의 cue position/rotation은 source UE 좌표를 Client 축 `(x,z,-y)`로 변환하지만, 이 axis swizzle은
  playable Artist model의 import-facing basis를 actor root에 자동 합성하지 않는다.
- 실제 family isolation에서 root snapshot Mesh/Sprite/Decal이 캐릭터 오른쪽으로 정확히 90° 어긋났고,
  source `+X` canary는 Client `+X`에 남은 반면 admitted Artist model forward는 Client `+Z`였다.

V5는 개별 occurrence를 눈대중으로 돌리거나 global family yaw를 넣지 않는다. attachment data에
`snapshotRootSourceBasisYawDegrees=-90`을 저장하고 `cue/emitter/particle local * source basis * captured
root` 순서로 non-follow 30행에만 한 번 적용한다. named-bone follow 5행은 bone world가 이미 import basis를
소유하므로 `0°`다. 이 값은 raw UE authored field가 아니라 model-import admission과 axis canary로 닫은
`RECONSTRUCTED_EXPLICIT` basis다. 다른 캐릭터는 자신의 import evidence 없이 Artist의 `-90°`를 재사용하지
않는다.

### 7.3 weapon bone effect socket의 combined-scale 오판 — 원인·코드·실모델 회귀 CLOSED, 수동 화면 판정 대기

교정 전 `b_wp_1` effect anchor 경로는 Tool과 gameplay가 서로 달랐고, 이후 공용 helper로 합친 뒤에도
transform 계층을 잘못 식별했다. Artist playable prototype admission scale은 `0.0001`이지만 Artist rig의
`sdm` root가 `100` scale을 가진다. `CModel::Get_BoneMatrix("b_wp_1")`가 반환하는 것은 이 둘이 이미
합성된 combined matrix이므로 실제 basis 길이는 `0.0001 * 100 = 0.01`이다. 과거 helper가 combined
basis도 `0.0001`일 것이라고 검사해 정상 socket을 `invalid`로 거부한 것이 이번 오류 문구의 직접 원인이다.

반면 Playback의 cue offset, particle position, particle size는 이미 Client meter 단위다.

```text
meter-space EffectLocal
  * raw combined BoneWorld(scale 0.01 포함)
  = effect offset/size에 import scale을 다시 적용
```

따라서 normalization 없이 raw combined matrix를 사용하면 weapon-follow 5개(`source-active-000~004`)의
local offset과 particle 크기가 선형 `1/100`이 된다. 반대로 combined matrix에 과거의 `x10000`을 적용하면
unit basis가 아니라 `100` basis가 되어 100배 과대 교정된다.

교정 후 경로:

- Tool: raw bone + preview owner world를 `Build_SourceBoneAnchorWorld`에 제출 — import scale만 정규화
- gameplay: `CEffectPresentationService::Resolve_SourceAnchors -> Build_SourceBoneAnchorWorld` — 같은 helper 사용

따라서 같은 occurrence가 서로 다른 basis를 쓰던 코드 오류는 닫혔다. `#4`의 정상 예상 물리 크기 약 `.496 x .312 x 3.143m`가 화면에서도 회복되는지는 사용자 검증 대상이다.

교정 계약:

1. 장비 socket 전체의 기존 의미는 바꾸지 않는다.
2. Tool과 gameplay가 같은 Effect 전용 normalized source-bone helper를 사용한다. Tool에 수식을 복제하지 않는다.
3. bone world의 translation과 rotation은 보존한다.
4. prototype admission `0.0001`, rig root `100`, combined anchor `0.01`을 서로 다른 계층으로 유지한다.
5. Artist `b_wp_1` combined basis `0.01`을 검증한 뒤 3x3에만 reciprocal `100`을 적용한다.
6. 실제 animated normalized bone scale이 1이라는 계약을 검증한다.
7. normalized bone anchor는 model/bone world의 -90도 source basis를 보존한다.
8. root snapshot 30개는 typed source-root basis `-90°`를 cue local 뒤, captured root 앞에 정확히 한 번
   적용한다. follow 5개에는 중복 적용하지 않는다.

정규화 실패 시 raw bone fallback 없이 fail-closed한다. 실제 `Artist.wmodel`을 playable pretransform으로
연 뒤 bind pose와 `sdm_sk_onestroke` pose에서 `b_wp_1` combined scale `0.01/0.01/0.01`을 확인하는
Debug·Release 회귀가 함께 고정됐다. 코드 교정 뒤에도 처음 5개가 틀리면 material, typed Ribbon,
source anchor trajectory를 각각 분리해 조사한다.

### 7.4 바닥에 붙어 보일 때 확인 순서

1. 지금 보이는 것이 Decal 020~022인지 확인한다. Decal이면 바닥 투영 자체는 정상일 수 있다.

### G01-02. 처음 generic recipe 적용이 실패한 이유

초기에는 원본에서 읽은 숫자와 texture 이름을 현재 Effect Document와 generic shader에 바로 넣었다. 이때 다음 의미가 섞였다.

| 항목 | 원본 의미 | 잘못 합친 generic 의미 | 결과 |
|---|---|---|---|
| WModel vertex/bounds | cm 단위 carrier geometry | 그대로 meter 또는 중복 변환 | 너무 크거나 너무 작음 |
| MeshParticle StartSize | dimensionless component scale | cm 길이로 보고 `×0.01` | Mesh 전체 1/100 |

### G03-04. CPU fixed-step Playback

주요 코드:

- `Client/Private/Effect_Playback.cpp`
- `Client/Public/Effect_Playback.h`

현재 reconstructed Full은 `1 / 60초 = 16.6666667ms` fixed step을 사용한다.

각 step의 순서는 다음과 같다.

1. sample time을 step index로 계산
2. schedule start와 emitter delay를 빼 local emitter time 계산
3. burst time을 지난 burst를 spawn
4. spawn rate 누적값의 정수 부분만 spawn
5. SpawnPerUnit 이동 거리 누적 spawn
6. spawn module로 lifetime, position, velocity, size, rotation, color, bone/socket 등을 초기화
7. source event를 dispatch
8. update module로 위치, 속도, 가속, size/color over life, rotation, orbit, camera offset 등을 갱신
9. lifetime을 넘긴 particle 제거
10. evaluated frame에 Particle/Decal/Trail/Light/Post를 구성

현재 seam 주의: spawn한 particle도 같은 fixed step의 update를 즉시 받아 첫 화면에서 age와 위치가 `16.667ms` 앞선다. selected evaluator의 age 0 샘플과 Full runtime 첫 frame이 완전히 같지 않다.

### G03-05. Renderer와 GPU

주요 코드:

- `Client/Private/Effect_DocumentRenderer.cpp`
- `Client/Bin/ShaderFiles/Shader_EffectCommon.hlsli`
- Mesh/Particle/Decal/Trail용 Effect shader 파일
- `Engine/Private/VIBuffer_DynamicTrail.cpp`

Renderer 단계:

1. WModel과 DDS를 prewarm cache에 stage
2. material texture SRV, sampler, blend/rasterizer/depth state stage

8. Light와 ScreenPost는 Effect shader draw가 아니라 Presentation Manager로 submit

현재 material 공통 bind 분모:

- float4 vector 2개

## G04. 좌표, 단위, scale, rotation의 고정 계약

### G04-01. 좌표축

UE3 source에서 Client runtime으로:

- 위치/속도/가속도: `(x, y, z) cm → (x, z, -y) × 0.01 m`
- component scale: `(x, y, z) → (x, z, y)`, 길이 변환과 handedness sign을 적용하지 않는다.
- Mesh rotation turns: `(x, y, z) × 360° → (x, z, -y) × 360°`
- Sprite rotation turns: source scalar turns `× 360°`, billboard local Z roll
- cue position도 source cm이면 `(x,z,-y) × 0.01`

예:

- source position `[100,-100,0]cm` → Client `[1,0,1]m`
- source velocity `[300,500,0]cm/s` → Client `[3,0,-5]m/s`
- source Mesh scale `[2.3,2.3,0]` → Client `[2.3,0,2.3]`

### G04-02. geometry와 particle size를 반드시 분리한다

WModel carrier:

- source vertex/bounds는 cm다.
- model load 때 geometryPreScale `0.01`을 정확히 한 번 적용한다.

MeshParticle StartSize:

- model instance의 dimensionless component scale이다.
- 축만 `(x,z,y)`로 재배치한다.
- `0.01`을 적용하면 안 된다.

Sprite/Decal/Ribbon/Light StartSize:

- UE 길이 cm다.
- 축 재배치 후 `0.01`을 적용한다.

ScreenPost StartSize:

- screen-space unitless semantic이다.
- geometry scale과 같은 값이 아니다.

### G04-03. 확인된 Mesh 1/100 버그와 현재 수정

과거 Full Playback은 모든 `ParticleModuleSize.startsize`에 `×0.01`을 적용했다.

| emitter | 원본 StartSize | 잘못된 Full 값 | 의도값 |
|---:|---|---|---|
| 4 | `[2.5,2.5,2.5]` | `[0.025,0.025,0.025]` | `[2.5,2.5,2.5]` |
| 7 | `[3.8,3.8,3.8]` | `[0.038,0.038,0.038]` | `[3.8,3.8,3.8]` |
| 18 | `[-3,3,3]` | `[-0.03,0.03,0.03]` | `[-3,3,3]` |
| 26 stone | `[0.5..2]` | `[0.005..0.02]` | `[0.5..2]` |

현재 `Effect_Playback.cpp`의 `UE3_StartSizeToClient`는 MeshParticle이면 axis reorder만 하고, 그 밖의 length family에만 `×0.01`을 적용한다. 이 방향이 맞다.

### G04-04. transform 합성 순서

의도된 합성은 다음 책임을 분리한다.

`WModel geometryPreScale → particle signed scale/rotation/location → cue local transform → socket/root anchor → preview character world`

현재 추가 검증이 필요한 항목:

- Sprite renderer가 matrix decomposition 뒤 scale에 `abs()`를 적용해 negative size mirror를 잃는다.
- negative scale Mesh 2개는 sign을 유지하지만 one-sided material이면 winding/cull 방향이 바뀔 수 있다.
- Decal은 particle World scale과 static Decal size가 두 번 적용될 가능성이 있다.

### G05-02. anchor 분모

- emitter 0~4: `b_wp_1` follow, 총 5개
- source action recipe의 emitter 5~34: root snapshot, 총 30개
- 필수 anchor 5개 중 하나라도 resolve되지 않으면 Full Preview는 숨기고 중단한다.
- 따라서 지금 화면이 바닥에 붙는 현상은 “anchor가 전부 없음”이 아니다.

추가 정적 감사에서 30개 root 의미의 별도 mismatch가 확인됐다.

- 원본 action-cue recipe: `attachment.mode=SNAPSHOT_ROOT`
- Program emitter 5~34: `actionCueAttachment.enabled=false`, `runtimeAnchorSlotId=root`
- Playback: `enabled && !follow`일 때만 snapshot을 캡처하고, `enabled=false`면 매 frame 현재 `RootWorld`를 parent로 사용
- 결과: 의도는 root snapshot인데 현재 실행은 actor-follow root다.

Model View처럼 actor root가 고정된 장면에서는 두 결과가 같아 현재 바닥 픽셀의 직접 원인은 아니다. 그러나 이동 중인 캐릭터나 Product 경로에서는 30/35가 spawn 당시 위치에 남지 않고 actor를 계속 따라가는 확정 semantic mismatch다.

weapon follow 5개에는 더 직접적인 단위 문제가 있었다. 아래는 **교정 전 경로**다.

- Artist playable CModel pre-transform: `scale(0.0001) × Yaw(-90°)`
- Artist rig의 `sdm` root scale: `100`
- `CModel::Get_BoneMatrix()`의 `b_wp_1` combined basis: `0.0001 × 100 = 0.01`
- Tool과 gameplay reconstructed 경로가 raw bone matrix에 owner world를 바로 곱했다.
- Playback의 cue offset, particle position, particle size는 이미 meter 단위다.

따라서 교정 전에는 meter-space Effect local transform에 combined scale `0.01`이 다시 적용되어 weapon-follow
emitter 0~4의 local offset과 크기가 선형 `1/100`이 됐다. 현재 Tool과 gameplay reconstructed 경로는 공용
`Build_SourceBoneAnchorWorld`를 사용해 3x3에만 `x100`을 적용하고 bone translation/rotation과 owner world를
보존한다. 실제 Artist bind/`sdm_sk_onestroke` Debug·Release 회귀는 통과했지만, 사용자 위치·크기 수동
판정과 움직이는 gameplay RootWorld history는 별도 경계다.

장비 socket 전체 계약은 바꾸지 않았다. Effect 전용 reconstructed anchor에서 bone translation/rotation과
`Yaw(-90°)` basis는 보존하고 Artist combined scale `0.01`만 unit scale로 정규화한다. 4클래스·발탄 확장
전에는 manifest가 `prototypeAdmissionScale`, `rigRootScale`, `combinedAnchorScale`,
`normalizationReciprocal`을 각각 소유해야 하며 알 수 없는 조합은 fail-closed한다. 반대로 root 계열 30개는
같은 Artist source→actor 방향 basis가 빠질 위험이 있으므로 사용자 화면에서 전방 방향을 먼저 확정한 뒤
공용 basis를 한 번만 적용한다.

cue 위치:

- initial ink/Ribbon: `[0.3,0,0]`, 무기 anchor 기준
- weapon: `[0,0,0]`, 무기 anchor 기준, scale 3
- swing 15개: `[1,0,1]`, root snapshot 기준, scale 3
- hit 12개: `[0.6,0,0]`, root snapshot 기준, scale 1.3
- ZoomBlur: `[1,0,0]`, screen-space scale 0.4
- distortion: `[0,0.6,0]`
- Light: `[2,1,0]`

지면처럼 보이는 이유:

1. swing과 hit cue 대부분의 Client 수직축 Y가 `0`이다.
2. hit group에 실제 DecalParticle 3개가 있다.
3. Sprite emitter 23과 33은 source axis-lock으로 수평면 성격을 가진다.
4. 위쪽 무기 높이를 얻는 것은 early 5개뿐이다.
5. early ink/Ribbon의 재질 또는 Ribbon fidelity가 약하면 사용자는 late root/decal group만 강하게 보게 된다.

### G05-03. Tool timeline 동기화의 수정 전 인과와 현재 상태

| 다음 렌더 프레임 | 약 3초 delta를 받아 2.833초 끝 pose로 clamp | 60 step만 처리해 0→1초 | catch-up 60 step이 같은 초기 anchor를 봄 |
| 그 다음 렌더 프레임 | 이미 끝 pose | 남은 accumulator에서 1→2초를 60 step 처리 | catch-up 60 step이 같은 끝 pose를 봄 |

이 구조에서 초반 weapon-follow emitter 0~4의 과거 `b_wp_1` 궤적은 존재하지 않는다. 특히 emitter 1/2의 SpawnPerUnit은 각각 이동 거리 기반이고 emitter 3 Ribbon은 최소 이동 거리 `0.01m`가 필요한데, 60개 step이 같은 anchor 한 점을 보면 spawn 거리와 trail 길이가 거의 0이 된다. 반면 1.450642초 hit의 Decal/Sprite/Mesh는 두 번째 catch-up frame에서 한꺼번에 활성화된다.

따라서 사용자가 본 **“도화가 위쪽/앞쪽 붓 궤적은 약하고 바닥 Decal만 갑자기 보임”**은 다음 인과로 설명된다.

```text
동기 cache 준비 약 3초
  → 다음 Timer_60 delta도 약 3초
  → animation은 끝 pose, Effect는 60 step씩 두 프레임 catch-up
  → 과거 weapon bone 위치를 step별로 얻지 못함
  → initial ink SpawnPerUnit/Ribbon 궤적 소실
  → 1.45초 root-snapshot hit/Decal 묶음만 강하게 노출
```

수정 전 결과:

- Tool timeline 표시와 실제 Full effect time이 분리된다.
- Pause가 Effect Object의 playing 상태를 멈추지 못할 수 있다.
- Restart/Seek가 Object를 false로 만든 뒤 다시 playing으로 연결되지 않는 경로가 있다.
- loop/duration과 animation time owner가 하나가 아니다.
- 이 문제는 35개 전체에 공통이다.

원본 late schedule 자체도 2.132ms 안에 15개가 몰린다. 현재 코드는 prepared-cache wall delta 유입과 이중 clock을 제거했다. 새 빌드에서 여전히 과속이면 원본 군집, emitter delay, SubUV/material reveal, fixed-step spawn seam을 순서대로 본다. 구현 상세는 G16-01이다.

### G13-02. 현재 selected Program에는 메인 호의 직선 이동 velocity가 없다

4. Effect 전용 source bone anchor에서는 raw bone의 uniform import scale만 제거하고 rotation, translation, owner world는 보존한다.

### G13-06. `#4` weapon Mesh는 위치 버그와 Material 버그를 분리한다

사용자가 `1.432s` 프레임에서 도화가 위쪽의 작은 검은 본체로 지목한 가장 강한 후보는 `source-active-004`다. 데이터로 확정되는 계약은 다음과 같다.

| 항목 | 원본/Program 수치 |
|---|---|
| source system | `fx_pc_sdm_07.par_v_smd_onestroke_weapon_01` |
| renderer / attachment | `MeshParticle`, `WP_SDM_R_Battle -> b_wp_1`, follow |
| 시작 / lifetime / cap | `1.337739944s` / `.4s` / `3` |
| WModel | `Effect/Artist/Meshes/fm_v_wp_wsdm_base_01.wmodel` |
| carrier 크기 | `geometryPreScale=.01` 적용 뒤 약 `.0660 x .04135 x .41883m` |
| particle/cue scale | `2.5 x 2.5 x 2.5`, cue `3 x 3 x 3` |
| source motion | `ParticleModuleLocationDirect`의 location/offset/direction이 모두 `0`; 별도 ballistic velocity 없음 |
| source material | `fx_m_mi_o_00.fx_mi.fx_o_transition_05_2_ma` |
| render state | `blend_masked`, opacity clip `.333`, unlit, one-sided, depth enabled |

이 Mesh의 source material 입력은 diffuse `wp_mn_lrcn_01_d`, normal `_n`, spec `_s`, dissolve `fx_c_atypical_016` 네 texture와 specular power `40`, intensity `5`, dissolve thickness `1.1`, transition area `1`, emissive `1`, fresnel `1.5`다. 4개 runtime texture binding은 모두 존재한다.

하지만 현재 coarse renderer projection은 `base=diffuse`, `noise=spec` 두 slot만 선택한다. normal과 실제 dissolve texture, masked clip, specular, fresnel, dissolve graph 전체를 같은 의미로 실행하지 않는다. 따라서 다음 두 문제를 분리해야 한다.

1. **위치/크기:** raw `b_wp_1` combined matrix의 scale `0.01`을 unit basis로 정규화한다. prototype admission `0.0001`을 combined 기대값으로 쓰지 않는다. 이 교정 전에는 `#4`가 지나치게 작거나 준비 단계에서 거부될 수 있다.
2. **표면:** exact 4-texture recipe와 dynamic alpha/dissolve를 Material evaluator/HLSL에 연결한다. 이 교정 전에는 geometry가 보여도 검정·흰색 덩어리나 갑작스러운 소멸로 보일 수 있다.

### G14-02. 네 가지 provenance 등급

| 등급 | 뜻 | 이 프로젝트에서의 처리 |
|---|---|---|
| `SOURCE_EXACT` | pinned source export/tagged raw에서 직접 읽음 | 수치를 눈대중으로 바꾸지 않는다. C++ 소비가 먼저 exact여야 한다. |
| `CURRENT_REVISION_EVIDENCE` | 현재 설치 revision의 package/module에서 재해석 | 원본 시대와 다를 수 있음을 표시하고 사용자 비교 대상으로 둔다. |
| CDO/default reconstruction | cooked serialization에 값이 없어 현재 CDO·정책 기본값으로 채움 | delay/duration, 일부 localSpace, Decal/Ribbon 기본값을 별도 ledger로 관리한다. |
| `COOKED_STRIPPED` / approximation | arithmetic graph·static permutation·sampler/default provenance가 사라짐 | versioned evaluator와 사용자 눈검증 없이는 source exact로 승격하지 않는다. |

화면이 틀렸을 때 이 네 등급을 섞으면 안 된다. `SOURCE_EXACT` 값이 틀려 보이면 먼저 unit·axis·anchor·CPU/GPU 소비를 조사한다. `CURRENT_REVISION_EVIDENCE`나 CDO 값은 소비 코드를 닫은 뒤 occurrence tuning 후보가 된다. `COOKED_STRIPPED`는 근사임을 숨기지 않고 recipe adapter와 비교 영상으로 보완한다.

WModel은 unique carrier `7`, Mesh occurrence use `13`, `geometryPreScale=.01`이다. current renderer는 carrier preScale을 vertex/bounds에 한 번 적용하고 Mesh StartSize를 dimensionless로 유지한다. 따라서 현 코드의 전역 Mesh `100x` 재교정은 금지한다.

## G15. 4클래스·발탄 확장 전에 고정할 재사용 gate

1. 모든 occurrence/module/property/leaf/distribution에 G14의 네 provenance 등급을 저장한다.
2. unknown opcode/property, unconsumed row, silent fallback을 모두 `0`으로 만든다.
3. Mesh dimensionless, Sprite/Decal/location/velocity cm→m, turn→degree를 property별 unit gate로 검사한다.
4. anchor는 고정 animation frame마다 named bone translation/rotation/unit-scale/determinant golden을 만든다. Tool과 gameplay는 같은 helper를 사용한다.
5. notify global time, emitter delay, burst, lifetime, duration을 합친 한 숫자로 저장하지 않고 각각 보존한다.
6. recipeId별 versioned visual adapter가 exact input/texture/render-state denominator를 선언한다. material 이름 heuristic과 neutral provider는 최종 승인에서 금지한다.
7. real DDS를 사용한 shader/WARP replay와 실제 family sink draw를 함께 검증한다. numeric diagnostic oracle만으로 pixel fidelity를 승인하지 않는다.
8. Decal size exactly once/Y-yaw, Ribbon typed width/lifetime/color/tiling, Light/Post adapter를 family 공용 계약으로 둔다.
9. geometry는 raw→intermediate→WModel lineage, preScale exactly once, bounds/tangent/color를 검증한다.
10. Artist 전용 `35/34/57/13/16`과 recipe ID를 C++에 하드코딩하지 않고 effect manifest의 분모로 옮긴 뒤 확장한다.
11. 자동 검증 뒤에도 occurrence별 고정 시각 사용자 판정을 `APPROVED/RETUNE/BLOCKED`로 기록한다.

이 gate를 통과한 뒤에는 새 클래스나 발탄을 위해 두 번째 renderer를 만들지 않는다. 같은 extraction schema, Program parser, CPU evaluator, material adapter registry, six-family sink를 데이터만 바꿔 재사용한다.

### G16-02. Artist `b_wp_1` combined transform을 prototype scale로 오인한 오류

Artist playable `CModel` admission transform은 `Scale(0.0001) * Yaw(-90deg)`다. 그러나
`CBone::Update_CombinedTransformationMatrix`가 만드는 `b_wp_1` combined matrix에는 Artist rig의
`sdm` root scale `100`도 포함된다. 따라서 Effect anchor가 실제로 받는 basis는 `0.0001`이 아니라
`0.01`이다. source Effect의 local position/size는 이미 meter 단위이므로 raw combined 3x3을 그대로
parent로 쓰면 `#0~#4`의 local offset과 geometry가 `0.01`배 되고, combined scale을 `0.0001`로 검사하면
정상 matrix를 준비 단계에서 거부한다.

공용 `Build_SourceBoneAnchorWorld`는 다음 조건을 모두 검사한 뒤에만 정규화한다.

- 4x4 값 전부 finite.
- affine 마지막 열/`_44` 유효.
- 세 basis 길이가 Artist combined 계약 `0.01` 근처이고 서로 uniform.
- 세 basis가 orthogonal이며 determinant가 퇴화하지 않음.
- owner world도 finite/non-degenerate affine.

통과하면 raw bone의 3x3 basis 아홉 값에만 `100`을 곱한다. `_41/_42/_43` translation은 이미 character

animation rotation, asset basis `-90deg`, bone translation, actor/preview world를 보존한다. 실패하면 identity
fallback을 쓰지 않고 해당 anchor stage를 거부한다.

적용 범위:

- 실제 reconstructed Artist F presentation의 다섯 `b_wp_1` follow request.

### G17-03. yaw axis 오류

Program adapter는 `yawOnly=true`다. UE3 up axis `+Z`는 `(x,y,z)->(x,z,-y)` 변환 뒤 Client `+Y`다. Decal shader도 local X/Z가 footprint, local Y가 projection normal/depth다. 따라서 scalar ParticleModuleRotation은 reconstructed Decal에서 `RotationY(theta)`가 되어야 한다.

현재 공용 particle path는 scalar rotation과 rotation-rate를 모두 Z에 누적한다. `180deg`인 #20은 대칭 volume 때문에 오차가 덜 보일 수 있지만 #21/#22는 projection normal을 `3.6deg` 기울이고, XZ 평면에는 의도한 `176.4deg` yaw를 적용하지 못한다.

### G17-04. 기존 authored Decal을 보존하는 수정 계약

reconstructed Decal만 다음 계약을 사용한다.

1. scalar rotation/rate를 Client Y에 누적한다. Sprite 등 기존 family의 Z회전은 바꾸지 않는다.
2. particle World가 `Scale(Size.x, Depth, Size.y)`로 projection volume을 정확히 한 번 소유한다.
3. evaluated Decal에 `world owns projection volume` typed flag를 남긴다.
4. Renderer는 이 flag가 true일 때 shader `g_DecalSize=(1,1)`, `g_DecalDepth=1`을 보낸다.
5. legacy/authored Decal은 flag false이며 기존 World + `Detail.Decal` 상수를 그대로 쓴다.
6. zero/non-finite/singular World는 inverse 전에 draw를 거부한다. silent identity fallback은 금지한다.

영구 자동 검증은 세 occurrence의 step 91 basis length/center/Y-normal, #21/#22의 `176.400003deg` XZ yaw, signed-X mirror determinant, true/false flag별 shader 상수를 고정해야 한다. 수정 뒤 사용자 눈검증은 바닥 먹물의 footprint, 다른 지형으로 새는 20~39m projection depth, 방향을 따로 판정한다.

### G18-02. deferred start가 닫은 것과 fixed-step anchor history가 남긴 것

deferred start는 최초 prepared-cache wall time 약 3초가 animation/effect time으로 유입되는 문제를 닫았다. 그러나 Effect Tool은 outer frame마다 현재 root/anchor map을 한 번 만들고, `Advance_Preview(delta)` 내부의 최대 60개 fixed step은 같은 bone pose를 본다.

```text
outer frame pose(t1) 1개
  -> fixed step t0+1/60
  -> fixed step t0+2/60
  -> ...
  -> fixed step t1
모두 같은 b_wp_1(t1) 사용
```

정상 60fps의 작은 delta에서는 오차가 작지만 hitch, seek, catch-up에서는 follow emitter 5/35의 historical bone sample이 0/5다. SpawnPerUnit은 이동 거리, Ribbon은 연속 위치가 입력이므로 같은 한 점을 반복하면 중앙 붓 궤적이 짧아지거나 사라진다. 영구 수정은 animation clip을 각 fixed-step sample time에 평가해 `b_wp_1` transform history를 Playback에 typed callback/sample stream으로 전달해야 한다. synthetic path와 endpoint interpolation은 원본 bone animation을 대체하지 못하므로 금지한다.

정확한 예로 outer frame이 30Hz면 내부 step `t+1/60`, `t+2/60`이 둘 다 `bone(t+2/60)`을 본다. `.2s` hitch면 12 step이 전부 endpoint bone을 본다. Seek는 더 나쁘다. animation을 최종 `t`에 먼저 seek해 anchor map 한 번을 만든 뒤 Playback이 `0..t`를 replay하므로 Ribbon은 같은 위치만 받아 1cm gate 뒤 point 1개, 즉 draw 불가가 될 수 있다.

1초보다 큰 backlog도 별도 문제다. Playback은 호출당 최대60 step만 처리하지만 animation 표시 시간은 endpoint로 먼저 갈 수 있다. 이후 animation delta가 0이면 남은 accumulator를 drain하지 못하거나 Natural Stop tail에서 뒤늦게 burst로 처리한다. `playbackTime == animationReportedTime`을 매 frame 보장해야 한다.

현재 `CAnimationTargetService`와 Playback API는 timestamp별 pose/history를 제공하지 않는다. live `CModel`을 반복 seek하고 되돌리는 방식은 clip cursor, blend, root motion, visible pose를 파괴적으로 바꾸므로 정본 해결로 사용하지 않는다. reconstructed-only immutable timeline이 최소 안전 경계다.

```text
EFFECT_SOURCE_ANCHOR_TIMELINE
  fixed step index/time
  root matrix
  required slot matrices[5]
```

Artist F 2.833초는 step0 포함 약171 sample이고 `171 * 5 * 64 bytes`, anchor payload만 약53.4KiB다. 비파괴 animation pose sampler로 stage하고 Playback `Step(n)`은 timeline `n`만 소비한다. timestamp/slot/generation이 하나라도 없으면 current-map fallback 없이 이전 frame/state를 보존하며 fail-closed한다. partition `1/60`, `1/30`, irregular, `.2/1.2s stall`, direct seek에서 동일 particle/trail hash가 나와야 한다.

### G18-03. Spawn RateScale은 아직 결론을 내리지 않는다

selected Program에는 Spawn `RateScale` 35행이 모두 `0`으로 보존돼 있고, 현재 Playback은 Rate만 소비한다. nonzero Rate occurrence는 정확히 네 개다.

| occurrence | source Rate |
|---:|---:|
| `#0` | `7/s` |
| `#3` Ribbon | `40/s` |
| `#24` | `80/s` |
| `#26` | `50/s` |

`Rate * RateScale`을 문자 그대로 적용하면 네 occurrence의 continuous spawn이 전부 0이 된다. raw 35행을 다시 해석한 결과 이 `0`은 explicit scalar zero가 아니다. 모두 `RateScale: StructProperty<RawDistributionFloat>, size=36` 안에 `Distribution:ObjectProperty value=0`만 있고 lookup/op/default 숫자가 없다. 여기서 `value=0`은 null UObject reference다.

초기 semantic closure도 35/35를 `defaultDependent=true + DISTRIBUTION_CLASS_DEFAULT_VALUE_UNRESOLVED`로 막았다. 후속 source-execution builder가 이 blocker를 버리고 target-none을 zero-filled op1 descriptor로 만들면서 fabricated 0이 Program에 들어갔다. 따라서 현재 Program의 RateScale 0은 원본 값으로 사용하면 안 된다.

현재 pinned Engine package의 `Default__ParticleModuleSpawn`을 같은 parser로 읽으면 RateScale lookup은 `[1,1,1,1]`이다. 그러나 이 Engine CDO는 source-era package로 receipt에 pin된 증거가 아니므로 `SOURCE_EXACT`가 아니라 `CURRENT_ENGINE_CDO_RECONSTRUCTED` policy로만 승인할 수 있다.

현재 두 실행 경로는 실제로 다르다.

- compiled timing plan: `Rate * RateScale`이므로 네 개 모두 continuous spawn `0`
- live Playback: RateScale을 완전히 무시하므로 `7/40/80/50`을 사용. 단 Ribbon은 particle spawn branch 자체를 타지 않고 generic interval sampler를 사용

즉 영향은 4/35의 확정 cross-runtime mismatch다. 안전한 수정은 null distribution과 숫자 zero를 parser에서 구분하고, unresolved-default blocker를 다음 단계까지 보존한 뒤, 현재 Engine CDO identity 1을 별도 reconstructed policy ID/hash로 seal하는 것이다. 그 뒤 Program/receipt/expected sample SHA를 다시 만들고 Build_Document가 승인된 INLINE distribution을 Playback descriptor에도 overlay해야 한다. Playback과 compiled plan은 둘 다 같은 `Rate*RateScale` 수식과 RNG 순서를 사용한다. Product는 source-era CDO 증거가 없으므로 계속 OFF다.

identity1 provisional 60Hz 예상치는 continuous spawn만 `#0=4`, `#3=119`, `#24=15~16`, `#26=10`이다. float/double accumulator 차이 때문에 #24에서 15/16, 전체 rate 합계에서 148/149 차이가 현재 존재하므로 exact arithmetic도 하나로 고정해야 한다. fixed burst base는 172이며, 현재 CPU scale0은 burst172만, Playback ignore-scale은 continuous149+burst172=321 후보를 만든다. 이 수치는 CDO reconstructed policy와 accumulator arithmetic을 seal하기 전에는 Product 정답이 아니다.

### G18-04. typed plan validation과 실제 Step authority는 아직 분리돼 있다

stage는 35 emitter / 399 module / 629 distribution과 propertyPath join을 검증한다. 그러나 particle Step의 실제 spawn/update는 아직 `Element.SourceRecipe.Modules`를 순회하고 class/property 이름 문자열로 handler를 고른다. 즉 typed Program이 구조와 신원을 검증하지만, 399 module의 direct typed opcode가 sole execution authority인 상태는 아니다.

4클래스·발탄 확장 전에 parser가 만든 typed opcode/operand가 Step의 유일 소비 입력이 되어야 한다. source string scan은 검증·진단용으로만 남기고, unknown opcode, wrong component count, unsupported unit policy는 fail-closed해야 한다. 이 전환은 399/399 opcode dispatch denominator와 기존 string path가 실행되지 않았음을 harness로 고정한다.

### G18-05. false-success를 막을 draw denominator가 필요하다

현재 `Render_Particles`는 source-material fallback 차단에서 `S_FALSE`를 반환할 수 있고, Trail은 point가 2개 미만이거나 fallback-blocked면 draw 없이 건너뛴다. 상위 `Render`는 `FAILED(hr)`만 검사하므로 `S_FALSE`를 성공으로 취급하고 마지막에 `Effect frame rendered.`를 기록할 수 있다.

따라서 다음 denominator가 없으면 “35 emitter가 실행됐다”와 “GPU draw 또는 Presentation submit이 있었다”를 구분할 수 없다.

- family별 active occurrence 수: MeshParticle/Sprite/Decal/Ribbon/Light/Post
- material-blocked 수와 이유
- submitted draw/instance/triangle 수
- Light/Post presentation submit 수
- active인데 draw/submit 0인 occurrence stable ID

Full35 debug path는 active occurrence가 있는데 해당 family submit이 0이면 성공 문구를 내지 않고 structured incomplete status를 내야 한다. `S_FALSE` 자체는 API상 실패가 아니므로 상위에서 명시적으로 집계한다.

### G19-04. buffer 500 수정과 tessellation cap은 다른 문제다

### G19-05. reconstructed-only typed 복구 계약

6. emission window `3s`, action schedule `1.501614s`, point lifetime `2s`의 authority를 하나씩 명명하며 서로 대체하지 않는다.

## G21. 메인 Mesh material evaluator의 실제 코드 반영

### G21-01. 13개 메인 composite를 하나의 generic shader로 부르면 안 된다

메인 화면을 구성하는 MeshParticle 분모는 `#4,#7~#18`의 13개다. 이 13개를 source material 근거와 runtime texture admission으로 다시 join한 결과는 다음과 같다.

| 분류 | occurrence | 개수 | runtime profile |
|---|---|---:|---|
| finite typed evaluator | `#17` | 1 | `effect.ue3.missiletrail-01.v1` |
| bounded reconstructed evaluator | `#4,#7~#16,#18` | 12 | `effect.ue3.reconstructed-standard.v1` |
| 과거 grouped fallback | 없음 | 0 | 사용 금지 |

`#17`만 parent arithmetic과 소비 lane을 현재 증거로 닫을 수 있었다. 정확한 분모는 scalar 26, source texture 3, static switch 1, admitted resource 5, dynamic semantic 4다. `#7/#8`은 cooked 입력에 `uv_noise` 이름이 각각 4개 남아 있지만 승인된 runtime noise binding이 0이므로 finite evaluator로 거짓 승격하지 않았다.

### G21-02. CPU에서 GPU로 전달되는 값

`Effect_ReconstructedExecution.cpp`는 13개 분모와 `#17`의 exact predicate를 고정한다. `Effect_DocumentRenderer.cpp`는 다음 순서로 resource를 stage한다.

```text

-> materialOccurrenceId
-> material recipe/family rowSha256
-> sidecar recipe texture decision
-> material input / texture binding / sampler policy rowSha256
-> runtime DDS assetId + bytes + rawSha256
-> D3D11 SRV format/color-space + sampler
```

particle dynamic parameter는 Playback에서 distribution을 평가해 `float4`로 보존하고, Renderer가 해당 occurrence의 semantic lane에 함께 bind한다. 이번 변경은 별도 두 번째 HLSL을 만들지 않고 기존 common evaluator 소비 경계를 확장했다.

## G22. Decal 20~22 size·yaw 단일 소유권 구현

### G22-01. 교정 전 수식

교정 전에는 particle World가 `Scale(A,B,1)`을 이미 적용한 뒤 shader가 `g_DecalSize=(A,B)`, `g_DecalDepth=D`를 다시 적용했다. 따라서 full extent는 다음처럼 중복됐다.

```text

single-owner target = (cueScale*A, cueScale*D, cueScale*B)
```

또 scalar `ParticleModuleRotation`을 모든 Sprite처럼 Client Z에 넣었다. UE3의 up-axis +Z는 Client +Y로 변환되며 decal footprint가 local X/Z, projection depth가 local Y이므로 Decal yaw의 정답 축은 Client Y다.

### G22-02. reconstructed-only 구현 계약

현재 코드 변경은 authored/static Decal의 기존 경로를 건드리지 않고 `Reconstructed DecalParticle`에만 적용한다.

3. `EFFECT_EVALUATED_ELEMENT::bWorldOwnsDecalProjectionVolume=true`로 소유권을 Renderer에 전달한다.
4. 이 flag가 true면 shader의 `g_DecalSize=(1,1)`, `g_DecalDepth=1`을 사용한다.
5. flag가 false인 authored/static Decal은 기존 `Detail.Decal.vSize/fDepth`를 그대로 bind한다.
6. signed Size는 World determinant의 부호로 mirror를 보존한다. singular World는 draw를 `S_FALSE`로 억제하고 non-finite World는 `E_INVALIDARG`로 fail-closed한다.

## G23. 비파괴 animation bone sampler와 fixed-step anchor 통합 경계

### G23-01. 왜 현재 bone map 한 장으로는 호 궤적을 복원할 수 없는가

Tool의 outer frame이 30Hz라면 Playback은 내부에서 1/60초 step을 두 번 실행한다. 기존 경로는 animation이 outer frame 끝 pose까지 먼저 간 뒤 그 시점의 `b_wp_1` 한 장만 읽었다. 그래서 내부 step `t+1/60`, `t+2/60`이 모두 `Bone(t+2/60)`을 사용했다. 0.2초 hitch면 12개 step이 같은 endpoint를 사용하고, direct Seek는 0부터 target까지 모든 step이 target bone 하나를 사용했다.

이 오류의 영향은 단순 위치 한 칸이 아니다.

- follow Sprite spawn 위치가 한 점에 몰린다.
- SpawnPerUnit은 이동 거리를 보지 못해 spawn 0 또는 과소가 된다.
- Ribbon은 같은 점을 반복해 minimum-distance gate에서 제거되고 2점 미만이라 draw되지 않는다.
- #4 weapon Mesh의 짧은 visible window가 render frame 없이 소진된다.
- late hit/decal 군만 남아 사용자가 본 “위쪽 호 없이 바닥에서 한꺼번에 생성” 인상이 된다.

### G23-02. Engine에 추가한 비파괴 sampling API

Engine `CModel`에 현재 animation clip의 임의 tick에서 필요한 bone subset만 batch sampling하는 API가 추가됐다.

```cpp
bool Sample_CurrentAnimationBoneCombinedMatrices(
    uint32_t expectedAnimationIndex,
    float trackPositionTicks,
    std::span<const uint32_t> boneIndices,
    std::span<float4x4_t> outCombinedMatrices) const;
```

이 API는 live model을 seek하지 않는다. 계산 순서는 기존 런타임과 같게 유지한다.

```text
현재 local palette를 staging
-> 현재 clip의 channel을 동일 linear/Slerp 규칙으로 임의 tick sample
-> 현재 blend ratio 적용
-> root-motion suppression 적용
-> root = Local * Model PreTransform
-> child = Local * ParentCombined
-> 요청한 bone subset만 transactional output copy
```

expected clip mismatch, animation index/time/bone/span 오류, NaN, 잘못된 hierarchy/blend/matrix면 output을 바꾸지 않고 false를 반환한다. Debug에서는 animation track cursor, channel left-key cursor, 모든 live local/combined palette 비변경과 두 번 sampling의 bit determinism을 검사한다.

실제 `Artist.wmodel` 자동 회귀 수치는 다음과 같다.

| test tick | 42.5 |

`b_wp_1` combined matrix와 byte-identical이었다. 잘못된 animation, NaN time, invalid bone은 sentinel output을
유지하고 실패했다. 실제 matrix에는 Artist prototype `0.0001 scale * Y -90°`와 rig root `100`이 합성된

### G24-01. 음수 크기는 잘못 추출된 값이 아니라 원본의 선택형 flip 값이다

Full35에서 음수 Sprite StartSize를 실제로 갖는 occurrence는 정확히 2개다. 둘 다 hit system의 `PSA_Velocity` Sprite이며 Required module에 `bAllowImageFlipping=true`가 남아 있다.

### G24-02. 현재 코드 결함

Playback은 `Particle.vSize`를 signed 상태로 World scale에 넣는다. 그러나 `Make_ParticleSpriteWorld`가 World를 `XMMatrixDecompose`한 직후 X/Y/Z scale을 모두 `std::abs`로 바꾼다. billboard를 카메라/속도 방향으로 다시 조립하기 전에 부호를 지우므로 다음 정보가 복구 불가능해진다.

- #27의 음수 X 좌우 반전
- #28의 고정 음수 Y 상하 반전
- #28에서 X와 Y가 동시에 음수인 경우의 이중 반전

특히 음수 축이 두 개면 원행렬 determinant는 양수일 수 있다. 행렬 분해 결과만 보고 두 원본 부호를 역추론할 수 없으므로 Renderer에서 determinant를 검사하는 우회는 정답이 아니다. Playback이 distribution 평가 직후의 signed X/Y를 typed evaluated-particle 필드로 함께 넘겨야 한다.

### G24-03. 적용할 reconstructed-only 경계와 검증

수정 경계는 다음처럼 고정한다.

1. SourceRecipe Sprite의 Required module에서 `bAllowImageFlipping`을 읽는다.
2. true인 행은 evaluated particle에 현재 `Particle.vSize.x/y`의 부호를 명시적으로 보존한다.
3. Renderer는 decomposed magnitude와 typed sign을 결합한 뒤 velocity/camera/axis orientation을 적용한다.
4. 값이 정확히 0인 축은 0을 유지해 존재하지 않는 면을 임의로 부풀리지 않는다.
5. authored/static Sprite와 `bAllowImageFlipping=false` 경로는 기존 동작을 유지한다.
6. 전용 harness는 #27/#28의 min/max 네 경우, pivot, velocity alignment, 단일/이중 flip determinant와 legacy 불변을 검사한다.

현재 상태는 **원본 수치·원인과 signed size 전달 코드는 CLOSED**다. Playback이 signed X/Y를 evaluated
particle에 보존하고 Renderer가 billboard/velocity/axis orientation 뒤에도 그 부호를 유지한다. Debug 전용
11/11 검증과 Client Debug/Release build는 PASS지만, Release 전용 signed-Sprite 검증과 사용자 visual 판정은
아직 실행하지 않았다. 보라색 flat quad의 원인은 이 부호 결함과 별개다. 그쪽은 neutral white texture
provider, blue-heavy vertex color, material graph/texture admission 미완료가 주원인이고 signed flip은 방향과
실루엣만 교정한다.

### G24-04. `StartSize.Y=0`인 Sprite가 전부 높이 0인 것은 아니다

Full35 Sprite 중 order `1,2,16,19,29,30,31`은 selected Program에서 StartSize의 두 번째 plane component가 0이다. 그러나 이 7행은 Required의 `screenalignment` literal이 cooked row에 없고 현재 reconstructed handler가 CDO/default projection으로 `CAMERA_SQUARE`를 선택한다. Renderer의 `CAMERA_SQUARE` branch는 분해한 X 크기를 Y에도 복사한다.

```cpp
const float x = Scale.x;
```

### G31-08. prepared PASS 뒤 즉시 종료의 실제 원인과 first-draw 회귀

이번 즉시 종료는 하나의 원인으로 뭉개지 않는다. 과거 17:52 WER의
`Object_Manager` layer-map access violation은 matching full stack이 없어 계속 별도 `OPEN`이다. 이후
문구 없이 닫힌 실행에는 Effect draw의 `FAILED HRESULT`가 Engine frame failure를 거쳐 Client main loop
종료로 전파되는 경계도 있었다. 따라서 process 생존을 위해 오류를 전부 삼키는 대신 다음 두 계약을
분리했다.

1. frozen Effect packet, renderer identity, local resource와 denominator 위반은 첫 operation/HRESULT를
   status에 보존하고 해당 Effect object만 격리한다.
2. device removal, OOM, D3D Map/draw, global render target와 presentation capacity 실패는 계속 global
   failure로 전파한다. HRESULT 값만으로 local/global을 판정하지 않는다.

실제 first-draw harness가 처음 찾아낸 직접 결함은 renderer identity였다.

- Artist: native-v14 -> format-13 lowering이 `Element.Renderer`를 지워

- Lance BA1: legacy authored component `authored.approx.s002.mesh01`은 `Renderer==END`인 정상 format-12
  문서다. 이를 typed-only 규칙으로 거부하지 않고 kind와 geometry binding에서 legacy Mesh family를
  결정한다.
- 회귀 확장 중 `SourceRecipe.bEnabled`인 legacy Renderer-END 문서를 GPU에서 제외하는 잘못된 guard도
  발견했다. 실제 authored corpus는 18문서, particle/decal 1,300 occurrence이므로 이 guard를 제거하고

### G31-09. 2026-08-14 최종 동결 — starting recipe에서 stable Element authoring으로

G31-08까지의 first-draw 역사는 보존하지만 V6 최종 완료 정의는 원작 exact first-draw 분모를 계속
늘리는 일이 아니다. Track A 결과는 다음을 공급하는 starting recipe다.

```text
DDS/WModel identity와 texture role
+ source spawn/lifetime/velocity/size/color/UV/transform/attachment
+ material lane/blend/depth/pass evidence
+ typed family와 각 carrier adapter 입력
```

Track B는 이 recipe를 기존 Effect Tool authoring 문서로 연다. BA admitted stable row는 DDS/WModel,
material parameter, module, timing, transform, color와 UV를 편집한다. row 선택은 현재 All/Family/Solo
합성을 바꾸지 않는다. immutable projection은 직접 덮지 않고
`Save As Authored Copy -> Data/Effects/Authored/<new-id>.effect.json`으로 전환한 뒤 기존 Save/Reload와
generic renderer를 사용한다.

도화가 adapter는 exact packet을 일반 문서로 위장하지 않는다. `Play Core F`로 stage된 exact projection의
LocalDecal `#20/#21`과 Ribbon `#3`은 full Details inspection-only이고 direct Save As가 차단된다. transform은
stable occurrence tuning으로 저장한다. DDS/material/Detail을 직접 완성하려면 선택 Decal/Trail 하나를
generic Authored starting copy로 낮춘다. 이 copy는 Detail/Material/ResourceBindings를 보존하고 ordinary
drawable roundtrip을 통과하지만 native projector/VF/6-SRV packet을 보존했다고 선언하지 않는다.

공용화한 것은 stable identity/document/resource/save/publish 계약이다. Mesh instance,
Sprite billboard/SubUV, LocalDecal projector, Cascade particle-history strip, animation-notify strip은 서로
다른 adapter이므로 한 universal shader로 합치지 않는다.

현재 게시 분모는 visual program `13 = 3 BA x 4 stages + Artist F adapter`, renderer row `135`
(admitted `72`, fail-closed `63`), supplemental `5/5` admitted다. catalog와 sidecar는 한 transaction으로
tracked 제품 위치에 게시됐고 현재 Debug/Release dual output `--effect-runtime-fast`는 `23/23`, failures 0이다.
이 구조는 class 이름, skill ID, order와 material path switch를
generic consumer에 넣지 않지만, 제품 content는 아직 세 캐릭터 BA와 도화가 F까지만이다. Warlord/Valtan과
