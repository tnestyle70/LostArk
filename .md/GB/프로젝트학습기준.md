## 2026년 10월 12일 대화 질문과 재방어 형식

사용자는 Claude와 진행했던 W01의 면접관 말투와 다섯 칸 질문 형식을 명시적으로 다시 선택했다. 목표 범위는 LostArk 전체의 주요 구조와 기능이며, `Interview/기술소개서/기술소개서.pptx`의 실제 메인 카테고리를 기준으로 진행한다. 대표 기능 하나는 각 회차의 시작 단위이며 전체 학습 목표를 그 기능만으로 축소하지 않는다.

질문지는 우선 **대화에 직접 출력**한다. 문서 링크나 앞으로 만들겠다는 설명만으로 대신하지 않는다. 현재 PPT의 LostArk 순서는 전체 구조, 보스 패턴, 시퀀서, 프로파일링·최적화, 렌더링, 이펙트·툴, 데이터 관리, 공용 툴·협업·AI, 빌드·셰이더 컴파일이며 UE 비교와 문제 해결·개선 결과를 이어 붙인다. 각 주제에서 Engine·Client·Server·Shared·자체 Tools·Data·shader의 실제 연결과 필요한 기반 개념까지 넓힌다.

각 회차는 `⓪ 실제 파일·함수의 읽을 구간과 예상/관측 → ① 문제 → ② 단순한 해법의 한계 → ③ 메커니즘 → ④ 대조 → ⑤ 대가 → 직접 구현·조건 변경·검증`으로 구성한다. 질문에는 무엇을 열고 어떤 상태를 확인할지 붙인다. 말투는 간결하고 단호한 면접관 방식으로 하며, 실제 반례와 코드 근거로 재질문한다. 사용자 답을 받기 전에 풀이와 모범답안을 함께 출력하지 않는다. 막힌 부분의 설명이나 정답 코드를 요청하면 제공하고 도움받은 범위를 구분한다.

첫 읽기·구현은 시간 제한 없이 진행하고, 재방어는 사용자가 제시한 15·20·25·15·15초의 90초 다섯 칸 형식을 쓴다. 각 칸에는 근거가 필요하며 수치가 판단에 필요한 칸에는 단위와 계산 또는 측정 조건을 요구한다. 의미 없는 숫자를 모든 칸에 채우거나, 옛 W01의 사고 이력·2.27년·UE/Windows 비유를 LostArk 사실로 이식하지 않는다. 예상, 실제 관측, 현재 구조 분석, 당시 개인 기여를 구분한다.

답변 피드백은 `확인된 부분 → 틀리거나 근거가 없는 주장과 코드 위치 → 반례 또는 조건 변경 한 개 → 다음 검증 → 재방어 범위` 순서다. 말로 설명한 통과와 직접 구현·실행 확인을 별도로 남긴다. 한 오류를 전체 능력에 대한 실격 판정으로 확대하지 않는다. 이번 전범위 진행의 첫 회차는 PPT 3~5장의 L00 전체 구조·Client 프레임·Server tick·Level 전환이며, 기존 발탄 SPIN 학습은 보스 회차에서 이어간다.

## 유지할 방향과 고칠 운영

유지할 것은 구체적인 문제, 상태의 손추적, 반례, 자료 없이 설명하기, 조건을 바꾼 직접 구현이다. W01에서 index만 남은 옛 참조가 슬롯 재사용 뒤 무엇을 가리키는지 묻는 질문은 유용하다. 이런 사례를 먼저 다룬 뒤 수명과 식별자라는 원리에 연결한다.

다음 규칙은 그대로 사용하지 않는다.

- 모른다고 했는데 계속 시험만 보지 않는다. 처음 배우는 내용에는 짧은 설명과 예제가 필요하다. 설명을 받았다는 사실은 이후 독립 구현을 무효로 만들지 않는다.
- 정리 요청이나 문서 저장 요청을 무조건 회피라고 부르지 않는다. 실제로 시도했는지와 어디서 막혔는지를 확인한다.
- 답을 못했다고 과거 결정을 근거 없이 했다고 판정하지 않는다. 기억, 개념, 코드 추적, 구현, 표현 중 막힌 지점을 구분한다.
- 대가를 설명하는 능력은 현재 이해의 근거다. 과거 설계자였다는 증거는 아니다. AI가 만든 문장이나 선택 이유를 사용자의 과거 경험으로 귀속하지 않는다.
- 각 칸에 숫자를 강제하지 않는다. 정확성·소유권·실패 보존도 독립적인 요구사항이다. 숫자는 규모·시간·메모리·정밀도가 선택에 영향을 줄 때 사용한다.
- 설정값, API 보장, 가정에 따른 계산, 실제 측정을 구분한다. 랩어라운드 기간의 산술을 측정이라고 쓰지 않는다. 틱 빈도만으로 슬롯 재사용 빈도 상한을 가정하지 않는다.
- C1~C7은 질문을 떠올리는 관점이다. 슬로건에서 자료구조나 동기화 코드를 증명 없이 유도하지 않는다. 예를 들어 공유 비용이라는 관점만으로 특정 fence 위치가 정당화되지는 않는다.
- 원문에 있는 지연 수치, 특정 UE 구현, 운영체제·C++ 일반화는 해당 문제를 공부할 때 공식 문서와 현재 코드로 확인한다. 트리의 굵은 글씨나 AI의 단정은 근거가 아니다.
- 현재 코드는 실제 동작을 조사하는 자료다. 요구사항·언어/API 계약·테스트 결과와 충돌하면 버그일 수 있다. 코드에 있으므로 올바르다고 끝내지 않는다.
- 정답과 문장이 같으면 실패하거나 새로운 말을 하면 가점이라는 규칙은 쓰지 않는다. 정확성, 근거, 도움의 범위와 독립 수행을 각각 본다.
- SEED가 두꺼워지면 경보라는 판정을 하지 않는다. 처음 공부하는 범위가 늘면 기록도 늘 수 있다. 사실과 API 계약을 유도 사슬로 대체하지 않는다.
- 성공 간격 ×2.5, 성공률 80%, 축별 실패 개수는 최적 법칙이나 능력 진단이 아니다. 복습은 실제 기억과 일정에 맞춰 조정하며 요청 없이 자동 일정을 만들지 않는다.

원문의 W01 대화는 오류를 구체적으로 지적한 점은 좋지만, 개념 설명보다 실패 판정을 앞세우고 여러 반례를 동시에 요구했다. 사용자 손추적을 확인하기 전에 90초 시험으로 넘어가면 무엇을 배웠는지 확인하기 어렵다. 교사와 면접관 역할은 아래처럼 구분한다.

자료 자체의 불일치도 확인했다. 보존한 `03_유도카드_원문.html`의 `AX.C4` 두 번째 문장은 “관찰은 비싸다”인데 INDEX는 “수명은 관찰되지 않는다. 프로그램이 선언해야 한다”라고 쓴다. 과거 피드백은 사용자의 “관찰은 비싸다”를 사용자 오독으로 돌렸지만, 카드가 그 표현을 제공했다. 이것만으로 당시 답변 전체가 맞았다는 뜻은 아니며, 그 문구의 혼란을 사용자에게만 귀속하면 안 된다. 설명 자료의 오류와 학습자의 오류를 함께 검토한다.

## 한 기능을 배우는 실제 순서

| 구간 | 사용자와 함께 할 일 | 확인할 점 |
|---|---|---|
| 이해 | 실제 입력과 파일 한 곳을 열고 문제를 쉬운 말로 설명한다. 필요한 개념만 짧게 배운다. | 입력·출력과 잘못되면 생기는 일을 말할 수 있다. |
| 공동 추적 | 작은 값으로 상태표 한 번을 함께 채운다. | 어느 사건에서 어떤 값이 바뀌는지 연결한다. |
| 예측 | 다른 입력의 다음 상태를 사용자가 먼저 적는다. | 정답 문구가 아니라 상태 변화와 근거가 맞는다. |
| 직접 구현 | 원본을 가리고 작은 계약을 구현한다. 막힌 부분에만 도움을 준다. | 정상 입력과 경계·실패 입력을 직접 확인한다. |
| 실제 코드 연결 | 제품의 타입·함수·호출자·소비자를 대조하고 생략한 조건을 찾는다. | 연습과 제품의 공통점 및 차이를 설명한다. |
| 기술소개 | 검증한 내용을 다섯 칸으로 압축한다. | 주장과 근거, 대안의 비용, 현재 한계를 연결한다. |

구간은 이해에 맞춰 오갈 수 있으며 이미 확인한 내용은 반복하지 않는다. 90초 설명은 마지막 압축 연습이다. 처음부터 제한 시간이나 다섯 칸 완성을 요구하지 않는다. 처음 답은 두세 문장이어도 된다. 사용자가 전체 설명·코드·양식을 요청하면 제공하고, 그 뒤 다른 입력 예측이나 재구현으로 확인한다.

## CodingTest 여덟 단계를 프로젝트에 적용

원래 순서를 유지하되 프로젝트에 맞는 질문으로 사용한다. 한 기능에 여덟 문서를 만들지 않는다. 1~6에서 가능한 항목부터 1~3문장으로 적고, 막힌 칸은 설명·손추적·구현을 오가며 보완한다. 전 항목 완성이나 점수는 구현 착수 조건이 아니다. 7의 기대 결과는 실행 전에 적는다.

| 단계 | 프로젝트에서 묻는 질문 |
|---|---|
| 1 목표 고정 | 어떤 입력을 받아 어떤 규칙으로 무엇을 만들어야 하는가? |
| 2 제약 어휘 | 개수·단위·ID·순서·권위·수명·실패 시 보존해야 할 것은 무엇인가? |
| 3 예산 산술 | 한 번 로드할 때와 매 틱에 각각 무엇을 몇 번 하는가? 시간·메모리 예산 근거는 무엇인가? |
| 4 완전탐색 기준선 | 손으로 하던 가장 직접적인 절차를 코드로 옮기면 어떻게 되는가? 이미 충분하다면 그대로 사용한다. |
| 5 병목과 선택 | 무엇을 반복 조회·계산하는가? 필요한 읽기·추가·삭제·처리 순서를 정한 뒤 자료구조와 알고리즘을 고른다. |
| 6 선서술과 불변식 | 각 변수의 의미와 초기값은? 사건마다 변경·보존할 값은? 함수 입력·출력·호출 순서·종료·실패 처리는? |
| 7 네 가지 검증 | 원래 Build·Example·Edge·Judge. 프로젝트에서는 컴파일, 정상 입력, 경계·실패 입력, 실제 소비 경로로 대응한다. 제품 화면은 사용자가 확인한다. |
| 8 회고 | 예상과 실제가 처음 달라진 곳, 수정 이유, 남은 비용과 다음 조건 변경은 무엇인가? |

5~6단계에서는 자료구조 이름부터 정하지 않는다. 먼저 “무엇을 기억해야 다음 판단을 할 수 있는가”를 적는다. 정의 값과 실행 중 값, 소유 container와 조회용 index, stable ID와 배열 위치를 구분한다. 함수는 의미가 있는 상태 변화 단위로 나누며 호출자와 실패 시 보존 상태를 함께 설명한다.

## 낯선 코드에서 읽기와 비평을 시작하는 방법

사용자는 기술소개서의 전체 카테고리를 따라 책임과 연결을 이해하고, 핵심 기능의 내부 상태·실패 처리까지 배우는 방향에 동의했다. 한 번에 범위를 좁히는 것은 전체 학습을 포기한다는 뜻이 아니다. 파일 목록을 순서대로 완독하는 대신 구체적인 동작 하나와 관찰 가능한 결과에서 출발한다. 첫 파일·심볼·읽을 블록·답할 질문을 함께 지정한다. 현재 첫 경로는 보스 학습 기록의 SPIN schedule → entity의 소비 횟수 → stage 진입 초기화 → Update 반복문이다.

읽기는 질문에 필요한 범위까지 한다. 호출한 함수의 계약만으로 현재 질문에 답할 수 있다면 내부 탐색을 잠시 멈춘다. 예를 들어 반복 횟수를 배우는 동안 `ApplyPatternHit`은 판정 요청 한 번으로 다루고, 명중·피해의 실패 정책을 검토할 때 그 내부로 들어간다. 원본에서 찾은 구현과 요구사항에서 기대한 동작을 각각 적어 비교한다.

변수는 다음 다섯 종류로 나눠 본다. 저장 위치만으로 의미를 단정하지 않는다.

- 정의: 같은 규칙을 여러 실행에서 재사용하는 값.
- 실행 상태: 같은 입력이라도 과거 처리 이력에 따라 결과를 다르게 만드는 값.
- 입력: 호출자가 이번 판단에 제공한 값.
- 파생 값: 정의·입력·상태에서 다시 계산할 수 있는 값.
- 캐시·실행 시점 복사본: 중복처럼 보여도 비용·수명·정의 revision을 고정하려고 보관할 수 있는 값. 실제 이유는 소비자와 갱신 경로로 확인한다.

비평은 “길다”, “AI가 썼다”, “다른 변수에서도 구할 수 있다”에서 바로 삭제로 넘어가지 않는다. 먼저 어떤 입력에서 요구사항을 깨는지, 누가 상태를 변경하는지, 수명과 초기화·실패 경로가 무엇인지 확인한다. 그 다음 동일한 계약을 더 적은 상태와 의존성으로 유지할 수 있는지 비교한다. 삭제를 제안할 때에는 그 값이 구분하던 두 실행 이력을 대체 표현으로 여전히 구분할 수 있는지 확인한다. 중복 캐시라면 무효화 주체와 원본과의 일치 조건도 확인한다.

함수는 직접 호출자 → 입력과 사전조건 → 읽고 바꾸는 상태 → 결과와 부작용 → 실패 시 보존 상태 순으로 읽는다. 한 번에 너무 많은 책임을 갖는다는 지적은 서로 다른 변경 이유, 별도 검증 필요, 불필요한 의존 등 구체적인 비용으로 설명한다. 작은 함수가 많다는 사실만으로 좋은 설계라고 판단하지 않는다.

숙련된 판단을 연습할 때에는 정상 경로뿐 아니라 변경 영향, 중복 호출·취소·재진입, 데이터 불일치와 실패 후 상태, 관측 근거를 함께 본다. 기존 여덟 단계에 이 질문을 연결하며 새 채점 체계는 만들지 않는다. 답이 막히면 예제를 먼저 함께 풀고, 다른 입력이나 작은 조건 변경을 사용자가 예측한다.

## 검증 스크립트를 읽는 기준

2026-10-12 사용자는 Python으로 검증하는 절차, 현업의 사용 여부와 에이전트가 요구사항을 확인하는 방법을 질문했다. `.py`라는 확장자보다 무엇을 실행하고 어떤 결과를 비교하는지부터 설명한다. Python 문법 전체를 먼저 배우는 것을 C++ 프로젝트 이해의 선행 조건으로 만들지 않는다.

| 구분 | 이 프로젝트의 예 | 확인하는 범위 |
|---|---|---|
| 제품 데이터 검증기 | `Tools/KoukuSaydonPipeline/combat_hit_templates.py` | 저작 공격 정의를 검사하고 기본값을 채운 복사본을 만든다. Server 공격 실행은 하지 않는다. |
| 검증기를 시험하는 코드 | 같은 폴더의 `test_combat_hit_templates.py` | 정해 둔 입력에 Python 함수가 예상 결과·예외를 내는지 확인한다. C++ 구현과의 일치나 실제 피해까지 보장하지 않는다. |
| 실행을 묶는 도구 | `Tools/Build/Invoke-BuildAndRegression.ps1` | 선택 profile에 따른 빌드·검사 명령을 실행하고 결과를 기록한다. Python만 가능한 역할은 아니다. |
| 소스 문구 검사 | `Tools/EffectToolV2/test_effect_resource_catalog_facade_contract.py` | 특정 선언·문구의 존재를 확인한다. 줄바꿈까지 일치시키는 검사는 포맷 변경에도 깨질 수 있으며 게임 동작의 증거로 쓰지 않는다. |

첫 예제는 `test_owner_lifetime_rejects_repeat_tail`이다. 시작 100ms, 간격 100ms, 횟수 3이면 마지막 예정 시각은 300ms다. 수명 299ms인 정의를 거부해야 한다는 기대를 먼저 정하고, `validate_hits(..., 299)`가 `ValueError`를 내는지 확인한다. 예외를 기대한 테스트에서는 올바른 거부가 PASS다. 여기서 확인한 계약을 “서버가 세 번 공격했다”로 확대하지 않는다.

에이전트도 요구사항 → 관찰할 결과 → 실제 호출 경로 → 정상·경계·실패 입력 → 관련 검사 실행 → 예상과 실제 비교 → 부족한 검증 기록의 순서를 따른다. 새 기능·버그 수정은 가능한 경우 변경 전 실패와 변경 후 성공을 확인한다. 기대값을 구현의 결과에서 그대로 복사하지 않는다. 리팩터링의 전후 비교는 조사한 입력에서 동작 보존을 보여 주지만 기존 동작의 정당성까지 증명하지 않는다. 다른 에이전트의 코드 검토도 실행 검증을 대체하지 않는다.

학습할 때는 테스트 하나에서 세 가지만 찾는다. **무슨 입력인가, 기대 결과는 무엇인가, 실제 어느 코드를 실행했는가.** 그다음 일부러 한 조건을 바꿨을 때 실패하는 이유를 추적한다. 검사 개수나 PASS 문구보다 요구사항에 대한 검출 능력을 본다. 보고에는 실제 명령·대상·결과와 미확인 범위를 남긴다.

현업 사례로 LLVM은 Python 패키지인 lit를 사용해 컴파일러 테스트를 실행하고 결과를 모은다([공식 안내](https://llvm.org/docs/TestSuiteGuide.html)). Codex 공식 안내도 필요한 테스트 작성·실행, 결과 확인과 diff 검토를 별개 활동으로 설명한다([공식 안내](https://learn.chatgpt.com/guides/best-practices#improve-reliability-with-testing-and-review)). 모든 회사가 같은 언어나 검사 구성을 사용한다는 뜻은 아니다.

## 기술소개서의 다섯 칸

1. **문제와 제약**: 무엇이 필요하며 어떤 상황을 허용하면 안 되는가.
2. **직접적인 해법과 한계**: 가장 단순한 방법은 무엇이며 어떤 구체적인 입력에서 제한이 생기는가. 충분한 해법이라면 억지로 실패시키지 않는다.
3. **현재 메커니즘**: 실제 자료구조, 변수, 함수와 파일 호출 흐름은 무엇인가.
4. **대안과 대조**: 가능한 다른 방법과 선택 기준은 무엇인가. UE 비교는 같은 문제와 계약을 확인할 수 있을 때만 붙인다.
5. **얻은 것과 지불한 비용**: 어떤 요구를 만족했으며 어떤 복잡성·메모리·지연·유지 비용이 생겼는가. 어떤 조건에서 재검토해야 하는가.

여덟 단계는 설계와 구현을 진행하는 질문이다. 다섯 칸은 확인한 내용을 전달하는 설명 형식이다. 3-B의 정의·원리·예시·프로젝트 연결은 부족한 개념을 배우는 보조 방식이다. 세 양식을 동시에 통과하는 시험으로 만들지 않는다.

기술소개서에는 현재 구현 사실, 코드로부터 추론한 설계 이유, 실제 당시 결정 기록, 사용자의 확인된 기여를 구분한다. “현재 구조를 이렇게 이해했고 작은 구현과 변경으로 검증했다”는 설명도 유효하다. 이를 “처음부터 내가 설계했다”로 바꾸지 않는다.

## 지원 준비와 프로젝트 선택

다음 대형 프로젝트나 자체 엔진 출시를 지원의 선행 조건으로 삼지 않는다. 출시와 제품 완성 경험은 Liberation에서 이미 설명할 수 있는 자산이며, C++ 구현·진단 능력은 별도의 구체적인 작업으로 확인한다. LostArk 이후 새 제작을 할지는 독립적인 제품 목표와 지원 직무에 따라 정한다. 시간을 투자하면 출시가 보장된다고 가정하지 않는다.

전체 프로젝트는 계층의 책임과 연결을 파악하고, 이력서에서 핵심으로 주장할 기능은 직접 설명·수정·검증할 수 있게 깊이를 더한다. 라이브러리 내부 전체의 암기나 카테고리 트리 완주를 요구하지 않는다. 지원 직무가 정해지면 클라이언트·게임플레이, 엔진·렌더링, 서버 가운데 해당 요구에 맞춰 사례를 고른다. 처음에는 대표 사례 2~3개로 범위를 좁힐 수 있지만 이 개수는 채용 통과 기준이 아니다.

| 기존 자산 | 지원 자료에서 확인할 경험 |
|---|---|
| Liberation | 끝까지 완성·배포한 과정, 제품 범위와 난이도 판단, 사용자 관점에서 얻은 교훈. Blueprint 경험을 낮추거나 C++ 경험으로 바꾸지 않는다. |
| StarCraft·Minecraft Dungeons | 사용자가 직접 읽고 검수했던 구현·협업 사례. 남길 기술 주장은 해당 소스와 다시 대조한다. |
| LostArk | 현재 보스 데이터와 실행 흐름부터 요구사항·상태·소유권·실패 처리를 직접 확인한다. ImGui 편집과 품질·데이터 관리 기여는 구체적인 변경과 검증으로 설명한다. |
| Winters Engine·NYPC | 지원 직무에 맞고 현재 설명 가능한 사례를 골라 보강한다. 전 기능 재학습을 지원 착수 조건으로 만들지 않는다. |

대표 사례의 진행은 기존 여덟 단계를 따른다. 요구사항 한 개를 고르고 실제 입력→소비자를 추적한 뒤, 필요한 상태를 적고 작은 구현을 작성한다. 그 다음 조건 변경이나 실패 입력을 처리하고 제품 코드의 추가 제약을 대조한다. 실제 제품의 변경은 확인된 필요가 있을 때만 수행하며 학습 실적을 만들려고 정상 코드를 억지로 리팩터링하지 않는다.

지원 자료에는 역할·행동·확인한 결과를 쓴다. 기술소개서는 문제·직접 해법·현재 구조·대안·비용을 설명하고, 자기소개서는 실제 판단·피드백·후속 행동의 사례를 사용한다. 과거 선택 이유가 기록되지 않았다면 현재의 구조 분석으로 표시한다. 대안을 비교하는 목적은 현재 구조가 유일한 정답이었다고 증명하는 것이 아니라 적용 조건과 비용을 밝히는 것이다.

준비 상태는 대표 기능에서 설명, 필요한 파일 탐색, 작은 구현 또는 수정, 실패 원인 좁히기를 실제로 할 수 있는지로 살핀다. 도움받은 부분과 독립 수행 범위도 함께 남긴다. 모든 항목의 완벽한 통과나 주관적인 불안 소멸을 지원 조건으로 삼지 않으며, 사실에 맞는 제출본을 만들면서 지원과 학습을 병행한다. 코딩 테스트는 요구되는 지원처에 맞춰 별도로 준비하되, 프로젝트에서 배운 상태·불변식·복잡도 질문을 재사용한다.

[Interview의 초안 작성 방향](../../../Interview/기술소개서/2026-10-10_기술소개서_작성과_이해학습_방향.md)대로 현재 아는 범위의 전체 초안은 계속 쓴다. 깊은 학습은 기능 하나씩 진행한다. 조사 자료의 분량이나 PPT 완성도는 사용자의 이해·독립 구현·과거 기여를 대신하지 않는다. 기존 이력서의 성능 수치·네트워크 방식·담당 범위는 현재 증거와 맞는 주장만 제출본에 남긴다.

## AI와 사용자의 역할

### 실제 코드 정비 요청의 범위

2026-10-11 사용자는 기술소개서 설명만 고치는 것이 아니라 **실제 함수와 제어 흐름을 읽기 쉽게 정리하고 한국어 설명 주석을 추가**하도록 요청했다. 범위는 LostArk 솔루션 전체(Engine·Client·Server·Shared·자체 제작 도구)이며, 이후 Winters Engine·LoL도 명시적으로 포함했다. NYPC·Minecraft·Starcraft까지 수정하라는 뜻으로 확대하지 않는다. 이 요청에서는 아래의 사용자 직접 구현 연습을 착수 조건으로 두지 않고 AI가 실제 코드를 수정·검증한다.

정비는 동작과 공개 계약을 유지하면서 책임별 함수 구분, 압축된 제어문 전개, 상태·소유권·실패 흐름의 설명을 중심으로 한다. 식별자를 번역하는 줄별 주석이나 전체 formatter 적용만으로 완료를 선언하지 않는다. 외부 라이브러리와 생성·배포 사본을 직접 수정하지 않고, 인코딩과 동시 작업을 보존한다. 전체 대상과 실제 검토·수정·검증 완료 범위는 [코드 정비 RESULT](10-11/2026-10-11_CODE_READABILITY_RESULT.md)에 구분한다. PPT 원고 작업은 이 요청에 따라 중단했다.

2026-10-12 추가 요청: **사용자가 이전에 적은 한글 주석·질문·메모는 원문 그대로 유지하고 바로 아래에 보충 설명을 붙인다.** 틀리거나 오래된 설명도 임의로 지우거나 고쳐 쓰지 않는다. 현재 구현과의 차이, 용어 교정과 답변은 아래의 별도 설명에서 구분한다. 이미 정비한 파일에도 이 원칙을 소급 적용하며 작업 전 보존본과 대조한다. 저자를 구분할 근거가 없는 기존 한글 주석도 보존 대상으로 취급한다.

2026-10-12 렌더링 학습 보강 요청: PBR·BRDF·Fresnel·IBL·SH와 개별 이펙트의 셰이더 수식·family 선택을 실제 소스 주석으로 연결한다. 수식마다 입력 변수의 의미·단위·좌표계, 계산 순서, 결과를 소비하는 다음 함수를 설명한다. Fresnel은 입사각에 따른 반사율이며 환경 영상 자체를 선택·샘플링하는 경로와 구분한다. 표준 모델의 근사, 원본 cooked program의 번역, 프로젝트의 입력 보정도 같은 구현이라고 섞지 않는다. effect/element 데이터 → carrier → family/permutation descriptor → 상수·texture 바인딩 → shader → 합성 순서를 실제 파일로 확인하고, 각 원본 파일과 생성·배포 사본을 구분한다. roughness·F0·시선 방향·blend 조건을 바꿨을 때 어느 항과 결과가 달라질지 질문으로 남겨 기술소개서의 문제·현재 구조·대안·비용 설명에 활용한다. 실제 구현 사실과 추론한 설계 이유를 구분하고, 팀장 렌더링 옵션이나 현재 효과 품질은 이 설명 작업으로 바꾸지 않는다.

AI는 실제 코드와 자료를 조사하고, 필요한 개념·예제를 설명하고, 사용자 답에서 근거가 빠진 한 지점을 짚는다. 힌트는 질문 → 관찰 → 손추적 → 의사코드 → 부분 코드 순서로 구체화할 수 있다. 동일한 질문만 되풀이하며 설명을 막지 않는다. 사용자 원문은 보존하고 보완 내용을 별도로 적는다.

사용자는 다음 상태 예측, 작은 코드 작성, 조건 변경, 실패 진단을 직접 시도한다. 막힌 위치를 아직 특정하지 못하면 “어디서부터 모르겠다”라고 해도 된다. 그 경우 작은 입력 하나로 함께 범위를 좁힌다.

코드 설명에는 소유자·수명·직접 호출자·입력·출력·변경 상태·실패 처리를 필요한 만큼 포함한다. C++ 구현 PLAN을 만들 때의 전체 코드와 등록 규칙은 [local.md](local.md)를 따른다. 이 학습 기준을 이유로 제품 코드와 런타임을 자동 변경하지 않는다.

다음 세션은 이 문서와 대상 기능의 최신 기록을 읽고 마지막 미완료 질문 한 개에서 이어간다. 배경 재설명이나 전체 학습 체계 재작성을 사용자에게 요구하지 않는다. 새 코드 사실은 현재 파일로 다시 확인한다.

## 2026년 10월 12일 기능의 선택 이유를 따라가는 학습 합의

사용자는 전체 프로젝트와 발탄·쿠크 구조도를 이미 작성한 뒤, 다른 도메인에 같은 그림을 반복하는 것보다 실제 구현의 선택 이유를 이해하는 방향으로 전환했다. 프로파일러처럼 해결 문제가 다른 기능에도 동일한 설명 틀을 억지로 적용하지 않는다. 구조도는 필요한 연결을 찾는 지도로 사용하고, 앞으로의 시작점은 실제 기능 하나와 그 기능을 만드는 파일·상태·연산이다.

새 프로젝트나 출시작의 수를 늘리거나 상용 엔진 에셋 구매로 포트폴리오를 늘리는 일을 현재 준비의 선행 조건으로 두지 않는다. LostArk, NYPC, Winters Engine, Minecraft Dungeons, StarCraft에서 만든 기능을 설명·수정·검증하는 경험을 기술소개서와 자막 영상으로 옮기고 서류 제출과 병행한다. CS·C++·그래픽스·렌더링·수학·물리는 해당 구현을 이해하는 데 필요한 지점에서 연결한다. 모든 이론과 프로젝트를 완전히 정복한 뒤에만 지원할 수 있다는 조건은 만들지 않는다.

### 목표에서 구현으로 내려가는 사고 순서

사용자의 추가 요청은 “이미 만든 자료구조를 왜 썼는지 설명하는 것”보다 앞선 판단을 포함한다. **기능 목표가 왜 필요한지, 정말 필요한지부터 판단한 뒤 필요한 정보와 연산을 도출한다.** 기존 코드에서 컨테이너를 먼저 찾고 그 선택을 정당화하는 순서로 고정하지 않는다.

1. **목표의 필요성:** 누가 어떤 상황에서 무엇을 할 수 있어야 하는가? 없으면 어떤 문제가 생기는가? 범위를 줄이거나 기능을 두지 않는 대안도 검토한다.
2. **관찰 가능한 성공과 실패:** 정상 예 하나와 잘못되면 안 되는 예 하나를 정한다. 내부 클래스 이름 대신 사용자가 보게 되는 동작으로 쓴다.
3. **필요한 정보:** 그 판단을 지금 하기 위해 무엇을 알아야 하는가? 계속 기억할 정보와 기존 값에서 계산할 정보를 구분한다. 같은 시각·다른 이력처럼 결과가 달라야 하는 두 상황을 구별할 수 있는지 확인한다.
4. **정보에 가할 연산:** 누가 생성하고, 무엇으로 찾고, 어떤 순서로 순회하며, 무엇을 언제 수정·삭제하는가? 정렬·중복·실패 시 보존·복원 요구가 있는가?
5. **소유와 제약:** 여러 실행이 공유하는 규칙과 실행별 이력을 나누고 수명·스레드·수량·호출 빈도·메모리·수정 빈도를 확인한다.
6. **구조와 책임:** 이 요구에 맞춰 자료구조 후보를 비교하고 선택한다. 그 상태와 연산의 책임을 함수·매개변수·클래스·인터페이스·H/CPP·include·Data 폴더와 저장 형식으로 배치한다.
7. **현재 코드와 검증:** 실제 구현이 이 요구를 어떻게 충족하는지 대조하고, 빠진 조건·불필요한 상태·대안의 비용을 살핀다. 성능 우위는 실제 조건에서 측정하고 결과를 기술소개서에 반영한다.

이 순서는 기존 코드를 보지 말라는 뜻이 아니다. 필요와 성공조건을 짧게 가정한 뒤 바로 코드·데이터·사용 장면에 대조한다. 실제 코드 사실, 이번에 재구성한 설계 근거, 과거 개발 당시의 판단은 구분한다. `H/CPP를 나누었으니 좋다`, `unordered_map이니까 빠르다` 같은 표현으로 결론을 대신하지 않는다.

보스 패턴의 첫 질문은 “이미 있는 map의 의미” 앞에 **“각 보스의 공격 기회를 중복 처리하지 않으려면 무엇을 기억해야 하는가”**를 둔다. 여기서 필요한 정보와 연산을 먼저 생각한 뒤 BP01의 실제 정의·실행 상태·조회 함수와 비교한다. 파일이 아니라 작은 동작 하나를 학습의 단위로 삼는다.

### 실제 파일을 읽는 단위

한 회차에는 기능 하나와 핵심 함수 한두 개를 먼저 잡는다. 파일 전체 또는 모든 문법을 한꺼번에 외우도록 요구하지 않는다. 사용자가 이해하지 못한 문법은 짧은 예제와 실제 사용처로 먼저 설명하고, 그 뒤 상태 예측·조건 변경 질문을 한 개씩 제시한다. 시간 제한 면접 형식은 이후 재방어에 사용하며 새 개념 설명을 막는 관문이 아니다.

- **파일과 의존 관계:** 실제 진입점, main/Client app/Server app, 직접 호출자와 결과 소비자를 연결한다. H의 선언과 CPP의 정의, include와 전방 선언이 각각 어디서 필요한지 확인한다. Client 루프가 별도 Server 실행 파일의 함수를 직접 호출하는 것처럼 그리지 않는다.
- **자료구조와 상태:** 무엇을 식별·검색·순회·수정하는지, 값의 소유자와 수명, 공유 정의와 개별 실행 상태, 포인터·참조의 유효 기간을 먼저 정한다. 컨테이너 이름만 설명하지 않는다.
- **함수와 문법:** 입력·출력·실패·상태 변경에 맞춰 매개변수의 값/참조/포인터, const, string/string_view, namespace, inline/constexpr, virtual/override/interface의 의미를 설명한다. `const char* const*`처럼 순수 문법이 막힌 경우에도 실제 용례를 찾아 단계별로 읽는다.
- **Data와 HLSL:** 원본·게시 파일·메모리 표현의 차이, 필드와 ID가 실제 소비자로 이어지는 이유를 살핀다. 셰이더는 입력·단위·좌표계·수식·출력·합성 소비자까지 연결한다. 해당 기능에 없는 JSON·shader를 형식상 끼워 넣지 않는다.
- **선택과 대안:** 현재 코드의 사실, 현재 구조로 설명 가능한 장단점, 당시 개발자의 선택 이유, 실측 성능을 구분한다. 역사적 결정 근거가 없으면 “이렇게 선택할 수밖에 없었다”라고 꾸미지 않는다.

“가장 효율적인 자료구조”는 검색만 빠른 구조를 뜻하지 않는다. 실제 데이터 수, 조회·순회·수정 빈도, 메모리와 할당, 캐시 접근, 구현과 유지 비용, 실패 복구를 함께 비교한다. Big-O와 측정 결과는 다른 근거다. OOP와 DOD도 프로젝트 전체에 하나만 붙일 분류로 쓰지 않고, 객체 책임·다형성·메모리 배치·일괄 순회가 현재 문제에서 어떻게 조합되는지 확인한다. 구조가 현재 코드에 있다는 이유로 정답이나 최적해로 전제하지 않는다.

## 2026년 10월 12일 A00 — 프로젝트 구조의 필요성에서 시작
