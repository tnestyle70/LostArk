# 루트 모션과 애니메이션 로딩 — 조사 메모

작성자: JS · 2026-08-03

루트 모션을 한 번 구현했다가 전부 걷어냈다. 코드는 남기지 않았지만 그 과정에서 잰
값들은 다시 시도할 때 그대로 쓸 수 있어서 따로 남긴다. **구현 결과 문서가 아니라
참고용 실측 메모다.**

같이 진행한 클립 간 보간은 `60919cb`로 커밋됐고 이 문서와 무관하게 살아 있다.

## 1. 리그 계층 — 여기서 틀렸다

`b_root`가 스켈레톤 최상위일 거라 가정했는데 아니다.

```text
[0] RootNode  parent=-1  scale=(1, 1, 1)        <- PreTransform은 여기에만 곱해진다
[1] flm       parent=0   scale=(100, 100, 100)  <- 아마추어 노드에 x100
[2] b_root    parent=1   scale=(1, 1, 1)        <- 루트 모션 본
[3] b_effectworldzero  parent=2
[4] bip001    parent=2
```

`CBone::Update_CombinedTransformationMatrix`는 `PreTransformMatrix`를
**`m_iParentBoneIndex == -1`인 본에만** 곱한다. 따라서 `b_root`의 로컬 이동을 모델
공간으로 옮기려면 `PreTransform`이 아니라 **부모의 combined**를 태워야 한다.

```text
올바름:  350 x 100 x 0.0001 = 3.5 유닛      (캐릭터 키 1.15의 약 3배)
틀림:    350 x       0.0001 = 0.035 유닛    <- x100이 빠져 100배 작았다
```

메시가 `115 x 100 x 0.0001 = 1.15` 유닛으로 그려지는 것과, `CHARACTER_DESC`의
`fSpeedPerSec = 6`이 걸린 세계 크기와 앞뒤가 맞는다.

`Get_ParentBoneIndex()`로 부모를 잡고 그 combined를 쓰면 리그 구조가 달라도 맞는다.
다만 그 값은 지난 프레임 것이다 — `Update_CombinedTransformationMatrix`가
`Play_Animation` 맨 끝에서 돌기 때문이다. 이 위쪽 본들은 애니메이션되지 않아서 실제로
문제가 되진 않았다.

## 2. 회전 델타는 뽑을 필요가 없다

네 클래스 **731개 클립 전부**에서 `b_root`의 쿼터니언이 클립 내내 상수다.

```text
flm_sk_moving_normal_1  b_root
  rotation  t=0   (-0.000000, -0.000000, +0.707107, +0.707107)
            t=27  (-0.000000, -0.000000, +0.707107, +0.707107)   전부 동일
  position  t=0   (0, 0, 0)
            t=27  (+350.00, 0, 0)                                이동만 변한다
```

`(0, 0, 0.707107, 0.707107)`은 **Z축 +90°**이고 스켈레톤 전체의 기준 방향이다.

- 측정 시 나온 `0.03°`는 float32 정규화 오차다. `0.707107^2 x 2 = 0.99999988`이라
  `acos`가 0이 아닌 값을 돌려준다. 실제 키 값은 비트 단위로 같다.
- 몸이 도는 회전(최대 178°)은 자식인 `bip001`의 포즈다. **트랜스폼으로 빼내면 안 된다.**
- **본을 identity로 되돌리면 그 상수 90°가 날아가 캐릭터가 통째로 돈다.** 이동만 0으로
  지우고 회전·스케일은 손대지 말아야 한다. 이동도 0이 아니라 그 클립의 기준값으로
  되돌리는 편이 안전하다(리그마다 루트 바인드가 원점이 아닐 수 있다).

이전 개인 프로젝트(`161기/3D/Framework`)는 회전 델타까지 다뤄서
`m_vClipBaseRotation` 캐시와 `Clear_Y_Rotation`이 필요했는데, 이 데이터에서는 그 절반이
통째로 빠진다.

## 3. 기준점을 다시 잡아야 하는 조건

트랙 위치만 보면 클립 교체를 놓친다.

```text
27틱짜리 돌진이 끝나고 트랙이 30에 있던 idle로 넘어가면 30 > 27이라
"되감김" 검사를 통과하고, 서로 다른 두 클립의 루트 위치를 빼서
0 - 350 = -350, 즉 왔던 만큼 정확히 되돌아간다.
```

세 가지를 전부 봐야 한다.

1. 아직 기준을 안 잡음
2. **클립 인덱스가 바뀜**
3. 같은 클립이 되감김 (루프 또는 `Set_AnimTrackPosition`)

## 4. 호출 순서

`Play_Animation`을 부르는 건 `CCharacter`가 아니라 `CPart_Body::Update`이고, 그건
`CCharacter::Update` 안의 `__super::Update()` 시점이다. 캐릭터가 델타를 쓰려면 그
뒤여야 한다. 델타 추출 자체는 **블렌드보다 먼저** 해야 한다 — 나중에 하면 스냅샷과 새
포즈가 섞인 이동에서 델타를 재게 되어 전환 구간 이동량이 블렌드 비율만큼 깎인다.

## 5. 루트 이동이 있는 클립

| 클래스 | 클립 | `b_root` 이동 있음 | 최대 회전각 |
|---|---:|---:|---:|
| LanceMaster | 223 | 181 | 0.03° |
| GunSlinger | 187 | 137 | 0.03° |
| Artist | 99 | 73 | 0.03° |
| Slayer | 208 | 176 | 0.03° |

`run`과 `idle`은 `b_root` 델타가 0이다. **로코모션은 지금처럼 `CNavPathFollower`가 끌면
되고, 루트 모션이 필요한 건 돌진·이동기 계열 스킬이다.** 화이트리스트가 필요 없다 —
데이터가 알아서 갈린다.

## 6. 남은 설계 문제

- **내비게이션 우회.** 루트 모션은 트랜스폼을 직접 밀기 때문에 돌진으로 내비메시 밖이나
  벽 너머로 나갈 수 있다.
- **서버 권위.** 프레임워크 담당의 G3가 `C2S_MOVE -> GameRoom 권위 위치 ->
  S2C_WORLD_SNAPSHOT`이다. 클라이언트 루트 모션이 위치를 바꾸면 그 권위와 싸운다.
  돌진을 예측/확정으로 나누는 계약이 먼저 서야 한다.

## 7. TEST_LEVEL2 로딩이 느린 이유

Assimp가 아니다. `.wmodel`은 `CModel::Ready_BinaryModel`로 가고, Loader에서 `.fbx`를
읽는 곳은 `Ready_For_Level_GamePlay()` 하나뿐이라 이 레벨은 안 지난다.

원인은 용량이다.

| 모델 | 크기 |
|---|---:|
| **LanceMaster (바디)** | **108.5 MB** |
| Npc_Forman | 26 MB |
| Npc_Aylara | 24 MB |
| Npc_Schmidt / Npc_Beda | 2.8 / 1.8 MB |
| 장비 5 + 창 2 | 합쳐서 1.5 MB |
| 합계 | 약 165 MB |

그리고 그 108.5 MB의 내역이 이렇다.

```text
파일 108.5 MB, 섹션 226개 (애니메이션 223개)
  ANIMATION   107.6 MB  (99.2%)
  MESH          0.8 MB  (0.7%)
  SKELETON      0.1 MB  (0.1%)
  MATERIAL      0.0 MB  (0.0%)
```

### 상수 채널을 접으면 55%가 사라진다

```text
채널 49,506개 (클립당 평균 222개 = 224본 거의 전부)

kind    키 수        상수 채널        접으면 제거
pos     2,132,088    4,192  ( 8%)    1.9 MB / 32.5 MB
rot     2,132,088    30,827 (62%)   24.3 MB / 40.7 MB
scale   2,132,088    49,506 (100%)  31.8 MB / 32.5 MB
                                    ─────────────────
                                    58.0 MB / 105.7 MB (55%)
```

**스케일 채널은 100%가 상수다.** 213만 개 키가 전부 같은 값인데 32.5 MB를 차지한다.
회전도 62%가 상수다. 위치만 실제 데이터다.

`CChannel`은 이미 키가 1개인 채널을 처리한다(`1 == m_KeyFrames.size()` 분기). 따라서
쿠커가 상수 채널을 키 1개로 접어 굽기만 하면 런타임은 그대로 두고 파일이 절반이 된다.

대안으로 검토한 것들:

- **안 쓰는 클립 제외** — 나중에 스킬 선택 기능을 넣을 계획이라 전부 필요한 리소스다.
  기각.
- **Clone 시 애니메이션 공유** — 메모리는 N배에서 1배가 되지만 **로딩은 거의 안 줄어든다.**
  프로토타입 디코드는 어차피 한 번이다. `CModel::Clone`이 지금은
  `Prototype.m_Animations`를 인스턴스마다 `Clone()`한다.

## 8. 측정 스크립트

`buildScript/`에 옮겨뒀다. 전부 `.wmodel`을 직접 파싱하고 엔진을 띄우지 않는다.

| 스크립트 | 용도 |
|---|---|
| `wmodel_rootmotion.py <wmodel> [클립필터]` | 클립별 루트 본 이동 범위와 회전각 |
| `dump_rootkeys.py <wmodel> <클립>` | 한 클립의 `b_root` 원본 키 값 |
| `dump_skelrest.py <wmodel>` | 스켈레톤 상위 본들의 rest 스케일·부모 |
| `wmodel_keystats.py <wmodel>` | 키 통계와 상수 채널 비율 |
| `wmodel_clips.py <wmodel>...` | 클립 이름 목록 |
| `dump_wmodel_uv.py <wmodel>` | 서브메시별 정점 bbox와 UV |

`SUBMESH_DESC`와 `ANIMATION_CHANNEL`의 오프셋 규약은 파싱할 때 매번 걸린다.

- `vertexOffset` / `indexOffset`은 **바이트 오프셋**이고 인덱스는 **서브메시 로컬**이다
  (`WMeshReader.cpp`).
- `positionOffset` 등은 **채널 테이블 뒤에서 시작하는 키 블록** 기준이다
  (`WAnimationReader.cpp`의 `ReadVectorKeys(pKeyBlock, ...)`).
