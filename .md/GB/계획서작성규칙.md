# LostArk 계획서 작성 규칙

계획서는 설명문보다 **구현자가 그대로 반영할 수 있는 전체 코드 명세**가 중심이다.
기존 심볼은 저장소의 실제 이름을 그대로 사용하고, 새 심볼은 현재 LostArk C++ 스타일을 따른다.

## 0. 저장 위치

- 기본 경로: `.md/GB/<MM-DD>/YYYY-MM-DD_<TOPIC>_PLAN.md`
- 구현 결과: 같은 폴더와 주제명의 `_RESULT.md`
- 같은 작업의 계획서가 있으면 새 문서를 만들지 않고 갱신한다.

## 1. C1~C8 관점

계획 첫 부분에 아래 여덟 관점을 짧게 적고, 이번 작업에서 중요한 축 1~3개를 표시한다.

```text
C1 기준계          좌표, 단위, ID, 포맷 사이의 변환
C2 이동>계산       오프라인에서 만들 값과 런타임에서 계산할 값
C3 공유는 비싸다   공유 소유권, 중복 데이터, 동기화 비용
C4 수명은 선언된다 Prototype, Clone, Level, Layer, 파일의 수명
C5 이산화와 오차   피킹, 좌표, 스케일, 직렬화 정밀도
C6 가지치기        검증, 검색, 필터링, 불필요한 처리 제거
C7 권위와 정합성   Catalog, Scene 파일, Runtime 중 정본의 위치
C8 검증이 병목     빌드, 실행, 저장/재로드, 협업 회귀 검증
```

## 2. 문제 해결 ①~⑤

전체 15줄 안에서 다음 다섯 항목만 쓴다.

```text
① 문제·제약: 현재 증상과 반드시 지켜야 할 조건.
② 단순 해법의 문제: 가장 쉬운 접근이 실제로 깨지는 이유.
③ 해결 방식: 이번에 채택할 구조와 데이터 흐름.
④ 비교: 수업 코드, Winters Engine 또는 기존 LostArk 방식과 차이.
⑤ 대가: 늘어나는 코드·메모리·복잡도와 이 선택을 다시 볼 조건.
```

## 3. 자료구조·알고리즘 핵심

기능에 실제로 쓰이는 것만 적는다. 아래 asset/catalog/placement 예시는 MapTool·데이터 authoring 작업에
적용되는 경우에만 사용하며, Character Select·network·UI처럼 무관한 계획에 억지로 채우지 않는다.

```text
정의 데이터: 생성 가능한 에셋, 안정적인 asset ID, Catalog 소유권.
인스턴스 데이터: placement ID, kind, Transform, visible, Scene 파일 소유권.
런타임 객체: Prototype -> Clone -> Layer 등록과 shared_ptr 보유 위치.
불변식: ID 중복 금지, Catalog/Scene kind 일치, 유한 Transform, 양수 scale.
생성 알고리즘: Palette 선택 -> Picking -> record 생성 -> Clone -> Layer 등록.
저장 알고리즘: Runtime 조회 -> 검증 -> 임시 파일 기록 -> 원자적 교체.
로드 알고리즘: parse -> validate -> 임시 Clone -> 전부 성공 시 교체, 실패 시 rollback.
복잡도: A=asset 수, P=placement 수 기준 검색·화면·저장·로드 비용.
```

## 4. 파일 목록

물리 경로 기준으로 표를 만든다.

```text
| 구분 | 절대 경로 | 역할 |
|---|---|---|
| 추가 | C:/Users/user/Desktop/LostArk/Client/Public/NewFile.h | 신규 자료형 선언 |
| 수정 | C:/Users/user/Desktop/LostArk/Client/Private/Existing.cpp | 생성 흐름 연결 |
| 삭제 | C:/Users/user/Desktop/LostArk/Client/Private/OldFile.cpp | 중복 경로 제거 |
```

## 5. 파일별 전체 구현 코드

이 부분이 계획서의 본문이다.

- 새 파일: 파일 처음부터 끝까지 전체 코드를 싣는다.
- 기존 파일: 바뀌는 include, 선언, 구조체, 함수는 각각 **교체 가능한 완전한 블록**으로 싣는다.
- 함수 일부만 `...`로 생략하지 않는다. 함수가 바뀌면 함수 전체를 쓴다.
- 데이터 파일이 바뀌면 새 헤더, 행 형식, 실제 추가·변경 행을 모두 쓴다.
- 의사 코드만 적고 실제 C++ 구현을 빼지 않는다.
- 삭제할 코드는 정확한 기존 블록을 싣고 삭제 후 남을 호출 흐름을 보여준다.

각 파일은 다음 형식을 사용한다.

```text
### 5-N. C:/Users/user/Desktop/LostArk/Client/Private/Example.cpp

변경 종류: 추가 | 전체 교체 | 함수 교체 | 삭제
적용 위치: 실제 include, 선언 또는 함수 이름
```

그 아래에 `cpp`, `xml`, `text`, `powershell` fenced code block을 사용한다.

## 6. 프로젝트 등록

새 C++ 파일이 있으면 다음을 반드시 포함한다.

- `Client.vcxproj` 또는 `Engine.vcxproj`에 넣을 정확한 `<ClInclude>`/`<ClCompile>` 항목
- 대응 `.vcxproj.filters`의 정확한 항목과 Filter 경로
- 새 Filter가 필요할 때만 `<Filter Include>`와 새 GUID
- 데이터·셰이더 파일은 `<None>`/`<FxCompile>` 등록 코드

## 7. 적용 순서와 검증

마지막에는 짧게 다음만 적는다.

1. 파일 추가·교체 순서
2. 복사해서 실행할 수 있는 빌드 명령
3. 레벨과 단축키를 포함한 실행 절차
4. 성공 시 보이는 객체·로그·저장 파일
5. 실패 입력에서 기존 Scene이 유지되는지 확인하는 방법

계획서 안에 미완성 표식이나 코드 생략 사유를 남기지 않는다. 필요한 사실은 작성 전에 조사하고, 사용자 선택 없이는 확정할 수 없는 내용만 먼저 질문한다.
