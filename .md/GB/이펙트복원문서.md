## 1. 이번에는 왜 됐는가

### 1.1 한 문장 결론

맞다. 이번 복원의 핵심 전환점은 **기존 중앙 ShaderCache가 아니라 공식 동일 배포 cohort에 보존된
RefShaderCache를 새로 확보하고, 원본 active MIC의 `FStaticParameterSet`를 그 캐시의
`FMaterialShaderMap`에 구조적으로 연결한 것**이다.

하지만 `새 ShaderCache를 찾았다` 한 가지로 끝난 것은 아니다. 실제 성공 사슬은 다음 세 축이 모두
연결되었기 때문에 성립했다.

```text
올바른 cache 획득
  + 올바른 FStaticParameterSet identity/equality
  + 원본 shader object·DXBC·uniform/register replay
  = 감으로 만든 material HLSL을 원본 실행식 기반 HLSL로 교체
```

### 1.2 이전과 이번의 결정적 차이

| 구분 | 이전 | 이번 |
|---|---|---|
| material 입력 | MIC scalar/vector/texture/static 값을 읽음 | 같은 입력을 원본 ShaderMap과 exact join |
| shader 계산식 | stripped graph를 감으로 재작성 | 원본 PS DXBC에서 실제 UV·channel·alpha·RGB 식 복구 |
| texture 의미 | 이름과 모양으로 main/noise/dissolve 추측 | uniform expression과 native texture binding으로 `t#/s#` 연결 |
| register | 자체 packet에 임의 배치 | shader object의 CB/vector/scalar/texture binding wire 복구 |
| 검증 | 화면에 보이는지, 소수 CPU 예제 | 원본 DXBC 직접 WARP 21-case + runtime 19/15-case parity |
| 결과 표현 | `MANUAL_TUNED` 또는 bounded reconstruction | main RT0에 한해 source-DXBC candidate replay |

### 1.3 정확히 찾은 것은 무엇인가

공식 `45_975` manifest와 함께 보존된 RefShaderCache file version 974를 획득했다.

| 증거 | identity |
|---|---|
| official manifest | `45_975.json`, SHA-256 `331bfb3e...` |
| RefShaderCache | extracted 245,114,448 bytes, SHA-256 `83609267...`, UE868/licensee16 |
| signed EFEngine | SHA-256 `cc09e083...`, Authenticode Valid |
| Water active MIC package | SHA-256 `404fe05a...` |
| Water base package | SHA-256 `2f729139...` |
| Sprite source package | SHA-256 `6a469896...` |

정확한 표현은 `same revision`이 아니라 receipt가 입증한 **official same distribution cohort**다.
manifest에 같은 시점의 source MIC package, RefShaderCache, EFEngine이 함께 있었고 각 payload의
packed/unpacked MD5와 SHA-256을 검증했다.

## 2. 이전에는 왜 되지 않았는가

### 2.1 리소스 복원과 셰이더 실행식 복원을 같은 것으로 봤다

초기에는 다음 자료를 이미 상당히 복구했다.

- 35 emitter occurrence와 399 module, 629 distribution
- 7 WModel carrier와 48 DDS
- MIC의 scalar/vector/texture/static parameter
- blend/depth/cull과 sampler 후보

그러나 cooked Material package에서 원본 editor expression graph가 상당 부분 제거되었다. 이름과 숫자를
읽었다고 해도 `어떤 texture channel을 어느 UV로 읽고`, `어떤 순서로 곱하고 saturate/pow하며`,
`어느 dynamic parameter lane이 dissolve threshold인지`는 확정되지 않았다.

그래서 이전 HLSL은 다음과 같은 bounded 수동 복원이었다.

```text
Base × Noise × Mask
임의 rotation/time pan
smoothstep dissolve
눈으로 맞춘 alpha/gain/threshold/tint
```

이 방식은 첫 픽셀을 만드는 데에는 유효했지만 다음 문제가 있었다.

- 흰 카드·검은 카드·연보라 atlas quad처럼 carrier 전체가 노출됨
- main/noise/dissolve texture의 역할과 channel이 뒤바뀜
- dynamic parameter의 X/Y/Z/W 의미가 섞임
- alpha가 맞아도 UV 이동과 RGB가 원본과 다름
- 한 시점에 맞춘 수동식이 다른 시점·카메라·particle 값에서 깨짐

### 2.2 처음 조사한 ShaderCache는 대상 Material의 캐시가 아니었다

초기 설치 중앙 cache인 `9XUF...upk`는 유효한 ShaderCache였다. 하지만 도화가 main 두 family의
BaseMaterialId가 전체 logical package에 존재하지 않았다.

```text
#9/#10 BaseMaterialId 06e9...aa3c -> 0
#11     BaseMaterialId b1f4...16cc -> 0
```

primary export의 25 material map도 다른 landscape family였다. 따라서 그 안의 DXBC 240개가 정상이어도
도화가 F의 계산식으로 사용하면 안 됐다. `ShaderCache가 존재한다`와 `해당 Material의 ShaderMap이
그 캐시에 존재한다`는 서로 다른 주장이다.

### 2.3 조인 키를 16-byte tail이나 raw SHA로 오해했다

초기에는 MIC tail의 16-byte 값, raw serialized SHA, 직접 byte subsequence를 후보로 조사했다.
하지만 이 LostArk v868 실행체에서 실제 lookup key는 다음 계약이었다.

```text
FStaticParameterSet + EShaderPlatform
```

cross-package equality도 raw byte equality가 아니다.

- Base Material GUID
- static switch의 Name/ExpressionGUID/Value
- component mask의 RGBA
- terrain weightmap index
- row order 무관
- `bOverride` 무시
- package-local FName table index와 serialized offset 무시

이 규칙을 사용하지 않으면 같은 semantic permutation이 package마다 다른 raw bytes를 가져 false-negative가
발생한다. 반대로 16-byte 후보가 우연히 같다고 ShaderMap identity로 승격하면 false-positive가 된다.

### 2.4 RefShaderCache 구조를 중앙 cache와 같다고 가정했다

RefShaderCache는 shader descriptor 수와 embedded code 수가 같지 않았다. 일부 descriptor에는 해당
cache group의 embedded code가 연결되지 않는다. 초기 parser의 다음 가정은 RefShaderCache 첫 group부터
실패했다.

```text
descriptorCount == embeddedCodeCount
```

또한 main map의 quality ordinal이 기존 제한과 달랐다. RefShaderCache에서는 모든 descriptor가 embedded
code를 직접 소유하지 않으며, map에 연결되지 않은 descriptor도 존재한다. 이번 parser는 다음을 분리했다.

```text
shader type group
-> descriptor table(shader type + shader ID)
-> group-local compressed code table
-> native shader object
-> material map reference
-> FUniformExpressionSet
-> constant/resource binding wire
```

그 결과 RefShaderCache 전체에서 두 BaseMaterialId가 다수 발견되었고, engine-equivalence
`FStaticParameterSet`와 map-context suffix를 함께 검사해 family별 정확히 한 map을 선택했다.

### 2.5 화면 오류에는 shader 외 integration bug도 함께 있었다

모든 과거 실패를 Material 탓으로 합치면 안 된다.

- MeshParticle StartSize에 geometry `0.01`을 다시 곱해 선형 크기가 `1/100`이 됨
- Sprite/Decal과 Mesh의 unit 의미를 같은 방식으로 변환함
- SubUV atlas frame 선택이 누락되어 atlas 전체 quad가 노출됨
- timeline, root snapshot, weapon follow, fixed-step bone history가 섞임
- Decal footprint size가 World와 shader에서 중복 적용됨
- Trail point ceiling과 source 요구량이 불일치함

이번 ShaderMap 복구는 material-composition의 핵심 문제를 해결했지만, 위 execution/transform 문제는 별도
계층에서 각각 검증해야 한다.

### 2.6 V5에서 닫은 source-root basis와 family 오염

Artist playable CModel의 source import orientation은 Client Y축 `-90°`다. named bone follow는 model/bone
world를 통해 이 basis를 이미 상속하지만 root snapshot은 actor root에 직접 결합하므로 같은 basis를
자동으로 얻지 못한다. V5는 화면별 임시 yaw나 global family rotation을 넣지 않고 attachment data에
`snapshotRootSourceBasisYawDegrees`를 추가했다.

```text
FOLLOW_NAMED_ANCHORS  -> source basis yaw 0°  (bone world가 이미 소유)
SNAPSHOT_ROOT         -> source basis yaw -90° (cue local 뒤, captured root 앞에 정확히 한 번)
```

Artist F는 follow `5`, snapshot `30`이고 position과 orientation covariance를 함께 검증한다. 이 값은
Artist order 번호의 전역 상수가 아니다. 다른 캐릭터는 자신의 model-import/source-root 관계를 별도
증거로 선언해야 하며, 근거가 없으면 기본 identity를 유지한다.

같은 V5에서 흰 대형 Sprite card는 global scale 오류가 아니라 `#16`의 최대 3m card 50장과 잘못 열린
material carrier의 중첩으로 확정됐다. `#16`만 fail-closed하고 `#5/#6` 회색 연무의 정상 3m~4.249m
source 크기는 보존했다. Ribbon `#3`은 붓 mesh가 아니라 `b_wp_1` history이며 불투명 DDS alpha 대신
source static `use_gra_r_channel=true`, `gra_pow=1.5`를 coverage로 소비한다.

Decal isolation의 crack은 `#22` source DDS `fx_a_decal_014`다. 검은 먹물 후보 `#20/#21`은 exact
LocalDecal VS/PS와 6-SRV wire까지 회수했지만 current Rect carrier가 projector/fog/aux MRT/native pass를
제공하지 못하므로 계속 fail-closed한다. 화면을 맞추기 위해 crack을 임의 ink texture로 교체하지 않는다.

## 3. 이번 해결 방법

### 3.1 Active MIC identity를 먼저 고정했다

| family | occurrence | BaseMaterialId | source static set |
|---|---|---|---|
| Watertrail | `#9/#10` | `06e9a0ae14b09646b949a245fc42aa3c` | switch 13, mask/terrain 0 |
| Spritewave | `#11` | `b1f4ebf9dc948c41bd2830d999ba16cc` | switch 20, mask/terrain 0 |

여기서 runtime packet static row `14/9`와 source `FStaticParameterSet`의 `13/20`은 서로 다른 분모다.
전자는 runtime recipe input이고 후자는 ShaderMap lookup identity다.

### 3.2 RefShaderCache에서 MaterialShaderMap을 구조 join했다

결과는 family 2개 모두 exact map 1개다.

| family | pixel shader | uniform/CB | texture |
|---|---|---|---|
| Watertrail | ID `70bf...`, DXBC `b16e274c...`, 4,232 bytes | 5 vector / 37 scalar / CB0[16] | 3 |
| Spritewave | ID `39f7...`, DXBC `7e8dbb70...`, 4,024 bytes | 11 vector / 52 scalar / CB0[24] | 4 |

두 PS는 Local Vertex Factory BasePass permutation이다. 연관 VS permutation 4개도 함께 복구했다.
현재 설치 RefShaderCache와 공식 v974 RefShaderCache 사이에서도 semantic map equality 2/2와 PS DXBC
equality 2/2가 확인됐다.

### 3.3 stripped reflection을 native binding과 uniform expression으로 보완했다

원본 PS DXBC에는 `RDEF`가 없어 symbolic reflection name을 직접 얻을 수 없었다. 대신 다음 독립 증거를
결합했다.

- `FUniformExpressionSet`의 vector/scalar/Texture2D expression
- active MIC parameter override와 base Material fallback
- native shader object의 scalar/vector/resource binding array
- DXBC의 실제 `CB0`, `t#`, `s#` 선언과 sample pair
- parameter → CB slot/component → texture register/channel backward slice

이로써 `maintex`, `uv_noise_tex`, `dissolve_tex`, `noise_dissolve_tex`가 실제 어느 register와 channel을
사용하는지 결정했다. 이름이 비슷한 texture를 눈으로 골라 끼운 것이 아니다.

### 3.4 원본 DXBC를 직접 실행했다

원본 pixel shader bytecode를 재컴파일하지 않고 `ID3D11Device::CreatePixelShader`에 직접 전달해
Microsoft WARP에서 실행했다.

- original DXBC fixed-input replay: `21/21 PASS`
- 선택한 RT0 내부 material parameter/register/texture/channel closure: PASS
- one-RTV / six-RTV control: PASS

그 뒤 원본 수식을 shipped `Shader_VtxEffectMeshPreview.hlsl`의 전용 branch로 이식하고 같은 입력에서
원본 DXBC와 runtime shader를 비교했다.

- constant texture mutation: `19/19`, max error `1.3969838619e-8`
- nonuniform 4×4 spatial/UV: `15/15`, max error `0`
- Debug/Release actual EffectObject first draw: `failures : 0`

### 4.4 프레임별 변화와 0~1의 의미

현재 값 전체를 `0→1` 선형 근사하는 것이 아니다. `0..1`은 보통
`normalizedAge = particleAge / particleLifetime`라는 입력축이다. 출력은 cooked lookup 표본을 평가한다.

- `#9/#10` alpha: `1 → .861856 → .736764 → ... → .00131488 → 0`
- `#9/#10` size: 약 `0.8 → 1.1`의 비선형 표본
- `#11` dynamic X: 양수에서 약 `-0.969`까지 변화
- `#11` rotation-rate: `8 → 0`

runtime은 60Hz fixed step에서 `(time-start)*timeScale`로 lookup 위치를 구해 인접 cooked 표본을
보간한다. 남은 curve key는 constant/linear/Hermite를 구분한다. Main 3 전용 RuntimeMaterialV2 branch는
generic normalized-life 선형 dissolve를 사용하지 않는다.

다만 다음은 아직 source-era exact가 아니다.

- emitter delay/duration의 source-era CDO default
- native RNG 소비 순서
- source UE `CurrentTime`과 현재 local clock origin의 완전한 대응
- 일부 current-revision module payload의 source-era package identity
- LostArk custom EF handler의 native evaluator

원본 근거를 끝내 구할 수 없는 값은 normalized 0..1 curve로 근사할 수 있지만, 반드시
`RECONSTRUCTED` 또는 `MANUAL_TUNED`로 분리하고 원작 수치 복원 통계에 포함하지 않는다.

시간 수치의 직접 소비 경로는 `Effect_Distribution.cpp`의 lookup/key evaluator와
`Effect_Playback.cpp`의 normalized-age fixed-step update다. Material `CurrentTime` 산술이 복구됐다는 것과
원본 occurrence clock origin이 봉인됐다는 것은 별도 상태로 기록한다.

## 5. 다른 renderer에도 같은 방식이 적용되는가

### 5.1 공통으로 재사용할 수 있는 핵심 파이프라인

다음 증거 파이프라인은 MeshParticle에 한정되지 않는다.

```text
source package/MIC/Material raw identity
-> official distribution cohort manifest
-> FStaticParameterSet 또는 해당 shader-map identity
-> ShaderCache/RefShaderCache structural join
-> selected VF + pass + shader type + shader ID
-> compressed shader code/DXBC
-> uniform expression + native CB/resource binding
-> texture/sampler/channel/render-state closure
-> original bytecode offline replay
-> shipped runtime translation parity
-> actual renderer first draw
-> 사용자 visual approval
```

즉 **동일한 조사·조인·재생 방식은 재사용할 수 있다. 그러나 동일한 shader 구현 하나로 모든 renderer를
복원할 수 있는 것은 아니다.** renderer마다 VF, pass, input signature, texture binding, render target,
blend/depth/cull과 수명 owner가 다르다.

현재 parser/receipt의 일부도 아직 `Artist 31470`, main family 2개, occurrence 3개, 특정 package/hash에
고정되어 있다. 다른 class에서 파일을 복사해 상수만 바꾸지 않는다. 먼저 다음을 입력 manifest로 옮긴다.

- class/skill/cue/occurrence denominator
- source package와 official cohort manifest
- target BaseMaterialId와 active `FStaticParameterSet`
- 허용 VF/pass/shader type selector
- expected texture/register/render-target contract
- raw replay fixture와 runtime consumer

그 뒤 31470 golden fixture와 새 corpus가 같은 generic parser를 통과하게 만든다.

### 5.2 family별 재사용 범위

| family | 공통 방법 재사용 | 반드시 새로 닫을 것 |
|---|---|---|
| MeshParticle | 매우 높음 | TypeDataMesh, LocalVF selection, particle dynamic carrier, non-RT0 MRT |
| standalone Mesh | 높음 | spawn/lifetime가 없는 element transform, model material slot/pass selection |
| SpriteParticle | 높음 | sprite/particle VF, billboard/screen alignment, SubUV, camera-facing basis |
| DecalParticle | 중간~높음 | decal projection VF/pass, depth/near/far, scene depth와 MRT/DBuffer 관계 |
| Trail/Ribbon | 중간 | trail/ribbon VF, segment topology, age/distance UV, tangent와 width interpolation |
| LightParticle | 일부 | MaterialShaderMap보다 CPU PointLight field와 LightManager consumer가 우선; flare material은 별도 |
| ScreenPost | 일부 | scene texture input, global/post-process shader map, render graph 순서와 viewport |
| distortion | 중간 | distortion render target/pass, scene-color sampling, blend/state와 composite 시점 |

따라서 다음 occurrence를 복원할 때 `#9/#10/#11` HLSL을 복사하는 것이 아니라, 해당 family의 exact
shader map을 다시 선택하고 원본 DXBC에서 그 family의 계산식과 register를 새로 복구한다.

하나의 `FMaterialShaderMap` 안에도 여러 VF/pass shader가 공존한다. 실제 Water/Spritewave map에도
LocalVF 외 particle, beam, SubUV, GPU-skin 계열 shader가 함께 있다. 그러므로 MaterialShaderMap join은
`이 material permutation이 존재한다`를 증명할 뿐, `현재 occurrence가 LocalVF shader를 실제 선택한다`를
자동 증명하지 않는다. source renderer/TypeData, native call-chain 또는 actual draw의 shader selection까지
별도 gate로 닫는다.

구체적으로 Water map은 particle/beam 후보 PS `718295...`와 LocalVF 후보 PS `70bf...`를 함께 포함하고,
Spritewave map은 particle/SubUV/beam 후보 `d3aaa...`와 Local/GPU-skin 후보 `39f7...`를 함께 포함한다.
정본은 `skill.31470.main-ref-shader-cache.receipt.json`의 Water map/VF rows와 Spritewave map/VF rows이며,
같은 receipt의 `localVertexFactorySelectionAdmission=false`를 유지한다.

비교 기준은 material 식, 정점·형상 생성, 공간·축, 시간·RNG, 렌더 pass의 다섯 축이다. 이번 main
MeshParticle은 이 중 RT0 material 식을 크게 닫은 경우다. 다른 family는 같은 증거 파이프라인을 쓰더라도
형상과 pass의 비중이 달라진다.

| family | 이번 main과 다른 핵심 | 현재 위험 | 실패하면 보이는 형태 |

### 5.4 보라 billboard·파란 decal 단계를 넘었는가

main 3의 material 계산식에 한해서는 맞다. 감으로 조립한 shader에서 official ShaderMap/DXBC replay와

renderer별 failure signature로 분류할 수 있다는 점이 달라졌다. 새 family의 큰 quad나 파란 판을 보고
main material 성공까지 되돌리지 않고, 해당 family의 texture/default, VF, projection, topology gate에서
원인을 찾는다.

고점을 더 올리기 위해 남은 공통 작업은 다음과 같다.

1. 27 recipe/34 material occurrence의 cache coverage matrix
2. source renderer/TypeData에서 occurrence-selected VF/pass로 이어지는 native call-chain 또는 actual-draw evidence
3. root/cue projection, 3축 basis conjugation, playable yaw와 UPK→WModel pivot oracle
4. source CurrentTime, delay/duration/default, native RNG와 SubUV cadence oracle
5. Sprite billboard/SubUV, Decal volume/depth, Ribbon point/topology/UV의 family geometry oracle
6. external opacity, sampler, blend/depth/cull, fog/pass와 필요한 VS/non-RT0 MRT
7. family별 actual first draw, zero-draw/S_FALSE 거부와 rollback
8. 자동 gate 뒤 사용자의 fixed-time occurrence 승인

새 RefShaderCache 발견은 material 계산식의 가장 큰 벽을 넘긴 사건이지만 occurrence 전체, renderer geometry,
시간·RNG와 pass까지 자동으로 닫은 것은 아니다.

## 6. 도화가 이후 캐릭터·발탄 확장 방향

### 6.1 Golden fixture를 먼저 만든다

도화가 F main 3개를 다음 공용 toolchain의 golden fixture로 사용한다.

- package summary/NameTable/export random-access decoder
- source MIC `FStaticParameterSet` identity derivation
- RefShaderCache descriptor/code/native-object/material-map parser
- uniform expression evaluator와 CB/resource binding resolver
- raw DXBC D3D11 WARP replay
- runtime HLSL translation parity
- D/R production-path first-draw harness

이 golden fixture가 모든 family를 자동으로 복원한다는 뜻은 아니다. parser와 증거 형식은 공유하되
각 renderer/VF/pass별 oracle과 runtime sink를 별도 capability로 추가한다.

### 6.2 현재 다른 corpus의 출발점

이미 보유한 자료가 많아도 그것을 원작 shader 복원 완료로 승격하지 않는다.

### 6.3 확장 순서

현재 6-class roster 기준으로 Artist와 DimensionMaster 뒤의 네 캐릭터는 Lance Master, Gunslinger,
Slayer, Warlord다. 확장 순서는 다음과 같이 유지한다.

1. 도화가 F 35/35를 닫고 current schema를 동결한다.
2. 도화가의 나머지 skill로 같은 class/package 계보에서 반복성을 확인한다.
3. DimensionMaster의 이미 추출된 effect/PNG 기준을 같은 receipt와 replay 형식으로 전환한다.
4. Lance Master, Gunslinger, Slayer, Warlord의 skill corpus를 inventory-only로 먼저 분류한다.
5. 캐릭터별 대표 MeshParticle/SpriteParticle/Decal/Trail 하나씩 vertical slice로 복원한다.
6. 공통 family capability가 녹색이 된 뒤 각 class 전수 occurrence를 확장한다.
7. Valtan의 boss skill, hit, phase, environment effect corpus로 이동한다.

### 6.4 캐릭터 corpus의 최소 admission 단위

캐릭터별로 다음을 하나의 행으로 관리한다.

| 항목 | 필수 증거 |
|---|---|
| skill/cue | skill ID, clip, notify time, root/bone/socket, follow/snapshot |
| occurrence | stable emitter ID, renderer family, selected LOD, ordered module |
| material | Material/MIC package SHA, BaseMaterialId, FStaticParameterSet |
| shader | cache cohort, ShaderMap, VF/pass, shader ID, DXBC SHA |
| resource | mesh/texture asset ID, raw SHA, format/color space/sampler |
| replay | fixed inputs, original output, runtime output, tolerance |
| runtime | prepared transaction, first draw, rollback/error classification |
| manual | 사용자 비교 시점, 관찰, 승인/RETUNE |

다른 class의 비슷하게 보이는 texture나 shader를 proxy로 빌려 쓰지 않는다. exact join이 없으면 해당 행은
BLOCK 또는 명시적인 reconstructed/manual-tuned 행으로 남긴다.

### 6.5 Valtan 확장 시 추가할 경계

Valtan은 캐릭터 skill보다 다음 입력이 더 많다.

- boss phase/action과 Server-authoritative timing
- large mesh/character VF와 environment mesh VF
- hit/decal/distortion/post/light 조합
- room/arena scene depth, fog, lighting과 render pass
- destruction/debris particle와 map material의 결합

따라서 Valtan effect의 시각 복원은 Server action을 바꾸지 않고 snapshot/action time을 presentation cue에
연결해야 한다. Client local boss AI나 임의 timer로 이펙트를 재생해 원본 timing처럼 보이게 하지 않는다.

Valtan 몸/도끼의 deferred material과 Valtan Cascade VFX도 한 작업으로 합치지 않는다. 몸/도끼 exact
track은 Skeletal/Anim VF의 deferred MRT와 shadow pass, normal/spec/emissive/alpha 출력을 복구해야 한다.
Cascade track은 occurrence renderer와 particle dynamic input을 먼저 닫는다. Artist의 RT0 opacity 성공선을
Valtan body shader 완료 조건으로 그대로 사용하지 않는다.

## 7. Map Shader 복원 방향

Map Shader도 원칙은 같지만 분모와 pass가 훨씬 크다. 하나의 범용 `MapRestoredShader.hlsl`로 모든 맵
Material을 대체하는 방향은 금지한다.

현재 map 쪽에서 exact로 부를 수 있는 것은 주로 asset/placement/texture-path와 일부 source numeric이다.
예를 들어 static WModel/texture namespace 해석, Valtan map material의 D/N/S texture membership,
Landscape height/weight raw 값은 복구되어 있다. 반면 Bern의 일부 layer blend는 parent expression이 없어
deterministic display approximation이고, Valtan Landscape도 original Landscape ShaderMap/DXBC replay가
완료된 상태가 아니다. 이 경계를 유지한 채 shader track을 새로 연다.

### 7.1 Map material inventory

맵 package에서 다음을 먼저 전수 inventory한다.

- placed mesh → material slot → MIC/Material 경로
- BaseMaterialId와 `FStaticParameterSet`
- LocalVF, LandscapeVF, decal, foliage 등 vertex factory
- BasePass, depth, shadow, lightmap, fog, distortion, translucency pass
- texture/lightmap/normal/spec/mask/emissive dependency
- blend/depth/cull, two-sided, static lighting policy

같은 Material family라도 lightmap policy와 vertex factory가 다르면 별도 shader permutation이다.

### 7.2 Cache와 bundle acquisition

맵 package와 같은 공식 distribution cohort에서 다음을 묶는다.

```text
map/mesh/material/MIC packages
Engine/Core/EFEngine/LOSTARK binary identity
RefShaderCache/ShaderCache/global shader cache
SystemSettings와 TextureGroup/quality 설정
lightmap 및 scene-dependent resource
```

MaterialShaderMap은 Artist와 같은 identity 방식으로 join할 수 있다. 하지만 deferred lighting,
post-process, shadow와 일부 global shader는 `FMaterialShaderMap` 밖의 global shader cache를 별도로
해독해야 한다.

### 7.3 Map shader replay

Map은 1×1 texture alpha fixture만으로 닫지 않는다.

1. 대표 material family를 static/landscape/decal/translucent로 분류한다.
2. selected VF/pass의 VS/PS, 필요 시 HS/DS를 함께 복구한다.
3. lightmap/normal/view/fog/scene-depth 입력을 포함한 nonuniform fixture를 만든다.
4. raw DXBC를 WARP에서 실행해 MRT와 depth output을 읽는다.
5. current CModel/CMaterial/Map runtime translation과 같은 geometry·texture·camera에서 비교한다.
6. MapTool preview와 제품 map loader가 같은 resource-relative asset ID와 shader capability를 소비하게 한다.
7. 자동 parity 뒤 사용자에게 동일 카메라·시간·lighting에서 원본 비교를 요청한다.

### 7.4 Map Shader 성공 기준

```text
material slot identity
  + exact ShaderMap/VF/pass join
  + texture/lightmap/sampler closure
  + raw DXBC numeric replay
  + runtime MRT/depth parity
  + actual map first draw
  + 사용자 visual approval
```

texture가 붙고 geometry가 보이는 것만으로 Map Shader 복원 완료라고 하지 않는다.

## 8. 앞으로의 단일 실행 순서

### 증거 수집과 runtime 반영의 운영 순서

남은 작업을 한 giant implementation으로 합치지 않는다. cache/MIC/VF/pass/원본 DXBC와 source
transform/default/RNG 조사는 family별 disjoint receipt에서 병렬화할 수 있다. 반면
`Effect_Playback`, `Effect_DocumentRenderer`, 공용 HLSL과 Program→sidecar→Catalog transaction은 한 writer가
family별로 직렬 반영한다.

```text
병렬 evidence
  main transform/pivot oracle
  remaining family cache coverage와 VF/pass 후보
  temporal/default/RNG source 조사

직렬 runtime
  main transform/temporal gate
  -> actual renderer selection gate
  -> remaining MeshParticle
  -> SpriteParticle
  -> DecalParticle
  -> CascadeRibbon
  -> core renderer 33/35 동결
```

축 작업은 다른 family의 cache 조사와 함께 진행해도 된다. 다만 공용 UE→Client 좌표 계약을 고정한 뒤
Mesh local, Sprite billboard, Decal projector, Ribbon tangent/facing adapter가 각자 소비해야 하며 하나의
전역 회전/offset 보정을 전 family에 적용하지 않는다.

### 현재 바로 다음 runtime 작업

```text
합격한 #9/#10/#11 material HLSL 동결
-> captured root와 cue [1,0,1] 최종 projection 진단
```

`#17/#18`, `#26`의 ShaderMap join으로 이동한다. 위치가 다르면 source evidence가 있는 axis/pivot을 먼저 교정하고,
근거 없는 hand/weapon attachment나 임의 Y offset은 추가하지 않는다.

## 9. 증거와 상태 표기 규칙

| 표기 | 의미 |
|---|---|
| `SOURCE_EXACT` | source-era package/실행 identity와 값·평가 의미까지 봉인 |
| `SOURCE_DXBC_CANDIDATE_REPLAY` | exact ShaderMap/DXBC와 fixed-input 수치 replay가 닫힘 |
| `RECONSTRUCTED` | cooked/current evidence와 검증한 정책으로 결정론적 재구성 |
| `MANUAL_TUNED` | 원본 edge를 확보하지 못해 사용자가 수치 조정 |
| `AUTO PASS` | parser/build/replay/first-draw 통과, visual 완료 아님 |
| `USER MATERIAL PASS` | 사용자가 material sub-check를 승인, occurrence 전체와 구분 |
| `OCCURRENCE APPROVED` | transform/time/material/renderer를 포함한 occurrence 하나 승인 |
| `PRODUCT` | 전체 dependency와 rollback, D/R, manual denominator를 닫고 atomic publish |

`ShaderCache에서 DXBC를 찾았다`, `HLSL로 옮겼다`, `화면에 보였다`는 서로 다른 checkpoint다.
항상 join, numeric replay, runtime parity, actual draw, 사용자 승인, Product를 분리한다.
