# 기술소개서 작성과 이해 학습 방향 합의 기록

합의일: 2026-10-10

사용자가 현재 아는 범위에서 기술소개서 PPT를 먼저 작성한다. 이후 그 초안을 실제 코드와 데이터에 대조하고, 핵심 기능을 직접 구현하며, 설계 이유와 trade-off까지 설명할 수 있는 수준으로 발전시킨다.

이 기록은 학습과 작성 방향을 합의한 결과다. 학습 완료나 제품 기능 구현 완료를 뜻하지 않는다. 이후 갱신할 원문은 [Interview의 기술소개서 작성과 이해 학습 방향](../../../../Interview/기술소개서/2026-10-10_기술소개서_작성과_이해학습_방향.md)이며, 이 파일은 합의 시점의 기록으로 보존한다.

## 지금 진행할 일

사용자가 [기술소개서.pptx](../../../../Interview/기술소개서/기술소개서.pptx)에 자신의 말로 초안을 작성한다. 전체 코드를 먼저 완벽히 이해하거나 발표 문장을 완성하는 것을 선행 조건으로 두지 않는다. 설명할 수 있는 내용과 막히는 부분을 구체적으로 드러내는 것이 첫 목표다.

초안 목차는 다음 순서를 따른다.

1. 전체 프로젝트 구조와 데이터 관리: Engine, Client, Server, Shared, Tools와 Data, Resources, 게시 데이터, 실행 상태의 관계. CMaterial, Shader, Effect, ImGui의 역할과 연결.
2. 보스 패턴과 데이터: 정의와 실행 상태, 선택과 전이, 판정과 표현, 취소와 종료.
3. 시퀀서: 시간, 트랙과 대상, 상태 평가와 이벤트, 재생과 시간 이동, 반복과 정리.
4. 프로파일링과 최적화: 측정값의 의미, 병목 가설, 비교 조건, 변경 결과와 부작용.
5. 렌더링: Model과 Material에서 Shader, pass와 RenderTarget, 최종 화면까지의 흐름과 비용.
6. 이펙트와 이펙트 툴: 정의와 인스턴스, 발생과 수명, 좌표계와 부착, 재질 입력, 편집과 저장 및 반영.

각 항목에서는 “무엇을 하는가”, “입력부터 결과까지 어떻게 흐르는가”, “왜 이런 구조라고 이해하는가”, “아직 무엇을 설명하지 못하는가”를 적는다. 정확하지 않은 부분은 질문으로 남기고, 확인된 설계 의도와 자신의 추론을 구분한다.

## 초안 이후의 진행

기능 하나씩 다음 순서로 검토한다.

1. 슬라이드의 핵심 주장을 확인한다.
2. 실제 호출자와 소비자, 데이터 정본, 상태의 소유권과 수명, 실패 처리를 대조한다.
3. 예상 동작과 변수 값을 먼저 적고, 사용자가 breakpoint로 실제 실행을 확인한다.
4. 원본을 닫고 핵심 계약을 만족하는 작은 기능을 직접 구현한다.
5. 요구사항 변경이나 실패 입력으로 수정 범위와 정리 동작을 확인한다.
6. 검증한 사실과 trade-off, 한계를 반영해 설명을 고친다.

직접 구현은 학습 과정에 포함한다. 작은 구현의 성공만으로 제품 전체의 재구현 능력을 확정하지 않고, 생략한 제약을 확인하며 실제 기능의 범위로 넓힌다. 학습용 구현은 제품 런타임과 분리하며 제품 반영은 별도 요청과 해당 구현 절차를 따른다.

## 이해와 자신감을 확인하는 기준

목표는 맡았다고 설명하는 기능을 스스로 책임질 수 있는 것이다. 기능별로 다음 증거를 쌓는다.

- 자료 없이 구조와 처리 순서를 설명한다.
- 구조 선택의 이유와 대안의 비용을 설명한다.
- 핵심 동작을 스스로 구현한다.
- 조건 변경의 수정 위치와 부작용을 예상한다.
- 오류를 재현하고 근거를 찾아 원인을 좁힌다.
- 시간이 지난 뒤에도 핵심을 재구성한다.

코드 존재, 빌드, 실행, 사용자 화면 확인, 개인 기여와 성능 개선을 분리한다. 문서에 적었다는 사실이나 설명을 들은 느낌만으로 완료 판정을 하지 않는다.

AI는 초안의 정확성과 이해의 빈틈을 검토하고, 다음에 확인하거나 직접 구현할 범위를 좁힌다. 사용자의 초안 작성과 설명 기회를 유지하며, 요청 없이 PPT나 제품 코드를 대신 수정하지 않는다.

같은 방식은 이후 NYPC의 mushroom과 Next Nation, Winters Engine의 LoL, Minecraft Dungeons, StarCraft에도 적용한다. 프로젝트별 실제 구조와 검증 근거는 각각 확인한다.

## 문서 작성 범위와 검증

이번 요청의 산출물은 이 합의 기록과 Interview의 학습 방향 원문이다. C++ 구현 계획을 제안하는 PLAN이 아니므로 전체 코드나 프로젝트 등록 변경은 포함하지 않는다.

두 Markdown 문서의 UTF-8 읽기, 상호 링크와 PPT 경로의 존재, fence 쌍과 후행 공백을 확인했다. 신규 파일별 `git diff --no-index --check`에서 whitespace 결함은 없었다. 독립 검토에서도 초안 우선 순서와 직접 구현 목표, 합의 기록과 갱신 원문의 역할이 일치함을 확인했다.

LostArk의 전체 `git diff --check`는 결함이 없었다. Interview 전체 검사에서는 기존 `기술소개서/자막.txt` 변경의 후행 공백을 보고했으며 이번 범위 밖이므로 보존했다. 두 신규 문서는 로컬에 저장했고 commit/push는 수행하지 않았다.

제품 소스, 데이터, 렌더링 설정과 PPT는 수정하지 않았다. 문서 추가만 수행했으므로 제품 컴파일과 Client 실행은 하지 않았다. 사용자의 초안 작성과 기능별 이해 확인은 이후 진행할 일이다.
