사용자 요구를 어떤 식으로 해석하고, 어떤 원리와 사고 방식을 바탕으로, 프로젝트를 빌드하고 검증하는지,
어떤 파이프라인을 거쳐서 사용자의 요구를 해석하고, 프로젝트를 분석하고, 실질적으로 수정할 파일과 코드를 찾고,
반영을 한 다음에, 회귀에 대한 검증과 반영한 내용이 실질적으로 실행되는 exe에 반영이 되었는지를 어떻게 확인할 수 있을까?

# 코드 반영과 검증·빌드의 원리

작성 기준일: 2026-08-29
대상 저장소: `LostArk` 정본
문서 목적: 코드를 많이 빌드하고 하네스를 많이 실행하는 것이 아니라, **사용자 요구가 실제 제품 경로에 반영됐다는 최소·충분한 증거를 가장 짧은 시간 안에 얻는 방법**을 정리한다.

이 문서는 현재 구현을 무조건 옳다고 설명하는 문서가 아니다. 현재 구조를 실측한 뒤, 무엇이 제품 계약이고 무엇이 중복 검증·레거시·병목인지 판단하기 위한 기준 문서다. 아래에서 `현재`라고 적은 내용은 2026-08-29 저장소 실측이고, `목표`라고 적은 내용은 앞으로 정리할 구조다.

## 1. 사용자가 제기한 질문

질문의 취지를 다음과 같이 보존한다.

1. Data가 완전히 동기화되지 않았거나 발탄 크기 오류가 남아 있어도 실제 접속과 플레이는 가능하다. 그렇다면 현재의 수많은 검증툴과 하네스는 실제로 무엇을 보장하며, 없어도 되는 검증은 무엇인가?
2. 발탄 Pattern slot을 수정했을 때 사용자가 직접 Client.exe를 실행해 일일이 눈으로 확인하지 않아도 Codex가 어떤 원리로 slot과 실제 실행 pattern의 일치를 검증할 수 있는가?
3. 같은 Git 기준을 사용하는 다른 팀원도 같은 코드·데이터·빌드 결과를 얻고, 변경으로 생긴 회귀와 실제 EXE 반영 여부를 검증하려면 `.gitignore`, `.gitattributes`, 빌드, publisher, resource 동기화가 어떤 계약을 가져야 하는가?
4. 검증이 3시간 또는 Effect 작업처럼 16시간까지 늘어나는 본질적인 이유는 무엇이며, 어떤 검증만 남기고 어떤 하네스를 제거하거나 필요 시 실행으로 내려야 하는가?
5. Codex는 사용자 요구를 어떻게 해석하고, 실제 수정 파일을 어떻게 찾고, 코드를 반영한 뒤 회귀와 실행 산출물 반영을 어떻게 증명해야 하는가?

이 질문의 핵심은 “테스트를 줄여 달라”가 아니다. **테스트 개수 대신 증거의 정확도를 기준으로 전체 개발 파이프라인을 다시 설계하자**는 요구다.

## 2. 먼저 결론

프로젝트의 올바른 검증 단위는 다음 한 줄로 정의할 수 있다.

> 사용자 요구 → 변경된 정본 → 실제 소비 경로 → 발생 가능한 실패 → 그 실패를 구별하는 최소 검증 → 실행 산출물의 identity

여기에서 하나라도 끊기면 검증 개수가 많아도 완료가 아니다.

- 접속 성공은 **서버가 살아 있고 입장이 가능하다**는 liveness 증거다. 발탄 크기, slot 순서, 실제 pattern, 이펙트 모양이 맞다는 correctness 증거가 아니다.
- C++ compile 성공은 해당 번역 단위가 `.obj`로 만들어졌다는 뜻이다. 최신 `Client.exe` 또는 `Server.exe`가 link됐다는 뜻이 아니다.
- EXE hash 변경은 C++ 반영 증거가 될 수 있지만, 런타임 JSON만 바꾼 경우 EXE hash가 바뀌지 않는 것이 정상이다. 이때는 JSON/publisher 산출물 revision과 실제 loader 경로를 증명해야 한다.
- harness PASS는 harness가 실제 제품 코드를 재사용하고 실제 실패를 구별할 때만 의미가 있다. 제품 코드를 복사하거나 테스트 전용 구현으로 다시 컴파일한 harness는 제품과 다른 결과를 낼 수 있다.
- 시각 결과는 구조·수치·draw 발생까지 자동 검증할 수 있지만, 최종 pixel fidelity와 카메라 연출 품질은 사용자가 직접 판정해야 한다.
- 같은 Git commit만으로 같은 실행 상태가 보장되지는 않는다. dirty diff, 빌드 configuration, 외부 Resources, publisher revision, EXE/DLL/CSO hash까지 닫혀야 한다.

따라서 목표는 모든 검증을 삭제하는 것이 아니다. 다음 세 부류로 정리하는 것이다.

1. **항상 필요한 제품 빌드 증거**: compile, final link, 산출물 identity, 잘못된 입력 차단.
2. **변경 영역에만 필요한 계약 검증**: 해당 publisher, protocol, Server authority, rollback.
3. **사람만 판단할 수 있는 결과**: 이펙트 모양, 카메라 연출, 체감, 최종 visual fidelity.

## 3. 먼저 용어를 분리해야 한다

현재 병목의 상당 부분은 서로 다른 역할을 모두 “검증” 또는 “하네스”라고 부르는 데서 시작한다.

| 종류 | 실제 역할 | 성공이 의미하는 것 | 성공해도 알 수 없는 것 |
|---|---|---|---|
| Compiler | `.cpp`를 `.obj`로 변환 | 문법, 타입, 해당 번역 단위 compile 가능 | 최종 EXE link, 런타임 데이터, 화면 결과 |
| Linker | `.obj/.lib`를 `.exe/.dll`로 연결 | 최신 입력으로 실행 파일 생성 | 해당 경로가 실제 실행됐는지, 데이터가 맞는지 |
| Publisher | authoring Data를 runtime Data로 검증·투영 | runtime 입력이 정본에서 재현 가능 | 실행 중인 process가 새 데이터를 다시 읽었는지 |
| Validator | schema, ID, 참조, 범위, 중복 검사 | 특정 불변식이 유지됨 | 실제 제품 제어 흐름 전체 |
| Contract harness | 제품 경계의 입력·출력 실행 | protocol/authority/rollback 같은 동작 계약 | 화면 품질, harness 밖의 제품 구성 |
| Smoke | 제품 또는 가까운 실행 경로의 대표 시나리오 | 주요 경로가 시작부터 끝까지 연결됨 | 모든 분기와 시각 품질 |
| Visual QA | 사람이 화면과 연출을 판단 | 실제 보이는 결과가 의도에 맞음 | 자동 회귀 전체 |

좋은 파이프라인은 이들을 하나의 거대한 PASS로 뭉치지 않는다. 실패했을 때 어느 경계가 깨졌는지 바로 알 수 있어야 한다.

## 4. 현재 저장소를 실측한 결과

### 4.1 Solution과 프로젝트 수

현재 `Framework.sln`에는 10개 프로젝트가 있다.

- 제품 프로젝트 4개
  - `Engine`
  - `Shared`
  - `Server`
  - `Client`
- harness 프로젝트 6개
  - `NetworkProtocolHarness`
  - `CharacterSelectIsolationHarness`
  - `PhysicsContractHarness`
  - `WModelGeometryContractHarness`
  - `PointLightFalloffContractHarness`
  - `ValtanPatternAuditionServiceHarness`

제품 프로젝트보다 harness 프로젝트가 더 많다. 프로젝트 수 자체가 문제라는 뜻은 아니다. 현재 working copy의 `Framework.sln`은 기본 `Build.0`을 제품 4개에만 두어 harness 6개를 solution 기본 빌드에서 분리했다. 이것은 올바른 방향이다. 다만 별도 회귀 runner가 선택한 harness를 각각 다시 빌드하므로, runner의 변경 영역 분류와 build graph 구성은 여전히 별도로 정리해야 한다.

### 4.2 현재 working copy 회귀 스크립트의 실제 동작

현재 수정 중인 `Tools/Build/Invoke-BuildAndRegression.ps1`은 `Debug`/`Release` configuration과 함께 `Product`, `Core`, `FullDiagnostic` profile을 받으며 기본값은 `Core`다. `BuildDomains.json`의 입력·도구·물리 Resources·생성 output fingerprint가 같은 domain은 기존 receipt를 재사용하고, 달라진 domain만 validation/publish를 다시 실행한다. 파일 이름만으로 domain을 추측하지 않고 실제 dependency closure의 내용 hash로 변경 여부를 판정한다.

| Profile | 개별 MSBuild 호출 | 빌드 대상 | 이후 검증의 성격 |
|---|---:|---|---|
| `Product` | 4 | Engine, Shared, Server, Client | release surface, shader closure, runtime layout |
| `Core` | 6 | Product + NetworkProtocol, CharacterSelectIsolation | Effect source, Valtan/balance/navigation/destruction/rendering 검증과 Character Select `Core` live scenario 1회 |
| `FullDiagnostic` | 10 | Core + ValtanPatternAudition, PointLight, Physics, WModel | Character Select `Party2`/`Party4`, map surface/water, Valtan/Animation/Effect Tool, 광범위 Server contract와 진단 harness |

퇴역한 `EffectRenderContractHarness`와 `ActionPresentationTimelineHarness`는 solution, runner와 물리 프로젝트에서 제거됐다. 기본 `Core`가 선언한 domain은 모두 확인하지만 fingerprint가 같은 publisher/validator는 실행하지 않고 receipt를 재사용한다. 다음 최적화는 domain 확인 비용 자체와 영향 제품 compile/link 선택을 더 줄이는 것이다.

각 프로젝트는 다음 형태의 별도 process로 순차 실행된다.

```powershell
MSBuild.exe <project.vcxproj> /m /nodeReuse:false /t:Build /p:BuildProjectReferences=false ...
```

`BuildProjectReferences=false`는 앞서 명시적으로 빌드한 의존성을 다시 따라가지 않게 해 중복을 줄인다. 대신 runner의 수동 순서가 dependency graph의 새 정본이 된다. 새 참조가 생겼는데 runner를 고치지 않으면 누락될 수 있고, 호출마다 MSBuild process와 project evaluation을 다시 구성하므로 한 번의 solution graph보다 병렬·증분 판단을 덜 공유한다.

### 4.3 제품 소스를 직접 다시 컴파일하는 harness

현재 harness `.vcxproj`의 직접 `ClCompile Include`를 실측하면 다음과 같다. “제품 소스”는 `Client/Private`, `Engine/Private` 등 제품 구현 파일을 harness 프로젝트가 직접 다시 compile하는 경우다.

| Harness | 직접 compile 항목 | 제품 소스 직접 compile | ProjectReference |
|---|---:|---:|---:|
| `CharacterSelectIsolationHarness` | 3 | 1 | 1 |
| `NetworkProtocolHarness` | 1 | 0 | 1 |
| `PhysicsContractHarness` | 5 | 4 | 1 |
| `PointLightFalloffContractHarness` | 6 | 5 | 1 |
| `ValtanPatternAuditionServiceHarness` | 13 | 9 | 1 |
| `WModelGeometryContractHarness` | 1 | 0 | 1 |

활성 presentation 검증은 별도 broad project를 퇴역시키고 발탄 런타임 계약, Character Select 파티 primitive, SOUND 데이터 계약으로 분해했다. EffectRender의 고유 CSO/WARP 계약은 Product closure의 일회성 한 파일 probe로 옮겨 제품 CPP 재컴파일을 없앴다. 남은 domain-only harness가 제품 소스를 직접 다시 compile하면 다음 문제가 생긴다.

- Client에서 이미 compile한 파일을 harness가 다시 compile한다.
- harness 전용 macro/include/library 조합 때문에 실제 Client와 다른 프로그램이 된다.
- 제품 `.vcxproj`에는 반영됐지만 harness `.vcxproj`에는 누락되거나 그 반대인 이중 등록 문제가 생긴다.
- 제품 경로를 검사하는 대신 제품 소스의 “복제 조합”을 검사하게 된다.
- 작은 수정도 대형 harness 재compile을 유발한다.

제품 구현을 별도 재compile해야만 검증 가능한 구조는 우선적으로 다음 중 하나로 바꿔야 한다.

1. 실제 제품 library/API를 링크해 같은 구현을 호출한다.
2. `Server.exe --contract-test`처럼 **제품 binary 자체의 제한된 contract entry point**를 사용한다.
3. 순수 계산 계약만 작은 `Shared` library로 이동해 제품과 harness가 동일 객체 코드를 링크한다.
4. 고유한 회귀 신호가 없다면 harness를 삭제한다.

### 4.4 publisher가 중복 실행되는 경로

`Server/Default/Server.vcxproj`는 compile 전에 다음 publisher를 `Publish` mode로 실행한다.

- `Publish-WorldGameplay.ps1`
- `Publish-ValtanWorldDestruction.ps1`
- `Publish-GameplayBalance.ps1`
- `Publish-ItemCatalog.ps1`
- `Publish-ValtanClearRewards.ps1`
- `Publish-ServerNavigation.ps1`

그런데 전체 회귀 스크립트는 Server build 전후로 balance/navigation/destruction validator를 다시 호출한다. Publisher가 content hash 기반 incremental skip을 하지 않으면 동일 입력을 여러 번 parse·validate·serialize한다.

목표 구조에서는 다음 중 하나만 정본이어야 한다.

- Build graph가 변경된 domain publisher를 정확히 한 번 호출하고 validation 결과를 재사용한다.
- 또는 explicit publish 단계가 먼저 실행되고, Server build는 산출물 revision만 확인한다.

“Server를 build하면 자동 publish도 되고, 전체 runner도 다시 validate한다”는 이중 소유는 제거 대상이다.

### 4.5 Engine SDK 배포의 중복 소유

현재 `UpdateLib.bat`는 Engine header, `.lib`, `Engine.dll`, Engine shader, FMOD, Assimp, PhysX를 `EngineSDK`와 `Client/Bin/<Configuration>`으로 복사한다.

동시에 `Client.vcxproj`의 `PrepareEngineSdk`, `DeployClientCompiledShaders`, `DeployClientRuntimeDependencies`도 같은 종류의 파일을 복사한다. 두 경로가 일부 겹친다.

이 상태에서는 다음 질문이 생긴다.

- 어느 복사 경로가 정본인가?
- 하나만 실행한 빌드와 둘 다 실행한 빌드가 같은가?
- 오래된 DLL이 남았을 때 누가 탐지하는가?
- `UpdateLib.bat` 성공 후 Client target이 실패하면 어느 파일이 최신인가?

목표는 Engine 산출물 배포를 하나의 MSBuild target 또는 하나의 명시적 deploy 단계가 소유하고, 다른 경로는 그 결과를 소비만 하도록 만드는 것이다.

### 4.6 worktree는 전부 지워진 상태가 아니다

2026-08-29 read-only 점검 결과는 다음과 같다.

- Git에 등록된 worktree: 63개
- 실제 폴더가 존재하는 worktree: 26개
- 폴더가 없어 prune 가능한 등록 정보: 37개
- `C:\w\lostark-structure-cleanup-0829`을 포함한 실제 worktree가 남아 있다.

따라서 “worktree를 다 지웠다”는 상태와 일치하지 않는다. 여기에는 두 종류가 섞여 있다.

1. 물리 폴더는 이미 지웠지만 `.git/worktrees` 등록만 남은 항목
2. 폴더와 branch 작업 내용이 실제로 남아 있는 항목

`git worktree prune --dry-run --verbose`는 1번을 확인하는 read-only 점검이다. 실제 prune은 등록 정보를 청소할 뿐, 2번의 물리 폴더와 dirty 변경을 대신 판단하거나 삭제하지 않는다. 구조 정리를 시작하기 전에 26개 실재 worktree의 branch, dirty 여부, 필요한 commit을 별도로 감사해야 한다.

## 5. “접속과 플레이가 된다”와 “수정이 맞다”는 다른 주장이다

Data가 오래됐거나 발탄 크기가 틀려도 접속할 수 있는 이유는 이상하지 않다. 서로 다른 계약이기 때문이다.

### 5.1 접속 성공이 증명하는 범위

접속 성공은 대체로 다음만 증명한다.

- Client가 endpoint에 TCP 연결할 수 있다.
- protocol handshake가 현재 양쪽에서 해석 가능하다.
- Server가 session과 world admission을 거부하지 않았다.
- 치명적인 초기화 실패로 process가 즉시 종료되지 않았다.

### 5.2 접속 성공이 증명하지 않는 범위

다음은 전혀 별개의 문제다.

- 발탄 model scale이 맞는가?
- slot 7이 실제로 의도한 `patternId`를 실행하는가?
- Server가 새 balance/bootstrap을 읽었는가?
- Client가 새 Effect document와 texture를 읽었는가?
- 최신 CSO가 배포됐는가?
- 현재 화면의 `Client.exe`가 방금 link한 파일인가?
- 실패한 reload가 이전 정상 상태를 보존했는가?

예를 들어 발탄 source WModel 단위가 100배인 경우 현재 계약은 `modelPreScale=0.01`, `presentationScale=1.0`으로 정규화한다. 이 값이 틀려 발탄이 거대하게 보여도 network admission과 Server simulation은 계속 동작할 수 있다. 따라서 입장 성공을 크기 검증으로 승격하면 안 된다.

### 5.3 Data 불일치인데도 “되는” 대표 원인

- 런타임이 authoring JSON이 아니라 이전에 publish된 bootstrap을 읽고 있다.
- loader 실패 시 `parse -> validate -> stage -> commit` 계약에 따라 이전 정상 상태를 유지한다.
- Data가 startup 또는 level-enter 시 한 번만 로드되어 process 재시작/재진입 전에는 새 파일을 보지 않는다.
- 바꾼 값이 현재 시나리오에서 선택되지 않는 branch다.
- Server authority 값은 바뀌지 않았고 Client presentation만 달라졌다.
- 외부 `Client/Bin/Resources`가 Git과 다른 revision이다.
- Client link가 실패했지만 이전 `Client.exe`가 그대로 남아 실행됐다.

따라서 첫 질문은 “게임이 켜지는가?”가 아니라 다음이어야 한다.

> 이번 변경이 통과해야 하는 실제 소비 경로가 무엇이며, 이전 상태와 새 상태를 구별하는 관찰값은 무엇인가?

## 6. Codex가 사용자 요구를 해석하는 원리

### 6.1 요구를 파일명이 아니라 관찰 가능한 결과로 바꾼다

예를 들어 “발탄 pattern slot을 업데이트해 줘”를 바로 JSON 수정으로 번역하면 안 된다. 먼저 다음을 확정한다.

- 사용자가 바꾸려는 것은 slot의 표시 순서인가, Server 실행 순서인가, 단일 미리보기인가?
- stable `slotId`는 유지하고 `patternId`만 바꾸는가?
- 저장된 Flow만 바꾸는가, Product pattern 정의도 바꾸는가?
- Server가 실행하는 gameplay timing/damage도 바꾸는가?
- Client animation/effect/camera presentation도 바꾸는가?

같은 “pattern 변경”이어도 변경 축은 다르다.

| 변경 축 | 정본 예시 | 실제 소비자 | 필요한 핵심 증거 |
|---|---|---|---|
| Flow slot/order | `ValtanBossAuditionFlows.json` | Boss Tool, Flow Service, Server flow command | slot→pattern join, 순서, revision, lifecycle 일치 |
| Gameplay pattern | `Valtan.gameplay.json` | Server boss simulation | publisher/definition validation, Server contract |
| Presentation | `Valtan.presentation.json`, animation/effect cue 문서 | Client presentation | join, resource, draw/occurrence, 사용자 visual |
| Damage/balance | `DamageProfiles.json`, `BossProfiles.json` | Server catalog/simulation | balance publisher, Server restart, snapshot |
| Model scale/resource | Boss catalog/material/resource | Client model renderer | asset identity, finite transform, 사용자 visual |
| Protocol | `Shared` message | Client와 Server | encode/decode, malformed rejection, version compatibility |

### 6.2 실제 최종 소비자에서 역으로 추적한다

파일 이름 검색만으로는 정본과 레거시를 구별하기 어렵다. 다음 순서로 역추적한다.

1. 화면 또는 Server state를 최종적으로 바꾸는 class/function을 찾는다.
2. 그 함수가 받는 stable ID와 typed command를 찾는다.
3. command를 만드는 service/controller/tool을 찾는다.
4. service가 읽는 document와 loader path를 찾는다.
5. document가 authoring인지 published runtime인지 구분한다.
6. publisher와 schema, project 등록, 실패 소비자를 찾는다.

기본 검색 예시는 다음과 같다.

```powershell
rg -n "C2S_DEBUG_VALTAN_PATTERN_FLOW_START|strCurrentPatternId" Shared Server Client
rg -n "ValtanBossAuditionFlows|CValtanPatternFlowDocument" Client Tools
rg -n "BeforeTargets=|AfterTargets=|ProjectReference|Exec Command" **/*.vcxproj
rg -n "Publish-|Validate|contract-test" Tools Server Client
```

핵심은 검색 결과의 개수가 아니라 **한 개의 닫힌 호출 사슬**을 얻는 것이다.

```text
Authoring Data
  → parse/validate
  → staged document
  → typed command
  → Shared serialization
  → Server admission/authority
  → Server lifecycle/snapshot
  → Client read-only presentation
```

이 사슬 밖에 있는 파일은 우선 “필요한 파일”로 간주하지 않는다. 실제 caller가 없는 interface, 이전 runtime path, receipt만 소비하는 validator는 레거시 후보다.

### 6.3 수정 전에 실패 oracle을 먼저 정한다

Oracle은 “맞으면 무엇이 관찰되고 틀리면 무엇이 달라지는가”다.

발탄 slot 예시의 oracle은 다음처럼 구체적이어야 한다.

- 저장 문서의 선택 `slotId`가 정확히 한 번 존재한다.
- 그 slot의 `patternId`가 admitted Product inventory에 정확히 한 번 존재한다.
- 전송한 slot 배열과 Server가 pin한 Flow revision이 같다.
- Server lifecycle의 `strCurrentSlotId`와 `strCurrentPatternId`가 요청 배열의 동일 ordinal과 같다.
- 잘못된 pattern ID, 중복 slot, stale revision은 기존 실행을 유지한 채 거부된다.

“하네스가 PASS한다”는 oracle이 아니다. 위 관찰값을 얻기 위한 수단 중 하나가 harness다.

## 7. 코드를 수정할 파일을 찾는 기준

### 7.1 정본, 생성물, 소비자를 먼저 분류한다

수정 후보 파일을 찾았을 때 다음 표를 작성할 수 있어야 한다.

| 질문 | 답이 없으면 생기는 문제 |
|---|---|
| 이 파일이 authoring 정본인가? | 생성물을 직접 수정하고 다음 publish에서 덮어써짐 |
| runtime은 이 파일을 직접 읽는가? | 아무도 읽지 않는 JSON을 고침 |
| publisher가 다른 위치로 투영하는가? | source와 runtime이 서로 다른 revision |
| 실패 시 누가 이전 상태를 보존하는가? | 부분 commit 또는 조용한 fallback |
| stable ID의 소유자는 누구인가? | index/tag/path가 저장 identity가 됨 |
| 실제 product caller는 누구인가? | 미래용 interface와 죽은 코드 증가 |

이 저장소의 공통 원칙은 다음과 같다.

- Area gameplay authoring은 `Data/Worlds/<AreaId>/Gameplay.world.json`이 정본이다.
- MapTool authoring은 `Data/Maps/Authoring`이 정본이다.
- Map runtime 문서는 publisher만 `Client/Bin/DataFiles/Map`에 쓴다.
- gameplay/balance/item/navigation Server runtime은 각 publisher가 만든 bootstrap을 소비한다.
- Effect Product가 직접 읽는 authoring과 외부 Resources는 별도 identity 축이다.
- 생성된 runtime 파일을 직접 수정해 문제를 숨기지 않는다.

### 7.2 두 번째 runtime path를 만들지 않는다

정본 경로가 어렵다고 별도 JSON reader, 별도 model path, Client local fallback을 만들면 처음에는 빨라 보여도 이후 검증 경우의 수가 두 배가 된다.

```text
하나의 정본 + 하나의 publisher + 하나의 runtime consumer
```

이 구조를 유지해야 “무엇을 build하고 무엇을 검증할지” 결정할 수 있다. 동일 역할의 두 번째 경로는 성능 병목보다 더 큰 판단 병목이다.

### 7.3 변경 파일과 public 영향 범위를 분리한다

한 파일을 바꿨다고 그 파일만 build하면 되는 것은 아니다. 반대로 한 파일을 바꿨다고 전체 제품을 회귀할 필요도 없다.

- `.cpp` private 구현 변경: 그 project compile/link + 직접 소비 계약
- public header 변경: 모든 include consumer 재compile
- Engine public header 변경: Engine → SDK deploy → Client compile/link
- Shared message 변경: Shared → protocol contract → Server/Client compile/link
- Server authority 변경: Server compile/link + `Server.exe --contract-test` + 관련 integration
- authoring JSON 변경: schema/join + 해당 publisher + 해당 runtime reload boundary
- HLSL 변경: shader compile + CSO deploy/hash + 해당 renderer path
- 외부 asset 변경: stable asset ID + 존재/hash/format + 사용자 visual

## 8. C++ 빌드가 실제로 일어나는 원리

### 8.1 Compile과 link는 별도 단계다

C++ 변경은 대략 다음 과정을 거친다.

```text
.h/.cpp
  → preprocessor 결과
  → compiler
  → .obj
  → linker + .lib
  → Client.exe / Server.exe / Engine.dll
  → runtime dependency deploy
  → process 실행
```

따라서 다음 표현을 구별해야 한다.

- “compile PASS”: 바뀐 source가 `.obj`가 됐다.
- “link PASS”: 최신 `.obj/.lib`로 target EXE/DLL이 만들어졌다.
- “deploy PASS”: 실행 폴더에 최신 DLL/CSO가 복사됐다.
- “runtime load PASS”: process가 그 파일을 실제로 열었다.
- “behavior PASS”: 새 code path의 결과가 oracle과 일치했다.

이 다섯 단계 중 compile만 성공한 상태를 “EXE 반영 완료”라고 보고하면 안 된다.

### 8.2 실행 중인 Client가 old EXE를 남기는 경우

Windows에서는 실행 중인 `Client.exe`가 link output을 점유할 수 있다. 이때 compile은 끝났지만 link가 `LNK1104`, `MSB3021`, `MSB3027` 등으로 실패하고, 디스크에는 이전 EXE가 남을 수 있다.

이전 EXE가 존재한다는 이유만으로 빌드가 성공했다고 판단하면 가장 위험하다. 완료 조건은 반드시 다음을 포함해야 한다.

- 최종 link exit code 0
- target file의 새 hash와 timestamp
- target timestamp가 관련 최신 input보다 뒤임
- 실행 중인 process가 있으면 사용자가 종료한 뒤 재link

Codex는 Client/UI를 자율 실행하거나 조작하지 않는다. 빌드와 산출물 검증을 마친 뒤, 사용자가 직접 실행할 정확한 target과 확인 절차를 전달한다.

### 8.3 incremental build가 안전하려면 input graph가 정확해야 한다

증분 빌드는 “아무것도 안 한다”가 아니라, 입력이 안 바뀌었다는 graph 판단을 재사용하는 것이다. 다음 누락이 있으면 stale build가 생긴다.

- 새 `.cpp/.h`가 `.vcxproj`에 등록되지 않음
- code generator/publisher input이 MSBuild `Inputs`에 연결되지 않음
- runtime 복사 target이 `Outputs`를 선언하지 않음
- 외부 resource 변경이 build graph에 표현되지 않음
- configuration별 Debug/Release 경로가 섞임

목표 파이프라인은 clean build를 매번 강제하는 대신, **정확한 Inputs/Outputs와 artifact hash**로 증분 빌드를 신뢰할 수 있게 해야 한다.

## 9. Data 동기화와 EXE 반영은 서로 다른 문제다

### 9.1 C++ 변경

C++ 변경은 최종 EXE/DLL link가 필요하다.

증거 묶음:

- source commit 또는 dirty patch identity
- configuration/platform
- compiler/linker exit code
- `Client.exe`, `Server.exe`, `Engine.dll` 중 영향 산출물 SHA-256
- 산출 시간과 입력 시간 관계

### 9.2 HLSL 변경

현재 제품 경로가 runtime HLSL fallback 없이 compiled CSO만 읽는다면 HLSL source 변경만으로는 반영되지 않는다.

증거 묶음:

- HLSL source hash
- shader compiler 성공과 entry/profile
- 생성된 `.cso` hash
- Engine output과 Client runtime 배포 위치의 `.cso` hash 일치
- 해당 renderer/pass가 그 CSO를 참조한다는 코드 경로

`Tools/Build/Test-CompiledShaderClosure.ps1` 같은 검사는 이 경계에만 사용해야 한다. JSON slot 변경 때 실행할 이유는 없다.

### 9.3 authoring JSON을 runtime이 직접 읽는 경우

EXE hash는 바뀌지 않는 것이 정상이다.

증거 묶음:

- 실제 resolved path
- parse/validate 성공
- source revision/hash
- stage 후 commit 성공
- reload 시점 또는 level 재진입 조건
- stale revision 충돌과 실패 시 이전 상태 보존

### 9.4 publisher가 runtime bootstrap을 만드는 경우

증거 묶음:

- authoring input hash 또는 semantic revision
- publisher version
- generated runtime output hash/revision
- `Check/Validate`가 현재 산출물과 재생성 결과의 일치를 확인
- Server가 그 runtime path와 revision을 읽음
- startup load라면 Server 재시작

여기에서 “publish 성공”과 “현재 실행 중 Server가 새 bootstrap을 사용”은 다른 주장이다. startup-only data는 반드시 Server 재시작 이후의 snapshot revision으로 닫아야 한다.

### 9.5 외부 `Client/Bin/Resources`

현재 Resources는 기본적으로 shared Drive pack이며 전체가 Git 정본이 아니다. 따라서 같은 commit에서도 두 PC의 texture/model이 다를 수 있다.

기능 PR이 Git pull만으로 재현돼야 한다면 전체 pack을 잠그는 것이 아니라 **현재 Product 문서가 참조하는 최소 dependency closure**를 명시해야 한다.

- Resources-relative stable asset ID
- 물리 파일 존재
- format/header 기본 검사
- 필요하면 SHA-256
- 어느 authoring document가 참조하는지
- Git에 포함됐는지, shared pack 의존인지

미참조 전체 물리 팩과 추출 원본을 커밋하는 것은 재현성 해결이 아니라 저장소 팽창이다.

## 10. 발탄 Pattern slot 변경을 실제로 검증하는 방법

이 예시는 사용자가 제시한 질문에 대한 구체적인 답이다.

### 10.1 현재 실제 데이터와 코드 경로

저장된 Boss Tool Flow 정본은 다음이다.

```text
Data/Encounters/Valtan/ValtanBossAuditionFlows.json
```

각 항목은 stable `slotId`와 `patternId`를 가진다.

```json
{ "slotId": "flow.valtan.boss-tool.default.slot.000001", "patternId": "VALTAN_WHIRLWIND" }
```

실제 소비 경로는 다음과 같다.

```text
ValtanBossAuditionFlows.json
  → CValtanPatternFlowDocument::Resolve_Path/Load/Validate
  → CBossTool
  → CValtanPatternFlowService::Start
  → C2S_DEBUG_VALTAN_PATTERN_FLOW_START
  → Shared Write_Message / Read_Message
  → Server CGameRoom::Evaluate_ValtanPatternFlowStart
  → Server가 Flow revision과 slot 배열 pin
  → S2C_DEBUG_VALTAN_PATTERN_FLOW_LIFECYCLE
  → Client가 current slot/pattern/ordinal 대조
```

현재 `CValtanPatternFlowDocument::Validate`는 최소한 다음을 검사한다.

- document version과 정확한 property 집합
- stable `flowId`, `slotId`, `patternId`
- duplicate slot ID
- slot ordinal 형식
- admitted pattern inventory에 존재하는 pattern인지
- optional entry cinematic의 위치 계약
- slot 최대 개수

저장 시에는 disk source revision이 load 당시와 같은지 확인하고, 임시 파일을 다시 parse/validate한 뒤 교체한다. 즉 저장 충돌과 부분 저장을 막는 transaction 경계가 이미 있다.

`CValtanPatternFlowService`는 request sequence, boss placement, flow ID, flow revision, start slot, ordered slot 배열을 typed Shared message로 보낸다. Server lifecycle은 `strCurrentSlotId`, `strCurrentPatternId`, ordinal, pinned gameplay definition revision을 돌려준다. Client는 lifecycle의 현재 pattern이 보낸 동일 ordinal의 pattern과 맞는지 비교한다.

### 10.2 slot의 `patternId`만 바꾼 경우 필요한 검증

변경이 정말 `ValtanBossAuditionFlows.json` 한 행의 `patternId` 교체뿐이라면 필요한 증거는 다음이면 충분하다.

1. JSON parse 성공
2. exact schema와 stable ID 검증
3. `slotId` 중복 없음
4. 새 `patternId`가 `Valtan.gameplay.json`과 joined Product inventory에 정확히 존재
5. 저장 순서와 serialize→parse round trip 보존
6. Flow source revision 재계산
7. 요청 배열 ordinal과 Server lifecycle의 slot/pattern 일치

반대로 다음은 이 변경에 기본적으로 필요하지 않다.

- Artist 31470 HLSL/WARP oracle
- Map surface/water diagnostics
- PointLight falloff harness
- Character Select isolation
- 전체 navigation publish
- 모든 Effect material family 검증
- Client 전체 visual fidelity 판정

단, slot이 가리키는 **pattern 정의 자체를 새로 추가하거나 수정**했다면 범위가 달라진다. 이때는 `Valtan.gameplay.json`, `Valtan.presentation.json`, animation/effect cue join, Server pattern definition과 필요한 시각 검증까지 확장한다.

### 10.3 Codex가 Client 화면 없이 알 수 있는 것

Codex가 실행형 contract로 자동 확인할 수 있는 것은 다음이다.

- slot과 pattern의 stable join
- request serialization과 malformed rejection
- Server의 exact revision pin
- 시작 slot과 ordered lifecycle
- 잘못된 pattern, duplicate slot, stale revision 거부
- 실패 시 기존 run 보존
- deterministic Server simulation의 pattern sequence

Codex가 Client 화면 없이 확인할 수 없는 것은 다음이다.

- 해당 pattern animation이 사람 눈에 자연스러운가?
- Effect 발생 위치, 색, 크기, 타이밍이 의도와 같은가?
- 카메라 컷과 흔들림이 좋은가?
- 실제 LAN 환경에서 체감 지연이 적절한가?

중요한 오해를 바로잡으면, harness가 “Valtan Arena 화면을 본다”는 뜻은 아니다. Harness는 **제품 계약의 입력을 넣고 구조화된 출력 상태를 비교**한다. 실제 픽셀과 연출은 보지 못한다. 실제 Arena의 시각 결과까지 PASS라고 하려면 사용자 수동 관찰이 필요하다.

### 10.4 가장 신뢰할 수 있는 자동 증거 순서

신뢰도는 보통 다음 순서다.

1. 실제 `Server.exe --contract-test` 안에서 제품 state machine을 실행
2. 제품과 같은 compiled library/API를 링크한 작은 contract runner
3. Shared protocol round-trip runner
4. publisher/validator의 schema·join 검사
5. 제품 source 문자열을 읽어 특정 token이 있는지만 보는 source test
6. 제품 구현 파일을 별도 macro로 다시 compile한 거대 harness

5번과 6번이 무조건 쓸모없다는 뜻은 아니다. 하지만 고유하게 잡는 회귀가 없으면 기본 gate에서 제거할 우선순위가 높다.

## 11. 필요한 harness만 남기는 판단 기준

### 11.1 harness가 존재할 자격

새 harness 또는 기존 harness의 필수 유지 여부는 아래 질문에 모두 답해야 한다.

1. 실제로 재현된 P0/P1 또는 자주 발생하는 고비용 회귀가 있는가?
2. 기존 compiler, publisher, product contract가 잡지 못하는 고유 실패인가?
3. PASS/FAIL oracle이 구조화되어 있고 사람이 해석하지 않아도 되는가?
4. 제품 구현을 복사하지 않고 동일 compiled code를 사용하는가?
5. 실패 시 어느 owner와 file/domain이 문제인지 즉시 알 수 있는가?
6. 입력이 deterministic하고 외부 PC 상태에 흔들리지 않는가?
7. 실행 시간과 유지 비용이 회귀 비용보다 작은가?
8. 기본 gate에 들어갈 만큼 영향 범위가 넓은가, 아니면 changed-domain gate인가?

하나라도 답하지 못하면 다음 중 하나다.

- source validator로 축소
- 해당 domain 변경 때만 실행
- pre-push/release로 이동
- 제품 자체 contract entry point로 흡수
- 삭제

### 11.2 항상 실행할 가치가 높은 검증

아래는 변경 범위가 맞을 때 고유 신호가 분명하다.

- `NetworkProtocolHarness`: Shared wire encode/decode, malformed/trailing payload, bounded field
- `Server.exe --contract-test`: Server authority, rollback, entity/session state
- `CharacterSelectIsolationHarness`: private simulation/session isolation을 바꾼 경우
- publisher `Validate/Check`: authoring→runtime projection을 바꾼 경우

하지만 이들도 모든 변경에서 항상 실행할 이유는 없다. 예를 들어 UI rect JSON만 고쳤다면 live network isolation harness는 고유 신호를 주지 않는다.

### 11.3 기본 gate에서 제거할 우선순위가 높은 검증

- 제품 C++ 수십 개를 별도 project에서 다시 compile하는 harness
- source 파일에 문자열이 있는지만 검사하면서 실제 caller를 실행하지 않는 test
- 다른 receipt의 hash만 재확인하고 runtime consumer가 없는 evidence chain
- 실제 pixel을 만들지 않으면서 visual fidelity PASS를 주장하는 oracle
- 동일 publisher를 Server pre-build와 runner에서 중복 실행하는 gate
- unrelated domain 변경에도 무조건 실행되는 전체 회귀
- 실패 원인을 한 줄 “full regression failed”로만 반환하는 aggregator

Effect 작업에서 특히 경계해야 한다. 과거처럼 1,500줄 builder, 수백 줄 mutation test, 대형 receipt를 추가해도 실제 pixel이 그려진다는 보장은 없다. Effect 자동 검증은 다음 다섯 신호에 집중해야 한다.

1. occurrence→family→material/texture/geometry의 stable unique join
2. 올바른 renderer/pass 선택
3. action-time sweep 중 nonzero draw 발생
4. finite transform/lifetime과 명백한 unit/axis 오류 없음
5. resource/shader/GPU 실패 시 이전 상태 보존 또는 rollback

최종 모양과 연출 품질은 사용자가 판단한다.

## 12. 변경 종류별 최소 검증 매트릭스

아래는 목표 기본값이다. 실제 변경이 여러 행에 걸치면 해당 행의 합집합을 사용한다.

| 변경 | 항상 필요한 검증 | 조건부 확장 | 불필요한 기본 검증 |
|---|---|---|---|
| Markdown 문서만 | `git diff --check`, 링크/경로 확인 | 명령이 실제 존재하는지 read-only 확인 | C++ build, runtime harness |
| Client private `.cpp` | Client incremental compile + final link + EXE hash | 해당 기능 focused contract | Server, unrelated publisher |
| Engine public header | Engine build → 단일 SDK deploy → Client link | Engine renderer/physics focused contract | Character Select 등 무관 domain |
| Shared protocol | Shared build, protocol round trip, Client/Server link | 실제 Server integration | Effect/Map visual gate |
| Server gameplay | Server build/link, `--contract-test` | multi-player/world harness | Client render harness |
| Balance/Item Data | 해당 publisher Validate/Publish, output revision | Server contract, 재시작 후 snapshot | HLSL/Map harness |
| 발탄 Flow slot만 | Flow schema/join/revision/lifecycle focused contract | Shared/Server code도 바꿨을 때 build | Effect WARP, Map, PointLight |
| 발탄 gameplay pattern | Valtan split Product validation, Server contract | presentation도 바뀌면 Client/visual | Character Select isolation |
| Effect authoring | Effect source join, resource closure, nonzero draw 진단 | renderer/HLSL 변경 시 Client build/CSO, 사용자 visual | world/party harness |
| Map authoring/placement | Map publisher Check/Validate, stable placement join | loader 변경 시 Client build, authority 변경 시 Server | Effect material gate |
| HLSL | shader compile, CSO closure/hash, renderer focused check | 사용자 visual | balance/navigation publish |
| Camera authoring | schema/target/finite timeline, runtime load | 사용자 직접 연출 판정 | network 전체 회귀 |

이 표의 목적은 검증을 약하게 만드는 것이 아니다. **변경이 만든 위험에 정확히 대응하는 검증만 실행**해 실패 신호를 더 강하게 만드는 것이다.

## 13. 목표 검증 파이프라인

### 13.1 단계 0: 작업 상태 고정

검증 전에 다음을 기록한다.

- repository root
- branch와 `HEAD`
- dirty 여부
- 변경 파일 목록
- submodule/LFS 상태가 있다면 그 revision
- configuration/platform
- `LOSTARK_RESOURCE_ROOT` 등 결과에 영향을 주는 명시적 환경값

dirty worktree에서 commit hash만 기록하면 재현할 수 없다. 필요하면 현재 diff의 canonical hash를 함께 기록한다. 사용자 미커밋 변경을 자동 stage/commit해서는 안 된다.

### 13.2 단계 1: 변경 파일을 domain으로 매핑

가칭 `Invoke-ChangeVerification.ps1`이 필요하다면 역할은 새 검증 로직을 또 만드는 것이 아니다. 기존 command를 선택하는 얇은 orchestrator여야 한다.

```text
DiscoverChanges
  → MapFilesToDomains
  → ExpandPublicDependencies
  → SelectRequiredPublishers
  → SelectBuildTargets
  → SelectUniqueContracts
  → AssertArtifacts
  → EmitEvidence
```

예시 domain:

- `engine`
- `shared-protocol`
- `server-gameplay`
- `client-presentation`
- `valtan-flow`
- `valtan-gameplay`
- `effect-authoring`
- `rendering-shader`
- `map-authoring`
- `navigation`
- `ui-layout`
- `docs-only`

매핑되지 않은 제품 파일은 조용히 skip하지 않고 fail-closed해야 한다. 즉 “모르므로 full” 또는 명시적 분류 오류로 처리한다.

### 13.3 단계 2: publisher는 변경된 domain만 정확히 한 번

Publisher는 다음 계약을 가져야 한다.

- `Validate`: source를 읽어 schema/join을 검사하지만 runtime을 바꾸지 않음
- `Publish`: temp/stage에 생성하고 검증한 뒤 atomic commit
- `Check`: 현재 runtime output이 동일 source의 재생성 결과와 같은지 확인
- content hash가 같으면 expensive 변환 skip
- absolute path와 machine-specific 값은 결과 identity에 넣지 않음
- 실패 시 기존 runtime output 보존

Build target과 runner가 중복 호출하지 않도록 한 owner만 선택한다.

### 13.4 단계 3: 제품 graph는 한 번 build

목표 제품 graph는 기본적으로 다음이다.

```text
Engine ─┐
        ├─ Client
Shared ─┤
        └─ Server
```

하나의 solution graph 또는 solution filter에서 필요한 target을 한 번 호출해야 한다. harness는 제품 graph와 분리하고 changed-domain에 따라 선택한다.

현재 working copy의 `Product/Core/FullDiagnostic` profile은 이 방향으로 가는 과도기다. 제품과 진단 범위를 분리했다는 점은 유지하되, 세 profile 모두 고정 목록이라 변경 파일을 해석하지 못한다. 아래 `Fast/PrePush/Release`는 현재 구현 이름이 아니라, domain 선택까지 완료한 뒤의 목표 의미다.

권장 실행 mode는 세 단계면 충분하다.

| Mode | 목적 | 범위 |
|---|---|---|
| `Fast` | 일상 수정 확인 | 변경 domain publisher + 영향 project incremental link + focused contract |
| `PrePush` | 하나의 검증 가능한 commit | Fast + public dependency regression + Debug 또는 지정 configuration |
| `Release` | 통합/배포 직전 | 제품 전체 Debug/Release, cross-domain integration, 사용자 수동 smoke |

`Release`가 오래 걸리는 것은 허용할 수 있다. 모든 작은 수정이 매번 `Release` 비용을 내는 것이 병목이다.

### 13.5 단계 4: 필요한 contract만 실행

선택 규칙 예시:

```text
Shared/Network 변경
  → NetworkProtocolHarness

Server/GameRoom 또는 Server bootstrap 변경
  → Server.exe --contract-test

party/world transfer 변경
  → Server.exe --contract-test + CharacterSelectIsolationHarness의 해당 scenario

Character Select session isolation 변경
  → CharacterSelectIsolationHarness

Valtan Flow document/service 변경
  → 작은 Flow contract 또는 제품 Server contract

Effect renderer/shader 변경
  → resource closure + renderer stats + 사용자 visual
```

### 13.6 단계 5: artifact identity를 마지막에 확인

검증 마지막에는 최소한 다음 manifest를 만들 수 있어야 한다.

```json
{
  "head": "<git commit>",
  "dirtyPatchSha256": "<empty or hash>",
  "configuration": "Debug",
  "platform": "x64",
  "domains": ["valtan-flow"],
  "inputs": [
    { "path": "Data/Encounters/Valtan/ValtanBossAuditionFlows.json", "sha256": "..." }
  ],
  "outputs": [
    { "path": "Client/Bin/Debug/Client.exe", "sha256": "..." },
    { "path": "Server/Bin/Debug/Server.exe", "sha256": "..." }
  ],
  "dataRevisions": {
    "valtanFlow": "...",
    "serverGameplay": "..."
  },
  "gates": [
    { "name": "ValtanFlowContract", "result": "PASS" }
  ]
}
```

이 manifest 자체를 영구 receipt 체인으로 키울 필요는 없다. 해당 검증 실행의 증거로만 사용하고, source of truth로 승격하지 않는다.

## 14. 실제 EXE에 반영됐는지 확인하는 방법

### 14.1 C++ code 반영

가장 단순한 증명 절차는 다음이다.

1. build 전 target hash와 timestamp 기록
2. 영향 project build
3. compiler뿐 아니라 final linker exit code 확인
4. build 후 target hash와 timestamp 기록
5. 변경 source/object가 target보다 새롭지 않은지 확인
6. 필요한 focused contract 실행

PowerShell에서 산출물 identity를 읽는 예시는 다음과 같다.

```powershell
$target = 'Client\Bin\Debug\Client.exe'
Get-Item -LiteralPath $target | Select-Object FullName, Length, LastWriteTimeUtc
Get-FileHash -Algorithm SHA256 -LiteralPath $target
```

그러나 hash가 바뀌었다는 것만으로 behavior가 맞다는 뜻은 아니다. “최신 code가 들어감”과 “요구대로 동작함”을 각각 증명해야 한다.

### 14.2 DLL/CSO 배포 반영

Client는 EXE만으로 구성되지 않는다. 최소한 영향받은 다음 identity를 함께 본다.

- `Engine.dll`
- configuration별 third-party DLL
- Engine/Client compiled shader `.cso`
- PDB가 필요한 Debug 진단에서는 해당 PDB

producer 위치와 Client runtime 위치의 hash가 같아야 한다. 복사 target이 둘 이상이면 어느 경로가 마지막 writer인지부터 제거해야 한다.

### 14.3 runtime JSON/bootstrap 반영

JSON 변경에서는 EXE hash가 그대로여도 된다. 대신 다음을 확인한다.

- runtime loader가 resolved한 절대 경로
- source/published revision
- load가 일어난 process generation 또는 level generation
- Server snapshot에 실린 gameplay data revision
- reload 실패 시 이전 revision 유지

가능하다면 runtime log에는 무조건 전체 파일 내용을 찍지 말고 다음만 구조화해 남긴다.

```text
domain, resolvedPath, revision, loadGeneration, commitResult, failureReason
```

### 14.4 “현재 실행 중인 process”까지 닫는 방법

빌드 산출물 확인과 현재 process 확인도 다르다. 사용자가 실행한 뒤 진단할 때는 다음을 비교할 수 있다.

- process image path
- process start time과 EXE last-write time
- process가 보고하는 build ID 또는 commit/dirty identity
- Server가 보고하는 loaded data revision
- Client snapshot이 받은 revision

process start time이 새 EXE 생성보다 앞이면 재시작 전 process다. 이 경우 최신 EXE가 디스크에 있어도 현재 화면은 이전 code다.

## 15. `.gitignore`와 `.gitattributes`의 판단 기준

### 15.1 `.gitignore`의 역할

`.gitignore`는 재생성 가능한 local/build 결과와 개인 상태를 제외하는 파일이다.

포함하기 적절한 것:

- `.vs`, user settings
- `.obj`, `.pdb`, `.exe`, `.dll`, `.lib`, `.cso` 같은 build output
- `EngineSDK` 같은 재생성 deploy staging
- 임시 추출/cook workspace
- 개인 ImGui/local override

제외하면 안 되는 것:

- 유일한 authoring source
- publisher/schema/script
- 새 `.cpp/.h`와 project/filter 등록
- Git pull 재현에 필수인 최소 runtime dependency closure
- 실제 제품이 읽는데 다른 배포 경로가 없는 데이터

### 15.2 `.gitattributes`의 역할

`.gitattributes`는 다음만 담당해야 한다.

- binary/LFS 여부
- text/binary 판정
- 필요한 line-ending canonicalization
- merge/diff driver

현재 파일에는 다수 Effect/Valtan receipt가 raw-byte SHA에 묶여 있어 개별 경로별 `eol=lf` 또는 `eol=crlf` 규칙이 많이 들어 있다. 이것은 과거 hash chain을 유지하지만 다음 비용을 만든다.

- 파일 이동/삭제 때 stale attribute가 남음
- semantic 내용은 같은데 줄바꿈만 달라 validation 실패
- 하나의 문서가 downstream receipt 여러 개를 연쇄 무효화
- 새 팀원의 `core.autocrlf` 상태에 따라 원인 분석 시간 증가

정리 원칙은 무조건 규칙을 삭제하는 것이 아니다.

1. 실제 runtime/publisher가 raw byte identity를 요구하는지 확인한다.
2. 의미상 JSON identity면 canonical parse/serialize 또는 semantic hash로 이전한다.
3. 법적/외부 binary 근거처럼 raw byte가 본질인 자료만 byte hash를 유지한다.
4. consumer가 사라진 receipt와 attribute를 함께 삭제한다.
5. line ending은 넓은 일반 규칙을 우선하고 예외를 최소화한다.

### 15.3 같은 Git 상태의 재현성

다른 팀원이 같은 결과를 얻으려면 다음이 모두 같거나 명시되어야 한다.

- commit + dirty 여부
- LFS object 확보 여부
- compiler/toolchain major version
- Debug/Release, x64
- publisher script와 source Data
- 외부 Resources의 필요한 asset closure
- 시작 working directory
- Server endpoint와 process 재시작 경계

따라서 “제 PC에서는 된다”와 “같은 Git이면 된다” 사이를 build evidence가 메워야 한다.

## 16. 3시간·16시간 병목이 생긴 본질

현재 장시간 작업은 한 가지 원인이 아니라 다음이 누적된 결과다.

### 16.1 변경 범위를 모르는 전체 게이트

한 줄 Data 변경에도 모든 domain을 검증한다. 가장 직접적인 병목이다.

### 16.2 별도 MSBuild process 반복

현재 profile별로 `Product` 4개, `Core` 6개, `FullDiagnostic` 11개 프로젝트를 각각 별도 호출한다. `/nodeReuse:false`와 `BuildProjectReferences=false` 조합은 dependency 중복 build를 피하는 대신 process·project evaluation을 매번 만들고, 모든 의존 순서를 runner가 수동으로 소유하게 한다.

### 16.3 제품 source 재compile

대형 harness가 Client/Engine source를 다시 compile한다. 동일 코드를 여러 binary variant로 만든다.

### 16.4 publisher와 deploy의 이중 소유

Server pre-build와 runner validation, `UpdateLib.bat`와 Client deploy target이 겹친다.

### 16.5 raw-hash receipt 연쇄

의미상 변화가 아닌 line ending 또는 재생성 차이도 큰 evidence chain을 무효화한다.

### 16.6 자동화가 판정할 수 없는 visual 문제를 자동화로 닫으려 함

pixel fidelity를 구조 receipt로 증명하려고 builder/test/receipt가 계속 늘어나지만 최종 화면 판정은 남는다.

### 16.7 실패 지점이 늦고 모호함

거대한 runner 끝부분에서 실패하면 앞의 수십 단계 비용을 다시 낸다. domain별 빠른 fail과 캐시가 없다.

### 16.8 레거시 경로와 중복 정본

어느 데이터/loader/tool이 실제 제품 경로인지 확인하는 데 시간이 더 든다. 컴퓨터 실행 시간뿐 아니라 Codex와 사람의 판단 시간이 병목이다.

최적화의 우선순위는 다음이어야 한다.

1. 실제 runtime consumer가 없는 레거시 제거
2. 변경 domain 선택
3. 제품 graph 단일 build
4. publisher/deploy owner 단일화
5. harness의 제품 source 재compile 제거
6. semantic revision과 content cache
7. visual 판정의 사용자 경계 명확화

## 17. Effect 담당자와 MapTool 담당자를 위한 목표 경계

### 17.1 새 Effect 담당자

Effect 담당자가 알아야 할 최소 경로는 다음으로 제한해야 한다.

```text
skill/pattern occurrence
  → Effect stable ID
  → Effect authoring document
  → family/material/texture/geometry
  → renderer/pass
  → action-time draw
  → 사용자 visual 판정
```

담당자가 과거 복구 receipt와 모든 임시 candidate를 이해해야만 새 Effect를 만들 수 있다면 구조 정리가 실패한 것이다. Product가 읽지 않는 이전 evidence, one-off extractor, 대형 mutation harness는 별도 archive 또는 삭제 대상으로 감사한다.

자동 완료 조건은 join, resource, draw, finite 값, rollback까지다. 색감·두께·타격감·화면 결과는 사용자가 직접 본다.

### 17.2 MapTool 담당자

MapTool 담당자의 최소 경로는 다음이어야 한다.

```text
Data/Maps/Authoring
  → catalog/placement stable ID
  → publisher Validate/Publish
  → Client runtime Map document
  → CLevelRegistry MAP_LOAD_SCOPE
  → Level enter/reload
  → 사용자 카메라 연출 판정
```

테스트맵의 카메라 연출이나 Valtan 맵 제거는 다음을 분리한다.

- placement/map 데이터 제거
- catalog에 남은 미참조 정의 제거
- level descriptor/load scope 갱신
- collision/navigation/trigger Server authority 갱신
- runtime published document 갱신
- camera timeline authoring 갱신

맵 파일을 물리적으로 지우는 것만으로 끝내면 catalog, publisher, Server bootstrap, Client prototype 중 하나에 orphan이 남는다. 반대로 모든 Effect/Network harness를 돌릴 필요는 없다. map/level/authority 영향 경계만 확장한다.

## 18. 실제 정리 작업의 권장 순서

이 문서는 원리 문서이며 아래 항목이 아직 구현 완료됐다는 뜻은 아니다. 실제 삭제는 branch별 dirty 상태와 consumer를 확인한 뒤 작은 검증 단위로 진행한다.

### 18.1 1단계: 정본 inventory

- 모든 project, pre/post-build target, publisher, harness 목록
- 각 tool의 caller와 기본/수동 실행 여부
- authoring→runtime output→loader 표
- 외부 Resources dependency 표
- worktree/branch/dirty 상태

### 18.2 2단계: consumer 없는 항목 제거

- 실제 제품이 include/link/load하지 않는 legacy code
- retired runtime data copy
- consumer 없는 receipt/manifest
- 죽은 tool entry point
- stale `.vcxproj/.filters/.gitattributes/.gitignore` 규칙

삭제 전에는 `rg`, project XML, runtime resolved path를 함께 확인한다. 이름이 오래됐다는 이유만으로 삭제하지 않는다.

### 18.3 3단계: build graph 단순화

- 제품 graph와 harness graph 분리
- 12회 개별 MSBuild를 1회 graph build로 축소
- Engine SDK/dependency deploy owner 단일화
- Server publisher owner 단일화
- 정확한 Inputs/Outputs와 incremental skip 추가

### 18.4 4단계: harness 분류

각 harness를 다음 중 하나로 확정한다.

- `always-fast`
- `changed-domain`
- `pre-push`
- `release/manual`
- `delete`

분류 근거는 프로젝트 이름이나 과거 노력량이 아니라 고유 oracle과 실제 consumer다.

### 18.5 5단계: 실행 산출물 증거 자동화

- build 시작/종료 input/output hash
- final link 확인
- DLL/CSO deploy hash
- publisher revision
- process/restart 경계 안내
- focused gate 결과

### 18.6 6단계: 사용자 수동 smoke 최소화

Codex가 자동으로 닫은 구조 증거를 먼저 제공하고, 사용자는 자동화가 판단할 수 없는 항목만 본다.

예시:

```text
자동 PASS
- slot 000007 → VALTAN_TERRAIN_DESTRUCTION_3_OCLOCK join
- Flow revision 8f...가 Server에 pin됨
- lifecycle ordinal 15의 currentPatternId 일치
- Client.exe/Server.exe final link와 hash 확인

사용자 확인
- Server + Client 실행
- Lobby → Valtan
- Boss Tool에서 해당 Flow/slot 시작
- 실제 animation/effect/camera 연출 판정
```

이렇게 해야 사용자가 이미 자동으로 증명된 schema와 protocol을 다시 눈으로 확인하느라 시간을 쓰지 않는다.

## 19. 완료 보고의 형식

앞으로 “검증 완료”라고 한 문장으로 끝내지 않는다. 최소 네 상태로 분리한다.

### 구현

- 실제 바뀐 source/data/project 파일
- 제거한 legacy와 그 consumer 부재 근거
- public contract 변화

### 자동 검증

- 실행한 command
- 검증한 oracle
- PASS/FAIL
- 생략한 전체 gate와 생략 근거

### 산출물 반영

- build configuration/platform
- final link 여부
- EXE/DLL/CSO hash 또는 Data revision
- runtime reload/restart 필요 여부

### 사용자 수동 검증

- 사용자가 실행할 Server/Client target
- 정확한 Level/Tool/slot 경로
- 눈으로 판단할 항목
- 사용자가 관찰하기 전에는 visual PASS로 기록하지 않음

## 20. 채팅 하네스의 CMD 출력은 무엇을 증명하는가

### 20.1 CMD에 글자가 보인다는 사실 자체가 검증은 아니다

하네스 검증의 본질은 콘솔 창이 아니라 다음 다섯 요소다.

1. **기대값**: 무엇이 정답인지 독립적으로 정한다.
2. **자극**: 제품이 실제로 받는 입력과 같은 형태로 요청한다.
3. **실제값**: 제품 코드가 처리한 뒤 만든 상태나 출력을 관찰한다.
4. **비교**: 기대값과 실제값을 field 단위로 비교한다.
5. **실패 격리**: 틀렸을 때 이전 정상 상태가 보존되는지도 확인한다.

CMD의 `[PASS]`는 이 비교가 성공했다는 사람이 읽기 쉬운 표현일 뿐이다. 하네스가 입력으로 만든 값을 그대로 출력한 뒤 자기 자신과 비교하면 콘솔에 아무리 많은 PASS가 나와도 제품 증거가 아니다.

### 20.2 현재 채팅 검증이 실제로 지나는 범위

현재 별도의 `ChatHarness` 프로젝트는 없다. 사용자가 본 콘솔은 `Tools/NetworkProtocolHarness/Bin/Debug/NetworkProtocolHarness.exe`일 가능성이 높고, 채팅 부분은 `Tools/NetworkProtocolHarness/Private/NetworkProtocolHarness.cpp`의 `Test_ChatProtocol()`이다.

이 테스트는 실제 Shared codec인 `Write_Message`와 `Read_Message`를 사용해 다음과 같은 계약을 확인한다.

- `C2S_CHAT`의 문자열과 field를 encode한 뒤 같은 값으로 decode할 수 있는가
- `S2C_CHAT`의 sender와 message가 round trip 뒤 보존되는가
- 허용 길이 경계와 잘못된 payload를 거부하는가
- 다른 message type과 frame 경계가 섞이지 않는가

2026-08-29 working copy의 기존 Debug binary를 실측했을 때 전체 protocol suite는 약 45ms, 출력 508줄, PASS 503개였고 채팅 계약은 그중 7개의 PASS였다. 이 수치는 성능 보장이 아니라 “현재 protocol 실행 시간은 주된 3시간 병목이 아니다”라는 진단 근거다.

하지만 현재 테스트는 다음 제품 경로를 실행하지 않는다.

| 실행하지 않는 경로 | 남아 있는 위험 |
|---|---|
| `CNetworkManager::Send_Chat` | Client가 실제 frame을 queue하지 못할 수 있음 |
| 실제 TCP socket | partial send, disconnect, session routing 문제를 못 봄 |
| `CServerApp`의 `C2S_CHAT` decode | Server dispatch가 다른 handler로 가거나 누락될 수 있음 |
| `CGameRoom::Handle_Chat` | 같은 방 broadcast, 다른 방 격리가 틀릴 수 있음 |
| Client `S2C_CHAT` decode | Server가 보냈어도 Client event가 만들어지지 않을 수 있음 |
| `CClientReplication::Apply_ChatReceived` | 수신 event가 presentation state에 반영되지 않을 수 있음 |
| 제품 UI와 말풍선 | draw order, font, clipping, 수명은 자동 protocol 검증 범위 밖임 |

특히 `Client/Private/ChatWindowView.cpp`의 현재 sender scrollback은 send 결과와 무관하게 local echo를 먼저 붙일 수 있다. 따라서 Client 화면에서 내가 보낸 문장이 보였다는 사실만으로 Server relay가 성공했다고 판단하면 안 된다.

### 20.3 채팅을 실제 제품 경로까지 CMD로 증명하려면

새로운 거대한 `ChatHarness.exe`를 만들 필요는 없다. 실제 Server process와 socket을 이미 사용하는 integration driver 또는 `Server.exe --contract-test`의 적절한 suite에 다음 작은 계약을 추가하는 편이 낫다.

```text
Expected
  sender session = A
  peer session = B, same room
  outsider session = C, different room
  message = "hello room"

Stimulus
  A가 제품 codec과 실제 socket으로 C2S_CHAT 전송

Actual
  A와 B가 S2C_CHAT(sender=A, message="hello room") 수신
  C는 수신하지 않음

Failure cases
  room 미배정 session은 relay하지 않음
  invalid UTF-8/길이는 거부
  B send queue 실패가 A나 다른 peer의 state를 깨뜨리지 않음
```

권장 콘솔 출력은 PASS 이름만 나열하지 말고 핵심 실제값을 포함한다.

```text
[CHAT][SEND] session=A room=7 bytes=10
[CHAT][RECV] session=A sender=A messageHash=... PASS
[CHAT][RECV] session=B sender=A messageHash=... PASS
[CHAT][ISOLATION] session=C received=0 PASS
[CHAT][SUMMARY] delivered=2 isolated=1 failures=0
```

이렇게 해야 “문자열 codec이 된다”, “Server가 같은 방으로 relay한다”, “Client 화면이 보인다”를 서로 다른 증거로 분리할 수 있다.

## 21. 발탄 Pattern도 같은 방식으로 검증할 수 있는가

### 21.1 결론: 가능하지만 현재 검증은 한 명령으로 닫혀 있지 않다

발탄도 채팅과 동일하게 **실제 저장 Flow의 기대 slot**과 **Server가 실행 중 보고한 실제 pattern lifecycle**을 비교하면 CMD에서 검증할 수 있다.

다만 현재 저장소에는 이 계약의 조각들이 서로 다른 도구에 나뉘어 있다.

| 현재 검증 | 실제로 보는 것 | 보지 않는 것 |
|---|---|---|
| `Project-ValtanPatternMaster.ps1 -Mode ValidateV2` | 실제 저장 Flow, pattern source/product join, 중복·누락·schema | Server 실행과 lifecycle |
| `NetworkProtocolHarness::Test_ValtanPatternFlowProtocol` | flow start/result/lifecycle packet codec와 255/256 slot 경계 | 실제 JSON, 실제 Server |
| `ValtanPatternAuditionServiceHarness` | Client service의 request/lifecycle 상태 전이 | 실제 Flow JSON과 `CNetworkManager`; synthetic 3-slot 값을 사용 |
| `Server.exe --contract-test`의 Valtan flow | 실제 `CGameRoom`과 `CValtanBrain`의 queue/tick/lifecycle | 현재 저장된 26-slot Flow; hardcoded 3-slot flow를 사용 |
| 사용자 Client 실행 | animation/effect/camera/pixel 결과 | 자동으로 재현 가능한 field-level 판정 |

각 도구는 일부 계약에는 가치가 있지만, 어느 하나도 현재 저장된 Flow 전체가 실제 Server에서 같은 순서로 실행됐다는 단독 증거는 아니다.

### 21.2 실제 제품 경로

발탄 Flow 한 건은 다음 경계를 지난다.

```text
Data/Encounters/Valtan/ValtanBossAuditionFlows.json
  ↓ parse / strict validate / raw-byte SHA-256
CValtanPatternFlowDocument
  ↓ saved revision과 ordered slots
CBossTool + CValtanTuningCommandService
  ↓ PublishSavedFlow / active candidate revision 확인
CValtanPatternFlowService::Start
  ↓ C2S_DEBUG_VALTAN_PATTERN_FLOW_START
Shared codec
  ↓ TCP
CServerApp
  ↓
CGameRoom::Evaluate_ValtanPatternFlowStart
  ↓ catalog revision pin + transactional stage/commit
CValtanBrain fixed tick
  ↓ server-authoritative current pattern
S2C flow result / lifecycle
  ↓
Client Flow service 또는 integration driver
```

여기에서 slot과 pattern은 같은 개념이 아니다.

- `slotId`와 `ordinal`은 Flow 안의 위치와 occurrence identity다.
- `patternId`는 실제 gameplay pattern 정의를 가리킨다.
- 같은 `patternId`가 여러 slot에 반복될 수 있으므로 `patternSequence`와 slot identity를 함께 봐야 한다.
- Flow SHA는 “어느 저장본을 실행했는가”를 고정한다.
- pinned gameplay definition revision은 실행 중 catalog가 바뀌어 결과가 섞이는 것을 막는다.

### 21.3 올바른 기대값과 실제값

발탄 검증에서 가장 중요한 것은 oracle을 독립시키는 일이다.

| 역할 | 값의 출처 |
|---|---|
| 기대값 | 실제 저장 `ValtanBossAuditionFlows.json`을 strict parser로 읽은 ordinal/slotId/patternId |
| 입력 | 그 저장본의 raw SHA와 ordered slot array를 제품 Shared codec으로 전송 |
| 실제값 | 실제 `CGameRoom/CValtanBrain`이 tick한 뒤 보낸 lifecycle의 ordinal/slotId/patternId/patternSequence |
| 비교 | 같은 occurrence의 기대 row와 Server lifecycle을 비교 |

피해야 할 방식은 harness가 request에서 가짜 lifecycle을 직접 만들고 다시 request와 비교하는 것이다. 그 방식은 Server의 admission, sequencing, pause/resume, terminal state를 전혀 증명하지 못한다.

Server가 authoring JSON을 직접 다시 읽어야 한다는 뜻은 아니다. 현재 경계에서는 다음 두 증거가 합성된다.

1. validator가 실제 저장 파일을 읽어 join과 raw SHA를 증명한다.
2. 실제 socket smoke가 그 SHA와 ordered slots를 Server에 보내고, Server authoritative lifecycle이 같은 순서를 실행하는지 증명한다.

### 21.4 한 번의 CMD 검증이 출력해야 할 내용

권장 출력 형식은 다음과 같다.

```text
[VALTAN_FLOW][SOURCE] flowId=flow.valtan.boss-tool.default revision=<sha256> slots=26
[VALTAN_FLOW][JOIN] ordinal=8 slotId=<id> expected=VALTAN_ARENA_BREAK_109 admitted=yes
[VALTAN_FLOW][REQUEST] request=41 startSlot=<id> encodedBytes=<n>
[VALTAN_FLOW][SERVER] result=QUEUED epoch=<non-zero> pinnedRevision=<catalog-revision>
[VALTAN_FLOW][ACTIVE] ordinal=8 slotId=<id> expected=VALTAN_ARENA_BREAK_109 server=VALTAN_ARENA_BREAK_109 sequence=17 PASS
[VALTAN_FLOW][DONE] observed=26/26 terminal=COMPLETED_HOLD failures=0
```

최소 assertion은 다음과 같다.

1. 실제 파일 raw SHA와 document revision이 같다.
2. 모든 slot ID가 고유하고 ordinal 순서가 유효하다.
3. 각 pattern ID가 현재 admitted gameplay catalog에 존재한다.
4. request의 ordered array와 실제 파일의 ordered array가 byte/field 수준에서 같다.
5. Server 결과가 `QUEUED`이고 flow epoch가 0이 아니다.
6. lifecycle의 flow ID와 SHA가 요청한 저장본과 같다.
7. 각 occurrence의 ordinal, slot ID, pattern ID가 기대 row와 같다.
8. 새 occurrence마다 `patternSequence`가 올바르게 증가한다.
9. 실행 중 pinned definition revision이 바뀌지 않는다.
10. 마지막 terminal state와 observed count가 기대와 같다.
11. stale SHA, unknown pattern, duplicate slot, invalid start slot은 기존 실행을 손상하지 않고 거부된다.

### 21.5 현재 저장 Flow를 예로 든 실측

2026-08-29 시점 working copy의 `Data/Encounters/Valtan/ValtanBossAuditionFlows.json`은 다음 상태였다.

- flow ID: `flow.valtan.boss-tool.default`
- slot 26개, unique slot ID 26개
- unique pattern ID 21개
- admitted gameplay pattern 33개 중 Flow가 참조한 pattern 누락 0개
- raw SHA-256: `0c6d6da3a16eebe2985806ac737fe498cca388a4e84ddff419e1b6d500768fcd`
- `ValidateV2` 결과: 오류 0개

이 hash와 개수는 문서의 영구 정답이 아니라 해당 working copy snapshot이다. Flow를 저장하면 반드시 새 raw SHA와 새 ordered rows를 다시 읽어야 한다.

### 21.6 어느 기존 실행기를 확장해야 하는가

권장안은 새 발탄 전용 대형 EXE를 하나 더 추가하는 것이 아니다.

- 기존 Character Select live driver 또는 제품 Server entry를 일반 integration runner로 정리한 뒤 `valtan-pattern-flow` scenario를 추가한다.
- 고정 인원 이름을 가진 raid 전용 project를 다시 만들지 않고 scenario가 증명할 public 계약을 이름으로 사용한다.
- request와 lifecycle codec은 기존 Shared implementation을 그대로 링크한다.
- actual Flow parser는 제품 document와 동일 객체 코드를 쓰거나, validator가 내보낸 immutable expected rows를 입력으로 사용한다.
- synthetic Client service test는 실제 TCP smoke가 같은 실패를 더 강하게 잡으면 기본 gate에서 제거하거나 작은 state-machine unit으로 축소한다.

발탄 debug audition command는 Release에서 의도적으로 거부된다. 따라서:

- Debug: 실제 Flow playback과 lifecycle을 검증한다.
- Release: build/link와 `REJECTED_RELEASE_BUILD` 경계만 검증한다.
- animation, Effect, camera, 파괴 연출의 눈으로 보이는 품질: 사용자가 Client를 직접 실행해 최종 판정한다.

CMD PASS는 pattern ID와 slot 순서가 맞다는 증거가 될 수 있지만, “모션과 이펙트가 아름답고 카메라가 의도대로 보인다”의 증거가 될 수는 없다.

## 22. 발탄 변경 종류별 최소 빌드·검증 파이프라인

같은 “발탄 수정”이라도 변경 파일에 따라 필요한 compile이 다르다. Data-only 변경에 Client 전체 rebuild를 붙이면 병목이고, Shared packet 변경에 Data validator만 붙이면 검증 누락이다.

| 변경 | 필요한 compile/link | 자동 검증 | 실행/재시작 경계 |
|---|---|---|---|
| Flow JSON의 slot 순서·ID만 변경 | 원칙상 C++ compile 없음; 기존 binary identity 확인 | 실제 Flow `ValidateV2` + publish/revision check + Debug 실제 TCP flow smoke | 해당 revision을 Server가 활성화했는지 확인; startup-scoped이면 Server 재시작 |
| pattern gameplay 정의 변경 | 보통 C++ compile 없음 | pattern publisher Validate/Publish + Flow join + Server lifecycle/damage focused contract | Server가 새 catalog revision을 load/activate해야 함 |
| `CValtanPatternFlowDocument` parser/save 변경 | Client compile/link | 실제 파일 parse/save/CAS/rollback focused test + TCP flow smoke | 새 Client EXE 필요 |
| `CValtanPatternFlowService` 변경 | Client compile/link | request/lifecycle state contract + TCP flow smoke | 새 Client EXE 필요 |
| Shared flow packet 변경 | Shared build 후 Server와 Client relink | focused protocol codec + malformed/boundary + TCP flow smoke | 양쪽 binary가 같은 protocol revision이어야 함 |
| `CGameRoom` admission/sequencing 변경 | Server compile/link | focused Server flow contract + invalid/rollback + TCP flow smoke | 새 Server EXE와 process 재시작 |
| `CValtanBrain` pattern 실행 변경 | Server compile/link | fixed-tick occurrence/terminal contract + TCP flow smoke | 새 Server EXE와 process 재시작 |
| animation binding 변경 | 필요한 Client presentation code만 변경 시 compile; JSON만이면 없음 | binding schema/join/source identity | Client data reload 또는 재시작 뒤 사용자 육안 |
| Effect asset/graph 변경 | C++ 변경 없으면 compile 없음 | Effect schema/path/dependency validation | Client data reload 또는 재시작 뒤 사용자 육안 |
| camera/map placement 변경 | C++ 변경 없으면 compile 없음 | Map publisher, stable ID, scope, placement/runtime join | publish 뒤 Test/Valtan map에서 사용자 육안 |

Data-only 빠른 경로의 목표는 다음 정도다.

```text
1. 실제 저장 Flow parse + ValidateV2
2. raw SHA와 changed rows 출력
3. 필요한 Valtan runtime set만 Publish/Check
4. 이미 검증된 Debug Server/driver binary hash 확인
5. actual socket으로 flow start
6. lifecycle 전체 occurrence 비교
7. 결과와 revision 기록
```

여기에는 Engine, Client, EffectRender, PointLight, Character Select isolation compile이 들어갈 이유가 없다. 반대로 Shared packet이나 Server sequencing을 바꿨다면 기존 EXE로 Data smoke만 돌려서는 새 코드가 실행됐다는 증거가 되지 않는다.

## 23. 현재 빌드·컴파일·검증 파이프라인의 핵심 병목

### 23.1 가장 큰 병목: 변경 영역을 모른다

현재 `Product/Core/FullDiagnostic`은 사람이 고르는 고정 묶음이다. 기본 `Core`는 변경된 파일이 채팅인지 발탄인지 Effect인지 판단하지 않고 같은 목록을 실행한다.

이 구조의 비용은 단순히 “테스트가 많다”가 아니다.

- 무관한 publisher가 대용량 Data를 다시 읽는다.
- 무관한 harness project가 MSBuild evaluation과 link를 한다.
- 실제 process integration이 timeout까지 기다릴 수 있다.
- 실패가 나와도 현재 변경과 관계있는지 다시 조사해야 한다.

우선 필요한 것은 test 삭제가 아니라 `changed path → domain → public dependency → proof` 매핑이다. 매핑되지 않은 경로는 조용히 skip하지 말고 `Core` 또는 명시적 분류 실패로 보내야 한다.

### 23.2 MSBuild를 4/6/11번 별도 process로 실행한다

현재 runner는 profile에 따라 제품과 harness 프로젝트를 각각 별도 MSBuild process로 순차 실행한다.

- `Product`: 4회
- `Core`: 6회
- `FullDiagnostic`: 11회

`/m`은 한 프로젝트 내부 compile 병렬성은 줄 수 있지만, 바깥 PowerShell loop가 다음 프로젝트를 기다리므로 프로젝트 graph 전체의 병렬성은 쓰지 못한다. `/nodeReuse:false`는 node 재사용을 끄고, 매 호출마다 evaluation과 toolchain 초기화 비용을 다시 낸다.

`BuildProjectReferences=false`는 이미 빌드한 의존성을 다시 따라가지 않게 하는 대신 다음 위험을 만든다.

- runner의 명시 순서와 `ProjectReference` graph가 이중 정본이 된다.
- 새 dependency를 프로젝트에는 추가하고 runner에 빼먹을 수 있다.
- 어느 project가 왜 rebuild됐는지 graph 단위 진단이 어렵다.

제품은 현재 기본 `Framework.sln`의 제품-only `Build.0` 구성을 이용해 한 번의 graph로 빌드하고, 진단 harness는 별도 solution filter 또는 diagnostic graph로 묶는 편이 낫다.

### 23.3 같은 Valtan `ValidateV2`가 한 run에서 최대 네 번 호출된다

현재 경로를 합치면 `FullDiagnostic` 또는 관련 `Core` 실행에서 같은 무거운 Valtan master 검증이 다음 경로로 반복될 수 있다.

1. Server pre-build의 `Publish-GameplayBalance.ps1`
2. Client pre-compile의 Valtan split product validation
3. runner가 직접 호출하는 `Project-ValtanPatternMaster.ps1 -Mode ValidateV2`
4. runner의 `Publish-BalanceRuntimeSet.ps1 -Mode Validate`가 다시 `Publish-GameplayBalance.ps1`을 거쳐 호출

제품 `Product` build만 해도 Server와 Client build target을 통해 두 번 만날 수 있다. 이 validator는 수천 줄 규모 Python tuning pipeline과 여러 Data join을 수행한다. 같은 source revision에 대한 성공 결과를 한 번 만들고 downstream이 그 receipt를 소비해야 한다.

호출 수를 4회에서 1회로 줄이면 해당 단계의 호출 횟수는 75% 줄어든다. 다만 전체 wall time이 75% 줄어든다고 주장하려면 단계별 timing이 먼저 필요하다.

### 23.4 Publisher의 소유자가 Server build와 runner 두 곳이다

`Server/Default/Server.vcxproj`는 compile 전에 다음 여섯 publisher를 실행한다.

- World gameplay
- Valtan world destruction
- gameplay balance
- item catalog
- Valtan clear rewards
- Server navigation

현재 이 Exec target들에는 MSBuild가 이해할 수 있는 완전한 `Inputs/Outputs`가 없어 Server compile 진입 때마다 script가 시작된다. 이후 `Core` runner가 balance, navigation, destruction 등을 다시 Validate한다.

문제는 다음 세 단계가 자주 중복된다는 것이다.

```text
parse/validate
  → publish가 내부에서 수행
  → runner Validate가 다시 수행

serialize/hash
  → publish output 생성
  → Check/다른 aggregate script가 다시 읽음
```

해결은 한 owner를 정하는 것이다.

- 권장: explicit domain publish phase가 source revision당 한 번 atomic publish하고 Server build는 revision만 소비한다.
- 대안: MSBuild target이 `Inputs/Outputs`와 content hash로 정확히 incremental하게 publish하고 runner는 그 결과를 재사용한다.

두 방식을 동시에 유지하면 안 된다.

### 23.5 Engine SDK와 runtime dependency 배포가 중복된다

`UpdateLib.bat`는 Engine header/lib/DLL/PDB/shader와 FMOD, Assimp, PhysX를 복사한다. Client project의 `PrepareEngineSdk`, `DeployClientCompiledShaders`, `DeployClientRuntimeDependencies`도 일부 같은 산출물을 복사한다.

이 중복은 다음 비용과 오류를 만든다.

- 큰 PDB와 third-party DLL의 반복 copy
- 어느 단계가 최종 파일을 덮었는지 알기 어려움
- build는 성공했지만 Client/Bin이 이전 파일인 stale deploy
- batch와 MSBuild 양쪽의 경로 규칙 유지 비용

MSBuild-native deploy를 한 owner로 만들고 `UpdateLib.bat`는 그 target을 부르는 얇은 호환 wrapper로 줄이거나 제거해야 한다. 배포 증거에는 source hash, destination hash, skip/copy 이유가 남아야 한다.

### 23.6 Effect source 검증이 기본 Core에서 무조건 실행된다

실측 당시 `Data/Effects`는 약 551개 파일, 약 160MB였고 runtime `Resources/Effect`는 수천 개 파일 규모였다. `validate_effect_sources.py`는 source 문서뿐 아니라 Git index, attributes, resource byte/hash/LFS 상태까지 넓게 확인한다.

Effect 변경에는 필요한 검증이지만 채팅, Server room, Valtan slot-only 변경에 매번 실행할 근거는 없다. 다음 입력이 바뀌었을 때만 선택해야 한다.

- `Data/Effects/**`
- `Client/Bin/Resources/Effect/**`
- Effect parser/runtime/public schema
- Effect를 참조하는 animation/skill binding 계약

전체 resource closure는 PrePush 또는 Release에서 별도로 유지할 수 있다.

### 23.7 Harness가 제품 CPP를 직접 다시 컴파일한다

현재 일부 harness는 제품 library를 링크하지 않고 `Client/Private` 또는 `Engine/Private` CPP를 자신의 project에 직접 넣는다.

- `ValtanPatternAuditionServiceHarness`: 제품 CPP 9개
- `PointLightFalloffContractHarness`: 제품 CPP 5개
- `PhysicsContractHarness`: 제품 CPP 4개

`FullDiagnostic`에서 실제 활성 harness만 보아도 제품 CPP direct compile 항목이 여러 project에 중복된다. `DataJson.cpp`와 timeline 관련 구현처럼 같은 CPP가 서로 다른 macro/include 조합으로 여러 번 컴파일된다.

이것은 compile 시간만의 문제가 아니다.

- 제품 Client와 다른 preprocessor 조합을 검증한다.
- 제품 project에 새 dependency를 넣어도 harness가 우연히 통과할 수 있다.
- harness macro 때문에 제품에서는 존재하지 않는 우회 경로가 생긴다.
- CPP 등록과 link dependency를 여러 project에서 동기화해야 한다.

순수 로직은 작은 공용 library의 동일 object code를 링크하고, 제품 orchestration은 실제 Client/Server binary의 contract entry point를 사용해야 한다. 고유 failure signal이 없는 direct-source harness는 대체 증거를 만든 뒤 삭제한다.

### 23.8 거대한 translation unit가 작은 변경의 compile/link를 키운다

실측 당시 대표 파일은 다음 규모였다.

- `ServerGameplayContractTests.cpp`: 약 2.1만 줄, Server 제품 binary에 함께 compile
- `NetworkProtocolHarness.cpp`: 약 5.4천 줄, 500개가 넘는 assertion
- `Effect_Tool.cpp`: 약 3만 줄
- `Effect_DocumentRenderer.cpp`: 약 2만 줄
- protocol codec, `GameRoom.cpp`, MapTool 구현도 대형 TU

header 한 줄이 넓게 포함되면 큰 TU들이 다시 compile되고, Server contract test code가 제품 Server link/PDB에도 영향을 준다. Server/Shared에는 명확한 PCH 이득도 제한적이고 Client/Engine은 `/MP`와 `/FS` 비용을 함께 가진다.

다만 TU 분해와 PCH는 가장 먼저 할 일이 아니다. 중복 validator와 잘못 선택된 project를 먼저 제거하지 않으면 구조 개편 비용만 크게 든다. timing에서 실제 compiler front-end가 상위 병목으로 확인된 뒤 다음 순서로 한다.

1. 자주 바뀌는 header 의존 축소
2. pure contract suite를 Server 제품 TU에서 분리하되 동일 library를 링크
3. 안정적인 공통 header만 PCH 후보로 선정
4. PDB contention과 `/FS` 측정

### 23.9 실행형 integration이 무관한 변경에도 반복된다

퇴역한 `ValtanFourPlayerHarness`의 일반적인 admission/reset 계약은 protocol과 Server contract에 남기고, 실제 process/socket/room 격리는 `CharacterSelectIsolationHarness`가 소유한다. 실제 통합 증거가 의미 있다는 것과 모든 변경에 모든 scenario를 실행해야 한다는 것은 다르다.

Character Select의 `Scenario=All`은 `Core`, `Party2`, `Party4`를 각각 새 Server process로 직렬 실행해 timeout 상한을 합치면 수분까지 갈 수 있다. 정본 runner는 기본 `Core`에서 `Scenario=Core`만 실행하고, `Party2`와 `Party4`는 `FullDiagnostic`에서만 실행한다. process startup, port readiness, shutdown join 실패가 있으면 실제 assertion보다 대기 시간이 길어진다.

선택 기준은 다음이어야 한다.

- protocol/session/room/party/world transfer 변경: 실행
- Flow JSON slot-only: 한 client Valtan flow scenario만 실행
- Effect asset-only: 실행하지 않음
- release/public network boundary: 전체 scenario 실행

각 process 단계는 startup, admission, action, shutdown 시간을 따로 기록해야 한다.

### 23.10 Shader closure와 대형 파일 hash scan도 매번 반복된다

현재 compiled shader closure는 producer/consumer source를 다시 찾아 여러 쌍의 hash/identity를 검사한다. Data publisher와 Effect validator도 별도의 디렉터리 scan과 SHA 계산을 한다.

각각은 개별적으로 짧을 수 있지만 같은 run에서 Git index scan, resource enumeration, JSON parse, SHA 계산을 여러 script가 반복한다. 공통 manifest cache는 다음 key로 제한해 재사용할 수 있다.

```text
root에 독립적인 relative path
+ file size
+ mtime는 빠른 후보
+ 최종 content SHA
+ validator contract version
```

mtime만으로 PASS를 캐시하면 안 되고, commit/push 증거에는 최종 content hash가 필요하다.

### 23.11 build 성공과 새 EXE 실행 사이에 stale output이 생긴다

C++ 변경의 실제 반영은 `compile → object → link → deploy → process start`까지 끝나야 한다.

- 실행 중인 `Client.exe`가 output을 점유하면 link가 실패하거나 새 파일이 다른 위치에 생길 수 있다.
- 이전 EXE가 남아 있으면 명령은 성공해도 사용자가 오래된 binary를 실행할 수 있다.
- 작업 디렉터리가 `Client/Default`가 아니면 상대 Data/Resources가 다른 곳을 볼 수 있다.
- Server process를 재시작하지 않으면 새 bootstrap이나 startup-loaded Data가 반영되지 않는다.

따라서 결과에는 최소한 executable path, build configuration, last write time, SHA-256, process start time, loaded Data revision을 함께 남겨야 한다.

### 23.12 Data-only 변경에 EXE hash를 요구하거나, 코드 변경에 Data hash만 보는 혼선

EXE와 Data는 서로 다른 identity 축이다.

```text
Code proof
  source commit → object/link → EXE/DLL hash

Data proof
  authoring JSON/asset hash → publisher revision → runtime artifact hash

Runtime proof
  process binary hash + loaded data revision + scenario result
```

Flow JSON만 바꿨을 때 EXE hash가 그대로인 것은 정상이다. 반대로 `GameRoom.cpp`를 바꿨는데 Flow revision만 새롭다고 해서 새 Server code가 실행된 것은 아니다. pipeline이 두 축을 따로 기록해야 불필요 rebuild와 거짓 PASS를 동시에 없앨 수 있다.

### 23.13 Git/LFS/line-ending identity 검사가 큰 연쇄를 만든다

raw-byte SHA receipt는 정확하지만 line ending, BOM, regeneration order가 달라져도 hash가 바뀐다. `.gitattributes`, LFS pointer, external `Client/Bin/Resources` 정책이 섞이면 같은 Git commit이라도 물리 resource closure가 다를 수 있다.

정리 원칙은 다음이다.

- 의미 계약은 canonical parse 결과와 schema/join으로 검사한다.
- byte identity가 실제 runtime 계약인 파일만 raw SHA를 사용한다.
- text file은 `.gitattributes`에서 line ending을 고정한다.
- runtime Resources는 feature가 실제 참조하는 최소 dependency closure만 Git 계약에 포함한다.
- “모든 asset pack hash가 같아야 build 가능” 같은 전역 gate를 만들지 않는다.

### 23.14 단계별 시간과 cache hit를 기록하지 않는다

현재 가장 근본적인 관측 병목은 “3시간 중 무엇이 몇 분이었는가”가 기록되지 않는다는 점이다. script 이름과 최종 PASS만으로는 다음을 구분할 수 없다.

- compile이 느린가
- link/PDB가 느린가
- publisher가 대용량 Data를 읽는가
- process readiness timeout인가
- 파일 copy나 antivirus I/O인가
- 이미 같은 입력을 다시 검증했는가

모든 runner step은 다음 record를 남겨야 한다.

```json
{
  "step": "Valtan.ValidateV2",
  "selectedBecause": ["Data/Encounters/Valtan/ValtanBossAuditionFlows.json"],
  "inputRevision": "<sha256>",
  "startedUtc": "...",
  "durationMs": 1234,
  "cache": "miss",
  "exitCode": 0,
  "outputRevision": "<sha256>"
}
```

이 telemetry는 검증을 추가하지 않고도 바로 넣을 수 있고, 삭제·통합 우선순위를 추측이 아닌 수치로 바꾼다.

### 23.15 suite filtering보다 먼저 runner selection을 고쳐야 한다

`NetworkProtocolHarness`는 현재 chat만 선택하는 CLI 없이 전체 protocol test를 실행하고 500줄이 넘는 PASS를 출력한다. `Server.exe --contract-test`도 광범위 suite다.

`--suite chat`, `--suite valtan-flow` 같은 filtering은 유용하지만 우선순위를 잘 잡아야 한다. protocol 전체 실행이 약 45ms라면 runtime filter로 아끼는 시간은 작고, 해당 project compile/link와 500줄 로그 노이즈가 더 큰 문제다.

권장 순서는 다음이다.

1. 무관한 변경에서 project 자체를 선택하지 않는다.
2. 기본 출력은 summary와 실패 actual/expected만 남긴다.
3. `--verbose`에서 개별 PASS를 출력한다.
4. 실제 process suite처럼 수초~수분인 영역부터 scenario filter를 넣는다.

### 23.16 병렬 실행과 cache는 쓰기 경계를 이해한 뒤 적용한다

모든 validator를 무조건 병렬 실행하면 shared runtime output을 동시에 바꿔 race를 만든다.

병렬 가능:

- read-only schema/join validator
- 서로 다른 binary의 read-only focused contract
- input/output 폴더가 완전히 분리된 compile graph

직렬 또는 transaction 필요:

- 같은 `Server/Bin/DataFiles`를 쓰는 publisher
- 같은 `Client/Bin`으로 DLL/PDB를 deploy하는 단계
- 같은 TCP port를 쓰는 integration scenario
- 같은 revision을 activate하는 Valtan tuning command

cache key는 최소 `binary hash + data revision + contract version + scenario options`여야 한다. Debug binary가 달라지거나 validator 코드가 바뀌면 이전 PASS를 재사용하면 안 된다.

## 24. 병목 제거와 발탄 CMD 검증을 구현하는 순서

### 24.1 1단계: 동작을 바꾸지 않고 시간부터 잰다

runner의 모든 build, publisher, copy, harness, process start/stop에 stopwatch와 JSON record를 붙인다. 한 번의 `Core`와 `FullDiagnostic` baseline에서 다음을 얻는다.

- wall time 상위 10개 step
- 실제 rebuild된 CPP 수와 link 여부
- publisher별 parse/publish 시간
- copy byte 수
- process timeout 대기 시간
- 동일 input revision 중복 호출 횟수

이 단계가 끝나기 전에는 “이 하네스를 지우면 16시간이 해결된다”는 식의 시간을 단정하지 않는다.

### 24.2 2단계: 의미 변화 없는 중복부터 제거한다

우선 제거 대상은 검증 자체가 아니라 같은 검증의 반복 실행이다.

1. Valtan `ValidateV2`를 source revision당 1회로 통합한다.
2. publisher 소유자를 explicit publish 또는 MSBuild target 중 하나로 정한다.
3. `UpdateLib.bat`와 Client deploy의 중복 copy owner를 하나로 만든다.
4. protocol 기본 로그를 summary로 축소한다.
5. Server/Client build 결과 hash와 loaded revision을 공통 record로 남긴다.

이 단계는 회귀 범위를 줄이지 않으므로 가장 안전한 속도 개선이다.

### 24.3 3단계: 제품과 진단 build graph를 각각 한 번만 평가한다

- `Framework.sln`의 제품-only 기본 graph는 유지한다.
- 제품 build는 configuration당 한 번 호출한다.
- harness는 diagnostic solution/filter에 묶고 선택된 것만 한 번 호출한다.
- explicit project order 배열과 `ProjectReference` 이중 정본을 없앤다.
- Engine public header가 바뀐 경우에만 SDK deploy와 Client downstream을 확장한다.

### 24.4 4단계: changed-domain 선택기를 넣는다

선택기는 `git diff --name-only`만 보는 단순 glob을 넘어 public dependency를 반영해야 한다.

```text
Data/Encounters/Valtan/**
  → Valtan validator/publisher
  → actual flow smoke

Shared/Protocol/**
  → Shared build
  → affected Server/Client relink
  → protocol + actual socket scenario

Server/Private/GameRoom*
  → Server build
  → room/party/Valtan focused contract

Data/Effects/** or Resources/Effect/**
  → Effect validator
  → 사용자 visual 경로 안내

Engine public header
  → Engine + SDK deploy + affected consumers
```

공용 mapping에 없는 새 제품 경로는 fail-closed한다. 문서, local 파일, build artifact는 별도 제외 규칙을 둔다.

### 24.5 5단계: 실제 저장 Flow의 end-to-end CMD scenario를 만든다

기존 actual socket integration driver에 다음 scenario를 추가한다.

1. `ValidateV2`가 승인한 실제 Flow rows와 SHA를 읽는다.
2. 격리된 Debug Server를 loopback endpoint로 시작한다.
3. 한 client를 실제 Valtan world에 admission한다.
4. production Shared codec으로 flow start를 전송한다.
5. result와 모든 lifecycle을 수신한다.
6. expected row와 Server actual row를 occurrence별 비교한다.
7. terminal과 shutdown을 bounded wait로 끝낸다.
8. actual/expected/revision/timing을 한 JSON과 짧은 CMD summary로 남긴다.

이 scenario가 안정되면 synthetic `ValtanPatternAuditionServiceHarness`가 잡는 고유 회귀를 비교한다. 실제 제품 경로가 모두 포함하고 있다면 기본 gate에서 제거하거나 state-machine unit만 남긴다.

### 24.6 6단계: harness를 유지·이동·삭제한다

| 대상 | 권장 판단 |
|---|---|
| `NetworkProtocolHarness` | Shared codec 경계이므로 유지; project는 Shared/protocol 변경에만 선택, 로그 축소 |
| `Server.exe --contract-test` | 실제 제품 code를 쓰므로 유지; suite 분리와 test TU link 구조 개선 |
| `ValtanFourPlayerHarness` | 고정 4인 제품 가정을 굳히므로 퇴역; 일반 admission/reset은 protocol·Server contract, live 8-actor raid는 기존 integration driver의 명시 scenario로 검증 |
| `CharacterSelectIsolationHarness` | 기본 Core에는 `Core` scenario 한 번만 유지하고, `Party2`/`Party4`는 FullDiagnostic/관련 변경에서 실행 |
| `ValtanPatternAuditionServiceHarness` | actual Flow/TCP scenario로 대체 후 고유 state-machine assertion만 남기거나 삭제 |
| `EffectRenderContractHarness` | 퇴역 완료; V1/V2 stage·commit/resource-root는 focused contract, 실제 compiled CSO draw/readback은 Product WARP probe가 소유 |
| PointLight/Physics/WModel harness | 해당 Engine/rendering domain에서만 선택; 제품 경로와 중복되는 project는 통합 |

삭제 조건은 “느리다”가 아니라 다음 세 질문으로 정한다.

1. 이 하네스만 잡는 실제 failure가 있는가?
2. 그 failure를 더 실제에 가까운 제품 binary/actual socket/validator가 잡는가?
3. 대체 증거가 실패하는 모습을 확인한 뒤에도 이 하네스가 추가 신호를 주는가?

세 번째 답이 아니면 삭제할 수 있다.

### 24.7 7단계: 마지막으로 compiler 구조를 최적화한다

중복 호출과 잘못된 선택을 제거한 뒤에도 compile이 상위 병목이면 대형 TU, header fan-out, PCH, PDB contention을 다룬다. 이 순서를 지켜야 구조 개편이 실제 wall time을 줄였는지 알 수 있다.

### 24.8 목표 최종 흐름

```text
사용자 요구
  ↓ 요구를 observable contract로 변환
변경 파일/데이터 정본 탐색
  ↓ changed-domain + public dependency 계산
필요 publisher 1회
  ↓ content/revision evidence
필요 product graph 1회 incremental build
  ↓ binary/deploy evidence
focused contract
  ↓ field-level actual vs expected
필요한 actual socket/process scenario
  ↓ authoritative runtime evidence
사용자 수동 Client 확인
  ↓ visual fidelity 결정
commit/push
  ↓ 같은 source + dependency closure + evidence
```

이 흐름에서 채팅과 발탄은 같은 검증 원리를 사용한다. 차이는 채팅의 실제값이 “누가 어떤 message를 받았는가”이고, 발탄의 실제값이 “Server fixed tick에서 어느 slot의 어느 pattern occurrence가 활성화됐는가”라는 점이다.

## 25. 최종 판단 원칙

프로젝트가 커질수록 검증을 추가하는 것은 쉽고, 제거하는 것은 어렵다. 그러나 검증도 제품 코드와 같은 유지 비용을 가진다. 다음 문장을 기준으로 판단한다.

> 이 검증이 실패했을 때 실제 제품에서 어떤 잘못을 막았는지 한 문장으로 설명할 수 없으면, 기본 파이프라인에 둘 이유가 없다.

> 이 검증이 PASS해도 실제 제품 경로가 틀릴 수 있다면, 제품 경로와 같은 compiled code 또는 같은 runtime artifact를 보도록 고쳐야 한다.

> 자동화가 볼 수 없는 픽셀과 연출을 receipt로 대신 증명하려 하지 말고, 구조적 오류까지만 자동으로 제거한 뒤 사용자 판단으로 넘긴다.

> 같은 Git이라는 말은 source identity일 뿐이다. 실제 실행 결과를 주장하려면 build identity, deployed dependency identity, loaded Data revision까지 이어져야 한다.

이 원칙으로 정리하면 목표는 “하네스 0개”가 아니다. **제품 경로를 직접 증명하는 작고 빠른 검증만 남고, 나머지는 변경 영역별·release별·사용자 판정별로 정확히 분리된 상태**다.
