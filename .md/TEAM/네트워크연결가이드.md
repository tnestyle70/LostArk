# LostArk 팀 네트워크 연결 가이드

이 문서는 팀 LAN Server 주소 교체, 실제 4인 접속, 같은 PC의 자동 격리 테스트를 빠르게 수행하는
실행 가이드다. 주소와 만료일의 단일 정본은
[`Tools/Network/TeamLanEndpoint.json`](../../Tools/Network/TeamLanEndpoint.json)이며, 상세 public 계약과
외부 네트워크 보안 경계는
[`TEAM_GAMEPLAY_INTERFACE_HANDBOOK.md`](TEAM_GAMEPLAY_INTERFACE_HANDBOOK.md)의
`서로 다른 장소에서 Server와 Client 연결`을 따른다.

## 먼저 결론

현재 구현에는 Server 자동 탐색이 없으므로 Client에는 접속할 Server의 구체적인 IPv4가
반드시 필요하다. 격리 테스트의 `localhost`를 제외하면 현재 Client는 일반 DNS hostname을
해석하지 않으므로 LAN·VPN·공인 endpoint도 IPv4로 지정한다.

| 구분 | 값 |
|---|---|
| 현재 Client 접속 endpoint | `10.207.18.103:7777` |
| 직전 팀 endpoint | `192.168.0.20:7777` |
| Server listener | `0.0.0.0:7777` |
| 실제 4인 LAN 테스트 | 여러 PC가 `10.207.18.103:7777`으로 접속 |
| 자동 4인 격리 테스트 | 같은 PC의 `127.0.0.1:17778` |
| Character Select 독립 session 테스트 | 같은 PC의 `127.0.0.1:17777` |

`0.0.0.0`은 Server가 현재 PC의 모든 네트워크 어댑터에서 받겠다는 bind 주소다. Client가 접속할 수
있는 목적지 주소가 아니므로 `LOSTARK_SERVER_HOST=0.0.0.0`으로 설정하지 않는다.

각 Client PC의 자기 IPv4는 서로 달라야 정상이다. 모든 PC가 같은 IP를 갖는 것이 아니라, 서로 다른
출발지 IP를 가진 Client들이 Server PC의 한 주소인 `10.207.18.103`으로 모인다.

## 1. IP를 바꾸기 전에 Server PC를 확인한다

Server로 사용할 PC에서 다음 명령을 실행한다.

```powershell
$connectedInterfaceIndexes = @(
    Get-NetIPInterface -AddressFamily IPv4 |
        Where-Object { $_.ConnectionState -eq 'Connected' } |
        ForEach-Object { $_.InterfaceIndex }
)
Get-NetIPAddress -AddressFamily IPv4 |
    Where-Object {
        $_.AddressState -eq 'Preferred' -and
        $connectedInterfaceIndexes -contains $_.InterfaceIndex -and
        $_.IPAddress -notlike '127.*' -and
        $_.IPAddress -notlike '169.254.*'
    } |
    Select-Object InterfaceAlias, IPAddress, PrefixLength
```

실제 Wi-Fi 또는 Ethernet 어댑터가 새 endpoint를 소유해야 한다. WSL, Hyper-V, VPN 가상 어댑터의
주소를 같은 LAN의 Server 주소로 잘못 고르지 않는다.

현재 Server PC는 `Wi-Fi 2`에서 `10.207.18.103/24`를 소유하므로 `.103`이 맞다. 직전
`192.168.0.20`이나 다른 주소로 바꿀 때도 먼저 Server PC가 그 주소를 실제로 소유하는지
확인해야 한다. 주소를 소유하지 않은 상태에서 Client 설정만 바꾸면 아무도 접속할 수 없다.

## 2. 팀 정본을 바꾸지 않는 1회 endpoint 확인

다른 Server IPv4를 한 Client에서 잠깐 확인하는 것이 목적이면
`TeamLanEndpoint.json`, `.vcxproj.user`, C++ fallback을 부분 변경하지 않는다. Server PC가
해당 IPv4를 실제로 소유하고 `0.0.0.0:7777`에 수신 중인 상태에서, Client를
실행할 PowerShell process에만 임시 환경값을 설정한다.

```powershell
$env:LOSTARK_SERVER_HOST = '192.168.0.20'
Push-Location Client/Default
..\Bin\Debug\Client.exe
Pop-Location
Remove-Item Env:LOSTARK_SERVER_HOST -ErrorAction SilentlyContinue
```

위 명령은 현재 PowerShell에서 직접 실행한 Client에만 적용된다. Visual Studio는
sync가 작성한 `.vcxproj.user`와 IDE cache를 사용하므로 이 임시 shell 절차를
Visual Studio 팀 설정으로 사용하지 않는다.

Server 주소를 `.103`에서 다른 주소로 팀 전체에 바꾸거나 Visual Studio로 4인 테스트하려면
반드시 다음 3절의 공용 endpoint 변경을 한 단위로 적용한다.

## 3. 팀 공용 endpoint를 바꾸어 PR에 반영할 때

팀원 모두가 같은 기본값을 쓰게 하려면 다음 파일을 한 변경 단위에서 함께
갱신한다. 각 PC의 적용 순서는 `pull -> Sync-TeamLanEndpoint.ps1 -> Visual Studio
project Reload 또는 IDE 재시작 -> 선택 configuration fresh build`이다.

현재 `.103`을 사용할 때의
[`TeamLanEndpoint.json`](../../Tools/Network/TeamLanEndpoint.json)은 다음과 같다.

```json
{
  "schema": "lostark.team-lan-endpoint",
  "version": 1,
  "serverBindAddress": "0.0.0.0",
  "serverHost": "10.207.18.103",
  "port": 7777,
  "activeThroughKst": "2026-09-30T23:59:59+09:00"
}
```

다른 주소로 교체할 때는 Server PC가 그 주소를 소유한 것을 확인한 뒤 위 JSON의
`serverHost`와 아래 표의 나머지 공용 계약을 함께 바꾼다.
`serverBindAddress=0.0.0.0`, port `7777`, 격리 하네스의 `127.0.0.1:17777/17778`은 유지한다.

| 파일 | 바꾸는 값 |
|---|---|
| `Tools/Network/TeamLanEndpoint.json` | `serverHost` 정본 |
| `Client/Private/NetworkManager.cpp` | 환경변수 없이 직접 실행한 Client의 compiled fallback |
| `Client/Default/Client.vcxproj` | x64 Debug/Release 공유 debugger 환경값 |
| `AGENTS.md`, `CLAUDE.md` | 세션 시작과 런타임 public 계약 |
| `.md/TEAM/README.md` | 팀 문서 진입점의 현재 endpoint |
| `.md/TEAM/TEAM_GAMEPLAY_INTERFACE_HANDBOOK.md` | 실행·진단 정본 |
| `.md/TEAM/네트워크연결가이드.md` | 팀 실행 체크리스트 |

`Framework.slnLaunch`에는 IP 리터럴이 없으므로 `Server + Client`와 `Client Only` profile은 그대로
사용한다. Server 코드와 project의 기본 bind도 계속 `0.0.0.0`이므로 concrete Wi-Fi 주소로 바꾸지 않는다.

과거 `.md/GB/<날짜>/`의 `.103` PLAN/RESULT는 당시 실행 증거다. 현재 endpoint를 바꾼다는 이유로
역사 문서를 전역 치환하지 않는다.

변경 뒤 최소 정합성 검사는 다음과 같다.

```powershell
Get-Content -Raw Tools/Network/TeamLanEndpoint.json | ConvertFrom-Json | Out-Null
[xml](Get-Content -Raw Client/Default/Client.vcxproj) | Out-Null
powershell -NoProfile -ExecutionPolicy Bypass `
    -File Tools/Network/Sync-TeamLanEndpoint.ps1
git diff --check
```

PR 전에는 Client x64 Debug/Release, NetworkProtocolHarness Debug/Release, Server Debug/Release와
각 configuration의 `Server.exe --contract-test`도 통과시킨다. 실제 LAN 도달성은 하네스가
아니라 다른 PC의
`Test-NetConnection`으로 별도 확인한다.

## 4. 현재 `.103` Server와 Client 실행

### 4.1 Server PC

동기화 출력에서 다음 값들을 확인한다.

```text
Machine role: server-host
Server debugger bind: 0.0.0.0:7777
Client debugger endpoint: 10.207.18.103:7777
Visual Studio start target: Server + Client profile
```

Visual Studio의 `Server + Client` profile을 선택한 뒤 사용자가 `Ctrl+F5`를 누른다. 실제 플레이용
Server에는 `--smoke-timeout-ms`를 붙이지 않는다. Server CMD에 다음 listener가 보여야 한다.

```text
Listening on 0.0.0.0:7777
```

Server 플레이 중에는 `10.207.18.103`을 가진 `Wi-Fi 2` 어댑터 연결을 유지한다.

### 4.2 다른 Client PC

모든 Client PC가 같은 commit과 같은 configuration을 사용해야 한다.

```powershell
git rev-parse HEAD
powershell -NoProfile -ExecutionPolicy Bypass `
    -File Tools/Network/Sync-TeamLanEndpoint.ps1
Test-NetConnection 10.207.18.103 -Port 7777
```

기대값은 다음과 같다.

```text
Machine role: client
Client debugger endpoint: 10.207.18.103:7777
TcpTestSucceeded: True
```

Client PC에서는 `Client Only (Server Already Running)` profile 또는 Client project만 사용자가
`Ctrl+F5`로 시작한다. 다른 PC에서 Server project까지 함께 시작하지 않는다.

직접 `Client.exe`를 실행하면 `.vcxproj.user`가 적용되지 않는다. 그 경우 실행하는 PowerShell의
환경값을 구체적인 Server 주소로 맞춘다.

```powershell
$env:LOSTARK_SERVER_HOST = '10.207.18.103'
Push-Location Client/Default
..\Bin\Debug\Client.exe
Pop-Location
```

Release를 실행하면 경로만 `..\Bin\Release\Client.exe`로 바꾼다.

## 5. 실제 여러 PC의 4인 연결 테스트

자동 4인 하네스와 실제 LAN 테스트는 목적이 다르다. 실제 LAN 테스트는 Wi-Fi 경로, Windows
Firewall, 공유기 AP/client isolation, 서로 다른 PC의 build/resource 정합성까지 확인한다.

### 5.1 준비

1. 기본 방화벽 계약이 허용하는 같은 `LocalSubnet`에 Server PC와 세 대의 Client PC를
   연결한다. 다른 routed subnet이나 VPN은 해당 source CIDR을 허용하는 방화벽 규칙을
   별도로 준비한 경우에만 사용한다.
2. Server를 시작하기 전 모든 PC가 같은 공유 branch의 commit을 pull하고 `git lfs pull`을
   완료한다. `git status --short`로 endpoint, protocol, Server/Client source와 generated-data
   입력에 서로 다른 tracked 변경이 없는지 확인한다. 작업 branch를 테스트하면 네 PC가
   같은 의도적 diff를 가지고 있어야 한다.
3. 모든 PC에서 같은 Release 정본 빌드를 실행해 Client/Server binary와 generated
   gameplay data를 같은 source로 새로 만든다.

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass `
       -File Tools/Build/Invoke-BuildAndRegression.ps1 `
       -Configuration Release
   git rev-parse HEAD
   ```

4. 네 PC의 `git rev-parse HEAD`와 configuration이 같고,
   `Client/Bin/Resources`의 `Fonts, Character, Deploy, Effect, Map, Sound, UI` 입력이 같은지 확인한다.
5. Debug로 공유 테스트하려면 모든 PC를 Debug로 fresh build한 뒤 Server를 끄고, Server PC에서
   `Server\Bin\Debug\Server.exe --reset-valtan-runtime-to-packaged`를 한 번 통과시킨다.
6. 모든 PC에서 `Sync-TeamLanEndpoint.ps1`을 실행한다.
7. Server PC에서 `Server + Client`를 시작한다.
8. 다른 세 PC에서 `Test-NetConnection 10.207.18.103 -Port 7777`이 성공한 뒤 Client만 시작한다.

표준 4인 구성은 Server PC의 Client 한 명과 다른 PC의 Client 세 명이다. room 정원은
해당 shared world에 들어간 player 수로 계산한다.

### 5.2 같은 shared world에 들어간다

4인이 서로 보이는 통합 확인은 `Bern` 또는 `Valtan`에서 수행한다. `Character Select`는 session-private
설계이므로 여러 사람이 같은 Server를 사용해도 서로 보이지 않는 것이 정상이다.
Bern은 shared replication 확인에 사용하고, `ROOM_FULL`, replacement와 empty-room reset은
첫 네 명이 모두 Valtan에 있는 상태에서 검증한다.

### 5.3 확인 항목

- 첫 네 Client가 모두 Server 승인을 받고 같은 world에 진입한다.
- 네 Client가 player 네 명의 snapshot, 위치와 nickname을 일관되게 본다.
- 이동과 스킬 결과가 Server snapshot으로 다른 Client에 복제된다.
- 첫 네 Client가 모두 Valtan에 들어간 상태에서 다섯 번째 Valtan 입장은
  `Valtan human player slots are full. Lobby remains active.`로 거부된다.
- 한 Client가 정상 종료한 뒤 남은 Client가 3인 상태를 보고, 새 Client가 들어오면 다시 4인으로 수렴한다.
- Valtan에서 네 명이 모두 퇴장한 뒤 다음 네 명이 reset된 새 세대로 입장할 수 있다.

화면의 실제 표시와 조작 결과는 사용자가 직접 확인하고 기록한다. 자동 하네스 PASS를 실제 4대 PC의
LAN 연결 PASS로 대신 사용하지 않는다.

## 6. 퇴역한 고정 4인 loopback 테스트

`ValtanFourPlayerHarness`와 `Run-ValtanFourPlayerHarness.ps1`은 2026-08-29에 퇴역했다. 이 하네스는
실제 스킬·보스·레이드 AI를 검사하지 않고 `4명 승인 -> 5번째 ROOM_FULL`을 제품 요구로 고정했다.
향후 목표인 인간 4명 + Server AI 4명의 8전투원 raid와도 의미가 맞지 않는다.

일반 `ROOM_FULL` wire codec은 `NetworkProtocolHarness`, 초과 입장의 무변경 거부와 slot replacement,
empty-room reset은 `Server.exe --contract-test`가 계속 소유한다. 현재 `NetworkProtocolHarness`는
8개 전투원 snapshot 왕복도 고정한다. 이는 wire 수용량 증거이며 4개 봇의 판단·스킬·생존이나 실제
4개 Client가 8개 전투원을 관찰한다는 증거는 아니다. 그 경계는 Server raid composition 구현과 함께
기존 제품 contract 및 하나의 live scenario로 추가한다. 고정 4인 standalone project를 복원하지 않는다.

## 7. Character Select 독립 session 테스트

Character Select에서 두 Client가 서로 보이지 않아야 하는 Server-private simulation 계약은 다음 wrapper로
검증한다. Debug 하네스 전에는 runtime activation lock을 공유하는 실제 Debug Server를 반드시
종료하고, Release wrapper port `17777`도 비워 둔다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
    -File Tools/Network/Run-CharacterSelectIsolationHarness.ps1 `
    -Configuration Debug

powershell -NoProfile -ExecutionPolicy Bypass `
    -File Tools/Network/Run-CharacterSelectIsolationHarness.ps1 `
    -Configuration Release
```

wrapper는 기본적으로 `127.0.0.1:17777`을 사용하며 자신이 시작한 Server만 종료한다. 기본 mode는 다음
경계를 함께 검사한다.

- 서로 다른 Character Select session의 player와 entity가 broadcast되지 않는다.
- 한 session에서 소환한 monster와 damage가 다른 session에 섞이지 않는다.
- Bern에서는 두 Client가 shared world를 함께 본다.
- Bern에서 Valtan으로 이동해도 승인된 live session이 유지된다.
- 전체 결과가 `failures : 0`으로 끝난다.

`-G02IdentityFast`를 추가해도 Character Select isolation과 Bern shared proof는 그대로 실행하고,
Bern→Valtan transfer proof만 생략한다. 따라서 전체 world transfer 회귀를 대신하지 않는다.

## 8. Client 한 대씩 독립 확인

4인 테스트 전에 각 Client PC에서 다음 순서로 개별 문제를 분리한다.

1. `Sync-TeamLanEndpoint.ps1` 출력이 `client`와 `.103:7777`인지 확인한다.
2. `Test-NetConnection 10.207.18.103 -Port 7777`이 성공하는지 확인한다.
3. Client를 하나만 실행해 Lobby가 `Server: 10.207.18.103:7777`을 표시하는지 본다.
4. Bern 또는 Valtan 한 곳에 입장해 Server 승인을 받는지 확인한다.
5. Client를 종료한 뒤 Server에 session이나 player가 비정상 잔류하지 않는지 확인한다.

이 단계가 실패하면 4인 동시 테스트를 먼저 시도하지 않는다. 한 Client의 경로를 해결한 뒤 같은 절차를
나머지 PC에 반복한다.

## 9. 같은 Wi-Fi가 아닌 경우

모든 PC의 SSID 이름이 반드시 같아야 하는 것은 아니지만, Client에서 Server endpoint까지 라우팅 가능한
경로가 있어야 한다. 현재 `10.207.18.103`은 사설 IPv4이므로 다른 장소의 공유기나 모바일망에서는 보통
직접 도달할 수 없다.

- 같은 Wi-Fi/핫스팟과 같은 LAN: 현재 `.103`을 그대로 사용한다.
- 서로 라우팅된 사내 subnet: route와 함께 승인된 source IPv4/CIDR를 허용하는 별도
  방화벽 규칙이 필요하다.
- 서로 다른 장소: VPN IPv4를 팀 endpoint로 사용하고, VPN source CIDR을 별도
  방화벽 규칙으로 허용한다.
- 공인 인터넷 직접 노출: 일반 NAT 공인 IPv4는 공유기가 소유하고 Server PC가
  소유하지 않으므로 현재 `TeamLanEndpoint.json + Sync-TeamLanEndpoint.ps1` 단일 endpoint
  절차로는 지원하지 않는다. 공인 advertised endpoint와 Server owner address를 분리하는
  구현, TCP 7777 포트포워딩과 제한된 원격 방화벽 계약을 별도 작업으로 먼저 추가한다.

현재 repository 방화벽 규칙은 `RemoteAddress LocalSubnet`이다. 단순히 Server를 `0.0.0.0`에 bind했다고
외부 인터넷의 모든 Client가 자동으로 접속할 수 있는 것은 아니다. sync는 routed/VPN/공인
source 허용을 추가하지 않는다. 외부용 규칙은 Debug/Release Server.exe와 TCP 7777,
승인된 exact source를 따로 지정하고 repository가 소유한 `LocalSubnet` 규칙을 `Any`로
넓히지 않는다. 외부 공개는 별도 보안 작업으로 다룬다.
일반 NAT의 공인 IPv4를 `serverHost`에 바로 넣으면 소유권 검사 때문에 Server PC가
`server-host`로 판정되지 않으므로 현재 sync를 `-Role Server`로 우회하려 하지 않는다.

같은 Wi-Fi인데도 연결되지 않으면 공유기의 AP isolation 또는 client isolation이 켜져 있는지 확인한다.

## 10. 오래된 `.20`이 계속 보일 때

Client host 우선순위는 process 환경변수, 명시적 Debug local opt-in, compiled fallback 순서다.
Visual Studio와 직접 EXE 실행의 process 환경을 구분해 진단한다.

- Visual Studio: sync가 `.vcxproj.user`에 적은 `LocalDebuggerEnvironment`가 Client process 환경이
  되므로 sync 재실행 후 project Reload 또는 IDE 재시작이 필요하다.
- 직접 `Client.exe`: 실행 shell의 process 환경과 그 shell이 상속받은 User/Machine 환경을
  확인한다.

```powershell
Get-Item Env:LOSTARK_SERVER_HOST -ErrorAction SilentlyContinue
[Environment]::GetEnvironmentVariable('LOSTARK_SERVER_HOST', 'User')
[Environment]::GetEnvironmentVariable('LOSTARK_SERVER_HOST', 'Machine')
Remove-Item Env:LOSTARK_SERVER_HOST -ErrorAction SilentlyContinue
```

위 `Remove-Item` 명령은 현재 PowerShell process에서만 제거하며 영구 User/Machine 값,
이미 열린 Visual Studio와 실행 중 Client의 환경은 바꾸지 않는다. 영구 값이 있다면
새 Server IPv4로 교정하거나 제거한 뒤 새 shell과 Visual Studio를 연다. 그다음
`Sync-TeamLanEndpoint.ps1`을 다시 실행하고 Visual Studio project를 Reload하거나 IDE를 재시작한다.
Git 제외 `Client.vcxproj.user`는 직접 수동 편집하지 않고 sync 결과를 사용한다.

직접 실행한 오래된 `Client.exe`는 소스의 새 compiled fallback을 포함하지 않을 수 있으므로 다시 빌드하거나
실행 shell에서 `LOSTARK_SERVER_HOST=10.207.18.103`을 명시한다.

## 11. 증상별 빠른 진단

| 증상 | 먼저 확인할 것 |
|---|---|
| sync가 `not-listening` | Server가 아직 꺼져 있으면 정상이다. 설정 동기화는 완료된 상태다. |
| sync가 `client`인데 이 PC가 Server여야 함 | 이 PC가 `serverHost` IPv4를 실제 `Connected + Preferred` 상태로 소유하는지 확인한다. |
| 방화벽 관리자 권한 오류 | Server PC에서 관리자 PowerShell로 sync를 한 번 실행한다. |
| `Error=10049` | Server bind에 존재하지 않는 concrete IP를 넣었다. `0.0.0.0`으로 복구한다. |
| `TcpTestSucceeded: False` | Server listener, Server PC 주소, TCP 7777 방화벽, AP/client isolation 순서로 확인한다. |
| TCP는 True지만 Lobby에서 거부·종료 | Client/Server의 commit, configuration, protocol과 generated bootstrap을 맞춘다. |
| `Stage loading failed`로 Lobby에 남음 | 네트워크보다 Client Resources 또는 Loader 실패를 먼저 확인한다. |
| Lobby가 계속 `.20` 표시 | process 환경변수, `.vcxproj.user` sync, IDE cache, Client 재빌드 순서로 확인한다. |
| Character Select에서 다른 사람이 안 보임 | session-private 설계이므로 정상이다. Bern 또는 Valtan에서 4인을 확인한다. |

## 12. 현재 `.103` 정본 적용을 확인할 때

1. Server와 Client를 모두 종료한다.
2. Server PC가 `10.207.18.103`을 실제로 소유하고, 모든 Client가 `.103`까지 같은
   `LocalSubnet` 또는 승인된 route/방화벽으로 도달할 수 있는지 확인한다.
3. 팀 공용 endpoint 변경 파일 전체가 `.103` 기준인지 확인하고 공유 commit을
   모든 PC에 pull한다.
4. 모든 PC에서 `Sync-TeamLanEndpoint.ps1`을 다시 실행한다.
5. Visual Studio project를 Reload하거나 IDE를 재시작한다.
6. 모든 PC의 Client/Server를 같은 configuration으로 fresh build해 `.103` compiled fallback과
   현재 generated data를 반영한다.
7. 직접 EXE를 실행할 shell의 `LOSTARK_SERVER_HOST`를 `.103`으로 교정하거나 제거한 뒤
   새 shell을 연다.
8. Server는 계속 `0.0.0.0:7777`로 시작한다.
9. 다른 PC에서 `Test-NetConnection 10.207.18.103 -Port 7777`을 확인한다.
10. 각 Client를 독립 확인한 뒤 실제 4인 LAN 테스트를 반복한다.

한 Client PC의 `.vcxproj.user`만 다른 주소로 바꾸는 것은 팀 endpoint 교체가 아니다. 다른 PC와
compiled fallback이 갈라지므로 사용하지 않는다. 만료 뒤에도 `-AllowExpired`로 조용히 우회하지 않고
endpoint와 public 계약을 먼저 갱신한다.

sync는 새 `server-host`의 방화벽 규칙은 확인하지만, 이전 Server PC가 `client`로
바뀌어도 기존 Debug/Release TCP 7777 규칙을 자동 삭제하지 않는다. 같은 PC의 IP만
바꾸는 경우에는 기존 규칙을 계속 사용한다. Server 역할을 다른 PC로 영구 이전하면
이전 PC의 exact repository Server 규칙은 대상과 역할을 확인한 뒤 관리자 방화벽
정책으로 별도 정리한다.
