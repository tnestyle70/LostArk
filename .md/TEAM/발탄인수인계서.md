# 발탄 패턴·Boss Tuning 정본 인수인계서

이 문서의 1~6장은 기존 `formatVersion: 1`, `scope: PHASE_ONE` 단일 파일과 이미 연결된 제품 계약을
migration 참고로 설명한다. 현재 public 저작 경계는 `Data/Valtan`의 gameplay, presentation,
combatobjects, worldeventsets, legacy-compatibility 다섯 split source를 stable ID로 join하는 계약이다.
각 source의 `formatVersion: 1`과 이를 투영한 Server `Gameplay.bootstrap` v26은 서로 다른 version 축이다. 7장 이후는
[2026-08-25 발탄 Boss Tuning 구현 계획](../GB/08-25/2026-08-25_VALTAN_BOSS_TUNING_BALANCE_TOOL_HOT_RELOAD_IMPLEMENTATION_PLAN.md)의
목표와 [동일 작업 RESULT](../GB/08-25/2026-08-25_VALTAN_BOSS_TUNING_BALANCE_TOOL_HOT_RELOAD_RESULT.md)의
실제 구현 경계를 함께 설명한다. `현재 구현`, `제한`, `후속` 표기를 구분하며, 후속 항목을 이미 동작하는 런타임
기능으로 보고하거나 기존 v1 `Valtan.pattern.json`에 임의로 먼저 추가하지 않는다.

## 1. 이 문서가 고정하는 북극성

발탄의 몸 애니메이션, Server 판정, Product Effect를 서로 다른 임시 목록에서 맞추지 않는다.
작업자는 다음 split authoring 정본을 같은 `patternId -> stageId -> actionId`와 하나의 joined revision으로 본다.

```text
Data/Valtan/Valtan.gameplay.json
        |  Server pattern graph / selection / stage / action / hit / motion / event / branch
        |
        +-- strict patternId / stageId / actionId join -- Data/Valtan/Valtan.presentation.json
        |                                             animation / Effect / camera invocation
        |                                             |
        |                                             `-- effectAssetId
        |                                                   Data/Effects/Authored/*.effect.json
        |                                                   element / material / resource
        |
        +-- stable references
        |     Data/Balance/DamageProfiles.json
        |     Data/Valtan/Valtan.combatobjects.json
        |     Data/Valtan/Valtan.worldeventsets.json
        |     Data/Valtan/Valtan.legacy-compatibility.json
        |     Data/Actors/BossCatalog.json combatObjectVisuals
        |
        `-- projector generated Product (read-only)
              Data/Encounters/Valtan/ValtanEncounter.json
              Data/Animation/Authored/Valtan/Valtan.patternbindings.json
              Data/Animation/Authored/Valtan/Valtan.patterneffectcues.json
              rotations / Server·Client bootstrap
```

제품 Server와 발탄 Arena는 두 authoring JSON을 두 번째 런타임으로 직접 읽지 않는다. publisher가 strict join한
typed projection만 소비한다. Balance Tool은 gameplay만 편집하고 presentation은 read-only 상태와 전용 Tool
deep-link로 보여 준다. Animation Tool과 Effect Tool은 같은 joined revision을 소비하되 자기 presentation field와
authored Effect content만 편집한다.

exact direct-authored JSON의 안전한 path와 identity가 확인되면 Effect `Open Editor` admission은 Product cue/Actor
join 및 Track A adapter/drawable/timeline preview와 독립이다. Valtan 한 Product join 실패는 그 행만 격리하며
player 또는 다른 authored Effect의 Saved/Open index를 `0`으로 만들지 않는다. `Open Editor`, `Play Product`,
`Play Server Pattern`, `Save`, `Bind`는 별도 명령이고 Play/preview가 Save·Bind를 자동 수행하거나 Save가 자동
재생·pattern binding을 만들지 않는다.

`INDEPENDENT EFFECT`는 복사본을 만드는 폴더가 아니다. 같은 stable Effect asset을 단독으로 열고 재생하는
library view다. 패턴 stage에는 사용 reference만 남고 같은 asset의 편집 행을 이중으로 만들지 않는다.
각 entry는 선언한 `ownerPatternId/ownerStageId`에 **정확히 한 번** 참조되어야 한다. 현재 도끼는
`HIGH_JUMP/AIRBORNE`, 도넛은 `FIST_IN_OUT/INNER`만 owner다. 도넛은 INNER에서 unified Effect를 한 번
시작하고 `OUTER.effectRefs`는 비워 둔다. 여기에 같은 independent ID를 다시 넣으면 projector와 Client exact
join이 모두 실패하도록 닫혀 있다. 실제 Arena cue와 Effect Tool authoring preview는 모두 `stopPolicy: natural`인
Effect의 문서 lifetime을 다음 stage까지 유지하므로 unified INNER -> OUTER visual을 한 번의 spawn으로 재생한다.
명시적 `CUE_END`만 source end window에서 계속 종료된다.

위 두 entry는 현재 split presentation source가 명시적으로 소유한 목록이다. 전체 Encounter를 기준으로 보면
`effect.valtan.red-blade-wave.active`도 `SERVER_COMBAT_OBJECT`가 소유하는 독립 world-root Effect다. 현재 이
붉은 검기는 `VALTAN_RED_BLADE_WAVE` 패턴의 `[WORLD]` 행에서 Open/Play할 수 있지만 최상위
`INDEPENDENT EFFECT`에는 아직 자동 파생되지 않는다. 새 `Create Solo Effect`를 추가해 이 owner를 복제하지
않는다. 후속 도구 확장은 `ValtanCombatObjects.json + BossCatalog.json`의 검증된 두 combat-object visual
(도끼, 붉은 검기)을 최상위 owner library로 자동 파생하고, 도넛 같은 `SERVER_PATTERN_STAGE`만 presentation source가
명시적으로 보충하는 방향으로 한다.

현재 split-owned pattern 중 `boss.flag.counterable`을 여는 패턴은 없다. 이를 억지로 counterable로 바꾸지 않고,
gameplay source의 `counterReactionLayers`가 기존 Product에서 실제로 counterable인 네 stage를 reference-only layer로
정확히 가리킨다. 세 단계 `VALTAN_TRIPLE_COUNTER`와 `VALTAN_CENTER_GRAB_COUNTER_64/COUNTER_WINDOW`의
window/success/failure action은 기존 Encounter와 `Valtan.patternbindings.json`의 clip을 그대로 사용한다.
이 layer는 Animation/Effect Tool에 표시되지만 일곱 패턴 admission이나 Phase-1 랜덤 풀을 늘리지 않는다.

## 3. 정본 필드의 담당 경계

### 보스 패턴 담당자

다음 값을 `Valtan.gameplay.json`에서 조정한다.

- pattern selection: health bar 범위, phase, weight, 최대 연속 사용, 사거리
- Server stage: duration, hit shape, hit schedule, push/knockdown, `serverDamageProfileId`
- target/aim policy, stage motion, combat-object spawn action
- `WALL_CONTACT`, `TIMEOUT`, `PART_DESTROYED` 같은 branch graph
- `TRIGGER_WORLD_EVENT_SET`의 `worldEventSetId`와 gameplay event/branch

Effect asset path, animation clip, `cameraInvocationId/cameraCueId`를 Server 코드나 gameplay source에 넣지 않는다.
camera invocation은 `Valtan.presentation.json`, camera keyframe은 전용 camera 문서가 소유한다. gameplay-only
candidate는 `Validate Draft -> Save Authoring -> Publish Candidate -> Apply Hot Reload` 뒤 다음 decision/pattern부터
적용된다. `ENCOUNTER_RESET`, `SERVER_RESTART`, presentation byte 변경은 live apply하지 않는다.

1페이즈 일반 패턴의 선택 정본은 gameplay source의 `decisionModel`이다. `selectionSets[]`가 mode/candidates/weight/
enabled를, `selectionWindows[]`가 gameplay phase/health band/selectionSetId/compatibilityRotationId를 소유한다.
160~130, 130~109 두 health band 모두 `WEIGHTED_POOL`이며 후보는 `WHIRLWIND / DASH_CHARGE / FOUR_SLASH /
FIST_IN_OUT / HIGH_JUMP` 정확히 다섯 개다. range, armor/phase, cooldown, 최대 연속 사용 조건은 각 managed pattern
행이 소유한다.
기존 `ValtanPatternRotations.json`의 이 구간 ordered list가 먼저 재생되지 않으므로 weight 변경은 다음 normal
선택부터 실제 Server 랜덤 경로에 반영된다. 130/109 health-bar mechanic queue는 항상 이 랜덤 선택보다 우선한다.

gameplay source에는 raw 피해량을 중복 저장하지 않고 다음 stable damage profile을 저장한다. 실제 값은
`Data/Balance/DamageProfiles.json`의 `damageRatePercent`이며 방어력 등을 적용한 최종 피해량은 Server가 계산한다.

### 애니메이션 담당자

`Valtan.presentation.json`에서 각 stage의 animation occurrence만 조정한다.

- `clip`, `sourceStartMs`, `playMs`, `playRate`
- 유한 반복 횟수 `repeatCount`
- stage 끝 처리 `endPolicy`: `EXACT`, `HOLD_LAST_POSE`, `LOOP_TO_STAGE_END`
- `LOOP_TO_STAGE_END` 구간의 단 하나인 looping remainder를 표시하는 `repeatUntilStageEnd`
- 원본/프로젝트 조정 근거인 `mappingBasis`

presentation source는 해당 pattern이 사용할 수 있다고 승인한 원본 `sourceActionId/sequenceIndex` 목록이다.
primary sequence 외 반응 animation을 결합할 때도 먼저 여기에 role과 함께 선언한다. Animation Tool의
`Valtan Pattern Master`가 실제 튜닝·전체 재생 화면이며, 기존 1~67 `Valtan Pattern Reference`는 원본 후보를
찾는 read-only 근거 화면이다.

기존 binding의 boolean `loop`는 숫자 반복 횟수가 아니다. `repeatCount`는 유한한 동작 반복의 의미를 기록하고,
occurrence는 실제로 재생할 stable occurrence를 순서대로 명시한다. publisher는 presentation source에 없는 clip을
암묵적으로 복제하지 않는다. `repeatCount > 1`이면 그 수와 같은 개수의 동일 clip occurrence가 있어야 하며,
Animation/Effect Tool은 그 count를 재생 경계로 소비한다. `repeatUntilStageEnd`만 기존 binding의 boolean
`loop`로 투영한다.

`EXACT`는 모든 source cut의 `playMs / playRate` 합이 Server stage와 2ms 이내로 같아야 한다.
`HOLD_LAST_POSE`는 명시적으로 마지막 pose를 stage 끝까지 유지한다. `LOOP_TO_STAGE_END`는 `playMs: 0`이며
`repeatUntilStageEnd: true`인 occurrence 하나만 남은 wall time을 채운다. 설명 없는 underfill이나 loop는
publisher와 Tool admission에서 거부한다.

돌진 WINDUP의 현행 세 occurrence는 같은 600ms를 세 번 재생한 것이 아니라 `600 + 600 + 2450ms`다.
이번 정본은 이 실측을 숨기지 않고 `repeatCount: 3`과 세 source cut을 함께 보존한다. 정확히 `600ms x 3`으로
바꾸려면 pose jump와 telegraph cue를 함께 다시 승인하고 WINDUP 총시간도 1800ms로 바꿔야 한다.

### Effect 담당자

`Valtan.presentation.json`은 managed Effect의 stable `effectAssetId`, owner occurrence, source window,
anchor/local transform/follow/stop/repeat과 독립 Effect 사용 위치를 소유한다. 실제 element, material, resource,
Revolution과 effect-local lifetime은 `Data/Effects/Authored/*.effect.json`에서 조정한다.

각 cue invocation은 cue가 붙는 정확한 `clipOccurrenceId`와 source-local 시작/끝 시간을 presentation source에
저장한다. cue의 stage/action owner나 source window를 generated Product cue JSON에서 따로 고치지 않는다.

`sourceEndMs`는 의미상 optional인 nullable 값이다. split source의 exact object에는 key를 유지하되 `null`이면
명시적 끝이 없고 `bHasSourceEnd=false`이며, 숫자이면 `bHasSourceEnd=true`인 `cue_end` window다. join은 반드시
has-value를 먼저 비교하고 양쪽 모두 값이 있을 때만 숫자를 비교한다. `null`을 내부 기본값 `0`이나
`sourceStartMs`와 비교해 drift로 판정하면 natural cue와 independent owner join이 다시 깨진다.

managed cue 15개는 `scalePolicy`를 반드시 명시한다. 이 정책은 보스 actor 크기와 바닥 footprint를 같은 배율로
묶지 않기 위한 호출 계약이며 Effect element 자체를 재저작하는 배율이 아니다.

| policy | 현재 수 | 합성 규칙 |
|---|---:|---|
| `OWNER_RELATIVE` | 4 | sampled owner root의 translation, rotation, scale을 모두 상속한다. `presentationScale: 1.0`이 적용되는 몸 부착 Effect다. |
| `GAMEPLAY_FOOTPRINT` | 9 | owner translation/rotation은 유지하고 owner scale은 제거한 뒤 authored `worldScale: [1.5, 1.5, 1.5]`를 사용한다. 보스 크기와 별개인 공격 footprint다. |
| `ARENA_ABSOLUTE` | 2 | owner scale을 제거하고 authored `worldScale: [1.5, 1.5, 1.5]`를 사용하는 arena 연출 lane이다. 현재 합성 수학이 footprint와 같아도 semantic policy는 합치지 않는다. |

Balance Tool은 이 정책과 최종 resolved scale을 read-only로 보여 준다. 정책 변경은 presentation 담당이 하고,
Effect element의 mesh/particle/decal geometry는 `Data/Effects/Authored/*.effect.json`에서 Effect 담당이 조정한다.

- 현재 v1 All Effects의 패턴 `Play Authoring Timeline`은 전체 body sequence와 현재 선택한 exact Effect occurrence 하나를
  함께 재생한다. 같은 패턴의 모든 저장 Effect를 한 번에 spawn하는 기능으로 해석하지 않는다.
- 패턴의 저장 Effect를 선택한 뒤 authoring timeline을 재생하면 그 Effect의 stage-global cue offset,
  anchor/follow/local transform/stop window를 유지한 채 body와 함께 튜닝한다.
- `INDEPENDENT EFFECT`의 도넛(`SERVER_PATTERN_STAGE`)은 같은 full-pattern Product cue 경로를 쓰고,
  도끼(`SERVER_COMBAT_OBJECT`)는 Server가 복제하는 world combat-object root 경로를 쓴다.
- 도끼의 `Play Independent Effect`는 현재 stage된 Valtan root를 한 번 snapshot해 translation과 rotation만 보존하고
  actor presentation scale은 제거한다. 이후에는 fixed world root로 재생하며 Effect local clock은 `0ms`에서 시작한다.
  이는 독립 저작 preview이므로 pattern의 TAKEOFF 1933ms offset을 기다리지 않는다.
- 실제 추적 위치, 무작위 선택, damage와 hit는 Server pattern/combat-object 담당이다.
- Effect Tool의 world proxy는 시각 저작 보조이며 Server gameplay 정답이 아니다.
- 현재 Effect 문서가 구조상 valid하지만 drawable element가 없는 경우에도 `Play Authoring Timeline`은 막히지 않는다.
  Effect만 재생 불가 상태로 알리고 body animation 전체 타임라인은 animation-only로 계속 재생한다. 반대로
  `Play Saved Effect`는 drawable이 될 때까지 fail-closed인 것이 정상이다.

2026-08-24 사용자 튜닝 복구 기준 authored element inventory는 도넛 5, HIGH_JUMP TAKEOFF 1, LAND 2,
sky axe 5이며 stable-ID 누락/중복은 0이다. stable-ID union이 다시 넣었던 legacy 44행은 successor lineage에
`INTENTIONALLY_REMOVED`로 봉인한다. 이 숫자는 영구적으로 element 삭제를 금지하는 값이 아니라 현재 튜닝본의
회귀 기준이다. 의도적인 추가/삭제는 successor lineage와 Effect Tool inventory test를 같은 변경에서 갱신하고,
source validator와 `CEffectCatalog` lookup의 authored identity 일치로 확인한다.

`effect.valtan.sky-axe.active`의 authored geometry와 도끼 속도·회전·decal 구성은 Effect V1 저작 데이터가 소유한다.
Boss core는 그 element 값에 `0.75`를 강제하거나 특정 authored scale 수치로 덮어쓰지 않는다. actor
`presentationScale`과 cue `scalePolicy`가 구조적으로 맞아도 실제 도끼 크기·속도·방향·바닥 정렬은 사용자가

### 고공 점프와 추적 도끼

`serverMotion.travelStageId`는 `LAND`다. TAKEOFF의 1933ms animation 중 `1133~1500ms`에만 빠르게 상승하고
AIRBORNE은 정점에서 유지한다. LAND는 시작 `0~267ms`에 잠근 착지점으로 빠르게 하강한 뒤 나머지 animation wall을
지상에서 재생한다. Server-authoritative Client는 `b_root` X/Y/Z를 모두 잠그고 Server snapshot만 world transform을
소유한다. AIRBORNE의 Server action은
`combatobject.valtan.high-jump.target-axe`만 생성한다. Client Effect ID는 BossCatalog의 visual mapping이 소유한다.

Client presentation은 stage마다 model animation index 하나만 비교하지 않는다. `TAKEOFF -> AIRBORNE -> LAND ->
RECOVERY` occurrence index와 local presentation clock을 함께 유지해, 30Hz Server snapshot이 같은 AIRBORNE action을
반복해도 `mesh_att_battle_8_01_loop`를 매 snapshot마다 0초로 재시작하지 않는다. 반대로 같은 model animation
index를 재사용하는 서로 다른 occurrence라면 occurrence 전이로 restart/seek한다. RECOVERY는
`mesh_att_battle_8_01_loop` 재사용이 아니라 `mesh_idle_battle_1` 400ms exact다.

gameplay event의 생성 기준은 `volleyPolicy: PER_ALIVE_PLAYER`와 3회 `spawnSchedule`이다. AIRBORNE의
`0/1333/2666ms`마다 살아 있고 낙하 중이 아닌 플레이어를 다시 집계해 combat object를 한 개씩 만들고, 같은
transaction에 저작된 발탄 스폰 중앙 기준 랜덤 고정 도끼 4개를 더한다. companion의
`origin.kind: RESOLVED_VOLLEY_POSITION`이 resolve된 좌표를 소비한다. projector가 만드는 legacy Product에서만 이를
`originPolicy: LOCKED_TARGET_PER_ALIVE_PLAYER`로 표현한다. object lifetime은 owner AIRBORNE에서 투영된 각 spawn부터 `6500ms`지만,
플레이어·랜덤 도끼 모두 각 wave가 resolve한 생성 pose에 즉시 고정된다. Product의 legacy
`LOCKED_TARGET_PER_ALIVE_PLAYER` 표기는 target association을 보존하는 projection일 뿐 이동 추적 권한이 아니다.
판정은 각 object 생성 후 1200ms에 한 번, CIRCLE 3.5m이며 BossCatalog가
`combatobject.visual.valtan.high-jump.target-axe.v1 -> effect.valtan.sky-axe.active`를 연결한다.

아레나 도끼는 `boss.fSpawnPosition*`을 중앙으로 반경 14m 안에서 결정론적으로 뽑는다. 각 중심점은 Server
navigation exact walkability와 중앙 높이 차이 1m 이하를 통과하고, 네 도끼는 서로 7m 이상 떨어진다. 같은
pattern sequence/wave는 같은 좌표를 만들며 player 도끼와 랜덤 도끼는 한 transaction으로 commit/rollback한다.
각 웨이브의 타격 시점은 AIRBORNE 시작 기준 약 `1.200/2.533/3.866초`다.

## 6. 의도적으로 남긴 콘텐츠 확인점

- `휠윈드 1.2초`는 전체 패턴이 아니라 SPIN stage 1.2초로 해석했다.
- `VALTAN_FLOOR_WIPE_130`의 stable ID와 trigger는 130줄을 유지한다. 이전 표시명 `115줄`은 데이터와 모순이라
  중립 표시명으로 교체했다. 실제 trigger를 115로 바꾸려면 rotation/health-bar mechanic 검증과 함께 별도 승인한다.
- 돌진 WINDUP은 세 번이라는 의미와 실제 세 source cut을 모두 저장했다. 동일 600ms 세 번으로 아직 바꾸지 않았다.
- 4연속 공격은 이름과 맞게 Server contact를 총 4회로 복원했다.
- 도끼는 AIRBORNE 6.5초 안의 세 웨이브로 구현되어 있다. 각 웨이브는 당시 생존 플레이어별 1개와 아레나 중앙
  기준 랜덤 4개이며, 플레이어 도끼만 각자 첫 1200ms pulse까지 추적한다. 4초 지속 추적으로 해석하지 않는다.
- 도넛 independent owner는 INNER 한 곳뿐이다. OUTER 판정은 Server stage로 계속 존재하지만 같은 Effect ref를
  OUTER에 한 번 더 넣지 않는다.
- 도넛은 INNER에서 natural cue를 한 번 시작하고 문서 lifetime으로 OUTER까지 이어진다. 같은 Effect를 OUTER에서
  다시 spawn하지 않는다. 실제 색·크기·발생 시점의 visual fidelity만 사용자 timeline/Arena 확인 대상으로 남는다.
- Carrier V1 historical receipt와 cue-v2 재구성 도구는 historical evidence로 유지한다. 현행 direct-authored
  Product 변경에 맞춘다는 이유로 raw receipt나 sealed candidate를 재작성하지 않는다.
- 새 `Data/Effects` 제품 원본이나 successor receipt를 추가했으면 `Validate-EffectSources.ps1`을 실행한다.
  Effect JSON은 물리 폴더가 정본이며 `Client.vcxproj/.filters`에 파일별로 등록하지 않는다.

이 항목들을 바꾸면 소유 source, joined projection, validator, Server/Effect harness를 같은 PR에서 갱신한다.

### 7.1 현재 구현과 남은 경계

legacy `CBalanceTool`의 generated `ValtanEncounter.json` Save는 계속 차단한다. 발탄 저장은 stable-ID draft를 split

### 7.2 단일 화면과 단일 파일을 혼동하지 않는다

Boss Tuning은 한 화면·한 transaction·한 joined revision으로 동작하지만 모든 domain 값을 한 파일에 복제하지 않는다.
한 값의 저작 정본은 정확히 하나다.

| 정보 | v2 저작 정본 | 다른 source와 join하는 값 |
|---|---|---|
| 패턴 graph, 선택, stage, spawn volley | `Data/Valtan/Valtan.gameplay.json` | 전체 typed Server definition |
| 보스 HP/AP/move/collision/health bars | `Data/Balance/BossProfiles.json` | gameplay source가 stable boss row를 join |
| 피해 배율 | `Data/Balance/DamageProfiles.json` | gameplay source가 `serverDamageProfileId`만 저장 |
| combat-object origin/hit/geometry/damage | `Data/Valtan/Valtan.combatobjects.json` | gameplay source가 `combatObjectArchetypeId`와 volley만 저장 |
| animation occurrence | `Data/Valtan/Valtan.presentation.json` | `patternId/stageId/actionId`, clip/source window/end policy |
| managed Effect 호출 시점·부착 | `Data/Valtan/Valtan.presentation.json` | stable asset/owner occurrence/window/anchor/follow/stop/repeat |
| Effect element/material/resource/lifetime | `Data/Effects/Authored/*.effect.json` | presentation source가 `effectAssetId`만 참조 |
| camera invocation owner/start/duration policy | `Data/Valtan/Valtan.presentation.json` | stable camera cue와 호출 edge |
| camera keyframe/FOV/shake | `ValtanCinematicCamera.json` | presentation source가 stable `cameraCueId`를 join |
| stable world-event set membership | `Data/Valtan/Valtan.worldeventsets.json` | gameplay event가 stable set ID만 저장 |
| 벽 group/mutation/nav/placement와 109 외 binding | 현행 `ValtanWorldEvents.json`의 World/Map 소유 rows | stable set을 통해 join, Balance Tool 직접 편집 금지 |
| combat-object visual | `BossCatalog.json` | archetype stable ID만 저장 |
| unmanaged 26개 Product closure | `Data/Valtan/Valtan.legacy-compatibility.json` | split source에 넣지 않는 read-only transition manifest |

`Data/Valtan/Valtan.combatobjects.json`이 object-owned origin/hit/geometry/damage를 소유한다. 현행
`Data/Encounters/Valtan/ValtanCombatObjects.json`은 gameplay owner/lifetime과 companion을 합친 projector Product다.
다음 파일은 계속 직접 편집하지 않는다.

legacy compatibility manifest는 기존 Product hash와 ordinal 기준 unmanaged closure를 이미
`Valtan.legacy-compatibility.json`에 봉인한다.

- `patternEntries[]`: unmanaged pattern runtime row, binding/cue closure, Encounter ordinal/hash
- `sharedRotationRows[]`: rotation ID/ordinal/hash와 ordered
  `patternRefs[] { patternId, ownership: MANAGED | LEGACY }`
- `legacyCombatObjectOwners[]`: unmanaged archetype의 owner pattern/stage, derived lifetime, original ordinal만
- `initialMigrationReceipt`: 최초 source Product path/hash. 이후 generated Product 전체 hash와 비교하지 않는다.

`rotation.valtan.100.84`처럼 managed/unmanaged pattern이 섞인 ordered row를 pattern별로 복제하지 않는다. Promote는
pattern entry를 제거하고 shared reference ownership만 LEGACY -> MANAGED로 바꾼다. 명시적 rotation edit 없이 row나
다른 reference를 삭제하지 않는다. object origin/hit/geometry/damage는 managed 여부와 무관하게 모두
`Valtan.combatobjects.json`이 소유한다. manifest는 RED_BLADE_WAVE owner/lifetime만 보존한다. full coverage가 끝나면
transition manifest를 폐기한다.

manifest root는 `schema: lostark.valtan-legacy-compatibility`, `formatVersion: 1`, `encounterId`와 위 네 block을 가진다.
partial closure, shared-row duplicate, owner 없음/복수, 최초 source hash 불일치는 migration을 거부한다. raw payload는
새 authoring API가 아니라 no-op compiler 입력이다.

- `Data/Encounters/Valtan/ValtanEncounter.json`
- `Data/Encounters/Valtan/ValtanPatternRotations.json`
- `Data/Encounters/Valtan/ValtanCombatObjects.json`
- `Data/Animation/Authored/Valtan/Valtan.patternbindings.json`
- `Data/Animation/Authored/Valtan/Valtan.patterneffectcues.json`
- Server bootstrap과 revision candidate 내부 artifact

## 8. split source를 strict join한 v2 내부 IR 계약

### 8.1 root 구성

아래 monolith JSONC는 기존 설계를 보존한 **in-memory joined IR 설명**이며 writable authoring schema가 아니다.
실제 source codec은 gameplay field를 `Valtan.gameplay.json`, presentation field를
`Valtan.presentation.json`에 나누고 stable `patternId/stageId/actionId`로 strict join한다. 새 구현이 아래 예시를
`Valtan.pattern.json` v2로 저장해서는 안 된다.

```jsonc
{
  "schema": "lostark.valtan-pattern-master",
  "formatVersion": 2,
  "bossArchetypeId": "BOSS_VALTAN",
  "encounterId": "ENCOUNTER_VALTAN",
  "scope": "PHASE_ONE",
  "previewPaths": {},
  "retiredPatternIds": [],
  "decisionModel": {
    "selectionSets": [],
    "selectionWindows": [],
    "mechanics": []
  },
  "counterReactionLayers": [],
  "independentEffects": [],
  "patterns": []
}
```

| root field | 의미와 검증 |
|---|---|
| `schema` | 정확히 승인된 schema ID여야 한다. unknown schema는 거부한다. |
| `formatVersion` | joined IR version이다. v1 `Valtan.pattern.json`은 migration 입력일 뿐 load만으로 덮어쓰지 않는다. |
| `bossArchetypeId` | Server stable archetype ID다. Prototype tag나 asset path를 쓰지 않는다. |
| `encounterId` | revision과 publisher가 묶을 stable encounter ID다. |
| `scope` | 초기에는 반드시 `PHASE_ONE`. 현재 live stable pattern ID coverage가 닫히기 전에는 `FULL_ENCOUNTER`로 올리지 않는다. |
| `previewPaths` | authoring join 문서의 Resources/repository 상대 ID만 허용한다. 절대 경로와 `..`는 거부한다. |
| `retiredPatternIds` | 삭제한 stable ID 재사용을 막는다. Product ordinal/참조가 닫힌 뒤에만 retire한다. |
| `decisionModel` | phase/health 구간별 후보 프로그램과 강제 mechanic을 소유한다. |
| `counterReactionLayers` | split source 밖의 기존 counter reaction을 read-only reference로 보존한다. |
| `independentEffects` | 복제 asset이 아니라 검증된 owner를 여는 library reference다. |
| `patterns` | stable pattern과 stage graph definition이다. 배열 index는 저장 ID가 아니다. |

v2로 옮길 때 기존 Product row의 stable ID 순서와 legacy-only row의 상대 ordinal을 projection receipt에 봉인한다.
no-op migration은 기존 global fallback의 RNG ticket 결과를 바꾸면 안 된다. `retiredPatternIds`에 넣었다는 이유만으로
다른 row를 앞으로 당겨 확률 구간을 조용히 바꾸지 않는다.

### 8.2 `decisionModel.selectionSets`

selection set은 “어떤 후보가 어떤 순서와 weight로 경쟁하는가”만 소유한다.

```jsonc
{
  "selectionSetId": "selectionset.valtan.160.130",
  "mode": "WEIGHTED_POOL",
  "candidates": [
    { "patternId": "VALTAN_WHIRLWIND", "weight": 20, "enabled": true },
    { "patternId": "VALTAN_DASH_CHARGE", "weight": 30, "enabled": true }
  ]
}
```

- `selectionSetId`는 stable ID다.
- managed selection set의 `mode`는 현재 `WEIGHTED_POOL`이다. post-109 ordered program은 legacy Product가
  read-only로 소유한다.
- `candidates` 배열 순서는 weighted ticket interval과 ordered cursor의 정본이므로 serializer가 정렬하지 않는다.
- `weight`는 **1..100000 양수**다. 비활성화는 별도 `enabled: false`만 사용하고 마지막 weight를 보존한다.
- 같은 set에 pattern ID를 중복 넣지 않는다.
- authored 확률은 `weight / 현재 enabled weight 합`일 뿐이다. 거리·cooldown 등 eligibility까지 적용한 실제 확률은
  매 decision마다 달라지므로 Server trace가 따로 보여 준다.

v1 pattern의 flat `selectionWeight`는 split source에서 명시적인 `compatibilitySelectionWeight`로 이름을 바꿔
legacy/global fallback에만 보존한다. managed selection-set 후보를 편집해도 이 값은 바뀌지 않는다. 따라서 같은
pattern이 두 window에서 서로 다른 weight/enabled를 가져도 다른 phase의 fallback 확률이 조용히 변하지 않는다.
projector는 managed set/window를 `ValtanPatternRotations.json` formatVersion 3의 ordered `candidates`와 stable
`windowId/gameplayPhase/selectionSetId`로 내보낸다. Server bootstrap formatVersion 25의
`PATTERNROTATIONWINDOW + PATTERNROTATIONCANDIDATE`가 이를 소비하며 managed row를 STEP으로 중복 출력하지 않는다.

### 8.3 `decisionModel.selectionWindows`

```jsonc
{
  "windowId": "window.valtan.phase1.160-to-130",
  "gameplayPhase": 1,
  "maximumHealthBarInclusive": 160,
  "minimumHealthBarExclusive": 130,
  "selectionSetId": "selectionset.valtan.160.130",
  "compatibilityRotationId": "rotation.valtan.160.130"
}
```

HP bar는 감소하므로 위 예시는 160~131 구간이다. 다음 window는 maximum 130, minimum exclusive 109로
130~110 구간을 표현한다. window끼리 같은 phase/bar를 중복 소유하거나 빈 구간을 만들면 publisher가 거부한다.
130/109 crossing mechanic은 window 선택과 별도이며 queue되면 normal selection보다 우선한다.
post-109 legacy rotation 여섯 개는 `ORDERED_INTRO_THEN_WEIGHTED`의 `patternIds` 순서와 의도적 중복을 그대로
보존하는 read-only Product다.

### 8.4 `decisionModel.mechanics`

```jsonc
{
  "mechanicId": "mechanic.valtan.floor-wipe-130",
  "patternId": "VALTAN_FLOOR_WIPE_130",
  "trigger": {
    "kind": "HEALTH_BAR_CROSSING",
    "healthBar": 130
  },
  "triggerOrder": 1,
  "oncePerEncounter": true,
  "failurePolicy": "ABORT_ENCOUNTER_REQUIRE_RESET"
}
```

- 한 Server tick에서 여러 bar를 건너면 지나간 threshold를 모두 수집한다. `healthBar` 감소 순서가 1차 정렬이고,
  `triggerOrder`는 **같은 bar 안에서만** tie-break다. 작은 order로 다른 bar를 추월시키지 않는다.
- 1차 `oncePerEncounter` runtime ledger key는 현행과 같은 stable `patternId`다. `mechanicId`는 authoring/program
  identity이며 ledger key로 바꾸지 않는다.
- 이미 실행/queue된 mechanic은 Hot Reload로 threshold를 바꿔도 중복 실행하지 않는다.
- 아직 실행하지 않았는데 새 threshold 아래에 boss가 있으면 candidate preview에서
  `WILL_QUEUE_IMMEDIATELY`를 경고하고 commit 뒤 정확히 한 번 queue한다.
- forced mechanic은 normal weight, range, cooldown과 별도의 우선 경로다. 일반 pool에 중복으로 넣지 않는다.

`VALTAN_ARENA_BREAK_109`는 phase-changing topology boundary다. 이 health bar만 100으로 바꾸면 109..100 legacy
rotation 구간이 phase 1에서 먼저 선택되는 모순이 생긴다. 현재 Tool은 해당 health bar를 read-only로 표시하고,
split validator·Product publisher·Server catalog admission이 다음 식을 각각 독립적으로 검증한다.

```text
arena transition bar
== final phase-1 managed window minimumHealthBarExclusive
== first post-phase ORDERED fromHealthBar + 1
```

health bar를 실제로 조정하려면 후속 typed `SET_PHASE_BOUNDARY`가 mechanic trigger, 인접 phase-1 window, 첫
post-phase span을 한 transaction으로 바꾸고 gap/overlap/empty span/phase reachability를 검증해야 한다. 그 전에는
`triggerOrder`만 편집 가능하다.

boolean consumed 하나로 끝내지 않고 `QUEUED -> ACTIVE -> COMPLETED` 상태를 기록한다. 130/109 같은 critical
mechanic의 transition preflight가 실패하면 normal selection으로 돌아가거나 같은 tick에 무한 requeue하지 않는다.
`FAILED_REQUIRES_RESET`으로 encounter를 fail-closed하고 `failurePolicy`에 따라 controlled reset을 요구한다. reset이
완료돼 새 encounter ledger가 만들어진 뒤에만 다시 arm한다.

### 8.5 pattern identity와 eligibility

각 pattern은 다음 의미 단위를 소유한다.

| field | 계약 |
|---|---|
| `patternId` | 네트워크·trace·참조에 쓰는 stable ID. 이름 변경과 무관하며 재사용 금지다. |
| `displayName` | Tool 표시용 UTF-8 문자열. 로직 분기에 쓰지 않는다. |
| `category` | 현 Product의 `NORMAL | IMPORTANT | MECHANIC`을 lossless하게 보존하는 typed 값이다. |
| `actionId` | pattern 시작 semantic action ID다. stage ID와 같다고 가정하지 않는다. |
| `entryActionId` | 첫 stage를 배열 index가 아닌 stable action ID로 지정한다. |
| `targetPolicy` | 시작/매 tick target resolve 정책이다. target이 없는 경우도 명시한다. |
| `aimPolicy` | 시작 방향 고정, 매 tick 추적, motion anchor 방향 등을 명시한다. |
| `eligibility` | armor/phase/HP/range/cooldown/repeat 조건을 한 typed block으로 묶는다. |
| `invulnerableWhileRunning` | pattern 전체 무적 정책. stage별 shield와 혼동하지 않는다. |
| `presentationSources` | 승인된 원본 action/sequence/role 근거다. runtime ID가 아니다. |
| `stages` | 명시적 graph node 목록이다. |

`eligibility`의 목표 구성은 다음과 같다.

```jsonc
{
  "armorRequirement": "ANY",
  "phaseRequirement": "ANY",
  "minimumGameplayPhase": 1,
  "maximumGameplayPhase": 1,
  "minimumHealthBarInclusive": 1,
  "maximumHealthBarInclusive": 160,
  "minimumRangeM": 0.0,
  "maximumRangeM": 12.0,
  "cooldownPolicy": "DERIVED_SOURCE_ACTION",
  "selectionCooldownMs": null,
  "cooldownGroupId": null,
  "repeatPolicy": {
    "kind": "SOFT_AVOID_UNLESS_ONLY_ELIGIBLE",
    "limit": 2
  }
}
```

v1의 `maximumConsecutiveUses`는 위 soft policy로 이동한다. soft limit 때문에 모든 후보가 막히면 repeat block만
한 번 완화하고 그 사실을 trace에 남긴다. `HARD_CAP`을 추가하려면 모든 후보가 막힌 경우의 CHASE/IDLE behavior와
harness를 먼저 넣는다. cooldown은 기본적으로 source action timing에서 유도하고, 사용자가 override를 켠 경우만
`EXPLICIT + selectionCooldownMs + cooldownGroupId`를 저장한다.

### 8.6 stage graph와 시간 단위

모든 시간은 명시적으로 `Ms` suffix를 쓰고 Server fixed tick에서 정수 tick으로 검증·투영한다. frame count,
Client delta time, animation vector index를 gameplay 저장값으로 쓰지 않는다.

| stage field | owner | 계약 |
|---|---|---|
| `stageId` | gameplay + presentation join key | pattern 내부 stable 표시 ID다. |
| `actionId` | gameplay + presentation join key | Server stage/action stable ID다. branch target은 이 ID를 사용한다. |
| `stageKind` | gameplay | Server state 의미를 가진 enum이다. unknown 값 fallback 금지다. |
| `durationMs` | gameplay | stage wall clock이다. animation 길이와 자동 동일시하지 않는다. |
| `defaultNextActionId` | gameplay | 정상 완료 뒤 다음 stage를 명시한다. `null`이면 pattern 종료다. |
| `hit` | gameplay | shape, schedule, damage reference, impulse를 묶은 typed block이다. |
| `motion` | gameplay | 이동 종류, 거리/anchor/travel stage와 실패 fallback을 소유한다. |
| `events` | gameplay | stage의 ENTER/EXIT edge에서 실행되는 typed gameplay event다. `IMPACT`는 edge가 아니라 stage ID다. |
| `branches` | gameplay | WALL_CONTACT/PART_DESTROYED/TIMEOUT 같은 outcome과 target action을 연결한다. |
| `sequenceRole` | presentation | WINDUP/ACTIVE/RECOVERY 같은 authoring 역할이다. 로직 switch의 대체물이 아니다. |
| `animation` | presentation | stage wall에 배치한 body occurrence 목록이다. |
| `effectCues` | presentation | managed Effect invocation이다. |
| `cameraInvocations` | presentation | stable cue, owner edge/start offset, duration policy를 소유한다. |

array의 다음 원소를 implicit next stage로 사용하지 않는다. 정상 완료도 `defaultNextActionId`로 명시하고 특수 outcome은
`branches[]`로 override한다. 모든 transition은 Server의 한
`resolve -> preflight -> commit -> emit` 경로를 사용한다.

world invocation의 v2 저작 필드는 `events[]` 안의 `TRIGGER_WORLD_EVENT_SET` 하나뿐이다. v1 root의
`worldEventTriggerRefs`는 migration 입력이며 v2 Save에서 제거한다. Tool의 World lane과 flat Product binding은 이
typed event에서 파생하고 별도 `worldEventRefs` 배열을 저장하지 않는다.

### 8.7 hit definition

v1의 flat `hitShape`, `hitCount`, `hitIntervalMs`, `hitOffsetsMs`는 v2 codec에서 lossless typed block으로 묶는다.

```jsonc
{
  "shape": {
    "kind": "CIRCLE",
    "outerRadiusM": 10.0
  },
  "schedule": {
    "kind": "EXPLICIT_OFFSETS",
    "offsetsMs": [0, 350, 700, 1050]
  },
  "serverDamageProfileId": "damage.valtan.circular-spin",
  "pushRangeM": 0.0,
  "pushMs": 0,
  "knockdown": false,
  "downMs": 0
}
```

- `NONE`, `CIRCLE`, `RING`, `CONE`, `BOX`, `CROSS`, `SIX_DIRECTIONS`마다 필요한 geometry field가 다르다. 불필요한 값을
  0으로 묵인하지 않고 tagged-union validator가 exact field set을 검사한다.
- hit offset은 `0 <= offset < durationMs`여야 하고 오름차순·중복 없음이어야 한다.
- interval 방식과 explicit offsets를 동시에 쓰지 않는다.
- raw damage를 gameplay source에 넣지 않는다. `serverDamageProfileId`가 `DamageProfiles.json`의 Valtan-owned row 하나에
  정확히 resolve되어야 한다.
- Client collider와 Effect 모양은 debug/presentation mirror다. 실제 overlap과 damage는 Server fixed tick이 한다.

### 8.8 motion과 target

pattern motion은 현행 `LEAP_TO_TARGET | LEAP_TO_ANCHOR`, stage motion은 `FORWARD`처럼 실제 consumer가 있는
종류만 admission한다. 각 종류는 anchor/landing/apex/travel stage 또는 distance와 target sample edge,
navigation projection, 실패 fallback을 exact payload로 가진다. `serverMotion.travelStageId`는 정확히 같은 pattern의
stable `stageId` namespace만 참조한다. branch와
`defaultNextActionId`가 쓰는 `actionId` namespace와 섞지 않는다.

- `NEAREST_EACH_TICK`: 매 decision/aim tick에 유효 target을 다시 resolve한다.
- `LOCK_NEAREST_ON_START`: pattern 시작 시 stable PlayerId를 잠근다.
- `LOCK_RANDOM_ALIVE_ON_START`: Server deterministic RNG로 생존자 한 명을 시작 시 잠근다.
- `NONE`: 109 중앙 이동처럼 player target이 없어도 실행 가능한 mechanic이다.
- aim은 현 Product의 `TRACK_TARGET_EACH_TICK | LOCK_FACING_ON_START | FACE_MOTION_ANCHOR | NONE`을 모두 보존한다.
- target 소실 시 임의 player 0번이나 origin으로 fallback하지 않는다. authored fallback이 없으면 transition을 typed
  ABORT로 종료한다.
- landing과 combat-object 좌표는 Server navigation/bounds를 통과해야 한다. Client transform을 정답으로 보내지 않는다.

### 8.9 typed event

generic `{ kind, targetId, value }`는 v1 migration 입력으로만 받고 v2 Save에서는 event별 exact payload를 쓴다.
1차 admission event는 다음 여섯 개다.

| kind | 필요한 payload | 적용 예 |
|---|---|---|
| `SET_BOSS_FLAG` | `flagId`, `enabled` | GROGGY ENTER/EXIT |
| `SET_STAGGER_GAUGE` | `mode`, `value` | counter/stagger stage |
| `SET_SHIELD` | `mode`, `value` | mechanic 보호막 |
| `SPAWN_COMBAT_OBJECT_VOLLEY` | archetype, target/layout/count/cap | HIGH_JUMP 도끼 |
| `SET_GAMEPLAY_PHASE` | `gameplayPhase` | 109 IMPACT ENTER에서 phase 2 |
| `TRIGGER_WORLD_EVENT_SET` | `worldEventSetId` | 109 outer wall destruction |

event에는 stable `eventId`와 `trigger: ENTER | EXIT`를 둔다. `IMPACT / ENTER`는 IMPACT stage의 ENTER edge라는
뜻이지 별도 IMPACT trigger enum이 아니다. event enum만 만들고 Server consumer가 없는 placeholder를 먼저
추가하지 않는다. 새 event는 parser, projector, Server preflight/commit, rollback, protocol state, harness를 같은
변경 단위로 닫는다.

### 8.10 branch와 원자 transition

branch는 `outcome`, `nextActionId`, 필요하면 typed priority/guard만 저장한다. 현 Product의 `TIMEOUT`,
`WALL_CONTACT`, `PART_DESTROYED`, `COUNTER_HIT`, `STAGGER_BROKEN`을 lossless하게 지원하며 unknown outcome을
TIMEOUT으로 처리하지 않는다.

Server transition 순서는 다음과 같다.

1. current stage와 발생 outcome을 시작 generation에서 resolve한다.
2. next action, EXIT/ENTER event, target/navigation, combat-object capacity, world binding을 전량 preflight한다.
3. 하나라도 실패하면 boss flag/phase/stage/object/world를 한 항목도 부분 변경하지 않는다.
4. 성공하면 stage, phase/flag/shield/stagger, object set, event ledger를 한 transaction으로 commit한다.
5. commit 뒤 snapshot과 audition lifecycle/decision trace를 emit한다.

no-target, boss death/reset, armor/part break, wall contact, timeout도 이 경로 밖에서 stage index를 직접 바꾸지 않는다.

### 8.11 animation occurrence와 반복

```jsonc
{
  "endPolicy": "EXACT",
  "repeatCount": 1,
  "occurrences": [
    {
      "clipOccurrenceId": "valtan.attack.whirlwind.active.clip.01",
      "clip": "mesh_att_battle_20_03",
      "mappingBasis": "PROJECT_AUTHORED",
      "sourceStartMs": 0,
      "playMs": 533,
      "playRate": 0.4441666667,
      "repeatUntilStageEnd": false
    }
  ]
}
```

- `clipOccurrenceId`는 cue가 붙는 stable occurrence ID다. 배열 index로 cue를 연결하지 않는다.
- `repeatCount > 1`은 유한 반복이다. 그 수에 대응하는 explicit occurrence가 있어야 한다.
- 무한 반복은 숫자 1 이상의 `loop`가 아니다. `endPolicy: LOOP_TO_STAGE_END`, `playMs: 0`,
  `repeatUntilStageEnd: true` occurrence 하나가 남은 stage wall을 채운다.
- `EXACT`는 occurrence wall time 합이 stage duration과 허용 오차 2ms 안에서 같아야 한다.
- `HOLD_LAST_POSE`는 남은 wall time 동안 마지막 pose를 유지한다.
- `playRate`는 presentation 속도다. Server hit time과 stage 종료를 바꾸지 않는다.

clip/source segment의 단일 정본은 `Valtan.presentation.json`이다. Animation Tool은 이 presentation codec과
source hash transaction으로 occurrence를 편집하며, Balance Tool은 같은 값을 read-only/deep-link로만 본다.

### 8.12 managed Effect cue invocation

v2 managed cue는 단순 `effectRef`만이 아니라 다음 호출 정보를 `Valtan.presentation.json`이 완전히 소유한다.

- stable `cueId`와 `effectAssetId`
- owner `stageId`, `clipOccurrenceId`
- source-local `sourceStartMs/sourceEndMs`; stage-global offset은 저장하지 않고 timeline이 파생
- anchor ID, follow policy
- local position/rotation/scale
- start/stop policy, finite repeat 또는 stage-end loop 의미

실제 particle/mesh element, material, texture, Revolution, asset lifetime은 authored Effect 문서가 소유한다.
projector는 managed cue row를 `Valtan.patterneffectcues.json`에 완전히 생성한다. Effect Tool은 presentation
codec을 사용하므로 generated Product cue의 owner/window/transform을 직접 저장하지 않는다.

stage-global cue offset은 앞선 stage duration, occurrence wall과 source-local window에서 projector/UI가 계산하는
derived 값이다. gameplay/presentation source나 Product authoring 입력에 별도로 넣지 않으며 stale/injected global offset은 validator가
거부한다.

`Play Authoring Timeline`의 `Selected Effect`는 선택 occurrence 하나를, `All Effects`는 선택 branch의 모든 cue를
동일 pattern wall clock에서 재생한다. 각 cue는 독립 handle로 prewarm/spawn/seek/stop/rewind된다. cue 하나가
drawable하지 않아도 body와 다른 cue는 계속되고, 실패 lane만 이유를 표시한다. 이 재생은 로컬 저작 preview다.
Arena 적용은 Effect artifact가 candidate Client submanifest에 들어가고 multi-client readiness를 통과해야 한다.

### 8.13 독립 Effect와 combat-object

`independentEffects`는 asset 복사본이 아니라 owner library다.

- 도넛: `SERVER_COMBAT_OBJECT`, `FIST_IN_OUT/INNER`의 `event.valtan.fist-in-out.spawn-donut` owner다.
- 도끼: `SERVER_COMBAT_OBJECT`, `HIGH_JUMP/AIRBORNE` owner, BossCatalog visual join을 따른다.
- 붉은 검기: 전체 Product에는 있지만 아직 split-owned scope 밖이다. 승격 전에는 Product read-only join이다.

v2 exact tagged union은 다음 두 shape만 허용한다.

```jsonc
{
  "independentEffectId": "valtan.independent-effect.donut-in-out",
  "displayName": "INNER / OUTER 도넛",
  "ownership": "SERVER_COMBAT_OBJECT",
  "spawnEventId": "event.valtan.fist-in-out.spawn-donut"
}

{
  "independentEffectId": "valtan.independent-effect.target-axe",
  "displayName": "플레이어 추적 도끼",
  "ownership": "SERVER_COMBAT_OBJECT",
  "spawnEventId": "event.valtan.high-jump.airborne.spawn-target-axe"
}
```

- `independentEffectId`는 배열에서 unique stable ID다.
- `SERVER_PATTERN_STAGE`는 `cueId`만 요구하고 `spawnEventId/effectAssetId/ownerPatternId/ownerStageId`를 금지한다.
- `SERVER_COMBAT_OBJECT`는 `spawnEventId`만 요구하고 `cueId/effectAssetId/combatObjectArchetypeId/clientVisualId`를
  금지한다.
- cue/event ID도 presentation source 전체에서 unique하고 실제 reachable stage에 정확히 하나 있어야 한다.
- 하나의 cue/event를 independent library entry 둘이 참조할 수 없다.
- v1의 owner/effect/visual echo는 exact join이 맞을 때만 위 shape로 migration하고 drift면 거부한다.

v2에서 pattern-stage library entry는 managed `cueId`만 가리키고 `effectAssetId`/transform을 두 번 저장하지 않는다.
combat-object library entry는 stable spawn `eventId`만 가리킨다. 그 event가 archetype ID를 한 번 소유하고
`clientVisualId/effectAssetId`는 BossCatalog/EffectCatalog에서 join한다.
현행 v1 independent entry의 중복 field는 migration 입력으로만 읽는다.

combat-object Product `lifeMs`는 companion의 optional `lifetimeMs`를 우선하고, 생략하면 기존 owner stage
duration에서 파생한다. `SPAWN_COMBAT_OBJECT`는 명시적 lifetime을 요구한다. 범위는 1~600000ms이고
마지막 timed hit가 수명 안에 있어야 한다. Server room이 진행 중 pattern과 별도로 object definition과
birth pose를 보존하며 만료·owner 사망·reset에서 despawn한다. Client는 같은 lifecycle의 world-root Effect를 쓴다.

join은 `combatObjectArchetypeId -> BossCatalog clientVisualId -> EffectCatalog effectAssetId -> Authored Effect` 순서로
보여 준다. presentation join이 끊겨도 Server pattern/damage를 가짜 local Effect로 대체하지 않고 해당 lane만
격리한다.

### 8.14 `Valtan.combatobjects.json` authoring companion

신규 companion은 runtime Product를 복사한 파일이 아니라 managed/unmanaged를 가리지 않고 모든 Valtan
combat-object의 object-owned field만 가진 strict 문서다.

```jsonc
{
  "schema": "lostark.valtan-combat-object-authoring",
  "formatVersion": 1,
  "encounterId": "ENCOUNTER_VALTAN",
  "objects": [
    {
      "combatObjectArchetypeId": "combatobject.valtan.high-jump.target-axe",
      "kind": "FIXED_AREA",
      "spawn": {
        "origin": {
          "kind": "RESOLVED_VOLLEY_POSITION"
        },
        "direction": {
          "kind": "NONE"
        }
      },
      "movement": {
        "kind": "STATIC"
      },
      "hits": [
        {
          "hitId": "hit.valtan.high-jump.target-axe.impact",
          "trigger": {
            "kind": "TIMED",
            "atMs": 1200
          },
          "repeat": {
            "count": 1,
            "intervalMs": 0
          },
          "shape": {
            "kind": "CIRCLE",
            "outerRadiusM": 3.5
          },
          "serverDamageProfileId": "damage.valtan.high-jump",
          "pushRangeM": 1.0,
          "pushMs": 150,
          "knockdown": true,
          "downMs": 1000
        }
      ]
    }
  ]
}
```

exact union 규칙은 다음과 같다.

- `kind`: 현재 consumer가 있는 `FIXED_AREA | MISSILE`만 허용한다.
- companion `spawn.origin/direction`은 object 한 개가 event에서 받은 spawn context를 어떻게 초기화하는지만 소유한다.
  `RESOLVED_VOLLEY_POSITION`은 gameplay event가 계산한 좌표를 사용한다. 생존 플레이어 resolve, 대상당 count,
  radial layout은 gameplay volley event만 소유한다. v1 `LOCKED_TARGET_PER_ALIVE_PLAYER`는 migration 때 이 두 계약으로
  분해하고 companion에 남기지 않는다.
- `RESOLVED_VOLLEY_POSITION` origin은 `kind` 외 field를 금지한다. `BOSS_POSITION`처럼 실제 object-owned offset을
  쓰는 origin만 forward/right offset을 가진다. `NONE` direction도 추가 field를 금지한다.
- `movement`: 고정 object는 `{ kind: STATIC }`, projectile은
  `{ kind: LINEAR, speedMps, maximumDistanceM }` exact payload를 쓴다.
- `trigger`: `TIMED`는 `atMs`, `CONTACT`는 추가 시간 field 없음이다.
- `shape`: stage hit과 같은 `CIRCLE/RING/CONE/BOX/CROSS/SIX_DIRECTIONS` typed geometry를 쓴다.
- `repeat.count >= 1`; count 1이면 interval은 0이어야 한다.
- `serverDamageProfileId`는 Valtan-owned DamageProfiles row에 resolve되어야 한다.

이 문서에는 `ownerPatternId`, `ownerStageActionId`, `lifeMs`, `clientVisualId`를 저장하지 않는다.

- owner와 volley는 `Valtan.gameplay.json` event가 소유한다.
- managed object lifetime은 optional `lifetimeMs`가 있으면 그 값을 쓰고, 없으면 owner stage duration에서 파생한다.
- visual은 BossCatalog가 소유한다.
- legacy unmanaged object owner/lifetime/ordinal만 승격 전 `Valtan.legacy-compatibility.json`에 보존한다.
  geometry/damage definition은 companion 한 곳에만 있다.

projector는 이 세 정본을 join해 현행 `Data/Encounters/Valtan/ValtanCombatObjects.json` flat runtime row를 완전
생성한다. archetype 중복, owner 없음/복수, derived life 불일치, visual 없음은 publish를 거부한다.

### 8.15 camera와 wall event set

split source는 camera keyframe이나 wall placement를 복제하지 않는다.

- camera: `Valtan.presentation.json` stage의 `cameraInvocations[]`가 stable `cameraInvocationId`, `cameraCueId`, trigger/start offset,
  `durationPolicy: STAGE_REMAINDER | EXPLICIT`와 EXPLICIT일 때만 `durationMs`를 소유한다. keyframe/FOV/easing/shake는
  camera 문서에서 편집한다.
- v2 camera 문서 cue는 `cueId + keyframes/lens/shake`만 소유한다. 현행 v1의 pattern-level `cameraCueIds`와
  camera cue의 `patternId/stageId/durationMs`는 exact join 후 stage `cameraInvocations`로 옮기고 두 legacy echo는
  v2 Save에서 제거한다. `STAGE_REMAINDER` duration은 owner stage
  wall에서 파생하며 camera 문서가 같은 값을 echo하지 않는다.
- world invocation: `events[].TRIGGER_WORLD_EVENT_SET` payload의 `worldEventSetId + owner stage + trigger edge`만 저장하고
  별도 ref 배열은 만들지 않는다. stable set membership은 `Data/Valtan/Valtan.worldeventsets.json`, 실제
  group/mutation/nav/placement와 109 외 binding은 World/Map Tool 영역이 소유한다.
- 109의 stable set ID는 `worldeventset.valtan.arena-break-109.outer-wall`이다.
- 109 full-collapse set은 현행 enabled 97 groups / 97 DESPAWN mutations / 135 placements closure를 exact
  fixture로 확인한다. member ID와 placement/nav closure는 각각 unique여야 하며 빈 navigation closure는
  절벽 뒤를 새 walkable floor로 만들지 않는 두 wall에만 정상 입력으로 남는다.
- companion의 exact JSON 형태는 다음과 같다. root와 set/member에서 열거되지 않은 field는 거부한다.

```jsonc
{
  "schema": "lostark.valtan-world-event-set-authoring",
  "formatVersion": 1,
  "areaId": "LV_LUT_HEARTRB_ED",
  "encounterId": "ENCOUNTER_VALTAN",
  "sets": [
    {
      "worldEventSetId": "worldeventset.valtan.arena-break-109.outer-wall",
      "members": [
        {
          "memberId": "worldeventmember.valtan.outerwall109.1090000000000001",
          "bindingId": "binding.valtan.outerwall109.1090000000000001.impact",
          "groupId": "destroyable.group.valtan.outerwall109.1090000000000001",
          "mutationId": "mutation.valtan.outerwall109.1090000000000001.despawn",
          "offsetMs": 0,
          "receiverCollisionId": "",
          "enabled": true
        }
      ]
    }
  ]
}
```

`memberId`와 `bindingId`는 문서 전체에서 stable/global unique다. `groupId`는 `mutationId`가 가리키는 mutation의
실제 group과 같아야 한다. `offsetMs`는 0 이상이고 `receiverCollisionId`는 빈 문자열 또는 존재하는 collision stable
ID다. member는 `patternId`, `stageId`, `triggerKind`를 저장하지 않는다. 그 세 값은 gameplay source의 owner pattern,
owner stage, `ENTER` edge에서 compile한다.

G01~G08의 보존 경계는 다음과 같다.

- companion은 현행 109 enabled binding 97개의 membership만 소유한다.
- 현행 `ValtanWorldEvents.json` exact root는
  `{ schema, formatVersion, areaId, encounterId, provenance, groups, mutations, bindings }`다.
- projector는 stable `bindingId`로 찾은 97개 row만 같은 ordinal에서 교체한다. 새로운 binding의 삽입·삭제는
  G09 전 거부한다.
- 기존 105 groups, 105 mutations, 나머지 127 bindings와 provenance는 World/Map 소유 pass-through다.
- no-op migration/project harness는 다른 127 binding의 ID·ordinal·모든 field와 groups/mutations/provenance의
  canonical hash가 전후 동일한지 검사한다. managed subset 밖의 byte slice가 바뀌면 stage를 폐기하고 기존 문서를
  유지한다.

현재 migration/validator/projector는 companion과 gameplay invocation을
현행 `Data/Encounters/Valtan/ValtanWorldEvents.json`의 같은 97개 `(patternId, stageId, triggerKind)` flat binding row로
compile하므로 기존 Server가 새 lookup 없이 소비한다.
- G09에서만 immutable set definition과 room별 destroyed state를 분리하고 direct stable-set runtime lookup/Hot Reload를
  연다. 그때 97-row transitional projection을 폐기한다.
- Server는 기존 `Apply_WorldDestructionStageEntry -> Prepare_StageTrigger` 경로를 stable set lookup으로 확장한다.
  두 번째 world-event 실행 경로를 만들지 않는다.

## 9. Server에서 패턴을 고르고 실행하는 방식

### 9.1 현재 우선순위를 보존하면서 phase 오류만 고친다

현재 Server의 큰 우선순위는 health state 갱신과 crossed mechanic queue, intro, pending forced pattern,
rotation/weighted selection, global weighted fallback이다. v2에서 selector를 새로 쓴다는 이유로 이 순서를 조용히
뒤집지 않는다. 목표 decision envelope는 다음 순서다.

1. active pattern이 있으면 새 pattern을 고르지 않고 pinned generation의 stage를 계속 실행한다.
2. HP bar가 감소한 구간에서 아직 처리하지 않은 health mechanic을 deterministic하게 queue한다.
3. Debug audition이 승인되면 shared encounter reset 뒤 stable pattern ID를 forced occurrence로 queue한다.
4. 아직 끝나지 않은 intro가 있으면 intro source를 선택한다.
5. pending health mechanic이 있으면 normal pool보다 먼저 선택한다.
6. 현재 gameplay phase와 health bar에 맞는 selection window/set을 찾는다.
7. candidate eligibility를 평가하고 ordered 또는 weighted 알고리즘을 실행한다.
8. `PHASE_ONE` migration 동안 v2가 소유하지 않는 phase/window는 봉인된 Product eligible rows 전체를
   compatibility fallback으로 평가한다. split-owned row도 기존 phase 조건이 맞으면 포함된다.
9. 유효 후보나 target이 없으면 임의 pattern으로 fallback하지 않고 `NONE/CHASE/IDLE` reason을 반환한다.

즉 `PHASE_ONE`은 authoring coverage 표시이지 phase 2 후보를 legacy-only row로 제한하는 runtime filter가 아니다.
WHIRLWIND/FOUR_SLASH/HIGH_JUMP/FIST_IN_OUT 등 현재 `maximumPhase: 3`인 managed row도 기존 ordinal과 weight로
compatibility fallback에 들어간다. 제외하려면 별도 밸런스 변경으로 diff/receipt와 expected RNG fixture를 갱신한다.

Valtan phase는 더 이상 `BossProfiles.phaseTwoHpPercent`만 보고 109 pattern 전에 바꾸지 않는다. Valtan profile은
`AUTHORED_PATTERN_EVENT` phase policy를 사용하고, 109 mechanic의 IMPACT ENTER event가 phase 2를 한 번만 commit한다.

`BossProfiles.json`은 이미 v4이며 다음 exact tagged union으로 교체되어 있다.

```jsonc
// generic boss
"phasePolicy": {
  "kind": "HEALTH_PERCENT_THRESHOLD",
  "thresholdPercent": 68
}

// Valtan
"phasePolicy": {
  "kind": "AUTHORED_PATTERN_EVENT"
}
```

Valtan union에는 `thresholdPercent`를 쓰지 않으며 generic union에는 반드시 1~99 값을 둔다. v3
`phaseTwoHpPercent`는 migration 입력으로만 읽고 v4 Save에서는 제거한다. validator는 BossProfiles schema/version,
balance provenance, gameplay bootstrap, `CGameplayCatalog`, `CValtanBrain` 계약을 함께 고정한다. Valtan
`phasePolicy`와 gameplay `SET_GAMEPLAY_PHASE` consumer 중 하나만 존재하면 publisher가 거부한다.

### 9.2 candidate filtering

normal candidate마다 다음 값을 같은 Server decision에서 평가한다.

- selection kind/set membership와 enabled 상태
- armor requirement
- gameplay phase와 pattern phase range
- HP bar eligibility
- target 존재와 engage 상태
- target distance의 minimum/maximum range
- cooldown ready tick 또는 explicit cooldown group
- consecutive use와 repeat policy
- definition/reference resolve 상태

soft repeat 때문에 후보가 모두 제외되면 repeat exclusion만 완화해 한 번 더 계산하고
`SOFT_REPEAT_RELAXED`를 기록한다. armor, phase, HP, range, cooldown 같은 다른 실패는 완화하지 않는다.

### 9.3 weighted 선택과 재현성

Server는 후보를 authoring order 그대로 누적 interval로 만든다. 예를 들어 유효 weight가 20/30/50이면 ticket
구간은 `[0,20)`, `[20,50)`, `[50,100)`이다. normalized authored 확률과 실제 유효 후보 확률을 Tool에서 분리한다.
managed window에서는 이 순서가 `ValtanPatternRotations.json` v3 `candidates[]` ordinal이며 Encounter의 전체
`patterns[]` 순서가 아니다. disabled row도 trace에는 authored weight와 exclusion reason을 남기되 effective weight와
interval 길이는 0이다. managed window가 없는 legacy/global 선택에서만 pattern의
`compatibilitySelectionWeight`를 사용한다.

현행 deterministic RNG는 Server tick과 다음 pattern sequence에서 만든 입력을 SplitMix64 계열로 섞는다.
구체적인 seed/input/mixed value/ticket/total weight를 trace에 보존한다. row 순서를 바꾸면 같은 weight라도 ticket
구간이 달라지므로 reorder는 실제 밸런스 변경이다. Client가 같은 계산을 흉내 내 선택 근거로 표시하지 않는다.

### 9.4 Decision Observatory packet

trace는 `SelectPattern()`을 UI에서 한 번 더 실행해서 만들지 않는다. `CValtanBrain::Update`의 같은 decision envelope가
early return과 selector 결과를 함께 만든다.

header에는 다음이 들어간다.

- decision sequence와 Server tick
- room active revision, pending revision, 선택 occurrence revision
- boss HP/bar/phase/armor, 별도 mutable boss state revision
- target PlayerId, distance, engage/no-target 상태
- intro 상태, selection window/set, ordered cursor
- pending mechanic head와 queue reason
- source: `INTRO | FORCED_HEALTH_BAR | FORCED_AUDITION | ORDERED | WEIGHTED | GLOBAL | NONE`
- RNG raw input, mixed value, ticket, total weight
- selected pattern ID와 expected pattern sequence

candidate row에는 다음이 들어간다.

- pattern ID와 Server가 실제 사용한 effective weight
- cumulative ticket interval
- cooldown remaining ticks
- consecutive count와 repeat 결과
- exclusion bitset
- 사람이 읽을 수 있는 reason code

필수 reason은 wrong kind, not-in-set, armor, phase, HP, no-target, min/max range, cooldown, soft-repeat-block,
soft-repeat-relaxed, disabled, unresolved-definition이다. managed/legacy 여부와 draft dirty는 Server truth가 아니므로
Tool이 stable pattern ID로 local authoring 정보에 join한다.

전체 후보 상세 문자열을 30Hz snapshot에 싣지 않는다. Debug-only subscribe/query, decision edge packet, bounded
ring buffer를 사용하고 Release에서는 명시적으로 거부한다. 전투 HUD가 아니라 전용
`CValtanDecisionDebugViewModel`이 소비한다.

### 9.5 pattern 시작과 generation pin

선택이 성공하면 Server는 pattern sequence를 증가시키고 그 순간 room active
`GameplayCatalogGeneration`을 occurrence에 pin한다. 다음 값은 pattern이 끝날 때까지 그 generation을 사용한다.

- pattern/stage graph와 duration
- hit geometry/schedule와 damage profile
- stage action/branch/motion
- pending forced mechanic definition
- spawn된 combat-object definition
- camera/Effect 등 Client가 맞춰야 할 occurrence definition revision

Hot Reload가 중간에 commit되어도 active pattern의 다음 stage가 newest catalog를 다시 읽지 않는다. 일반 선택의 새
weight와 threshold는 다음 decision부터 적용한다. Product ordered sequence는 순서 전체를 pin하므로 그 실행의
다음 Pattern도 같은 revision을 사용하고, 새 encounter/reset부터 새 저장 순서와 definition을 사용한다.

### 9.6 stage fixed-tick 실행

Server stage runtime은 ENTER edge를 한 번 실행하고 elapsed tick으로 motion과 hit pulse를 평가한다. 한 fixed tick이
여러 hit offset을 건너면 빠진 pulse 없이 순서대로 처리하되 동일 player/hit identity 중복을 막는다. wall contact나
part destruction outcome이 생기면 authored branch를 resolve하고 8.10의 원자 transition을 사용한다.

Client는 snapshot의 pattern/stage/action/elapsed/pattern sequence/definition revision을 presentation에 투영한다.
Client animation 종료나 Effect 종료가 Server stage를 끝내지 않는다.

### 9.7 130과 109 mechanic의 정확한 흐름

```text
HP bar crossing
  -> once ledger 확인
  -> forced mechanic queue
  -> 현재 active pattern 종료
  -> queued pattern 시작
  -> pinned generation으로 stage graph 실행
```

130은 `VALTAN_FLOOR_WIPE_130`을 queue하고 두 smash 판정을 실행한다. 109는
`VALTAN_ARENA_BREAK_109`을 queue하되 target 없이 Arena center anchor를 사용한다.

```text
TAKEOFF -> DROP -> IMPACT
                     |- IMPACT hit
                     |- outer-wall event set
                     |- camera impact cue
                     `- SET_GAMEPLAY_PHASE(2)
          -> IMPACT_HOLD -> WIDE_REVEAL -> RECOVERY -> finish
```

phase, stage, flag, damage/object/world event의 preflight가 모두 성공한 IMPACT ENTER에서만 phase 2를 commit한다.
TAKEOFF 전에 phase 2 snapshot이 나가거나 같은 event가 두 번 state revision을 올리면 실패다. 나머지 camera sequence는
같은 active pattern으로 계속되고, 다음 pattern 선택부터 phase 2 program을 사용한다. 현재 split source에는 phase 2 전체
pattern coverage가 없으므로 그 부분은 legacy read-only로 표시한다.

## 10. F1 Balance Tool의 Boss Tuning 화면

### 10.1 진입과 화면 구조

사용자는 Valtan Arena에서 F1을 누르고 `Balance Tool -> Valtan`을 선택한다. 현재 구현은 왼쪽 Boss 선택, 가운데
scrolling workbench, 오른쪽 Server Truth의 3열 구조다. Tool을 닫았다 다시 열어도 현재 draft, source hash conflict,
Server active revision과 audition 상태가 `CMainApp` 소유 service에 남는다.

```text
Valtan
  Phase / Decision
    Mechanics: 130, 109
    Selection Windows / Sets
      160..131: Enabled / Weight / Share
      130..110: Enabled / Weight / Share
  Split-owned Patterns (dynamic)
  Independent Presentation
    Donut
    Target Axe
  Legacy Product / Read-only (dynamic)
  Legacy Rotations / Read-only (post-109 six bands)
```

가운데 workbench는 현재 `Phase and selection structure`, `Managed mechanics`, `Managed rotation`, `Independent
presentation`, `Legacy Product / read-only`와 pattern별 collapsing section을 한 화면에 펼친다. 각 managed pattern 안에서
Server decision 값, gameplay stage/hit/branch/object spawn을 편집하고 presentation occurrence/cue/camera/world reference는
read-only로 본다. legacy row를 숨기면 실제 Server가 선택할 수 있는 pattern과 Tool 설명이 달라지므로 현재 row를 항상
inventory로 보인다.

mechanic editor의 health bar와 trigger order를 같은 의미로 보지 않는다. 130/109의 order는 같은 bar tie-break이고,
109 arena health bar는 phase topology 원자 편집이 구현되기 전 read-only다. managed selection은 pattern 공통 weight가
아니라 각 window/set 후보 행의 `Enabled`와 `Weight`를 직접 편집하며 호환 fallback weight는 별도 read-only 근거로
표시한다.

아래 tab/tree UX는 다음 확장 목표이며 이번 완료 상태가 아니다.

- `Decision / Pattern / Stages / Combat Object / Diff` 전용 tab
- body/hit/Effect/camera를 한 clock에 겹치는 authoring timeline
- Camera/World/Animation/Effect Tool로 가는 clickable deep-link
- live/pending/validation badge가 붙는 full pattern tree

오른쪽 `Server Truth`에는 HP/bar/phase/armor, target/distance, current pattern/stage/action, elapsed/remaining,
pattern sequence, room/pinned revision, pending mechanics, audition lifecycle, 최근 damage/object/camera/world event,
Client lane 오류를 보여 준다. `Authored Preview`와 `Live Server Actual`은 색과 제목을 명확히 다르게 한다.

### 10.2 상단 revision과 명령

표시 revision은 최소 다음 다섯 개다.

- `Disk Authoring`
- `Published Candidate`
- `Server Active`
- `Client Presentation`
- `Pattern Pinned`

명령 의미는 다음과 같으며 하나의 `Save` 버튼으로 합치지 않는다.

| 명령 | 정확한 의미 |
|---|---|
| `Reload` | admitted `current-authoring` saved head가 있으면 complete artifact set을 hash/strict join 후 복원한다. 없을 때만 repository split baseline을 사용하며 unsaved draft는 명시적 폐기 없이 버리지 않는다. |
| `Validate Draft` | 임시 staging root에서 parse/join/validator만 실행한다. disk와 runtime을 바꾸지 않는다. |
| `Save Authoring` | stable-ID patch를 적용한 complete `AUTHORING_ARTIFACTS` immutable revision을 만들고 untouched bytes를 유지한다. repository/Product/runtime은 바꾸지 않는다. |
| `Publish Candidate` | 저장 source로 projection/provenance/Server·Client immutable bundle을 만든다. active pointer는 유지한다. |
| `Apply Hot Reload` | `HOT_RELOAD`로 분류된 candidate revision ID만 Server에 요청한다. JSON/path를 packet으로 보내지 않는다. |
| reset-required candidate | `ENCOUNTER_RESET` badge와 진단을 표시하고 Apply를 비활성화한다. controlled reset 명령은 아직 없다. |
| `Revert Draft` | 현재 admitted saved head로 복원하고, saved head가 없으면 repository split baseline으로 돌아간다. Server rollback 명령이 아니다. |

현재 저장/publisher는 bounded child process를 동기 실행하고 structured result를 parse한다. timeout이면 소유 child만
종료하며 Client/UI나 Server를 종료하지 않는다. async progress/cooperative cancel은 후속 UX다. Valtan field 하나를
저장할 때 PlayerProfiles/PlayerSkills 같은 무관 문서를 다시 쓰지 않는다.

### 10.3 field별 적용 badge

| 수정 종류 | badge | 동작 |
|---|---|---|
| weight/order/enable, eligibility | `NEXT_DECISION` | active pattern은 유지한다. |
| stage timing/hit/motion/branch | `NEXT_PATTERN` | active occurrence는 old generation이다. |
| animation/Effect cue/camera | 현재 Arena Apply 거부 | 실제 hash-keyed Client presentation generation이 아직 없다. |
| combat-object volley/definition | `NEXT_SPAWN` | 이미 spawn된 object는 old generation이다. |
| arena phase boundary health bar 단독 변경 | 현재 reject | mechanic/window/legacy span 원자 `SET_PHASE_BOUNDARY` 전까지 read-only다. |
| Effect element/material | local preview만 | Arena candidate는 presentation bytes가 active baseline과 다르면 거부한다. |
| 이미 지난 phase, HP/AP/move/armor/collision | `ENCOUNTER_RESET` | 현재 state를 비율로 추측해 변경하지 않는다. |
| world invocation set/owner/trigger | 현재 reject | active pattern definition과 mutable world state 분리가 필요하다. |
| world-event-set membership / wall placement/mutation/nav | 현재 reject | destroyed state를 임의 복원하지 않는다. |
| schema/packet/new C++ event/new asset registration | `SERVER_RESTART` | Hot Reload 범위가 아니다. |

한 candidate에 여러 badge가 섞이면 publisher가 가장 강한 `applyClass` 하나로 승격한다. 일부 field만 먼저 적용하지
않는다. reset-required field가 하나라도 있으면 전체 candidate는 Apply 전에 차단되며, 직접 PREPARE를 만들더라도
Server가 `ENCOUNTER_RESET required`로 거부한다.

### 10.4 pattern 재생 버튼

- 현재 Balance Tool이 직접 제공하는 재생은 `Play Server Pattern`이다. stable `bossPlacementId + patternId` 요청으로
  실제 Server audition 경로를 실행한다.
- `Play Authoring Timeline`, `Effect Only`, `Body | Hit Area | Selected Effect | All Effects | Camera Guide` layer는
  Animation/Effect Tool의 기존 저작 재생 경계 또는 후속 통합 UX다. 현재 Balance Tool 버튼으로 구현됐다고 보지 않는다.
- 도넛 Effect만 볼 때는 owning Effect Tool의 exact authored document를 열어 재생하고, 그 결과를 Server hit나 boss
  행동 검증으로 기록하지 않는다.

109 wall destruction, target axe, 실제 movement/hit/damage는 Server audition만 정답이다. Valtan Arena의 최초 isolated
Play와 Ordered Flow 시작은 shared room encounter를 reset하는 Debug 명령이다. Server가 owner session/sequence lease를
발급하고 다른 요청은 거부한다. owner disconnect, world transfer, timeout 때 lease를 회수하고 관전자 모두에게
reset reason을 알린다.

공용 audition service는 다음 lifecycle과 pinned definition revision을 보존한다.

```text
PENDING -> ACTIVE -> COMPLETED
                  `-> ABORTED(reason)
```

각 event는 request sequence, Server room별 monotonic `roomAuditionEpoch`, Server pattern sequence를 포함한다.
`roomAuditionEpoch`는 Client local `iWorldInboundGeneration`이 아니며 room reset/audition 때 Server가 증가시키는 wire
identity다. request sequence, room epoch, pattern sequence, pinned definition revision이 함께 맞아야 같은 audition이다.
Effect Tool과 Balance Tool이 NetworkManager deque를 각각 소비하지 않고 `CValtanPatternAuditionService` 하나가
결과를 받아 두 화면에 배포한다.

Boss Tool의 `Next Pattern...`은 live Product, 같은 owner Flow/isolated 또는 idle에서 선택하는 별도 예약 한 칸이다.
saved Ordered Slots에 추가하지 않는다. 공용 playable inventory의 split-owned pattern 전체를 이름/stable ID로 검색한다.
All Effects/Ordered Flow 목록과 예약은 별개이며, 사용자 저장 Flow는 stable slot ID와 현재 순서로 보존한다.
저장 슬롯 수를 pattern inventory 수에 맞춰 자동으로 채우거나 과거 목록으로 되돌리지 않는다.

- A가 마지막 hit, attachment, prop/world destruction을 commit하고 실제 COMPLETED receipt를 낸 뒤에만
  B를 한 번 승격한다. B는 다음 fixed tick에서 시작하고 A와 같은 pinned definition revision을 사용한다.
  idle 예약은 가짜 COMPLETED receipt 없이 다음 tick에 시작한다. live 채택은 관측한 실제 pattern sequence를
  검증하며 기존 Queue/Clear의 epoch/token CAS를 느슨하게 만들지 않는다.
- 예약·교체·취소·승격은 player/boss 위치, HP/resource/cooldown, 벽·바닥·prop을 reset하지 않는다.
  다른 owner, stale epoch/predecessor/request sequence는 거부한다. 동일 command retry는 원래 결과를 돌려준다.
- current, 승인된 Next, 미확정 command를 별도 표시한다. 응답이 불명확하면 `Retry Same Next Command`로
  같은 요청만 재전송한다. 예약 수락 전 교체 후보를 승인된 카드처럼 표시하지 않는다.
- `NEXT_RESERVED → WAITING_FOR_PLAYER → PENDING → ACTIVE`에서 WAITING은 생략될 수 있다.
  승격 전 예약은 취소·교체할 수 있다. PENDING 뒤 플레이어가 없어 다시 WAITING이 되면 이미 소비된 예약이므로
  취소·교체를 잠그고, B ACTIVE 뒤 다음 예약을 허용한다. 이 대기에 15초 시작 timeout을 적용하지 않는다.
- 전멸하면 typed `Revive Player`로 사용자가 부활시킨 뒤 진행한다. 자동 부활·중앙 이동은 하지 않는다.
  A abort, 보스 사망, owner 이탈, world/room 세대 변경은 Next를 중단한다.
- Next를 선택하면 Repeat를 끄고, Flow 중이면 현재 occurrence 뒤 남은 Flow 재생을 종료한다. 저장 배열은 보존한다.
  미확정 command 중에는 겹치는 시작을 막는다. 확정된 같은 owner의 실행은 Reload/Start의 전체 preflight 뒤
  reset 한 번으로 교체할 수 있고, 거절/송신 실패 때 기존 실행과 lease를 유지한다.
- `Save Flow`는 파일 저장 뒤 Product publisher와 immutable candidate/기존 2PC를 호출한다. 저장 기본 순서와
  inter-step pursuit는 `ValtanBossAuditionFlows.json`이 소유하며 gameplay는 `scriptedSequence.flowId`로 참조한다.
  배열 순서와 반복 Pattern을 유지하고 입장 cinematic을 자동 삽입하지 않는다. 선택형 입장 cinematic은
  `VALTAN_ENTRANCE_CINEMATIC` 또는 `VALTAN_ENTRANCE_CINEMATIC_IDLE` 중 최대 하나만 배열 첫 슬롯에 둘 수 있다.
  현재 기본 저장 Flow는 아레나 내부에서 Idle을 유지하는 두 번째 컷신을 첫 슬롯으로 사용하고, 기존 첫 번째
  컷신 정의는 Camera/Boss Tool에서 다시 선택할 수 있도록 dormant 정의로 보존한다. `SAVED`와 Server의
  `COMMITTED/ALREADY ACTIVE`를 구분하며, 실패 시 저장본·이전 runtime을 보존하고 `Apply Saved Flow`로 재시도한다.
- `Reload Flow`는 pending 적용 명령이 확정된 뒤 저장본의 배열 첫 슬롯(화면 01)부터 FLOW_START를 제출한다.
  파일 parse/validation 또는 새 시작 실패는 이전 실행을 보존한다. 진행 중 Product 순서의 pin은 다음
  encounter/reset까지 유지되므로 중간 ordinal이 새 배열을 소비하지 않는다.
- 공용 service는 Boss Tool이 닫혀 있어도 NetworkManager에서 lifecycle을 처리한다. Release Server는 Next Debug
  command를 거부한다. 이 계약은 Shared의 현재 `NETWORK_PROTOCOL_VERSION`을 함께 사용하며 다른 version peer와 혼용하지 않는다.

### 10.5 선택 근거를 읽는 방법

Tool은 “weight가 높아서 선택” 같은 요약만 보여 주지 않는다. 한 decision을 선택하면 다음 순서로 읽는다.

1. source가 forced mechanic인지 normal weighted인지 확인한다.
2. selection window와 set이 현재 phase/bar와 맞는지 확인한다.
3. 모든 후보의 exclusion bit와 cooldown/range/repeat 값을 확인한다.
4. eligible 후보의 effective weight와 누적 interval을 확인한다.
5. RNG ticket이 어느 interval에 들어갔는지 확인한다.
6. selected pattern과 실제 다음 pattern sequence가 일치하는지 확인한다.
7. draft 값과 Server active/pinned revision이 같은지 확인한다.

weight를 조정한 직후 active pattern이 바뀌지 않는 것은 정상이다. `NEXT_DECISION` 뒤 여러 번의 Server 선택 trace와
histogram으로 observed 빈도를 본다. Debug fixed seed는 audition reset 옵션일 뿐 Product RNG state를 바꾸지 않는다.

### 10.6 신규 pattern 생성과 legacy 승격

`Create Normal Pattern`, `Create Mechanic Pattern`, `Duplicate`, `Promote Legacy Pattern`, `Delete`는 현재 구현되지
않았다. 후속 구현은 다음 closure를 모두 만족해야 Publish할 수 있다.

- 새 stable pattern/action/stage/occurrence/cue ID와 retired-ID 비재사용
- selector set/window 또는 mechanic trigger에서 정확히 한 reachable entry
- 모든 stage의 explicit normal/branch 종료 경로
- damage profile, animation clip, Effect cue, camera/world/combat-object reference resolve
- Product ordinal과 legacy fallback RNG compatibility 정책
- Server consumer와 Client presentation consumer
- wrong ID/path/version, duplicate, rollback을 포함한 harness
- 새 C++ 파일이면 `.vcxproj/.filters` 등록

incomplete draft를 메모리에 둘 수는 있지만 Save/Publish admission 결과는 field별로 fail-closed한다. legacy-only row를
한 번에 역수입하지 않고 pattern 하나씩 exact row와 모든 join이 닫힐 때 승격한다.

## 11. 패턴별 Boss Tuning 가이드

### 11.1 휠윈드 `VALTAN_WHIRLWIND`

조정 대상은 selection set weight/order, cooldown/repeat/range, WINDUP/SPIN/RECOVERY duration, target tracking,
SPIN hit radius와 4개 offset, damage/push, animation play rate, cue transform과 start/stop이다.

현재 SPIN stage는 1200ms이고 hit은 0/350/700/1050ms다. source cut 533ms를 1200ms wall에 맞추는 presentation
play rate와 Server hit wall을 구분한다. Tool에서 radius를 바꾸면 Client Effect 크기가 자동으로 gameplay 정답이
되는 것이 아니므로 hit guide와 Effect drawable 상태를 같은 timeline에서 따로 확인한다.

### 11.2 돌진 `VALTAN_DASH_CHARGE`

조정 대상은 3개 finite WINDUP occurrence, charge distance/duration/speed, swept collision, wall contact branch,
GROGGY duration/flag, part destruction, RECOVERY/PART_BREAK 종료다.

```text
WINDUP --TIMEOUT--> CHARGE
CHARGE --WALL_CONTACT--> GROGGY
CHARGE --TIMEOUT-------> RECOVERY
GROGGY --PART_DESTROYED--> PART_BREAK
GROGGY --TIMEOUT---------> RECOVERY
```

벽 충돌 처리에서 stage 배열의 다음 칸을 추측하지 않는다. 모든 edge가 공용 transition을 거쳐 GROGGY
ENTER/EXIT flag를 정확히 한 번 처리해야 한다. audition reset은 wall/prop state까지 Server가 같은 transaction으로
초기화할 수 있을 때만 시작한다.

### 11.3 4연속 공격 `VALTAN_FOUR_SLASH`

조정 대상은 SLASHES의 1790/2560/3330ms, SPIN의 600ms contact, cone geometry, damage/push, 두 active animation
occurrence와 HOLD budget, SLASHES/SPIN/RECOVERY cue다.

3회 베기와 1회 회전을 합쳐 Server contact는 총 4회다. 원본 Effect row를 3+3으로 합쳐 6회 피해를 만들지 않는다.
회전 Effect binding ID가 있다는 것과 실제 drawable이 화면에 나온다는 것은 다른 상태다. Tool은
`binding resolved -> effect prepared -> Spawn_WorldRoot -> draw submitted`를 각각 표시한다.

### 11.4 도넛 `VALTAN_FIST_IN_OUT`

현재 foreground는 `INNER 100ms`, animation NONE, stage hit NONE 한 개다. ENTER의
`SPAWN_COMBAT_OBJECT`가 `combatobject.valtan.fist-in-out.donut`를 한 번 만든다. object는 2600ms 동안
생존하고 1600ms에 RING 8~16m를 한 번 판정한다. 다음 패턴은 이 lifetime을 기다리지 않으며, 살아 있는
독립 object가 남은 foreground 완료 경계에서는 공통 inter-step pursuit 대기도 삽입하지 않는다.

다섯 element의 `localSpace`는 false다. 모든 지연 element가 생성 시점 boss world root를 공유하므로 이후
발탄의 이동·회전은 Effect 중심을 바꾸지 않는다. particle의 authored scale lerp는 계속 진행한다.
BossCatalog의 visual `worldScale: [1.5, 1.5, 1.5]`는 기존 크기를 보존한다. stage cue와 stage damage는
제거되어 중복 실행하지 않는다. owning Effect Tool은 시각 튜닝용이고 독립 피해와 다음 패턴 병렬 실행은
`Play Server Pattern` 또는 Flow에서 확인한다.

### 11.5 고공 점프와 추적 도끼 `VALTAN_HIGH_JUMP`

현재 데이터에 별도 `VALTAN_AXE_THROW` pattern은 없다. 사용자가 부르는 “도끼 던지는 패턴”은 현재
`HIGH_JUMP/AIRBORNE`의 Server combat-object action이다. 독립 pattern이 필요하면 기존 Effect를 복제하지 말고
새 stable pattern/animation/stage graph가 실제로 준비된 뒤 같은 combat-object archetype을 reference해 승격한다.

고공 점프의 조정 대상은 target lock, leap apex, TAKEOFF/AIRBORNE/LAND/RECOVERY wall, landing fallback,
LAND hit, 도끼 warning/impact/lifetime/hit geometry/damage와 visual join이다.

v2 volley payload는 다음 의미를 가진다.

| field | 1차 범위 |
|---|---|
| `volleyPolicy` | `PER_ALIVE_PLAYER` |
| `countPerResolvedTarget` | 1~8 |
| `layout` | 1개면 `TARGET_CENTER`, 2개 이상은 `RADIAL_AROUND_TARGET` |
| `radiusM/startAngleDegrees/angleStepDegrees` | radial 위치 결정 |
| `allowOverlap` | 기본 false |
| `maximumTotalObjects` | 웨이브당 최대 36 |
| `spawnSchedule` | `INTERVAL`, 3회, 첫 0ms, 간격 1333ms |
| `arenaRandom` | `BOSS_SPAWN_POSITION` 중심, 4개, 반경 14m, 높이 허용 1m |
| target sample | 각 웨이브 시점, alive/engaged PlayerId 안정 정렬 |

세 웨이브는 AIRBORNE 진입 tick과 그로부터 40/80 fixed tick 뒤에 생성한다. 각 웨이브의 player 대상은 다시
집계하며, 같은 웨이브의 player 묶음과 랜덤 4개는 한 번에 stage/commit한다. 각 object의 실제 hit delay는
combat-object definition의 `hit.atMs=1200`이 소유한다.

Server는 대상과 모든 radial/random 위치를 먼저 계산하고 navigation/bounds, minimum spacing, 웨이브 36개 상한,
현재 live object를 더한 snapshot 128개 상한을 전량 preflight한다. 하나라도 실패하면 0개를 spawn한다. 성공한
object는 각자 시작 definition revision을 pin한다. Tool은 `대상당 도끼 수`, `현재 대상 수`, `예상 총 도끼 수`,
`동시 capacity`와 예상 중첩 피해를 동시에 표시한다.

도끼가 안 보일 때는 새 Effect를 만들지 말고 다음 join을 위에서 아래로 확인한다.

```text
AIRBORNE ENTER event
  -> Server object set commit
  -> spawn snapshot + definition revision
  -> combatObjectArchetypeId
  -> BossCatalog clientVisualId
  -> EffectCatalog effectAssetId
  -> authored Effect document identity/revision
  -> prepare result
  -> Spawn_WorldRoot
  -> draw submitted
```

### 11.7 중앙 이동·벽 파괴·2페이즈 `VALTAN_ARENA_BREAK_109`

### 11.8 phase 2 확장

현재 joined root scope는 계속 `PHASE_ONE`이고 phase 2 전용 자동 selection program은 아직 없다. 다만 애니메이션 담당자가
`Data/Valtan/Valtan.presentation.debug.json`의 23개 chain 중 승격된 20개는 다음 animation-first 경로로 joined 정본에
들어와 있다.

```text
Valtan.presentation.debug.json (animator intake)
  -> Valtan.animation-chain-promotions.json (reviewed stable ID / phase / source hash)
  -> promote_valtan_animation_chains.py
  -> Valtan.gameplay.json + Valtan.presentation.json
  -> ValtanEncounter.json + Valtan.patternbindings.json
  -> All Effects / Animation Tool / stable-ID Server audition
```

- 현재 closure는 `19개 P2 + 1개 P3 candidate`, `20 patterns / 97 stages / 97 occurrences`다.
- source chain 하나는 `VALTAN_SEQUENCE_<CHAIN>` pattern 하나가 되고, 각 source occurrence는 `STEP_NN` Server stage와
  `valtan.sequence.<chain>.step-nn` action 하나가 된다. 다음 occurrence로 넘어가는 wall time은 reviewed WModel native
  duration 또는 animator의 explicit wall time으로 고정한다.
- 여섯 개의 `mesh_` 누락 clip spelling은 promotion manifest의 exact alias로만 정규화한다. fuzzy clip fallback은 없다.
- 신규 row는 `decisionModel.manualAuditions`가 소유하고 Product `selectionMode: AUDITION_ONLY`로 compile된다. 따라서
  일반/기믹 selector, weighted rotation, 연속 사용 횟수에 들어가지 않는다.
- manual audition stage는 최초 승격 시 `hit: NONE`, damage/motion/event/branch 없음이다. 애니메이터의 `success`, `fail`,
  `if`, `dead` 이름을 Server outcome이나 phase 전환으로 추측하지 않는다.
- All Effects의 `Manual Audition | P2/P3` 행과 Animation Tool `Valtan Pattern Master`는 같은 joined occurrence 순서를
  보여 준다. `Play Server Pattern`은 stable pattern ID로 실제 Server fixed-tick stage를 재생한다.
- 마지막 `warp-jump-four-hand-twohand-roar-roar-dead`는 P3 candidate 표시만 갖는다. 망령 모델 교체와 phase-3
  gameplay admission을 완료했다는 뜻이 아니다.
- repository Validate는 20개 `sourceChainId`와 manual Product의 clip 순서, source offset, mapping basis, play rate를
  exact-join한다. 분류되지 않은 신규 chain, clip drift 또는 반쪽 target pattern/stage가 있으면 PublishV2를 거부한다.
- moving pattern은 Server motion subwindow와 축 소유권을 먼저 닫는다. Local Preview의 `b_root` 성공을 Server Actual
  위치 증거로 쓰지 않으며 Server-authoritative body는 `b_root` 전 축 잠금을 유지한다.

근본 원인과 중앙점프→포효 전체 trace의 상세 계약은
`.md/GB/08-26/2026-08-26_VALTAN_SERVER_PRESENTATION_PARITY_CONTRACT.md`를 따른다.

애니메이션 담당자가 phase 3 chain을 추가하면 debug 파일을 저장한 뒤 promotion manifest의 source hash와 reviewed row를
갱신하고 먼저 `--mode Validate`를 실행한다. review가 끝났을 때만 `--mode Apply`로 split/Product 전체를 원자 교체한다.
source 문서나 WModel hash가 바뀌었거나 일부 Product만 바뀌면 projector는 기존 파일을 유지하고 실패한다.

패턴 담당자는 이 manual row를 Server에서 먼저 재생해 실제 body wall을 기준으로 hit, motion, event, branch와 damage를
`Valtan.gameplay.json`에 채운다. 자동 전투 편입은 별도 admission이다. 해당 pattern을 phase 2 selection set/window 또는
mechanic에 옮기고 `manualAuditions`에서 제거한 뒤 selector/trace와 Client presentation harness를 통과시켜야 한다.
현재 live stable pattern ID coverage와 phase reference closure가 닫힌 뒤에만 root scope를 `FULL_ENCOUNTER`로 올린다.

### 11.9 Trash 포획·counter·처형과 Next

현재 `VALTAN_TRASH`는 split gameplay/presentation 정본의 14개 stage를 사용한다. 시전 `STEP_07`의
counter 성공은 `420631` GROGGY로 이어지고 종료 뒤 다음 패턴으로 간다. 돌진 `STEP_08`은 충돌한 생존
player를 계속 포획하며, 포획만으로 돌진을 끝내지 않는다. 정면 nav 이동이 막히면 같은 tick의 최종 포획을
처리한 뒤 즉시 결과 tail로 간다. NONE은 miss 후 종료하고 PARTIAL/ALL은 1500ms impact에서 다시 분류한다.

- PARTIAL: `DAMAGE_GRABBED_PLAYERS`로 해당 boss 왼손에 실제 포획된 player에게만 damage를 적용하고 해제한다.
  1500~3000ms tail 뒤 종료하며 재돌진하지 않는다.
- ALL: `EXECUTE_GRABBED_PLAYERS`로 대상 전체의 HP=0, DEAD, 포획 해제를 같은 transaction으로 commit한다.
  실행 완료 상태를 가진 채 타깃 없는 1500~3000ms tail을 끝내고 정상 완료한다. Next는 전멸 대기로 남는다.
- ALL 판정의 roster는 비어 있지 않은 HP>0, DEAD/FALLING 아님 기준이다. `isCombatReady`를 사용해 포획자를
  제외하지 않는다. boss entity/LEFT_HAND slot, attachment sequence와 finite offset까지 검증하며 잘못된 포획은
  ALL로 세지 않는다. 모든 대상과 event capacity를 preflight하고 실패 시 일부 사망·해제를 commit하지 않는다.
- 포획 중 Client의 이동/스킬 command는 0이다. 해제 때 누르고 있던 키는 물리적으로 놓은 뒤 다시 입력해야 한다.

기존 aux pattern ID와 저장 Flow slot, aux Effect/Sound cue는 보존한다. `_CATCH_IF`는 같은 시전·돌진·결과,
`_CATCH_SUCCESS`는 같은 성공 tail, `_CATCH_FAIL`은 같은 miss tail을 공유한다. 보조 success를 실행했다고
존재하지 않는 포획자를 만들지 않는다. 네 패턴의 모든 stage graph는 back-edge 없이 유한해야 한다.

Client grab은 왼손 본의 고정 local origin에 붙인다. capture 시점의 상대 위치는 보존하지 않고 회전과
player scale만 보존한다. 실제 0.01 hand scale도 허용하도록 정규화한 basis determinant를 검사한다.
`CATCH_BREATH`의 `ARENA_EJECTION`은 기존 12m/s를 24m/s로 두 배 늘린다. 기본 거리 12m보다 아레나
외곽이 멀면 같은 높이의 마지막 지면+2m까지 유한 거리로 늘리고, nav clamp 없이 진행한 뒤 FALLING으로 간다.
일반 knockback의 nav/collision 처리는 바꾸지 않는다. v26 bootstrap은 source 기반
`PATTERNAUTHORINGMANAGED` membership과 typed Trash event를 함께 검증한다.

유령 표현 준비 실패는 본체 표현을 유지하면서 해당 자식만 격리한다.
플레이어 외형 복제는 이 ghost archetype 구현에 포함하지 않는다.

protocol v44 spawn의 `iOwnerBossNetEntityId`는 primary에서 0, ghost에서 살아 있는 같은 encounter의 primary ID다.
무소유 ghost·자기 소유·다른 encounter·종속 owner는 거부한다. 사망 despawn reason은 마지막 DEAD snapshot이
생략돼도 HP 0을 알린다. Server는 본체와 종속 entity/독립 피해를 즉시 정리하고, Client는 기존 Layer의
유효한 `mesh_dead_1` clip을 한 번 재생한 뒤 presentation을 제거한다. clip 없음·실패는 즉시 제거하며
중복 death는 재시작하지 않는다. reset/퇴장은 남은 corpse 표현도 즉시 정리한다.

## 12. Server-authoritative Hot Reload 계약

### 12.1 revision은 파일 timestamp가 아니다

revision ID는 staged runtime/presentation artifact의 `sorted relative path + file hash` manifest를 SHA-256으로
계산한다. top-level manifest는 Server gameplay submanifest hash, Client presentation submanifest hash,
allowed-domain mask, required presentation lane mask, apply class를 봉인한다. 각 process는 자기 subset뿐 아니라
parent hash도 검증한다.

1차 허용 domain은 `VALTAN_BOSS`다.

- managed Valtan pattern/rotation/stage/action/branch/motion
- 허용된 Valtan BossProfiles와 DamageProfiles row
- Valtan combat-object definition과 presentation reference
- 현재 active Client Product와 byte-identical한 Valtan animation/Effect/combat visual/camera/world artifact alias

player profile/skill, item, navigation, 다른 encounter/world가 섞이면 candidate 전체를 거부한다. world-event-set
definition과 placement/mutation/nav뿐 아니라 gameplay invocation의 set ID/owner stage/trigger edge 변경도 immutable
definition과 mutable destroyed state를 분리하는 후속 작업 전까지 허용하지 않는다. presentation artifact bytes가
바뀐 candidate도 실제 generation loader가 생기기 전까지 거부한다.

### 12.2 authoring Save와 candidate publish

`Save Authoring`은 loaded source SHA-256을 precondition으로 검사한다. 변경 source를 sibling staging에 쓰고
before/after manifest, backup journal, process lock으로 묶는다. crash 뒤 모든 cooperating reader는 미완료 journal을
먼저 old 또는 new 전체로 복구하고 섞인 source 집합을 소비하지 않는다.

`Publish Candidate`는 immutable candidate directory에서 projector, gameplay/effect/camera/world validator,
balance provenance sync를 실행한다. 모든 artifact와 submanifest가 완성된 뒤 rename과 candidate pointer만 바꾼다.
active runtime pointer는 아직 old revision이다. Tool이 변경한 balance field는 공식 receipt 동기화에서
`PROJECT_TUNED`로 분류한다.

candidate의 `applyClass`는 마지막 draft operation만 보지 않고 최종 materialized `BOSS_VALTAN` base와 runtime
baseline을 비교한다. 따라서 base stat을 저장한 뒤 0-operation으로 다시 Publish해도 `ENCOUNTER_RESET`이 유지된다.

### 12.3 Server global commit

`CServerApp`이 active/staged `GameplayCatalogGeneration`을 소유하고 shared/private room 모두에 같은 shared pointer를
준다. 각 `CGameRoom`이 disk를 따로 reload하지 않는다.

room thread의 첫 room tick 전에 다음을 한 번 수행한다.

1. Server worker가 candidate와 allowed-domain diff를 parse/validate/stage한다.
2. 모든 room이 candidate와 apply class를 preflight한다.
3. 하나라도 NACK이면 모든 room이 old generation을 유지한다.
4. 모두 준비되면 같은 global tick에서 room generation pointer를 교체한다.
5. 그 뒤 inbound command와 gameplay simulation을 실행한다.

room 생성/등록과 commit은 같은 registration epoch/admission gate를 사용한다. commit cohort를 잡은 뒤 생긴 private
room이 old generation으로 한 tick이라도 시작하지 않게 등록을 대기시키거나 candidate에 즉시 rebase한다. 실제
pointer swap은 allocation/I/O가 없는 infallible 단계여야 한다.

성공한 revision은 `current-candidate.json`과 구분된 Server runtime-active pointer/journal로 durable commit한다.
Server 시작 시 이 pointer가 있으면 exact immutable candidate parent/manifest/bootstrap/domain hash를 다시 검증해 해당
generation으로 시작한다. pointer가 없을 때만 packaged bootstrap이 baseline이다. corrupt/missing candidate를 A로
조용히 되돌리지 않는다.

canonical Product rotation은 formatVersion 3, packaged gameplay bootstrap은 formatVersion 26, Server catalog도
version 26 하나만 live admission한다. 이전 version은 offline migration 참고이며 v26 process에서 dual-read하지 않는다.
최초 배포는 새 Server binary와 packaged v26를 함께 배포하고 Server를 재시작하는 schema deployment다. 그 뒤 Hot
Reload는 v26 -> v26 candidate만 허용한다.

폐기된 예전 candidate 때문에 정상 startup이 막힌 경우 Server를 완전히 중지하고 Debug에서만 다음을 실행한다.

```powershell
Server/Bin/Debug/Server.exe --reset-valtan-runtime-to-packaged
```

named mutex가 실행 중 Server와의 병행을 막고, verified packaged pointer만 원자 기록한다. missing/retired old candidate
escape는 허용하지만 corrupt/ambiguous pointer·journal은 추측해 지우지 않는다. Release는 이 명령을 거부한다.

### 12.4 Client 2-phase readiness

1차 multi-client 지원은 현재 loopback 계약에 맞춰 같은 PC의 Debug Server/Clients가 동일 immutable Client
DataFiles revision directory를 공유하는 경우로 제한한다. artifact 전송을 packet에 얹지 않는다.

```text
Tool Publish Candidate
  -> C2S PREPARE_REQUEST(base, target, sequence)
  -> Server candidate stage
  -> S2C PREPARE(target, parent/submanifest hash, required lane mask)
  -> 각 Client world-entry presentation baseline과 candidate 비교
  -> READY / READY_DEGRADED / NACK + lane status
  -> Server global COMMIT 또는 전원 ABORT
```

Debug Client는 world entry 때 allowlist된 7개 presentation artifact의 hash/bytes를 baseline으로 고정한다. PREPARE는
candidate를 이 baseline과 비교하며, 작업 중 바뀐 repository disk를 다시 hash해 이미 로드된 세대로 간주하지 않는다.
required lane 하나라도 다르면 NACK이다. 이는 gameplay-only candidate를 위한 최소 안전 alias이며 실제
non-byte-identical presentation generation loader가 아니다. Server gameplay를 먼저 적용하고 Client 표현이 뒤늦게
따라오게 하지 않는다. prepare 중 join은 gate/cohort에 포함하고 disconnect는 원자적으로 제거한다. 동시에 두
prepare를 허용하지 않으며 동일 sequence/revision 재요청은 idempotent해야 한다.

### 12.5 in-flight pin과 late join

generation registry는 content hash key와 ref-count를 사용한다. active room 외에도 active pattern, pending mechanic,
combat object, camera/Effect occurrence가 old generation을 pin할 수 있다. 단순 current/previous 두 세대만 보관하면
세 번 연속 reload와 긴 occurrence에서 깨진다.

registry에는 retained generation 수/bytes/age cap을 둔다. pin이 남은 generation을 임의 삭제하지 않는다. cap을
넘으면 새 prepare를 거부하거나 운영자가 controlled encounter reset으로 pin을 해제한다.

late join의 `S2C_ENTER_ACCEPTED`와 snapshot은 room active revision뿐 아니라 현재 화면에 필요한 pinned revision
목록을 보낸다. pattern/combat-object spawn도 occurrence definition revision을 가진다. 현재 Client는 각 revision의
candidate parent를 검증하고 모두 같은 world-entry baseline의 byte-identical alias일 때만 world entry를 commit한다.
없거나 bytes가 다르면 newest revision으로 대체하지 않는다. 실제 hash-keyed presentation registry/pin은 후속이다.

### 12.6 mutable state와 definition revision

definition revision과 boss의 mutable state revision은 별도다. active occurrence는 시작 generation의 AP/damage를
사용한다. 현재처럼 direct hit가 새 active catalog의 AP를 중간에 다시 읽는 경로는 제거한다.

HP/AP/move/collision/armor 같은 base stat candidate는 `ENCOUNTER_RESET`이다. 새 generation으로 boss entity state를
다시 만든 뒤에만 적용한다. 현재 HP 비율을 추측해 새 maximum HP에 옮기거나 phase를 뒤로 돌리지 않는다.

### 12.7 failure와 rollback

다음 어느 지점에서 실패해도 old source/Product/runtime 또는 old active generation 한 세트가 유지되어야 한다.

- malformed JSON, wrong schema/version, duplicate/unknown ID
- projection/reference/provenance mismatch
- candidate hash/submanifest mismatch
- 금지 domain diff
- Server room preflight failure
- required Client lane NACK, timeout, missing artifact
- prepare 중 join/disconnect/새 private room race
- source/candidate promotion 중 process crash

실패 이유를 silent fallback이나 “reload failed” 한 문장으로 뭉개지 않는다. Tool에 document/field/revision/session/lane
reason을 보존한다.

## 13. 현재 작업자가 사용하는 수정 절차

아래 절차 중 gameplay-only `HOT_RELOAD` 경로는 현재 사용할 수 있다. base-stat reset과 presentation bytes 변경은 같은
절차에서 끝나지 않으며 각각 명시적으로 차단된다.

### 13.1 일반 pattern 수치 변경

1. Server와 Client를 사용자가 실행하고 Valtan Arena에 진입한다.
2. F1 -> Balance Tool -> Valtan에서 Server Active와 Disk Authoring revision을 확인한다.
3. pattern을 선택하고 `Play Server Pattern`으로 현재 값을 재현한다.
4. 한 의미 단위의 weight/range/stage/hit 값을 draft로 수정한다.
5. inline validator와 authored diff를 확인한다.
6. `Validate Draft -> Save Authoring -> Publish Candidate`를 순서대로 실행한다.
7. apply badge가 `HOT_RELOAD`인지 확인한다. `ENCOUNTER_RESET`이면 Apply가 비활성화되므로 성공으로 기록하지 않는다.
8. 모든 Client lane READY와 global commit tick을 확인한다.
9. 다음 decision/pattern의 trace와 actual stage/hit를 확인한다.
10. 사용자가 직접 화면의 animation/Effect/camera fidelity를 판정한다.

### 13.2 animation/Effect 변경

Animation Tool과 Effect Tool은 같은 `Valtan.presentation.json` identity와 preview 경계를 소비한다. occurrence/cue
owner를 generated Product JSON에서 고치지 않는다. Effect element/material 변경은 local preview에는 즉시 반영할 수
있지만 현재 Arena candidate의 byte-identical admission에는 들어갈 수 없다. selected cue만 성공했다고 `All Effects`
또는 Server audition/Hot Reload 성공으로 기록하지 않는다.

### 13.3 damage 변경

직접 stage hit의 `serverDamageProfileId`는 `Valtan.gameplay.json`에서, combat-object hit의 같은 reference는
`Valtan.combatobjects.json` companion에서 고른다. 실제 rate는 `DamageProfiles.json`의 해당 Valtan row에서
수정한다. Balance Tool은 join된 숫자를 한 화면에서 편집하되 Save transaction은 실제 소유 domain만 dirty로
기록한다. 실제 피해는 Server AP/방어력/상태를 적용한 `DAMAGE_EVENT.iAmount`로 확인한다.

### 13.4 camera/wall 변경

camera cue의 keyframe/FOV/shake는 소유 Camera 도구가 전용 문서를 편집한다. wall placement/mutation/nav는 현재
Balance Tool에서 read-only 상태만 보며 clickable Map Tool deep-link는 후속이다. wall data 변경은 G09와 controlled
reset 전에는 Hot Reload 대상이 아니다.

### 13.5 Git과 문서

코드, schema/data, projector, publisher, protocol, Server/Client consumer, harness, PLAN/RESULT를 하나의 검증 가능한
계약으로 묶는다. 생성물만 고친 commit을 만들지 않는다. 새 C++ 파일은 물리 폴더와 일치하게 프로젝트/filters에
등록한다. 신규 Git Data 원본은 Client project `96.DataFiles`의 `None` 항목으로만 등록한다. 사용자 Effect dirty
변경을 소유자 확인 없이 되돌리지 않는다.

## 14. 구현 요구 사항과 완료 판정

### 14.1 codec/publisher

- v1 read-only load와 explicit v2 migration이 있어야 한다.
- unknown/missing field, duplicate stable ID, illegal path, bad reference를 exact reject해야 한다.
- parse -> validate -> stage -> commit 순서와 source-hash conflict가 있어야 한다.
- split-owned row 수정이 legacy-only row의 field/ordinal을 바꾸지 않아야 한다.
- legacy manifest가 RED_BLADE_WAVE object owner/lifetime까지 보존하고 Promote가 exact closure만 제거해야 한다.
- mixed shared rotation Promote가 다른 ordered reference를 삭제/복제하지 않아야 한다.
- unmanaged object definition은 companion에 한 번만 있고 manifest에는 owner/lifetime/ordinal만 있어야 한다.
- world set authoring companion과 flat Product output path/role이 섞이지 않아야 한다.
- gameplay/presentation source, combat-object companion, Boss/Damage, Effect, camera/world reference, provenance, Server/Client artifact가
  한 transaction/revision으로 검증되어야 한다.
- no-op publish는 byte/semantic drift와 RNG ticket drift를 만들지 않아야 한다.

### 14.2 Server decision/stage

- intro -> forced mechanic/audition -> window/set -> legacy fallback 우선순위를 executable test로 고정한다.
- 모든 candidate exclusion reason과 soft-repeat relax를 검증한다.
- fixed seed에서 authored order/weight/ticket 결과가 deterministic해야 한다.
- no-target/death/reset/wall/part-break/next-action preflight 실패가 partial transition을 만들지 않아야 한다.
- active pattern A 중 revision B commit 시 A의 duration/hit/branch/damage/action이 모두 A generation이어야 한다.
- 109 phase는 TAKEOFF 전 1, IMPACT ENTER에서 2이며 정확히 한 번 state revision을 올려야 한다.

### 14.3 combat-object

- 1인/4인과 대상당 count 1~8의 예상 total을 검증한다.
- radial identity와 PlayerId ordering이 deterministic해야 한다.
- navigation/spacing/volley 32/snapshot 128 capacity 실패 시 zero partial spawn이어야 한다.
- active object는 old revision, 다음 volley는 new revision을 사용해야 한다.
- spawn packet의 object/archetype/visual/definition revision이 strict round-trip해야 한다.
- Client join/prepared/world-root spawn/draw 오류가 각각 진단되어야 한다.

### 14.4 Hot Reload/protocol

- valid stage/prepare/commit과 malformed/hash/ref/domain reject를 검증한다.
- stale/repeated/superseded request가 idempotent 또는 명시적 reject여야 한다.
- shared 3 rooms와 여러 private rooms가 같은 global tick에 revision을 바꿔야 한다.
- prepare 중 room 등록, Client join/disconnect, READY/NACK/timeout을 검증한다.
- required-lane 실패는 NACK, optional-only 실패만 `READY_DEGRADED`여야 한다.
- 세 generation overlap, ref-count GC, retention cap, late join required revision set을 검증한다.
- mixed apply policy candidate가 strongest class 하나로 승격되고 reset 거절 시 zero commit이어야 한다.
- Release에서 Debug trace/audition/reload command는 explicit reject해야 한다.

### 14.5 Tool/preview

- close/reopen, unsaved Reload, external source conflict, async cancel을 검증한다.
- Selected/All Effects의 prewarm/seek/rewind/stop과 한 cue 실패 격리를 검증한다.
- 같은 decision에서 Server selected row와 Tool highlight가 같아야 한다.
- local authoring preview와 Server Actual이 UI에서 혼동되지 않아야 한다.
- audition PENDING/ACTIVE/COMPLETED/ABORTED, owner lease와 disconnect cleanup을 검증한다.

### 14.7 현재 기준선과 수동 판정

이 문서는 이전 tuning/hot-reload 작업에서 기록한 개별 PASS 수치를 현재 integration의 증거로 재사용하지 않는다.
`presentationScale`, cue `scalePolicy`, HIGH_JUMP occurrence/clock, independent world-root 변경 뒤의 정확한 자동 결과는
대응 integration RESULT에 실제 실행 명령과 함께 새로 기록한다. 문서 편집이나 과거 generated Product의 존재만으로
현재 Debug/Release build, publisher, harness를 PASS 처리하지 않는다.

향후 integration RESULT에 기록되는 자동 기준선도 animation, Effect, 도끼, 도넛, camera 또는 wall occurrence의 화면 품질을 뜻하지 않는다.
Effect 복구·successor lineage와 drawable 진단은 해당 Effect 작업 결과에서 별도로 관리하며, 발탄 tuning
정본이나 legacy row를 자동 변경하는 근거로 사용하지 않는다.

Agent의 자동 완료 범위는 build, publisher/JSON/XML 검증, protocol/Server contract와 필요한 live integration scenario의 구조화 로그까지다.
Client/UI를 자율 실행하거나 animation, 도끼, 도넛, 4연공격 회전 Effect, camera, wall destruction을 visual PASS로
판정하지 않는다. 최종 육안 판정은 사용자가 직접 하고 RESULT에 자동 검증과 분리해 기록한다.

### 14.8 최종 완료 조건

- Balance Tool이 `Valtan.gameplay.json`만 gameplay 정본으로 손실 없이 edit/save하고,
  `Valtan.presentation.json`은 read-only/deep-link로 보여 주며 generated Product를 직접 쓰지 않는다.
- 두 source의 `patternId/stageId/actionId` closure와 presentation occurrence가 하나의 joined revision으로 publish된다.
- exact direct-authored Effect의 Open Editor admission과 Product/Actor/Track A preview readiness가 분리되고,
  한 Valtan failure가 player 또는 다른 authored Effect의 Saved/Open index를 비우지 않는다.
- Play, Save, Bind가 자동으로 서로를 호출하지 않는다.
- split-owned와 legacy-only row가 숨김없이 분리되고 phase 2 승격 경로가 있다.
- phase/selection/stage/animation/Effect/object/camera/world가 한 timeline과 revision에 join된다.
- Server 선택과 후보별 근거가 실제 selector trace와 동일하다.
